# 手机语音陪伴调研

远期方向的调研结论，不是当前迭代计划。参照对象是 ChatGPT 手机 app 的 Live 语音模式。

产品定位：手机是随身的她，iPad 和 PC 是工作台。手机上不做阅读，做关系和筛选——路上戴耳机聊，聊到值得读的存起来，到 iPad 上再深读。

## 交互：照抄什么，改什么

照抄：

- 语音不开新界面，长在同一个线程里。ChatGPT 用一年时间从独立的球界面退回这个结论，和 `03-陪读交互-通话模型.md` 里"三档视图是同一通电话"一致——手机语音是第四档视图，不是第四个功能。
- 实时转写就是主视觉，不做动态球。转写同时干两件事：证明在听，且可回看。主场景是耳机加口袋，没人看屏幕。
- 只留静音和挂断两个控件，走路时要能盲按。
- 打断即停，但留 300 到 500 毫秒的确认窗口。路上有环境噪声，零延迟停会被误触发。ChatGPT 在这件事上花约 498ms。
- 延迟指标定"稳"不定"快"：首音 P50 低于 1.2 秒、P90 低于 1.5 秒。实测结论是在 1.3 到 2.3 秒之间摇摆读起来像卡壳，每次都落在同一拍上反而像在思考。
- 快嘴慢脑分层：小模型接住对话，检索和跨书联想这类重活后台跑完插回来。我们的重活天生慢，这条尤其关键。
- 耳机当一等公民，降噪麦直接改善打断判定。

改：

- 不要 backchannel。ChatGPT 的"嗯嗯""对"上线两天就挨骂，用户感知到的不是智能是烦。在听用转写光标表达。
- 不做全双工，做半双工加语义判停。判断"话说完没有"而不是"静了多久"，拿走大部分自然度，复杂度低一个量级。停顿容忍度要比 ChatGPT 默认更宽，用户是在想书里的内容。
- "存起来"必须是语音里的一等动作。ChatGPT 完全没有，用户只能挂断后自己复制粘贴。这是我们的立命之本。
- 语音会话必须能读 memory 并说出来。ChatGPT 至今做不到，是它最大的空档。
- 挂断触发蒸馏，和通话模型同一套语义。路上聊的不进 memory，回 iPad 她就不记得。
- 有限的主动开口：接通那一刻的开场，和用户明确要求时。不做定时推送。
- "只听不说"做成显式按钮，不做口头指令。

形象在手机端的价值是接通那一刻的一帧，不是常驻。默认走锁屏和后台语音，屏幕上什么都不放，用户主动看她时才播动画。省电问题自动消失。

## 技术可行性

能做：

- **麦克风**。页面地址 `tauri://localhost` 被 WebKit 当安全上下文（host 是 localhost，且 scheme 由 WKURLSchemeHandler 处理，两条短路都命中）；wry 0.55 已实现 `requestMediaCapturePermissionForOrigin` 并无条件放行；`NSMicrophoneUsageDescription` 已在 Info.plist。不用改 Tauri，不用私有 API。先例是 Capacitor，唯一已知破法是 origin 带端口，我们不带。
- **播放**。wry 已设 `allowsInlineMediaPlayback`，自动播放限制已解除。注意 CSP 没有 `media-src`，`<audio src="blob:">` 会被拦——TTS 走 fetch 到 ArrayBuffer 再 `decodeAudioData`，绕开 URL 也更快。
- **打断**。WebKit 的 getUserMedia 默认开回声消除，系统 voice processing 在链路里，不用自己写 AEC。

做不了：

- **OpenAI Realtime 用订阅凭据**。客户端要 ephemeral key，而它只能用标准 API key 在服务端换。订阅 OAuth token 授权的是另一套后端。要用就是 BYOK 加按分钟计费，和"订阅登录、零后端"冲突。
- **Claude 原生语音接口**。官方语音模式自己就是 STT 加文本模型加 TTS 拼的。
- **控制音频路由和蓝牙音质**。WebKit bug 167788 开了九年，webview 内容有自己的 audio session 且在另一个进程。麦克风一采集，蓝牙就从 A2DP 切 HFP，AirPods 变打电话音质。ChatGPT 同样如此，不算劣势。

必须实测：

- **后台 JS 是否被挂起**。这是整个设想的生死线。`UIBackgroundModes` 是 Info.plist 键不是 entitlement，加了不破免费签名（和 `CFBundleURLTypes` 同性质，与 Associated Domains 不同）；但 WKWebView 在 app 进后台时会停 JS 执行，有活跃音频时是否豁免没有权威答案。
- **Web Speech API**。`webkitSpeechRecognition` 在第三方 WKWebView 里可能可用——WebKit bug 239816 以 WORKSFORME 关闭，原因是需要加 `NSSpeechRecognitionUsageDescription`。成立的话就是免费、流式、系统级的中文 STT，砍掉一整段网络延迟。`speechSynthesis` 相反，多方迹象指向不支持。

## 延迟预算

拼装链路（STT + LLM + TTS），用户在国内：

| 段 | 耗时 |
|---|---|
| VAD 判定说完 | 200-400ms |
| STT 出终稿 | 150-300ms + RTT |
| LLM 首 token | 400-1200ms，方差最大 |
| TTS 首包 | 150ms + RTT |
| 解码起播 | 50-100ms |
| 合计 | 1.0-2.2s，典型 1.4s |

ChatGPT Live 首音中位 0.3 到 0.6 秒，差两到四倍。差距来自拼装要等完整文本才能开口，以及订阅后端的跨境往返。"第一句话出来就送 TTS"能压到 1.5 到 2 倍，压不到同一档。

保底方案零新增供应商：STT 用已接的硅基流动 SenseVoice，TTS 用同一个 key 的 CosyVoice2，流式首包约 150ms，中文强，国内直连。

另有一条口子：Claude Code 的 `/voice` 听写走的正是 Claude.ai 账号登录这种凭据形态，流式、20 种语言含中文、不计入用量限额。未公开接口，第三方使用有 ToS 风险。

## 验证步骤

第 0 层已跑完，全绿（iPad Pro 13-inch M5 模拟器，Xcode 26.5，CI run 30151592917）：

```
origin              tauri://localhost
isSecureContext     true
mediaDevices        true    getUserMedia true
MediaRecorder       true    mp4 / mp4;mp4a.40.2 / webm / webm;opus 均 true，wav false
AudioContext        true    state "suspended"
AudioWorklet        true
SpeechRecognition   true
speechSynthesis     true    getVoices().length 0
mediaSession        true
crypto.subtle       true
```

结论：`tauri://localhost` 确实是安全上下文，麦克风入口存在，不用为拿到它写 Swift 插件。`AudioContext` 是 suspended，播放要在用户手势里 resume 一次。两个读数要打折扣——`speechVoices: 0` 只说明冷读时列表还没填，不代表合成不可用；`audio/webm` 报 true 与 iOS Safari 的历史行为不符，模拟器跑在 Mac 上编码器可用性可能不同，选 mime 以真机为准，稳妥用 `audio/mp4`。探测代码留在 `src/smoke/voice-probe.ts`。

`crypto.subtle` 为 true 排除了一个当下隐患：`src/platform/app/library.ts` 的 `contentHash` 和 `src/platform/app/oauth.ts` 的 PKCE challenge 都直接用它且无兜底，缺失时是硬失败（任何不在库里的书打不开、Anthropic 登录一起挂），不是静默降级。

以下三层的原始设计，第 0 层保留作参考：

第 0 层，零成本不用真机：往 `src/smoke/smoke.ts` 的结果 JSON 加特性探测（`isSecureContext`、`navigator.mediaDevices`、`MediaRecorder.isTypeSupported`、`AudioContext`、`AudioWorklet`、`webkitSpeechRecognition`、`speechSynthesis.getVoices().length`、`mediaSession`、`crypto.subtle`），跑现成的模拟器冒烟 workflow，20 分钟出结果。直接证实或证伪"web 层拿不到麦克风"，决定要不要走写 Swift 插件那条几周的路。顺带体检：`crypto.subtle` 若为 false，说明加书时算的内容哈希在 iOS 上本来就是坏的。

第 1 层，一次侧载：`Info.ios.plist` 加 `UIBackgroundModes: [audio]` 和 `NSSpeechRecognitionUsageDescription`，出包装机。一次答四件事——加了 UIBackgroundModes 之后免费签名还能不能装、麦克风提示弹不弹、录到的音能不能转写、系统 AEC 在不在。然后锁屏 30 秒再回来读 `setInterval` 时间戳日志有没有洞，这答后台 JS 是否被挂起。同一页试一次 `webkitSpeechRecognition.start()`，看拿到中文流式结果还是 `service-not-allowed`。

第 2 层，戴耳机测打断：边播 440Hz 正弦边录，读录到信号在该频段的 dBFS，外放和耳机各一次。低值说明系统 AEC 在干活。

不确定度最高的三条（后台 JS、Web Speech、免费签名带 UIBackgroundModes）全部落在第 0 和第 1 层，一次侧载覆盖。

## ChatGPT 踩过的坑

填充词过量。噪声环境误打断。语音模式读不到 memory 和文档。转写只给人看、模型读不到。语音答案比文字浅（凡涉及书内容一律过重模型，宁可慢）。强制迁移已有交互引发反弹（我们的按住说话保留，语音通话是新增档位）。中文语音质量要单独验，别信英文评测结论。
