# 手机语音陪伴调研

手机形态已经落地（docs/22：只做 info，简报加收藏文章加对话），语音是它上面唯一还缺的输入形态。这篇因此从"远期方向"改写成有落地阶梯的调研。参照对象仍是 ChatGPT app 的 Live 模式。外部结论的查证日期是 2026-07-29。

目标场景收窄了：看着今天的简报，按一下就能用语音来回聊这些新闻。原来那个"路上戴耳机、锁屏聊、聊到值得读的存起来"的场景推翻——不是不想要，是 WKWebView 后台挂 JS（见下），webview 这条路给不了。

## 现在手机上的语音是坏的

`MicButton` 默认开在每一个 Composer 上（`resolveComposerVoice` 只有显式 `voice={false}` 才关），`InfoCall` 传的是 `infoVoice`，所以简报和文章的对话窗都有麦克风按钮。按下去走 `invoke("start_voice_recording")`，而 `src-tauri/src/lib.rs` 里 `mod voice` 是 `#[cfg(desktop)]`，mobile 分支没注册这三个命令。手机上按麦克风得到的是一行 Tauri 的命令未找到错误，显示在 composer 的琥珀提示行里。

坏掉的只有采集这一段。链路的其余部分在手机上原样成立：STT 请求走 `cleanTauriFetch`（Tauri http 插件，走 IPC，绕开 webview 的 CORS 和 CSP），任意 https 主机都能发；润色 pass 走用户当前的 chat provider。

`NSMicrophoneUsageDescription` 写在 `src-tauri/Info.plist`，Tauri 同时读 `Info.plist` 和 `Info.ios.plist` 并合并进生成的 iOS plist，所以它确实进了 iOS 包。CI 的 ipa verify 步只断言了 `CFBundleURLTypes`，顺手加一条断言这个键的成本是一行。

## 真正的实时通道

老版本这里写着"OpenAI Realtime 用订阅凭据做不了，因为客户端要 ephemeral key，而它只能用标准 API key 在服务端换"。前半句对，后半句推翻。`/v1/realtime/client_secrets`、Gemini 的 `/v1beta/auth_tokens`、xAI 的 `/v1/realtime/client_secrets` 都是普通 REST 调用，持有标准 key 就能调，没有任何机制强制它来自服务器。文档写 backend only 是安全建议——别把开发者的 key 发到用户设备上——而 BYOK 下这个前提本来就不存在：设备就是持有 key 的那一端，它自己换 ephemeral 再连。零后端不是实时语音的死穴。

死穴是计费形态：一家都没有订阅通道，全部按量。

四条结论：

订阅额度一分钱用不上。ChatGPT 订阅和 Platform API 是两套独立产品独立计费，Plus 不给任何 API 额度；`src/ai/credentials.ts` 里那两个 OAuth triple 认证的是 Claude Code 和 Codex 后端，公开的 Realtime 端点不接受。走实时通道就是让项目发起人另开一个按量账户。

Gemini Live 最便宜也最好接：裸 key 进 URL，webview 自己的 WebSocket 就能连，只需要在 CSP 的 `connect-src` 里放行那一个 host。未知只有一条，国内可达性——generativelanguage.googleapis.com 直连行不行查不到公开信息，得拿设备试。

认证放 query 或子协议的（Gemini、xAI、Hume、Deepgram）webview 直接能连；放 header 的（阶跃）只能走 `tauri-plugin-websocket` 从 Rust 侧建连。这条决定接入工作量差一截，选型时先看这个。

国内延迟最优的可能是阿里 Qwen-Omni-Realtime 的 WebRTC 北京节点。文档明说浏览器直连被 CORS 挡住，但 SDP 握手是一次普通 POST，从 Rust 侧发就没有 CORS——推断，未验证。值得单独花半天试。

## Anthropic 没有实时语音

API 侧一个语音端点都没有。官方 API overview（platform.claude.com/docs/en/api/overview）列出的全部端点是 Messages、Batches、count_tokens、Models，以及 beta 的 Files、Skills、Agents、Sessions、Environments；唯一的 WebSocket 是 Managed Agents 的事件流，跑的是 agent 事件不是音频。

Claude 官方的语音模式自己就是 STT 加文本模型加 ElevenLabs TTS 拼的，turn-based，没有 speech-native 模型（2026-07-23 把 voice mode 开到 Opus/Sonnet 的报道）。这条老结论仍然成立，现在有硬出处。

对我们的意味：只要走实时通道，主力模型和语音模型必然分家。简报的编排、`buildLiveCompanionTools` 那套工具、memory，全在 Anthropic 或 OpenAI 订阅那一侧；实时通道里坐着的是另一家的模型，它看不见这些。要么把整套工具重新挂到它上面（工具定义是 pi-ai 的 `Tool` 形状，换 provider 要重写一遍适配），要么让它只做嘴、真答案还是回主模型——而后者一回主模型，实时通道省下来的延迟就还回去了。

## 拼装方案：STT → 文本模型 → TTS

不需要实时 API，复用现有的 `runAgentTurn` 循环和全部工具，主力模型不换，订阅额度照用。Anthropic 自己的语音模式就是这个架构，所以它的天花板不算低。

半双工（按住说话、松开等回答）要做的：手机侧的采集（见阶梯第 1 步）、松手直接发送而不是落进 composer、回答按句切分流式送 TTS、`decodeAudioData` 播。播放不能用 `<audio src="blob:">`——CSP 没有 `media-src`，回落到 `default-src 'self'`，blob 被拦；TTS 字节走 `cleanTauriFetch` 拿 ArrayBuffer 直接解码，绕开 URL 也更快。AudioContext 冷启是 suspended，要在按麦克风那次手势里 resume 一次。

自动轮转（VAD 断句）多要的：采样流上跑端点检测，判"话说完没有"而不是"静了多久"；打断要在播放期间持续检测人声，命中就停播放起新一轮。系统 AEC 在 getUserMedia 的默认链路里，不用自己写。停顿容忍度要比 ChatGPT 默认更宽，用户是在想内容。

延迟预算（国内直连）：

| 段 | 耗时 |
|---|---|
| VAD 判定说完 | 200-400ms |
| STT 出终稿 | 150-300ms + RTT |
| LLM 首 token | 400-1200ms，方差最大 |
| TTS 首包 | 150ms + RTT |
| 解码起播 | 50-100ms |
| 合计 | 1.0-2.2s，典型 1.4s |

ChatGPT Live 首音中位 0.3 到 0.6 秒，差两到四倍。"第一句话出来就送 TTS"能压到 1.5 到 2 倍，压不到同一档。诚实地说：半双工那一档不像 Live，像对讲机，但比打字快得多；自动轮转那一档像 Live 的慢速版，节奏对了，每次开口前多等一拍。按 docs/03 的老结论，延迟指标定"稳"不定"快"——每次都落在同一拍上读起来像在思考，1.3 到 2.3 秒之间摇摆才像卡壳。

供应商零新增：STT 用已接的硅基流动 SenseVoice（免费、中文最强、OpenAI 兼容），TTS 用同一个 key 的 CosyVoice2 加速版（双向流式，首包约 150ms 含网络，中文每万字 ¥0.3 量级，下单前复核）。想再快就换 ElevenLabs Flash v2.5（模型侧约 75ms，$50 每百万字符），但那是新增一家供应商和一个账户。SenseVoiceSmall 单次输入有 30 秒上限的说法没查实，第 1 步要顺手验一下。

## iOS WKWebView 的具体障碍

第 0 层探测已跑完（iPad Pro 13-inch M5 模拟器，Xcode 26.5，CI run 30151592917），探测代码在 `src/smoke/voice-probe.ts`：

```
origin              tauri://localhost
isSecureContext     true
mediaDevices        true    getUserMedia true
MediaRecorder       true    mp4 / mp4;mp4a.40.2 / webm / webm;opus 均 true，wav false
AudioContext        true    state "suspended"
AudioWorklet        true
SpeechRecognition   true
speechSynthesis     true    getVoices().length 0
mediaSession        true
crypto.subtle       true
```

它测的是 API 是否存在和安全上下文，没测的是真实采集、权限弹窗、编解码质量、后台行为——这些一个都不在模拟器的纯同步探测覆盖范围里。

逐条结论：

麦克风与 getUserMedia。成立。`tauri://localhost` 是安全上下文（host 是 localhost，且 scheme 由 WKURLSchemeHandler 处理），wry 0.55 已实现 `requestMediaCapturePermissionForOrigin` 并无条件放行，`NSMicrophoneUsageDescription` 已在 plist。不用改 Tauri，不用写 Swift 插件。唯一已知破法是 origin 带端口，我们不带。

AudioContext 需要用户手势。成立，探测读到 suspended。按麦克风的 pointerdown 就是手势，在那次里 resume 一次即可。

MediaRecorder 编码格式。模拟器报 `audio/webm` 可用，与 iOS Safari 的历史行为不符，模拟器跑在 Mac 上编码器可用性可能不同。不打算赌这个：采集改用 AudioWorklet 取原始 Float32，在 JS 里重采样成 16k 单声道 WAV，和 `voice.rs` 现在做的事一模一样。这样 STT 的 wire 格式全平台统一，也不用赌硅基流动接不接 m4a。

WebRTC。iOS 14.3 起第三方 WKWebView 支持 RTCPeerConnection（前提是 app 实现了 `WKUIDelegate` 的媒体权限回调，wry 已实现），我们的 `minimumSystemVersion` 是 16.0，够。没查实的是 CSP `connect-src` 管不管 RTCPeerConnection：CSP2 曾把 WebRTC 归在 connect-src，CSP3 改成独立的 `webrtc` 指令，WebKit 实现的是哪个未确认。走 WebRTC 的实时通道（OpenAI、ElevenLabs、阿里）才碰这条，第 4 步之前不阻塞。

回声消除。WebKit 的 getUserMedia 默认开 echoCancellation，系统 voice processing 在链路里，不用自己写 AEC。真机戴耳机和外放各测一次才算数（第 2 层：边播 440Hz 正弦边录，读该频段的 dBFS）。

锁屏和切后台。证据指向不成立。WebKit bug 203293、Apple 开发者论坛 thread 121822、openradar 5022510114406400 都说 app 进后台时 WKWebView 里的 JS 被暂停、音频停播，加 `UIBackgroundModes: audio` 也不行。这些报告是 iOS 13 时代的，2024 年以后有没有变化没查到权威说法。按最坏情况规划：手机语音是亮屏前台功能，锁屏耳机场景要的话得写原生插件，那是另一个量级的工程。这推翻了老版本里"默认走锁屏和后台语音，屏幕上什么都不放"的整段设想。

全双工（边录边放）。未查证。WebKit 在 getUserMedia 时会把 AVAudioSession 切成什么 category、会不会导致播放走听筒或音量骤降，没找到权威说法。webview 内容有自己的 audio session 且在另一个进程，app 控制不了（WebKit bug 167788 开了九年）。麦克风一采集蓝牙就从 A2DP 切 HFP，AirPods 变打电话音质——ChatGPT 同样如此，不算劣势。阶梯到第 3 步才需要真全双工，那时用一次侧载实测。

Web Speech API。`webkitSpeechRecognition` 在探测里存在，但存在不等于可用（WebKit bug 239816 以 WORKSFORME 关闭，原因是需要加 `NSSpeechRecognitionUsageDescription`）。成立的话就是免费、流式、系统级的中文 STT，砍掉一整段网络延迟；不成立就是 `service-not-allowed`。一次侧载里顺手试一下，不值得为它单独排期。`speechSynthesis` 相反，多方迹象指向第三方 WKWebView 不支持，`getVoices().length` 冷读为 0 不能当证据但也不能当反证。

## Android 差异

形态一致，两处要动。

AndroidManifest 要同时加 `RECORD_AUDIO` 和 `MODIFY_AUDIO_SETTINGS`。只加前者会得到 `not-allowed` 或 `NotReadableError`——Android 的音频子系统在没有 `MODIFY_AUDIO_SETTINGS` 时拒绝把麦克风交给 WebView。出处是 tauri-apps/tauri#10846，加上第二条后 getUserMedia 就正常了，issue 已 closed as resolved。wry 自己处理 `WebChromeClient.onPermissionRequest`，不用我们写。

页面 origin 是 `http://tauri.localhost`（WebViewAssetLoader），host 是 localhost 所以同样是安全上下文。Android WebView 的 MediaRecorder 支持 webm/opus，比 iOS 宽松，但既然 iOS 那边走 AudioWorklet + WAV，两边共用一条路就行。

Android 后台执行限制和 iOS 不同（前台服务能让进程活着），但 WebView 里的 JS 在后台跑不跑没查证。Android 还没发布，这条等到发布时再验。

## 落地阶梯

第 1 步：手机上的按住说话能用。`recorder.ts` 分平台——desktop 保持 Tauri 命令不动，mobile 走 getUserMedia + AudioWorklet 取 Float32，在 JS 里混单声道、线性重采样到 16k、编 16-bit PCM WAV。重采样和 WAV 编码是纯函数，和 `voice.rs` 的 `resample_linear` / `encode_wav_16k_mono` 同一套逻辑，放 `.ts` 配单测。STT、润色、落进 composer 那一段一行不改。Android 补两条 manifest 权限。产出：手机上对着简报口述提问，成稿落进输入框，用户看一眼再发——和桌面完全一致的体感。工作量小。模拟器能验的部分：把 `voice-probe.ts` 扩成真调一次 `getUserMedia` 并记录 resolve / reject / 超时在权限弹窗上，这就答了 wry 的 delegate 到底有没有放行；音质和转写质量要真机。顺带验 SenseVoice 的单次时长上限。

第 1.5 步（可选，几分钟）：在第 1 步落地之前，手机外壳给 Composer 传 `voice={false}`，把那个按下去必报错的麦克风按钮先关掉。

第 2 步：说完就发，回答念出来。松手直接发送不落 composer；回答按句切分，第一句出来就送 CosyVoice2；`cleanTauriFetch` 取字节，`decodeAudioData` 接 WebAudio 播。AudioContext 在麦克风手势里 resume。加静音和挂断两个控件，走路时要能盲按。产出：一问一答的语音，眼睛可以离开屏幕，首音 1.0-2.2 秒。工作量中。全部能在桌面上先做出来验，手机上只是同一套代码换个外壳。

第 3 步：自动轮转和打断。采样流上跑 VAD 做端点检测，靠语义判停而不是静音时长；播放期间持续检测人声，命中就停播起新一轮，留 300 到 500 毫秒确认窗口防环境噪声误触发。产出：不用按按钮，接近 Live 的节奏慢一档。这一步要真机戴耳机测 AEC，桌面验不了全部。

第 4 步：真实时通道。只有在 1 到 3 做完仍嫌慢时才做，且是 BYOK 另开账户的决定。两条接法差一截工作量：认证能放 URL query 或子协议的（Gemini、xAI、Hume、Deepgram），webview 自己的 WebSocket 就能连，只要在 CSP 的 `connect-src` 里加那一个 host；认证只能放 header 的（阶跃），得走 `tauri-plugin-websocket` 从 Rust 侧建连（支持自定义 header 和二进制帧，iOS/Android 都支持）。选供应商时优先协议是 JSON 事件加 base64 音频的（OpenAI Realtime 兼容那一系），避开自定义二进制协议的：二进制帧过 IPC 会被逐字节 JSON 化，实测 3.5 个字符每字节、峰值 20 倍（坑 54），24k PCM16 每秒 48KB 撑不起；base64 文本帧不走那条分支。

它不是第 3 步的升级版，是另一个东西：换模型就丢工具和 memory（见上）。

不确定度最高的三条（后台 JS、Web Speech、全双工的 audio session 行为）全部落在第 3 步之后，第 1 和第 2 步不依赖任何一条。这是这次阶梯划分的主要判据。

## 交互：照抄什么，改什么

照抄：

- 语音不开新界面，长在同一个线程里。ChatGPT 用一年时间从独立的球界面退回这个结论，和 docs/03 里"三档视图是同一通电话"一致。
- 实时转写就是主视觉，不做动态球。转写同时干两件事：证明在听，且可回看。
- 只留静音和挂断两个控件。
- 打断即停，但留 300 到 500 毫秒的确认窗口。ChatGPT 在这件事上花约 498ms。
- 快嘴慢脑分层：小模型接住对话，检索和联想这类重活后台跑完插回来。我们的重活天生慢，这条尤其关键。
- 耳机当一等公民，降噪麦直接改善打断判定。

改：

- 不要 backchannel。ChatGPT 的"嗯嗯""对"上线两天就挨骂。在听用转写光标表达。
- 不做全双工，做半双工加语义判停。判断"话说完没有"而不是"静了多久"，拿走大部分自然度，复杂度低一个量级。
- "存起来"必须是语音里的一等动作。ChatGPT 完全没有。手机上收藏文章本来就是主路径（docs/22），语音里说一句就存是它的自然延伸。
- 语音会话必须能读 memory 并说出来。ChatGPT 至今做不到。走拼装方案就是免费的——同一个 `runAgentTurn`，同一套工具。
- 挂断触发蒸馏，和通话模型同一套语义。
- 有限的主动开口：接通那一刻的开场，和用户明确要求时。不做定时推送。

形象在手机端的价值是接通那一刻的一帧，不是常驻。

## ChatGPT 踩过的坑

填充词过量。噪声环境误打断。语音模式读不到 memory 和文档。转写只给人看、模型读不到。语音答案比文字浅（凡涉及内容一律过重模型，宁可慢）。强制迁移已有交互引发反弹（按住说话保留，语音通话是新增档位）。中文语音质量要单独验，别信英文评测结论。

## 要拍板的

掏不掏钱，掏多少。实时通道全是按量计费，订阅额度一分钱用不上。每天早上聊 20 分钟，Gemini Live 约 $14/月，阶跃约 ¥12/月，OpenAI Realtime 约 $58/月，长会话因为上下文重复计费还要往上。第 1 到 3 步的边际成本接近零：STT 是已接的 SenseVoice 免费额度，TTS 是同一个 key 的 CosyVoice2。

语音模型能不能和主力模型分家。如果"她记得我们聊过什么"是不可让的，第 4 步就不做，阶梯到第 3 步为止。

锁屏耳机场景要不要。证据指向 webview 给不了。要的话是写原生音频插件的量级，不是加个 plist 键。

Gemini 那把 key 的网络条件。它是最便宜也最好接的实时通道，但 generativelanguage.googleapis.com 在国内直连行不行查不到公开信息。同步已经在用 Google Drive，看现有网络条件够不够。

第 1.5 步做不做——在第 1 步落地前，是否先把手机上那个按下去必报错的麦克风按钮关掉。
