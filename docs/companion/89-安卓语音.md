## 进程与分层

安卓分两个进程。主进程是现在的 app（Activity、webview、`libreading_partner_lib.so`），一行引擎代码都不加载。语音进程是 `android:process=":voice"` 里的前台服务 `VoiceService`，只有它 `System.loadLibrary("voice_engine")`。原生库加载失败、模型加载失败、llama.cpp 断言 abort、被 LMK 杀掉，都只死 `:voice`；主进程收到 socket EOF，给前端发 `state {running:false, reason:"failed"}`，打字和其余功能照常。

判轮、识别、出声的编排全在共享 Rust 里，Kotlin 只做音频 I/O 和系统接口。共享 Rust 在 Linux 上能编能测。

| iOS | 安卓 | 位置 |
|---|---|---|
| `AudioFront.swift`：VPIO、播放节点、路由、打断通知 | Kotlin `VoiceAudio`：AudioRecord、AudioTrack、AudioManager 的模式/路由/焦点 | `:voice`，`plugins/voice/android/` |
| `NeuralFront.swift`：Silero、Smart Turn（CoreML） | `vad.rs`、`mel.rs`、`smart_turn.rs`（ORT） | `:voice`，`plugins/voice-engine/engine/` |
| `VoiceTurn.swift`（`turn-detect.ts` 逐行移植） | `turn.rs`，同一份移植的第三份 | 同上 |
| `ConversationRun.swift` | `call.rs` | 同上 |
| `Recogniser.swift`（SpeechAnalyzer） | `asr.rs`（Qwen3-ASR，llama.cpp） | 同上 |
| `SpeechOut.swift` | `playback.rs` | 同上 |
| Kokoro 在主进程 Rust 里跑（`kokoro/engine.rs`） | Kokoro 在 `:voice` 里跑；主进程的 `SpeechSession` 经 `RemoteSynth` 调它 | `kokoro-onnx` crate，两端共用 |
| `ios.rs`：`Voice` 经 `run_mobile_plugin` 到 Swift | `android.rs`：`Voice` 同一组方法，经 socket 到引擎 | 主进程，`plugins/voice/src/` |
| `VoicePlugin.swift`：命令、事件、权限 | Kotlin `VoicePlugin`：权限、能力判断、拉起和绑定 `:voice` | 主进程，`plugins/voice/android/` |

新的 Rust 代码放 `plugins/voice-engine/`，一个独立的 Cargo workspace，`Cargo.lock` 进 git：

- `kokoro-onnx`：`plugins/voice/src/kokoro/` 里的 `engine.rs`、`tokens.rs`、`vocab.rs`、`voice.rs`、`manifest.rs` 原样 `git mv` 过来（五个文件里没有 `crate::` 路径，模块结构照搬就能编），`engine` 挂在 `ort` feature 后面，`ort` 依赖跟着搬。插件的 `kokoro/mod.rs` 用 `pub use` 把它们挂回原路径，插件的 `kokoro` feature 改成打开 `kokoro-onnx/ort`；`download.rs`、`bench.rs` 留在插件。iOS 编的还是同一份代码、同一个 `ort`。搬家之后另一个 commit 给 `Engine` 加按 style 行合成的入口 `synthesize_style`，原来的 `synthesize` 先取 style 行再调它。
- `voice-wire`：主进程和引擎之间的帧格式和消息类型，只依赖 serde。
- `engine`：`crate-type = ["cdylib", "rlib"]`，产物 `libvoice_engine.so`。依赖 `voice-wire`、`kokoro-onnx`、`ort`、`llama-cpp-2`、`realfft`，安卓上加 `jni`。

插件依赖 `voice-wire` 和 `kokoro-onnx`，不依赖 `engine`，所以 ORT 和 llama.cpp 永远不进主进程的库。

`android.rs` 和 `ios.rs` 是同一组 `Voice` 方法、同一组参数结构（`models.rs`）。iOS 走 Swift 的地方安卓走 socket；Swift 发给前端的每个事件，引擎发同名同结构的事件，前端的 `conversation.ts`、`voice-session.ts`（含坑 651 的折叠）一行不改。听写那四个命令在安卓上照 `fallback.rs` 拒绝。

## 主进程和引擎之间

通话开始时 `android.rs` 调 Kotlin `VoicePlugin` 的 `openEngine`（`run_mobile_plugin_async`），它做四件事：确认 `RECORD_AUDIO`（没有就弹系统授权，拒了就以「没有麦克风权限」拒绝 `start_conversation`）；`startForegroundService` 加 `bindService` 拉起 `VoiceService`；`ParcelFileDescriptor.createSocketPair()` 建一对 socket，一端经 `Messenger` 递给 `:voice`；另一端 `detachFd()` 后把 fd 号作为命令结果交回 Rust，`android.rs` 用 `UnixStream::from_raw_fd` 接住。之后主进程 Rust 和引擎 Rust 直接在这条 socket 上说话，Kotlin 不再经手。

主进程 Rust 调 Kotlin `VoicePlugin` 的方法只有三个，都不带参数，都回一个对象：

| 方法 | 回答 | 用处 |
|---|---|---|
| `capability` | `{ call: boolean }` | `voice_capability` 命令，见「内存门槛」；调用出错一律当 false |
| `noBackupDir` | `{ path: string }` | `getNoBackupFilesDir()`，插件启动时取一次，作 `Downloader` 的根 |
| `openEngine` | `{ fd: number }` | 上面四件事；它的拒绝就是 `start_conversation` 的拒绝 |

帧格式：4 字节小端长度 + 1 字节类型 + 内容；控制消息是 JSON，PCM 是裸的 16 位小端样本。单帧上限 4 MB，超了断开。

每个请求带 `id`，回答带同一个 `id`。

| 方向 | 消息 | 内容 |
|---|---|---|
| 主 → 引擎 | `Open` | 各模型文件的绝对路径、线程数；回 `Done`，或 `Error`（文件不全时是下载提示原句） |
| | `Close` | 挂断，关麦，模型留在内存；回 `Done` |
| | `Synthesize` | Kokoro fp32 模型的路径、音素串、该句的 style 行（256 个 f32）、speed；回 `Pcm`（样本在后面的 PCM 帧里）或 `Error {message}` |
| | `Enqueue` | 对应 `Voice::enqueue_speech`，SentenceMarks 在控制帧里，24 kHz PCM 在紧跟的 PCM 帧里；回 `Enqueued {ack}` 或 `Error` |
| | `Finish` / `SetVolume` | 对应 `finish_speech`、`set_speech_volume`；回 `Done` |
| | `StopSpeaking` | reason；回 `Position {SpeechPosition}` |
| 引擎 → 主 | `Event` | 一个 `ConversationEvent`，原样转给登记了 `conversation` 的 Channel |
| | `Speech` | 一个 `speech` 事件（`speaking` 1/0 带原因、`level`），原样转给登记了 `speech` 的 Channel |
| | `Done` / `Pcm` / `Enqueued` / `Position` / `Error` | 上面请求的回答 |

`Synthesize` 带模型路径，是因为前端在 `start_conversation` 之前就调 `prime_speech_cues`，合成可能比 `Open` 先到：引擎没载过 Kokoro 就按这个路径载，`Open` 载的是同一个文件就不再载。

主进程这端的逻辑在 `engine_link.rs`，不带 cfg，对任意 `Read + Write`，Linux 上用 `UnixStream::pair` 对着真引擎测；`android.rs` 只是胶水。连接是懒建的单例：通话和 `RemoteSynth` 谁先要谁建。引擎在回 `Open` 的 `Done` 之前就发 `state opened`；主进程从发出 `Open` 起扣住通话事件，`start_conversation` 回复之后才放，和 iOS 的 `beginEmitting` 同序；`Open` 失败时先放（`state failed` 在内）再拒。EOF 之后所有在等的请求以 `EXITED`（The voice process exited.）返回错误，进行中或正在开的通话发 `state failed`，下一个请求重新调 `openEngine` 拉起 `:voice`。

`:voice` 里 Kotlin 和引擎之间的 JNI 只有 Kotlin 调 Rust 这一个方向，Rust 从不回调 JVM：

- `nativeAttach(fd: Int): Boolean`：在 socket 上起服务循环。
- `nativeNextControl(): String?`：阻塞取下一条给 Kotlin 的指令（`open {capture}`、`close`、`volume {value}`、`exit`），JSON。冲掉播放不走这里。
- `nativeCapture(buf: ShortArray, n: Int, timeNs: Long)`：一帧麦克风。
- `nativeReadPlayback(buf: ShortArray): Int`：最多等 20 ms 取播放样本；返回 0 是暂无，-1 是马上 `pause()` + `flush()`。-1 是唯一的冲掉信号，由写线程自己在写下一批样本之前做；别的线程冲掉可能落在新样本之后把它们也冲掉。
- `nativePlaybackPosition(frames: Long, timeNs: Long)`：`AudioTrack.getTimestamp` 的结果，引擎据此算播放头、cut 和 envelope 的 `startsInMs`。`frames` 从最近一次 flush 或这条 AudioTrack 新建时起算，flush 之后归零。
- `nativeAudioEvent(kind: String)`：焦点丢了、麦克风被系统静音、输入设备没了、app 离开前台。

`VoiceService.onCreate` 里 `loadLibrary` 包在 `try/catch (UnsatisfiedLinkError)`，失败就经 `Messenger` 回「不可用」并 `stopSelf`；`onStartCommand` 先 `startForeground(…, FOREGROUND_SERVICE_TYPE_MICROPHONE)` 再做别的，返回 `START_NOT_STICKY`。`VoiceService` 不引用任何 Tauri 类（`:voice` 里没有 Tauri）。

`Messenger` 上三种消息：`MSG_ATTACH`（`arg1` 是请求号，`data` 里 `fd` 是 socket 的一端）、`MSG_ATTACHED`（同一个 `arg1`，`arg2` 1 成功、0 失败、2 原生库不可用）、`MSG_APP_STOPPED`。`openEngine` 收到 `MSG_ATTACHED` 才回答。前台：`onStartCommand` 每次都 `startForeground`，之后每条 `open` 指令再进一次前台（同一个 socket 上的第二通电话不再走 `openEngine`），`close` 指令 `stopForeground`。

## 采集与播放

都在 `:voice` 的 Kotlin 里，引擎发「开音频」时打开，「关音频」时全部还原。

- 模式：`AudioManager.mode = MODE_IN_COMMUNICATION`。
- 采集：`AudioRecord` 在开音频时就建好（`capture: false` 也建），只在 `capture: true` 时 `startRecording`；`MediaRecorder.AudioSource.VOICE_COMMUNICATION`，16 kHz 单声道 PCM 16 位，每次读 512 个样本（32 ms，正好一帧 Silero）。`AcousticEchoCanceler`、`NoiseSuppressor` 在 `isAvailable()` 时挂到这个 `audioSessionId` 上并打开，AGC 不碰。
- 播放：`AudioTrack`，`USAGE_VOICE_COMMUNICATION` + `CONTENT_TYPE_SPEECH`，24 kHz 单声道 PCM 16 位（Kokoro 的原生采样率），`MODE_STREAM`，`setSessionId(record.audioSessionId)` 和采集同一个会话，回声消除拿得到参考；因为录音对象先建好，先放声后开麦时 AudioTrack 不用重建，帧计数不会在引擎底下归零。一个写线程循环 `nativeReadPlayback`（每次 480 个样本，20 ms，一次过期的写最多把冲掉推迟这么久）→ `write(WRITE_BLOCKING)` → `nativePlaybackPosition`；`getTimestamp` 的 `nanoTime` 早于最近一次 flush 的戳丢掉，帧数不超过 flush 后写进去的数。
- 路由：用 `setCommunicationDevice`（API 31），从 `getAvailableCommunicationDevices()` 里按 BLE 耳机 > 蓝牙 SCO > USB 耳机 > 有线耳机 > 机身扬声器 挑第一个；没有耳机时走扬声器，和 iOS 的 `.defaultToSpeaker` 一样。`AudioDeviceCallback` 有设备增减就重挑；挑完一个输入都没有，报 `lost`（同 iOS「麦克风没了」）。挂断时 `clearCommunicationDevice()`、`mode = MODE_NORMAL`。
- 焦点：开音频时 `requestAudioFocus(AudioFocusRequest(AUDIOFOCUS_GAIN_TRANSIENT))`。`AUDIOFOCUS_LOSS` 和 `LOSS_TRANSIENT` 报 `interrupted` 挂断（来电走的就是这条）；`LOSS_TRANSIENT_CAN_DUCK` 不理。targetSdk 36 下只有 top app 或前台服务能拿焦点，`:voice` 有前台服务。
- 被系统静音：`registerAudioRecordingCallback`，本会话 `isClientSilenced()`（API 29）为真报 `lost`。
- 离开前台：主进程 `VoicePlugin.onStop` 经 `Messenger` 告诉 `VoiceService`，后者 `nativeAudioEvent("app-stopped")`，引擎以 `lost` 挂断，和 iOS 的 `didEnterBackground` 一样。`:voice` 死掉时系统按进程回收它设的模式、通信设备和焦点。

## 判轮、识别、出声

判轮。Silero v6.0 每 32 ms 一帧：输入 576 个样本（上一帧末尾 64 个 + 新的 512 个），state `[2,1,128]` 帧间带着，`sr=16000`，1 个线程。轮次状态机是 `turn-detect.ts` 的逐行移植，常数取 `NEURAL_TURN_DETECT`（`pauseMs` 250、`hangoverMs` 2500、`speechThreshold` 0.5），播放期间一帧还要过 -35 dBFS 且量的是截止到帧末的 100 ms（坑 652），`confirmMs` 300、`immunityMs` 2000、`resumeMs` 300 照默认。`pause` 时跑 Smart Turn v3.2：取这一轮最后 8 s，不足在前面补零，整窗零均值单位方差，Whisper log-mel（n_fft 400、hop 160、80 个 Slaney mel、丢最后一帧，128000 样本 → `[1,80,800]`），fp32 模型，输出已经过 sigmoid，线 0.5，2 个线程。

识别。Qwen3-ASR-0.6B，Q4_K_M 解码器 + Q8_0 mmproj，经 llama.cpp 的 mtmd：`n_ctx` 4096、`n_batch` 512、4 线程、贪心、最多 800 token；prompt 照实测时的 `asrd.cpp`：`<|im_start|>system\n<|im_end|>\n<|im_start|>user\n` + 音频 + `<|im_end|>\n<|im_start|>assistant\n`，不强制语言，输出去掉 `language X<asr_text>` 前缀。`start_conversation` 的 `locale` 和 `contextualStrings` 在安卓上不用。一个专用工作线程，同一时刻一个任务。

一轮的流程，对应实测里的 A-onset：

1. 本轮最后一个人声帧之后的第一帧（状态机开始计静音的那一帧），起一个识别任务，音频从本轮第一个人声帧前 0.25 s 到这一帧。
2. 静音满 250 ms 到 `pause`，照常跑 Smart Turn。
3. 状态机出 `end`（Smart Turn 判完，或 hangover 兜底）时，等最近一次第 1 步的任务出字，发 `speech-end {text, silentMs}`；识别为空就发空的 `speech-end`，前端照 iOS 保住空位。
4. 静音期间又出现人声帧，第 1 步的任务作废：代号加一，`llama_set_abort_callback` 让解码尽快停（mtmd 的编码没有中止接口，编完才停），结果丢掉。下次静音从本轮起点整段重认。

安卓不发 `final`：整句一次认完，`speech-end` 的文本就是最终文本，`TurnWindow` 和迟到 final 那一套用不上。

出声。主进程的 `SpeechSession`、relay、分句、g2p、提示音缓存全不动。`session::on_device_voice` 在安卓上返回 `KokoroVoice`，其 loader 给的 `Synthesizer` 是 `RemoteSynth`：把音素串、`voice.style_for(phonemes)` 那一行和 speed 发给引擎，引擎用 `kokoro-onnx` 合成（fp32、4 线程，中文 `zf_001`、纯英文句 `af_maple`，常数都在 `tts/kokoro.rs`），PCM 回到主进程，再经 `DevicePlayer` → `Voice::enqueue_speech` 回到引擎播。`playback.rs` 是 `SpeechOut.swift` 的移植：句队列、SentenceMarks、按播放头算 `cut`、duck 音量、25 ms 窗的 envelope。打断时引擎在同一进程里先让播放冲掉，再发带 `cut` 的 `speech-stop`，和 iOS 一样不等 invoke。

模型加载：`Open` 时先载 Silero 和 Smart Turn（几十毫秒）就开麦，Qwen 和 Kokoro 各在后台线程载；用户第一句说完时 Qwen 还没好，就等它好了再认。`Close` 后模型留在 `:voice` 里，进程被系统回收就下次重载。文件不全时 `Open` 以「在设置 → 可选 → 语音里下载」原句拒绝，前端照现有错误路径显示。

全是宽松许可证，和本仓库的 PolyForm Strict 不冲突；APK 里带 `plugins/voice/android/src/main/assets/voice-engine-licenses.txt`，收 ORT（含 ThirdPartyNotices）、llama.cpp 和五个模型的许可证全文。

只编 arm64-v8a。x86_64 安卓 pyke 没有 ORT 预编译，模拟器冒烟包（`android-engine-smoke.yml` 的 universal 包）的 x86_64 那一半没有 `libvoice_engine.so`，能力判断给 false，不出语音入口；发布包本来就只有 aarch64。

构建脚本 `scripts/android-voice-engine.sh`：用 NDK r28c（`NDK_VERSION` 28.2.13676358，和 android-apk.yml 同一个）给 `cargo build --release --target aarch64-linux-android -p voice-engine` 配 `CC/CXX/AR_aarch64_linux_android`、`CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER`（`aarch64-linux-android31-clang`）、`ANDROID_NDK`、`ANDROID_API_LEVEL=31`、`ORT_CXX_STDLIB=c++_static`（不设时 ort-sys 链 `c++_shared`），ORT 和 llama.cpp 都静态链 libc++，产物 strip 后放到 `plugins/voice/android/src/main/jniLibs/arm64-v8a/libvoice_engine.so`（gitignore），由 AGP 随插件模块并进 APK。本机不装 NDK，这个脚本只在 CI 上跑。

CI：

- `android-voice-engine.yml`（新，`workflow_dispatch`）：跑脚本，断言 `readelf -lW` 的 LOAD 对齐是 0x4000 或 0x10000、`readelf -d` 的 NEEDED 里没有 `libc++_shared.so` 和 `libomp.so`，打印 .so 大小，上传 artifact。
- `android-apk.yml`：在 `bun tauri android init --ci` 之后、`bun tauri android build` 之前跑脚本；签名后断言 APK 里有 `lib/arm64-v8a/libvoice_engine.so`，打印它的大小。现有的 16 KB 对齐检查自动覆盖它。`Swatinem/rust-cache` 的 `workspaces` 加上 `plugins/voice-engine`。

包体：`libvoice_engine.so` 预计 30–45 MB（ORT 链进去后 `--gc-sections` 会去掉一部分，llama.cpp + ggml + mtmd 约 8–10 MB），APK 里 .so 不压缩，APK 大约涨这么多；实际数以 CI 打印的为准。

## 内存门槛

条件全满足才有语音：API ≥ 31、`(classLoader as BaseDexClassLoader).findLibrary("voice_engine") != null`（只有 arm64-v8a 有这个库）、内存 ≥ 6,800,000,000 字节。内存在 API 34+ 读 [`MemoryInfo.advertisedMem`](https://developer.android.com/reference/android/app/ActivityManager.MemoryInfo#advertisedMem)（标称内存），更低的读 `totalMem`（内核可见，比标称少一截）。6 GB 机两个值都到不了 6.44e9，8 GB 机的标称值是 8e9 或 8 GiB。

主进程 `VoicePlugin` 构造时（插件注册时）算一次并缓存（都是硬件常量）；`:voice` 里原生库加载失败过一次，本次 app 进程内也改成 false。前端经新命令 `voice_capability` → `{ call: boolean }` 取，iOS 恒为 true，桌面恒为 false，安卓问 Kotlin 的 `capability`，出错一律 false，不报错。不满足就不出语音入口，没有降级模式。

`:voice` 通话中常驻：

| 项 | 内存 |
|---|---|
| Qwen3-ASR Q4_K_M + mmproj Q8_0，`n_ctx` 4096 | 1.57 GB（实测峰值 RSS） |
| Kokoro fp32 | 约 1 GB（iOS A16 上的数） |
| Smart Turn fp32、Silero、ORT 运行时 | 约 0.15 GB（估） |
| 进程本身 | 约 0.05 GB（估） |
| 合计 | 约 2.8 GB |

主进程不变。通话中 `:voice` 是前台服务进程，挂断后是缓存进程，系统缺内存时先杀它，不碰前台的主进程。

## 权限与 ACL

插件模块的 `AndroidManifest.xml`（AGP 合并进 app）：

- `RECORD_AUDIO`：运行时权限，`@TauriPlugin(permissions = [Permission(strings = [Manifest.permission.RECORD_AUDIO], alias = "microphone")])`，`openEngine` 里查和请求。
- `MODIFY_AUDIO_SETTINGS`：`setMode`、`setCommunicationDevice` 用，普通权限。
- `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_MICROPHONE`：普通权限。
- `<service android:name=".VoiceService" android:process=":voice" android:foregroundServiceType="microphone" android:exported="false"/>`。前台服务只在 Activity 可见时由按住卢明拉起，满足 `RECORD_AUDIO` 的 while-in-use 限制（[前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types#microphone)）。

不申请 `POST_NOTIFICATIONS`（没有它前台服务照跑，通知只进任务管理器）和 `BLUETOOTH_CONNECT`（`setCommunicationDevice` 的文档不要求它）。

Tauri：插件 `build.rs` 加 `.android_path("android")`；`android.rs` 里 `api.register_android_plugin("com.xinyuan.readingpartner.voice", "VoicePlugin")`，第 5 片时它关着（`KOTLIN_PLUGIN = false`，APK 里没有这个类时注册会在 UI 线程留下 ClassNotFoundException），这时能力为 false、模型目录退到 `app_local_data_dir`，第 6 片和 `.android_path` 一起打开；Gradle 模块照 `tauri-plugin-haptics` 2.3.3 的 `android/` 布局。ACL 新建 `src-tauri/capabilities/android.json`，`"platforms": ["android"]`，`"permissions": ["voice:default"]`；`ios.json` 不动。新命令 `voice_capability` 进插件 `build.rs` 的 `COMMANDS` 和 `permissions/default.toml`。

## 切片

依赖顺序：1 → 2 ∥ 3 → 4 → 5 → 6；7 不依赖任何切片，随时可做，先合也安全（安卓上 `voice_capability` 不存在时被 ACL 拒，能力为 false）。2、3、7 可以同时派。坑号预分如下，记在 `docs/pitfall/` 的「原生音频与语音」（`native-audio/`）或「Android 构建与签名」（`android-build/`）组。

每个切片都要过 `scripts/t.sh` 和 `bun run typecheck`；改了 Rust 的跑 `cargo test --manifest-path plugins/voice/Cargo.toml --features kokoro` 和 `cargo test --manifest-path plugins/voice-engine/Cargo.toml --workspace`。真模型的测试从 `VOICE_MODELS` 指的目录读（布局同下载目录），目录不在就 `#[ignore]` 跳过，合并前主会话带上目录跑一遍。

1. 引擎工作区和安卓构建（坑 660）。建 `plugins/voice-engine/` 三个 crate；`kokoro-onnx` 的搬家 commit 纯 `git mv` 加改 import；`engine` 此时只把 ORT 建一个 Environment、llama.cpp 调一次 `llama_backend_init`，证明两者能链进同一个 .so；`scripts/android-voice-engine.sh` 和 `android-voice-engine.yml`。验收：上面两组 `cargo test`（含 `kokoro/engine.rs` 的 `linux_compare` 真模型跑，输出和搬家前逐字节相同），`ios-simulator-smoke.yml` 绿，`android-voice-engine.yml` 绿并打印 .so 大小和 NEEDED。
2. 判轮（坑 661、662）。`vad.rs`、`mel.rs`、`smart_turn.rs`、`turn.rs`。验收：`tests/soul/voice/turn-detect.test.ts` 的 49 个用例逐条移成 Rust 测试，事件序列一致；夹具音频用 Kokoro 在 Linux 上合成、重采样到 16 kHz（不用用户录音），参照值在一次性 venv 里算好后连同音频进仓库（几十 KB）：mel 对 `transformers` 的 `WhisperFeatureExtractor(chunk_length=8)` 逐点差 < 1e-4，Silero 逐帧概率对官方 `silero-vad` Python 包 v6.0 差 < 1e-3，Smart Turn 概率对 pipecat [`inference.py`](https://github.com/pipecat-ai/smart-turn/blob/main/inference.py) 差 < 1e-3。
3. 识别（坑 663）。`asr.rs`：加载、整句识别、去前缀、中止和作废、加载失败返回 `Err` 不 panic。验收：对 `/home/xinyuan/voice-asr-bench/chunks/{norm,raw}_{1..5}.wav` 逐段识别、按序拼接，`score.py` 的 CER 和 `results/qwen3-asr-0.6b-gguf-q4km_{norm,raw}.txt`（13.98% / 14.93%）相差不超过 1pp；峰值 RSS（`VmHWM`）≤ 1.7 GB；中止测试：长音频识别中途作废，200 ms 内工作线程空出来（编码阶段除外）。
4. 通话编排和播放（坑 664、665）。`call.rs`、`playback.rs`，加一个 `AudioHost` trait（JNI 和 Linux 虚拟设备各实现一份）。验收：虚拟设备按快进时钟喂 wav、虚拟播放头走 24 kHz，场景测试：一句一轮出一个 `speech-end`；句中停顿 Smart Turn 判未完再接着说，只出一个 `speech-end` 且文本是整句；播放中说「等一下」出 `speech-duck` → `speech-stop`，`cut` 的句号和字偏移对得上播放头；误报出 `speech-resume`；模型缺文件时 `state failed` 带下载提示原句。真模型一组，假模型一组。
5. 主进程这一半（坑 666）。`voice-wire`；引擎的 socket 服务循环；`android.rs`（核心逻辑写成对任意 `Read + Write` 泛型、不带 cfg 的模块，安卓胶水才带 `cfg(target_os = "android")`）；`RemoteSynth`；`Downloader` 改按包，听的包按「开工前要确认」第 1 条的两个来源固定 revision；`voice_capability` 命令。验收：Linux 端到端，`UnixStream::pair` 一头是插件的 `SpeechSession` + `RemoteSynth`，另一头是引擎服务线程 + 虚拟设备：`speak_begin/push/close` 出声、`stop_speaking` 回的位置对、通话事件原样到假 Channel；引擎线程被 kill 后在等的请求都返回错误、发 `state failed`；`Downloader` 两个包的状态、续传、sha256 不符删文件。
