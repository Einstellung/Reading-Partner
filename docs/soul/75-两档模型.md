# 两档模型

2026-09-22 定。全app 只有两个模型档位，任务归哪一档由程序决定，设置里没有第二个入口。取代「一个默认模型 + 简报单独一个」的旧安排。

- 对话档（`defaultModelId`）：读者正在等、看着回复流出来的调用——阅读对话、Lumen、info 对话。
- 日常档（`everydayModelId`，null 表示跟随对话档）：没人等着的后台调用。

两档都只是模型 id，供应商永远是 `defaultProviderId`：凭据是单活的（`ai/auth/credentials.ts`），写在另一个供应商下的模型 id 没有 key 可用。

## 谁归日常档

判据：读者在界面上看着回复流出来的调用走对话档，没人等着的后台调用走日常档。2026-09-23 按这条重新归档，今天的无头调用全部归日常档：备课（`prep`，含章节脊梁、论文备课，以及同读这个 kind 的 legion subagent——文献研究、tasking）、蒸馏（`distill`：阅读对话、划线、复述三种观察蒸馏，effort 仍读 `chatThinking`）、每晚的 dream（`prep`）、简报两段（粗筛、分析）、三餐线写做法（`meals`）。`chat` 这个 kind 留作对话档，给读者真在等的无头调用用。会话不分线：三餐会话是读者实时在等的对话，和阅读对话、Lumen、info 对话一样走对话档；只有三餐线里写做法那次无头调用（`meals` kind）走日常档。

归类写在 `src/ai/model-tier.ts` 的 `ThinkingKind → tier` 一张表里，管的是无头调用。要把一件新活挪去日常档，就是往那张表里加一行。设置项只说日常档跑哪个模型，不说哪些活是日常档。

发起调用的四个地方（`soul/turn.ts` 量窗口、`soul/bell.ts`、`soul/recover.ts`、`ui/components/info/use-info-call.ts`）都直接用对话档，过同一个 `modelIdFor`。装配时量的上下文窗口必须是真正要发过去的那个模型的。

## 旧字段

`briefingModelId` 改名成 `everydayModelId`。读盘时做一次迁移（`migrateSettings`）：文件里有 `briefingModelId` 而没有 `everydayModelId`，就按日常档读。旧 key 不从文件里删——老版本的设备读自己那份，fields 合并看到一侧少了个 key 会把删除同步过去（和 `autoNotes`、`backgroundCollect` 同一个理由）。`palace/kinds.ts` 的 fieldGroups 里两个 key 都在，模型 id 和供应商一起结算（坑 237）。
