# 计数游标吞掉合并进已蒸馏段的消息

## 现象

A 设备的线程有四条消息（ts 10、10、30、30），蒸馏完，`distilledMessages[t] = 4`。B 设备离线时在同一线程问了一句（ts 20）。同步后线程按 `messages` 策略合并成 10、10、20、30、30，欠账算出来是 0：B 的那句永远不进蒸馏。B 那句带回复时，下一次 pass 的覆盖段是 ts 30 的两条，A 已经读过的又读一遍。`tests/memory/cursor-inserts.test.ts` 在修之前就是这两个结果。

## 原因

`distilledMessages[threadId]` 是条数，意思是「按线程顺序前 N 条已读」。线程原子合并时顺序只会在尾部追加，条数够用。`messages` 策略按 ts 排序并集（docs/59 §5），对端的消息可以落进前 N 条里面，条数于是盖住它，同时把一条已读的挤到 N 之后。

## 解法

游标改成已读消息的 key 列表 `distilledMessageKeys[threadId]`（消息 id，没有 id 时 `ts:role`），逐条判断读没读过；条数照写在旁边，等于列表长度，给老版本用。条数和列表长度对不上（老版本动过）或没有列表时，条数按老意思读成当前顺序的前 N 条，叠在列表上；扫欠账时把这种读法写回成列表，只读一次（`resolveCursors`）。见 docs/soul/58「消息游标」。
