# 只是重存了一次的设备，赢下整个文件

现象：两台设备同步同一本书的批注。A 上什么都没改，只是打开合上，app 把 `annotations-<id>.json` 用一模一样的内容重写了一遍。下一趟同步之后，B 上新画的批注没了，而且没有任何报错——UI 显示同步成功。

原因：两处叠加。

1. 判"本地变没变"看的是 mtime 和 size。app 会用相同内容重写文件（保存时全量序列化、退出时统一落盘），mtime 就变了，于是这个文件被当成本地有改动。
2. 两边都"有改动"时按 mtime last-writer-wins，赢家整个文件覆盖输家。A 的重写发生得晚，A 赢，B 的批注被 A 那份不含它的旧内容整体覆盖。

单看任何一条都不致命：LWW 在真的两边都改过时是可以接受的取舍，mtime 变了也确实"可能"变了内容。是"假的本地改动"喂给"整文件二选一"才造成静默丢数据。

解法：

- 判变更用内容 hash（`platform/sync/content.ts`），不用 mtime。mtime 和 size 只留作快照里的廉价预筛——它们能排除一个文件而不用读它，被它们标记的才去算 hash，15 秒一次的 tick 才不会每次读全部数据文件。
- 两边真的都改过时不选边，走三方合并：上次同步成功时的内容存在本地 `sync-base/`，作为 merge base（`platform/sync/merge/`）。
- 一个副作用：两边内容 hash 相同时（各自做了同样的编辑，或一边只是重存）直接判定为已一致，不下载不上传也不进冲突。
