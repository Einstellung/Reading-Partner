# 210 夜间批处理挂在多入口的 tick 上，一次启动跑了四遍，而且抢在迁移前面

## 现象

0.12 真机，一次启动 35 秒内 `dream-run` 事件出现四次：写 10、写 9、写 0、写 0。十条结论落盘两组，一组中文一组英文，内容一一对应。

同一次启动里，dream 在用户点迁移按钮之前 20 秒就跑完了。它读到的观察还是 8 位 id，写出的 19 条 statement 的 `evidence` 全是 `m-xxxxxxxx`；迁移第 6 步随后把观察文件名改成 16 位，这 19 条的证据全部悬空，`coveredObservationIds` 一条都匹配不上——那批观察于是又变回候选，下一晚还会再被写一遍。

## 原因

两件事，都不是 dream 自己的判断出错。

`runDreamIfDue` 的日闸只看状态文件，而状态文件是在一趟跑完之后才写的。`checkDailyRound` 有三个入口（启动、回前台、五分钟定时器），启动那几秒里三个都会打进来，加上定时器一共四次；四次都在第一次落盘之前读到"今天没跑过"，四次都放行。异步函数里"读状态 → 干活 → 写状态"没有进程内的在飞标记，就等于没有闸。

迁移是用户按按钮触发的，dream 是自动的，两者之间没有任何顺序关系。dream 只要早一步，写出来的就是一份指向即将被改名的文件的证据。

## 解法

三道闸，都在 memory 侧，`src/memory/dream/gate.ts`：

- 进程内在飞标记，`enter()` 在任何 await 之前置位。第二个调用直接返回 false，不排队——排队只是把四次跑推迟成四次跑。
- 进程内当日标记，一趟跑完（merged / no-change / failed 都算）就点亮，状态文件写失败也照样点亮。
- 跑之前扫观察目录，只要还有 `m-[0-9a-f]{8}\.md` 就返回 `waiting-migration`，不推进日期也不推进 hash，用户按完按钮当天还能跑。判据是文件本身而不是迁移标记：迁移刻意不存"已完成"状态，存了也会同步到另一台没迁移的机器上。

已经写坏的那批证据由迁移第 7 步 `widen-statement-ids` 修：用第 6 步同一个 `deriveObservationId` 把 statement 里 8 位的证据一起加宽。

多入口的 tick 是常态，把闸放在被调用的那一侧，不要指望调用点去协调。
