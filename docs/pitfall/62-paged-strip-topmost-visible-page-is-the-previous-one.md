# 翻页布局下「最顶上的可见页」是上一页

## 现象

翻页模式读到第 8 页，存下去的 `pageIndex` 是 6（第 7 页）。每次重开退一页，读一天退一天。900×1000 视口必现；834×1194 又是对的，所以从"某些机器上会漂"看不出规律。

## 原因

坑 23 定的持久化锚点是「`pageVisibilityMetrics` 里 pageNumber 最小的那项」，那条规则是按竖排连续列写的：视口顶边落在最顶上那个可见页里，它的可见区 origin 就是视口左上角在该页坐标里的位置。

横排页带没有这回事。页是紧挨排开的（坑 40），只要 fit-page 小于 fit-width，一整页就填不满视口宽，两侧邻页各露一条——这是布局本身，不是缺陷。于是"最左边的可见页"永远是上一页。900×1000、612×792 的页：fit-page 1.262，页宽 772，视口 900，居中后左边露第 7 页 51px、右边露第 9 页 71px。834×1194 上 fit-page 和 fit-width 数值相同，页宽正好铺满，左边什么都不露，同一条规则恰好答对——这就是它看起来时灵时不灵的原因。

## 解法

锚点按布局分。规则和逐布局设置表放一起，在 `src/reading/engine/layout-modes.ts`（`LayoutSettings.anchor` + 纯函数 `readingPosition`，有单测）：

- 竖排 `viewport-top`：最顶上的可见页 + 页内偏移，和坑 23、坑 22 一样，一个字没改。
- 翻页 `centered-page`：插件自己的 `getCurrentPage()`（可见占比最大的页，在 fit-page 下就是居中那页），不存页内偏移——还原时本来也只用页码。

翻页别自己按几何再算一遍居中页：`getCurrentPage()` 已经是切布局搬运位置、页码显示、`turnToPage` 的起点和 `dragStartPage` 用的那个答案，宿主再算一个就是多一个能对不上的意见。它和 `pageVisibilityMetrics` 出自 `commitMetrics` 同一次 dispatch，读出来一定自洽。

已经存在盘上的旧值不动：一个数字看不出是错存的还是读者自己翻到的。

实测（900×1000 与 834×1194，第 8 页）：两个布局的存-开-再存都回到同一页；竖排的页内偏移 412 也原样回来；翻页里手指翻页、切到竖排再切回来，存的都是屏幕上那一页。
