# 233 故意失败的 fetch 测试，要按真时间等完生产的退避阶梯

## 现象

2026-09-06 量全套件：4445 个测试 27 秒，其中五个文件占 16 秒。最慢的
`tests/info/sources/engine.test.ts` 单跑 7.6 秒，31 个用例、117 个断言，注释写着
「Injected fetch + extract keep it DOM-free」——没有网络，没有 DOM，没有文件系统。

`bun test <file>` 不给这个量级的用例打时间：31 个用例一个时间都不打，只在最后打一行
`Ran 31 tests across 1 file. [7.65s]`。于是「哪个用例慢」这个问题，bun 一个字都不回答。

## 原因

`src/info/extract/http.ts` 的 `fetchText` 对 5xx/429 重试两次，退避 0.5s 再 1s，睡在
真定时器上。测试里六个用例故意发 `textResponse("boom", 500)`——它们要验的是一次失败的
抓取降级成什么（该源标红、别的源不受牵连、item 退回摘要），退避阶梯不是它们的题目。
可代码不知道这件事，照走 1.5 秒。六个用例，7.5 秒。

`source-tools.test.ts` 的 1.6 秒是同一笔账的一个用例版本。

形状是通用的：**被注入的是 fetch，不是时间**。注入 fetch 让测试不上网，于是没人再想起
来失败路径上还有一个真定时器；而失败路径恰恰是重试逻辑唯一会被踩到的地方，所以「注入了
网络」的测试文件反而是最容易偷偷睡觉的那一类。

## 解法

生产代码把 sleep 也收成注入的（`fetchText` 本来就有 `opts.sleep`，缺的是编排层没往下传）：
`CollectDeps` / `TrialDeps` 加一个可选 `sleep`，转发到每个 `fetchText`。不传就是
`fetchText` 原本的默认值，线上路径一个字节没变；测试传一个 no-op，同样的重试按同样的次数
发生，只是不要钱。7645ms → 136ms，1602ms → 98ms，用例数和断言数不变。

定位办法（bun 不给 per-test 时间时）：把可疑文件的输出翻到最上面看 `console.warn`——退避
是失败路径上的东西，失败路径基本都在往 stderr 写东西，哪几行在打，账就记在哪几个用例上。
再顺着那行的调用栈往生产代码里找 `setTimeout`。

## 判据

改完拿 `expect() calls` 的总数当闸：`scripts/t.sh` 前后都是 122287，就说明没有一个断言在
提速里被删掉或放宽。文件时间会变，断言数不会。
