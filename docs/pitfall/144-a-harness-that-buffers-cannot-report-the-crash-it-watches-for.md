# 攒在内存里最后一次写的探针，报不了它自己要抓的那种死法

## 现象

跑二十分钟长按的探针，收集样本和 final 时间线，跑完写一个 JSON。取回来的文件是：

```json
{ "stage": "waiting-for-tap", "samples": [], "finalsTimeline": [] }
```

这一轮根本没被点开始，所以什么都没有——但真正的问题是：**就算它跑到第十八分钟才死，
取回来的也是这个。** 没有样本，没有时间线，连死在第几分钟都没有。

而这个探针存在的唯一理由，就是查「二十分钟的会话会不会中途死」。

## 原因

它把记录攒在内存里，靠「跑完」那一刻落盘。它要抓的死法恰恰是不给收尾机会的那种：
jetsam 杀进程不发 `beforeunload`，看门狗杀进程也不发，锁屏把 webview 的定时器挂起
（坑 141）之后连下一次循环都不会执行。

一句话：**探针的持久化策略，必须能扛住它正在观测的那种失败。**

顺带还有一个更细的问题：整份文档重写（读-改-写）本身有个窗口，文件既不是旧状态也不是
新状态。真在那一刻被杀，取回来的可能是半个 JSON。

## 解法

按事件追加，别攒着重写。

```ts
await writeTextFile(JOURNAL, JSON.stringify({ wall: Date.now(), ...record }) + "\n", {
  baseDir: BaseDirectory.AppData,
  append: true,
});
```

每条一行 JSON，写完一条再干下一件事。`append` 返回之后数据已经在文件里，SIGKILL 带不走
（要连页缓存一起没了才丢，那是断电不是杀进程）。每条带墙钟时间戳，这样「中间断了两分钟」
读出来是一个可见的空档，而不是「这段压根没记」。

高频事件不要进 journal——电平是 10Hz，写进去就是每秒十次 IPC。它们计数，进周期样本。

还有一条推论：**有了 journal，跑多久就没那么要紧了。** 原来二十分钟是因为「跑不完就白跑」，
所以要一次赌够；现在死在第四分钟就是四分钟的数据。默认时长因此从二十分钟降到六分钟，
斜率该露的还是会露，而代价从「一个通宵」变成「七分钟」。
