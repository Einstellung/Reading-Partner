# 电平事件的频率不是节流定的，是 tap 的缓冲区定的

## 现象

电平事件按 15Hz 节流（`now - lastLevelAt >= 1.0/15`），真机上量出来是 9.6-10.0Hz，
十二轮按住说话都是这个数，一次都没到过 15。节流那一行完全没起作用。

## 原因

节流只能减速不能加速。事件是在 tap 回调里发的，回调的节奏由缓冲区大小和采样率决定，
和节流阈值无关——只要缓冲区间隔比阈值长，阈值就永远不触发。

**具体是多大的缓冲区，这条坑本来没有量过。** 代码传的是
`installTap(onBus: 0, bufferSize: 4096, format:)`，4096 帧 / 48000 Hz = 85.3ms，
推出来是 11.7Hz——和实测的 9.6-10.0Hz 对不上。缺口在短按上可以用测量方式解释
（`analyse.py` 拿事件数除以计划时长，而按下到第一个 buffer 有 ~700ms 是空的），但
14 秒和 15 秒那几轮解释不了：要读成 10.0Hz 得有 2.2 秒的空窗。

4800 帧（正好 100ms、正好 10Hz）能同时解释所有长度。也就是说
**`bufferSize` 是一个请求，不是一个契约**，AudioUnit 很可能按自己的 IO 周期给了另一个值。
这一条到目前为止是推理，不是实测。

## 解法

结论不变、也不依赖那个数：要改电平频率就去改 `bufferSize`，别去调节流的数；10Hz 落在
电平条想要的区间里（CSS 是 `duration-75`，低于 ~13Hz 显得一格一格，高于 ~30Hz 每条事件
都是十三个 span 的整棵重渲染），所以缓冲区保持 4096，节流留着当上限。

要坐实到底是 4096 还是 4800，`consume()` 的第一条日志现在带上了实际值：

```
RP-DICT firstBuffer +743ms frames=4800 rate=48000
```
