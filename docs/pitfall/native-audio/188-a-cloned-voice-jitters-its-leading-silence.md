# 换个音色，句首静音的抖动大十倍

## 现象

同一个模型 `qwen-audio-3.0-tts-flash`、同一批 40 句语料，只换音色：系统音色 `longanhuan_v3.6` 的句首静音是 90 / 90 / 90 ms（p50 / p90 / max），标准差 7.2；换成声音复刻预生成的基础音色 `-longliuxulan` 之后是 230 / 324 / 380 ms，标准差 89.6。首帧 PCM 的到达时刻没有这个抖动，只有用户听见第一个字的时刻有——播音音色下这个时刻在 570–1257 ms 之间跳，抖 690 ms。

## 原因

抖动是基础音色（每个模型 597 个的那批复刻音色）的性质，不是这一代模型的性质：同模型换系统音色，标准差从 89.6 回到 7.2。`qwen-audio-3.0-tts-plus` 配同一个音色后缀也是 77.2。

也不是句子决定的：同一批 40 句在 flash 和 plus 上跑同一个后缀，逐句静音的相关系数只有 0.15（和小米那条腿比是 0.16），即每次合成随机，不存在"数字开头的句子静音长"这类可预测规律。

不是量法的假象：-40 / -45 / -50 dBFS 三档阈值量出来的 p50 差不超过 10 ms。

## 解法

客户端裁句首静音——拿到整句 PCM 后从头扫到第一个超阈值采样点。裁完，首字出声时间回到端到端首帧 PCM 那一行（704 / 871 ms），抖动一起消失。

这件事本来就要为小米做（`docs/33` 的"小米落地要点"第一条，它句尾 485 ms 也要裁），只是别以为静音稳的供应商就能省掉：小米标准差 20.7、`qwen3-tts-flash` 5.7，稳到可以当常数减，但不裁就是每天第一句的等待时间每次都不一样。

## 顺带

量首字延迟必须把句首静音算进去，只量到首帧 PCM 会漏掉整整几百毫秒，而且漏掉的那部分才是会抖的那部分。数据在 `docs/assets/tts-probe/latency-report-2026-08-27.md`，逐句的三档阈值在同目录 `raw-*-ali3-round-*.jsonl` 的 `lead_silence_ms_t40/t45/t50`。
