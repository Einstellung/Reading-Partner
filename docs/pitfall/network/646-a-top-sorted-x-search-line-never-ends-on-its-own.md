# 热门排序的 X 搜索线自己停不下来，第一条线吃光整次 run

## 现象

2026-10-15 第一次真跑主题搜索的第一次 run（"AI for science"，五条查询，Xvfb，1440×2420，热门排序加 `since:` 30 天）：读入上限 150 条、有效阅读 35 分钟。打乱后排第一的 `"AI for science"` 那条线读了 26 屏、留下 101 条，36 分钟有效阅读到顶，run 以 `limit (reading time)` 收尾；其余四条线（自主实验室、材料、蛋白质、天气）一页都没开，搜索页只用了 1 次。结果里 X 的候选全来自一条全主题查询，子方向只剩 arXiv 供料。

## 原因

`x-reader.ts` 判一条线读完靠三样：连续 8 条见过（或比上次最上面一条早）、连续 4 屏没新帖、连续 2 次滚不动。第一次 run 没有上次的位置，「见过」永远不触发；热门排序在 30 天窗口里每屏都有新帖，「没新帖」也不触发。剩下只有 run 的总上限（条数、有效阅读时长），而那是全部线共用的，先开的线一路读到上限。按时间倒序的每晚增量有「读到上次位置」兜着，第一次 run 没有。

上限用完后的补全也没有发生：101 条里 62 条是截断的，但时间上限已到，`followUp` 的永久链接页一页都没开（`permalink: 0`），截断的帖子只以开头进候选。

## 解法

`readXSearch` 给每条线分一份：开一条线时，把剩下的条数和有效阅读时长按还没读的线数平分（`Run.share`），这条线留够它那份条数或读够它那份时间就以 `share` 收尾，没用完的留给后面的线；最后一条线不分，由 run 的上限停。测试在 `tests/info/topic-search/x-reader.test.ts`「a busy line takes its share…」两条。截断帖在时间上限后补不全的事没改：补全吃的是同一份时间，要补就得在分份时给永久链接页留出时间，等第一期后再定。
