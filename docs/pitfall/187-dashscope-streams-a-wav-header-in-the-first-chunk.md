# DashScope 流式 TTS 的首帧是一整个 WAV 文件，不是裸 PCM

## 现象

把阿里 `qwen3-tts-flash` 流式返回的 base64 分片解码后按裸 PCM 首尾相接，每一条合成音频开头都有一声满刻度的咔哒。31 句里 31 句的全段峰值都落在前 5ms，`|x[0]|` 高达 0.57，统计出来是「削波 62 个样本、峰值中位数 -0.0 dBFS」，差点当成阿里的音频质量缺陷写进评测。

## 原因

首帧不是纯采样点：前面有 44 字节的 RIFF/WAVE 头，头里的 data chunk size 是占位符 `0x7FFFFFFF`（流式合成时总长度还不知道）。后续帧才是裸 PCM。那 44 字节被当成 16-bit 采样点解码就是开头那声爆音。文档没写这件事。

## 解法

解析首帧时检查开头是不是 `RIFF`，是就跳过 44 字节再拼。修掉之后阿里的峰值中位数从 -0.0 dBFS 回到 -7.3 dBFS，削波样本数归零。

相关一条：阿里的响应里没有采样率字段，24kHz 是靠与已知 24kHz 的另两家做逐句时长交叉验证推出来的。按字节数换算音频时长的代码，采样率是外部知识不是协议给的。

## 对照

硅基流动和小米给的都是真裸 PCM，没有头。这是 DashScope 独有的，多供应商适配层要按供应商分别处理，不能假设「流式音频分片都是裸采样点」。
