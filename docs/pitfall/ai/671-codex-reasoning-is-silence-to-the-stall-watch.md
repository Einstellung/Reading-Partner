# Codex 思考期间停摆看门狗什么也听不到

## 现象

Linux 上用真 ChatGPT 登录跑饮食对话（gpt-6.1-sol，思考档 high），停摆看门狗在流还活着时最长 32.3 s 没收到一次节拍。有一轮的思考摘要完全不流，`thinking_start` 后静默，摘要在 `output_item.done` 时整段到；另一些轮的摘要要等 7 到 25 s 才开始流。工具调用参数是流的（每次约 300 个 delta，1 到 3 s 内发完）。

## 原因

看门狗的节拍来自 `pi.live` 里半句的变化，pi-durable 只在半句内容非空时提交，思考没出字就不动。线上其实一直有字节：服务器每 5 s 发一行 SSE 注释（`:` 开头，14 字节），解析后的事件之间最长约 30 s，这时补一个 `event: keepalive`。pi-ai 的 SSE 解析丢掉注释，`keepalive` 事件会交给 `onProviderStreamEvent`，但 pi 不据此改 `pi.live`。

前台 90 秒的窗口够用。回前台那一刻的判断不够：`back()` 掐掉离开期间一次节拍都没有的流，Codex 在思考时离开，离开后那几秒宽限里通常没有节拍，连接即使像坑 522 那样活过了冻结也会被当场掐掉、重问；第二次就是 `STALL_MESSAGE`。

## 解法

前台不用改。回前台的判断要改的话，看的得是连接上的字节（5 s 一次的注释），不是 `pi.live`，也不只是解析后的事件，并且要给解冻后缓冲里的字节一点时间到达再判。这改的是 docs/soul/87「停摆」定下的规矩，要先在 iPhone 上量回前台时 `visibilitychange` 和缓冲字节谁先到，再定。
