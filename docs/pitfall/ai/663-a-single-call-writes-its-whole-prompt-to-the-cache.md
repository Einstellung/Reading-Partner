# 只调一次的模型调用把整份提示写进缓存，一个 token 都读不回来

## 现象

主题搜索一次 run 的模型调用日志里，每一步都是 `cacheWrite` 等于整份提示、`cacheRead` 为 0：重排写 24145、写稿 26274、卢明开口 2457。Anthropic 上写缓存按 1.25 倍输入价算，这几步等于输入白多付四分之一。写稿重写的那次也只读回 843 个 token（2026-10-19 的日志：第一次写 18985，第二次读 843、写 18081），正好是 system prompt。

## 原因

`streamChat` 不传 `cacheRetention`，pi 用默认的 `"short"`：在 system 上打一个断点，再在最后一条用户消息的最后一个块上打一个。`callModel` 把整份用户文字当一个字符串发，所以第二个断点在提示的最末尾，每次调用都把整份提示写进缓存。

- 重排、对照原文、去重判断、卢明开口在一次 run 里各只调一次，写进去的东西没有下一次来读。
- 写稿第二次调用的用户文字是「第一次的正文 + 要改的问题」拼成的一个字符串。缓存只在块边界上找前缀，第一次写在正文末尾的那个点在第二次的请求里不是块边界，于是只有 system 那个断点命中。

## 解法

- 只调一次的调用传 `cacheRetention: "none"`，一个断点都不发（`TopicModelCall.cache: false`，开口那步在 `info/issue/live.ts` 直接传 `"none"`）。`"none"` 连读也没有：没有断点就不查缓存，所以确实会被后一次调用复用的不能关。
- 会被复用的前缀单独成块：`ChatMessage.parts` 让一条用户消息带几个文本块，pi 把断点打在最后一块。写稿把第一次的正文原样作为第一块，读深结果和要改的问题各成一块接在后面（`TopicModelCall.tail`），第二次调用回看时在第一块末尾找到第一次写的那个点。
- 稳定的放前面，变的放后面：system 和正文在一次写稿的几次调用之间逐字不变，变化只出现在后面的块里。
- 请求的形状由 `tests/info/topic-search/prompt-cache-wire.test.ts` 在真 provider 对象上读出来核对（假 fetch，不出网）。
