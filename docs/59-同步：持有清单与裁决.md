# 同步：持有清单与裁决

> 2026-09-07 定案。现状引擎在 [13](./13-账户同步.md)，删除模型在 [50](./50-删除.md)，legion 在 [55](./55-legion.md)，两个记忆仓在 [48](./48-记忆：观察与statement.md)。

目标：把设备撞车从一例一补改成一个模型。三类撞车——文件级删除不传播（坑 208）、记录粒度粗一层（threads 整条线程是一条记录）、多文件没有原子提交（坑 236）——归到同一个根：同步只认"每个文件各自的两侧"，从不认"这台设备当时持有的整棵树"。

定三件事：每台设备发布一份持有清单（holdings，树快照），删除按树三方推断；threads 换消息级合并驱动；prose 类冲突交给 legion 上的 agent 裁决。

## 1. 现状引擎，一页

一趟 pass（`src/platform/sync/engine.ts:649`）按顺序做七件事：`ensureLayout` → 排 purge 队列 → 列远端 → 扫本地并算 hash → 读书墓碑 → `reconcile` 出计划 → 执行（purge、下载、合并、上传、books）。

**请求数。** `ensureLayout` 在 id 已缓存时 0 个（`driveBackend.ts:419`）。`listRemote` 是 1 个（`driveBackend.ts:459`，`pageSize=1000`，一页装得下当前全部文件）。下载 1 个、上传 1 个（多部件，appProperties 和字节同一请求，`driveBackend.ts:573`）、删除 1 个。一次合并是 1 下载 + 1 上传（`engine.ts:493`）。books 通道的 `hasBook` 在 `bookIds` 命中时 0 个（`driveBackend.ts:644`）。所以稳态空转一趟就是 1 个请求。

**base 在哪。** 三处各存一份不同的东西：`sync-state.json` 的 `snapshot` 存每个路径的 `{rev, mtime, size, hash}`（`state.ts:30`），`sync-base/<path>` 存上次同步成功时的**字节**（`localStore.ts:310`），远端每个文件的 appProperties 存它自己的 `{rev, mtime, hash}`。三者都不同步。

**冲突怎么判。** 本地变了 = 内容 hash 与 snapshot 不同（`reconcile.ts:91`，不看 mtime，坑 53）；远端变了 = 远端 rev 高于 snapshot 的 rev（`reconcile.ts:144`）。两者都真才进 `merges`，合并结果发布在 `max(远端 rev, snapshot rev) + 1`（`reconcile.ts:182`）。两侧 hash 相同直接收敛，不进任何冲突规则（`reconcile.ts:171`）。

**删除今天怎么办。** 不办。本地没有远端有，原样留着；远端没有本地有且本地没改，也原样留着（`reconcile.ts:148`）。唯二的出口是点名的：`purge` 队列（代码里写死路径，`engine.ts:558`）和书墓碑展开出来的死路径（`dead-paths.ts:466`，走 `purgeDead`，`engine.ts:614`）。两条都不是比对得出的结论。

**确定性由谁保证。** `merge/contract.ts:1-8` 的两条：不丢用户写的东西（要么留副本要么进 `sync-trash.jsonl`），以及每个决定只由 base/ours/theirs 三份内容决定。强制它的是代码本身——`chooseByContent`（`text.ts:100`）按内容 hash 定序，`conflictCopyPath`（`merge/index.ts:38`）按内容 digest 命名，`mergeOpaque`（`merge/index.ts:103`）按 `compareBytes` 选边。没有一处读 `local` 这个标签、读墙钟、或读设备身份。测试在 `tests/platform/sync/merge.test.ts`。

## 2. 持有清单

一份持有清单回答一个问题：这台设备手里持有什么。取图书馆的"馆藏"那个意思。不叫 manifest，因为 Drive 上已经有一个旧版的 `manifest.json` 索引占着这个词（docs/13），而且那正是被拆掉的全局单文件形态。

### 形态：一设备一份，单写者，永不合并

```
Drive: Reading Partner/data/holdings-<deviceId>.json
本地: sync-holdings/self.json          我上一趟发布的那份
      sync-holdings/<deviceId>.json    我上一趟据以推断的那份对端持有清单
```

`deviceId` 用现成的（`platform/app/device.ts:29`，首次运行生成、跨重启不变、不同步）。

放在 `data/` 里，所以现有那一次 listing 就把它们枚举了，**探测对端持有清单变没变是 0 个额外请求**。`listRemote` 按名字把 `holdings-*.json` 挑出去，不进 `RemoteState`，reconcile 永远看不到它们。本地那两份放 `sync-holdings/`，和 `sync-base/` 一样在同步范围之外。

不做全局唯一的 `tree.json`：那正是 `driveBackend.ts:15-21` 已经拆掉的东西——两台设备在同一个窗口里都写它就是一次丢更新，而且它一读失败整趟 pass 就没了。一设备一份、单写者、零合并，和 `info-collector-<id>.json` 与 legion 的 presence 是同一个形状（docs/55）。

### 格式

```json
{
  "v": 1,
  "device": "d-3f9a1c…",
  "at": 1757203200000,
  "app": "0.15.0",
  "complete": true,
  "files": {
    "annotations-8f3a….json": ["c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5f6", 11234],
    "observations/m-0fe3bfb7c2a41d90.md": ["7a8b…", 2048]
  },
  "retired": ["slides/deck-3.json"]
}
```

`files` 是 路径 → `[contentHash, size]`。hash 就是 `platform/app/content-hash.ts` 那个（sha256 截 16 字节 = 32 hex）。

**不放 rev。** rev 是"远端现在是什么"，那由 listing 的 appProperties 权威回答；持有清单回答的是另一个问题——"这台设备当时持有什么"。两个问题混进一个字段会让"我持有但没上传成功"和"我没有"分不开。

**`complete`** 说这一趟的扫描是完整的（`fs.list()` 正常返回）。为假的清单只用于展示，不参与推断。

**`retired`** 见 §8 第 7 条：因为同步范围变更而离开的路径，显式列出来，对端见到只停止同步、不删本地。

### 大小与请求数

按 `inSyncRange`（`syncFs.ts:103`）的分类估：

| 类别 | 条目数（当前量级） | 增长 |
|---|---|---|
| 根部固定文件 | 15 | 不增 |
| `annotations-*.json` / `threads-*.json`（按书） | 每本书 2 | 随书 |
| `threads-info-<date>.json` | 已 29+ | **每天 1** |
| `observations/*` | 已 100+ | 每天数条 |
| `article-bodies/*.json` | 随收藏 | 随收藏 |
| `prep-*/`、`retell-*`、`outline-*`、`rehearsal-*`、`runs/**` | 数十 | 随使用 |
| 每设备一份的 `info-collector-*`、`info-ask-*`、`memory-usage-*` | 3 × 设备数 | 不增 |

引擎注释里写的当前数据文件数是 273（`engine.ts:50`）。一条约 90–110 字节（路径 45 + hash 32 + 括号数字），273 条 ≈ 28 KB，1000 条 ≈ 100 KB——和今天最大的数据文件同一量级（`content.ts` 说 ~110 KB）。可接受。

请求增量：

| 情形 | 今天 | 之后 |
|---|---|---|
| 空转一趟 | 1（list） | 1 |
| 我的树变了 | 1 + 传输 | +1（上传我的持有清单） |
| 对端树变了 | 1 + 传输 | +1（下载对端持有清单） |
| 两边都变 | 1 + 传输 | +2 |

空转不涨，是这个方案最重要的一条性质。

### 能不能替掉 sync-base/

不能。持有清单里是 hash 不是字节，三方内容合并要字节。`sync-base/` 原样保留。

和 `snapshot` 也不重叠：snapshot 是"我和远端各文件同步到哪个 rev"，持有清单是"某台设备当时的整棵树"。三份东西回答三个问题，都留着。

### 两台设备并发发布

不存在。每台只写自己那一个文件名，一写者。两台同时发布产生两个文件，不是一次冲突。

## 3. 删除推断

### 树级三方规则

站在设备 A 的角度，对每个路径 P，输入四个：`base_B`（我上次据以推断的 B 的持有清单，本地缓存）、`now_B`（B 现在发布的那份）、我本地的 P、我的 `snapshot[P]`。

| base_B | now_B | 我本地 | 结论 |
|---|---|---|---|
| 有 P，hash h | 无 P | 有 P，hash = h | **B 删了，我也删**：走 `purgeDead`，进 `sync-trash.jsonl`，删本地、删远端、清 snapshot 和 base |
| 有 P，hash h | 无 P | 有 P，hash ≠ h | **删对改**：改赢（和 `records.ts:228` 同一条），保留并上传，`contested` |
| 有 P | 无 P | 无 P | 双方都没了，只清 base（今天的 `dropBases`） |
| 无 P | 有 P | 无 P | 新增，按今天的下载走 |
| 无缓存的 `base_B` | 任意 | 任意 | **什么都不推断** |

最后一行是全部安全性的来源，和 `MergeInput.base: null` 是同一条纪律（`contract.ts:27-33`）：没有 base 就分不出新增和删除，那就不删。

### 无 base 的场景怎么收场

三种：升级后第一趟、从没拉过这个对端的持有清单、退出登录再登录清了本地缓存。

处理一致：这一趟只**记录** `now_B` 到 `sync-holdings/<deviceId>.json`，不推断任何删除。从下一趟的差分开始推断。代价是删除比今天晚一趟（最多 `PULL_INTERVAL_MS + TICK_MS`，`engine.ts:82`），换来的是绝不会把"我从没见过"读成"对方删了"。

### 执行

不新增执行路径。`reconcile` 今天已经接受一个 `dead(path)` 谓词（`reconcile.ts:113`），把命中的路径丢进 `plan.purges`，引擎用 `purgeDead` 一处收口（`engine.ts:614`）：先读字节写进 `sync-trash.jsonl`（本地留 30 天，`localStore.ts:316`），再删本地，再删远端，最后清 snapshot 和 base。推断出来的删除就喂进这个谓词。

所以：**推断删除的落地代码量接近零**，新增的全在"算出那个集合"这一侧。这也意味着它自动继承了三十天的后悔药。

### 和墓碑、purge 队列的共存

| 机制 | 之后 | 理由 |
|---|---|---|
| `deleted-books.jsonl` | 留，不动 | 它删的是派生路径（`prep-<hash>/`、Drive 上的 PDF blob），包括在从没持有过这些文件的设备上删；语义是"这本书没了"不是"这个路径没了"（docs/50） |
| `deleted-observations.jsonl` | 本轮继续写，读永远保留 | 它还兼着"文件还在但 `get()` 答 null"，且老版本设备只认它（坑 208）。最早也要等所有设备发布持有清单满两个版本之后才停止写新行；一行 60 字节，留着不贵 |
| `requestRemotePurge` 队列 | 留，不动 | 它表达的是"某个版本决定这类文件不再是数据"，任何两棵树的比对都推不出这句话（`engine.ts:549-557`）。正交 |

这一步不退役任何东西。三者管的是三件不同的事，只是都长得像删除。

### 对端还在老版本

老版本既不发布持有清单也不读。新设备找不到它的清单 → 对它不推断任何删除 → 不退化。反过来，新设备 A 删了 P 并删掉远端副本，老设备 B 本地还留着 P：B 的 P 没改过时 reconcile 什么都不做（`reconcile.ts:195`），所以 P 不会自己回来；只有 B 编辑了 P 才会重新上传。和 docs/50 已经接受的"老版本客户端会推回被删的书，直到升级"是同一档。

## 4. 原子性

### 持有清单落地当提交，买到了什么

买到的是**推断的原子性**：删除只从持有清单的差分推断，绝不从远端 listing 推断。listing 在一趟传输的中途是半新半旧的树，谁也不许据它下"对方删了"的结论。

没买到的是**传输的原子性**。文件仍然一个一个上传（`engine.ts:765`，八路并发），清单最后传。所以远端在一趟里确实存在一个半新的窗口，从这趟第一个上传落地到清单上传落地。

### 半应用的窗口里，读者看到什么

对端在这个窗口里 pull，会拉到一部分新文件、一部分旧文件。**这是允许的**——数据就是数据，早拉一个文件没有坏处，今天也一直是这样。被禁止的只有一件：据此推断删除。

### 部分成功的 pass 也发持有清单

判据不是"这一趟干净"（那是 `lastSyncAt` 的判据，`engine.ts:805`），而是"这一趟的扫描完整"。清单说的是"我持有什么"，不是"远端和我一致"。

坏链路上一趟很难全绿（坑 52），只有干净的一趟才发就等于弱网设备的删除永远传不出去。而按"我持有什么"发布是诚实的——我本地删了 P 但远端删失败了，对端读我的清单推断出删除并自己删掉，这正是想要的结果。

唯一例外：`fs.list()` 抛错的 pass 本来就整趟结束，不会走到发布。

### 读者不按持有清单读

应用侧的 store 一律读本地文件，持有清单是同步自己的账本。让每个 store 去查它，等于把同步的概念摊进整个领域层。只有两个消费者：同步引擎自己，和迁移闸门（下条）。

### 对迁移闸门那一类问题

持有清单不让多文件迁移变原子。坑 236 的病根是"闸门读的那份数据，处理它的代码有跳过这条出路"，那条一般规则不变。

它给的是**可检出性**：迁移前后各一份树快照，"目标树已到、源树未走"这个状态第一次有了名字，能被检出、能被报出来，而不是变成一个谁也退不出的 Try again。做法：多文件迁移在开始前记下自己这台设备的树快照，结束后再记一份，两份的差分就是这次迁移的完整效果；闸门读的是**自己这台设备的差分**，而不是目录列举——另一台设备把目标同步过来，不改变我这台"源还在"这个事实，也不改变我该做什么。

## 5. 消息级 thread 驱动

### 今天为什么坏

`threads-*.json` 走 `records` 策略，形状是 `{ kind: "map", container: "threads" }`（`records.ts:90`），一条线程是一条**原子**记录。两台设备往同一条线程追加消息，`mergeCollection` 走到"both edited"分支，`chooseByContent` 选一整条线程，输的那条连着它的全部消息进 `sync-trash.jsonl`（`records.ts:203-206`）。`threads-info-<date>.json` 是两台设备同一天对同一个陪伴说话，所以这是常态不是边角。

### 新策略：`messages`

只对 `threads-*.json` 生效。文件仍是线程的 map，但线程记录不再原子：

1. 线程的标量键（`annotationId`、`book`、`focusChapter`、`parentThreadId`、`asideAnchor`、`createdAt`、`path`）走 `fields` 合并。
2. `messages` 走消息级三方。

### 消息身份

有 `id` 用 `id`（`threads.ts:83`，`t-<16hex>`）。没有就用 `<threadId>:<ts>:<role>`。

加 `role` 是必须的：`anchors.ts:14-19` 实测——292 条旧锚里 143 条（49%）指向两条消息，因为用户那轮和回复那轮在同一毫秒追加、`ts` 相同。加上 `role` 之后这一对分得开。

仍可能撞（同一毫秒两条 ai 消息）。撞了就**拒绝，不猜**（坑 209 的规则）：任一侧有一个 key 对应两条以上消息时，这条线程整条退回今天的原子行为，并报 `contested`。退化只影响这一条线程。

### 三方规则

| base | ours | theirs | 结果 |
|---|---|---|---|
| 无 | 有 | 无 | 保留（新增） |
| 无 | 有 | 有，内容相同 | 保留一份 |
| 无 | 有 | 有，内容不同 | 见下面「都改过」 |
| 有 | = base | 改过 | 取改过的 |
| 有 | 改过 | 改过 | 见下面「都改过」 |
| 有 | 无 | = base | 删除成立，进 journal |
| 有 | 无 | 改过 | 改赢（和 `records.ts:228` 一致） |

**都改过的解法：**

> 一方的 `text` 是另一方的 `text` 的前缀时，取长的那份；否则按 `chooseByContent`（`text.ts:100`）。

前缀优先是流式那条路要求的。`patchThreadMessage` 按 `ts` 反复重写同一条消息的 `text`/`parts`（`threads.ts:707`）。一趟合并可能落在流式中途，把一条只写了一半的消息写上盘（`engine.ts:499`）；下一次防抖写出完整版，于是"完整 vs 截断"作为两个编辑相遇。纯按内容 hash 定序有一半概率选中截断的那份，而且它会被发布上去。前缀规则把这种情况变成确定的"取长"。它对称、幂等，两台设备算出同一个结果。

不是前缀关系（真正的两处不同编辑）才落回 `chooseByContent`，输的那份进 journal。

### 排序

按 `ts` 升序，相同 `ts` 按 `role`（user 在前，这是真实的追加顺序），再相同按 key 的字典序。不按数组下标：两台设备的插入顺序不同，只有一个纯函数的排序能让它们落到同一份字节上。

### journal 收到什么

今天丢一条线程记一行，`id` 是 threadId。之后只丢一条消息，记 `{ path: "threads-<key>.json", id: "<threadId>/<messageKey>", record: <整条消息> }`。粒度细了，条数会变多，但 30 天 TTL 和按行 prune 不变（`localStore.ts:384`）。

### 对观察锚点的影响

`anchors.ts:20-29` 明写：pair 那半留在 id 旁边，就是因为线程记录原子、赢家可能是一台没跑过 id backfill 的设备，于是幸存的消息丢掉了 id。消息级合并之后，"输的那半整条消息进 journal"基本消失；但"都改过"仍可能选中一份没有 id 的版本——老版本 build 会原样带过它不认识的键（`threads.ts:70-77`），所以只有两侧真的对这条消息有不同意见时才会发生。

pair 那半继续留着，不因为这个驱动去掉。锚点解析代码一个字不用改。

## 6. 裁决层

### 为什么 agent 不能坐在确定性合并里面

`contract.ts:6-8`：两台设备各自独立合并同一对内容，必须落到同一份字节。一次模型调用不是 (base, ours, theirs) 的函数——它不确定、要联网、要凭据（凭据按设计每台设备各自持有、不同步，docs/13），而且要几秒到几十秒，而 pass 是逐项、有失败预算、有并发池的（`engine.ts:100`、`engine.ts:116`）。两台设备各调一次模型就是两份不同的文件，永不收敛。

所以顺序不能倒：**先确定性合并并停好两份，再由单个认领者裁决，裁决结果作为一次普通编辑同步出去。**

### 管线

1. prose 策略停下冲突副本 `<stem>.conflict-<digest>.md`（`merge/index.ts:38`、`:196`）。digest 取自内容，两台设备写出同一个文件名，副本收敛而不是繁殖。
2. 领域侧发现副本。观察 store 已经在枚举它们（`memory/observations/store.ts:249`，`CONFLICT_FILE` 在 `:106`）。
3. 建 run：`kind = "adjudicate-prose"`，`idempotencyKey = adjudicate:<path>:<digest>`。key 由内容决定，两台设备算出同一个 key，legion 的去重把它们收敛成一个 run（docs/55）。
4. 认领：按 presence 的租约，单认领者（docs/55）。另一台站着不动。
5. agent 看到：`sync-base/<path>` 里的 base（可能没有）、留下的那份、停在旁边那份、以及这个文件的角色（一条观察 / 用户画像）。按引用传参，run 文件里不存内容。
6. agent 可以写：把裁决后的正文经 store 的普通写落盘，并删掉那个冲突副本。两个动作都是普通的本地写，照常同步。它**不许**碰 `sync-base/`、`sync-state.json`、持有清单。
7. provenance：观察的 frontmatter 加一个字段 `resolvedBy: legion/<runId>`。没有 frontmatter 的（`user-profile.md`）只在 run 和 ledger 里留证。
8. 拿不准：不写正文，往 `legion/mailbox` post 一条 item（docs/55），UI 从那条 item 弹窗；冲突副本原地留着等人。之后的桌面宠物读同一个 mailbox。

### 只对 prose

records / fields / cursors 保持确定性规则，不上 agent。它们的冲突有正确答案（并集、按字段、取小），交给模型只会引入不确定。

### 两台设备抢在 run 文件同步之前

`idempotencyKey` 相同但 run id 是文件名、各自随机，于是短暂存在两个 run 文件。两份 run 相遇时按 key 去重：**run id 字典序小的赢**，另一份改成 `cancelled` 并指向赢家。规则是纯函数，两台设备算出同一个答案（和 presence 的破平同一手法，docs/55）。

如果两边都已经跑完并各写了一份正文：这就是两次对同一个 prose 文件的编辑，确定性合并照常跑，照常停下一个新副本。这时新的两份**都带 provenance**，规则是：

> 两侧都带 `resolvedBy` 的 prose 冲突，永不自动裁决，直接进 mailbox。

不加这条就会形成裁决 → 冲突 → 裁决的循环。

## 7. 落地顺序

| 档 | 内容 | 需要对端什么版本 | 混版期表现 |
|---|---|---|---|
| 1 | deviceId 接进同步；发布持有清单；缓存对端的那份；**推断关闭** | 不需要 | 无行为变化，只多两个文件 |
| 2 | 打开删除推断 | 对端也在档 1 之后 | 老版本对端：不推断，退化成今天 |
| 3 | 消息级 thread 驱动 | **两边都要升级**，单独发一版 | 见下 |
| 4 | 裁决层 | legion run/presence/mailbox 已落地 | 未认领的冲突照旧停在盘上 |

档 1 和档 2 之间至少隔一个版本：推断需要"缓存里已经有对端的持有清单"，那份缓存要靠档 1 跑一段时间才攒得出来。

**档 3 单独发一版。** 合并策略变更在混版期不兼容：A 按消息级合出并集 S 发布，B 按线程原子在自己那份和 S 之间选一整条线程，可能把 A 的消息丢进 journal 再发布，A 再合出并集……每趟多一次这个文件的上传，直到 B 升级。数据不丢（并集在 A 上，输的那份在 B 的 journal 里），但会持续抖。所以它不和档 1/档 2 共用混版窗口，窗口压到一个 TestFlight 周期。

### 怎么验，两台真机、没有服务端

主判据放在无头测试上，真机只做确认。

引擎的每一件依赖都是注入的（`engine.ts:159-207`），所以**两个 `SyncEngine` 跑在同一个内存假 backend 上**就是真正的收敛测试。要补的用例：

- A 删一个文件，B 不动 → 两趟之内两边都没有，`sync-trash.jsonl` 里有。
- A 删，B 在同一窗口改 → 改赢，文件还在，两边字节相同。
- A 离线两周后回来 → 不产生任何推断删除，只刷新缓存。
- 两台同时往一条线程追加各三条 → 六条都在，顺序两边相同。
- 一条消息流式写到一半被合并落盘 → 完整版最终胜出。
- 反复跑同一对输入两次 → 字节完全相同（幂等）。

真机确认清单：桌面 + iPad，各删一个观察、各追加一条 info 对话、一台飞行模式两天后回来。加一个开发者屏（或 `sync doctor` 命令）打印我的持有清单、对端的那份、以及本趟推断出的删除集合——没有这个，两台真机上出的问题没法归因。

## 8. 失败模式

1. **时钟偏斜** → 两台对"谁更新"意见相反 → 设计里没有一处按墙钟判断；持有清单的 `at` 只用于展示和 presence 租约，不进任何合并或推断判据。
2. **Drive 最终一致**：列出的持有清单比 `data/` 里的文件旧 → 可能据旧树推断删除 → 推断前校验：清单里某路径的 hash 与 listing 里该文件的 hash 不一致时，这个路径这一趟当"未知"，不推断。
3. **设备离线数周** → 它的清单陈旧，看起来像删了一大片 → 推断只作用于「我缓存的那份对端清单」到「对端现在这份」的差分；离线设备回来先刷新缓存、下一趟才推断。陈旧本身不产生删除。
4. **文件都传完了，持有清单上传失败** → 远端树是新的、清单是旧的 → 对端只按清单推断，看到的是上一趟的树，最坏延迟一趟；下一趟补发。绝不据 listing 补推断。
5. **文件改名** → 旧路径消失 + 新路径出现 → 树级看是一删一增，两个动作都正确执行。内容寻址的那些（`article-bodies/`、books）不存在改名。
6. **hash 碰撞** → 32 hex = 128 bit，生日界 2^64，个人库规模下忽略；且清单里 hash 只用来判"没变"，判错的后果是漏传一次而不是删错。
7. **路径离开 `inSyncRange`** → 上趟清单有、这趟没有 → 对端读成删除，删掉本地还有用的文件 → `retired` 段：范围收窄的那一版把因此消失的路径显式列进去，对端见到只停止同步、不删本地。范围变更同时仍要走 purge 队列点名（`engine.ts:558`）。
8. **`observations/meta.json` 游标** → 它被推断删除就丢掉全部蒸馏游标，代价是整批对话从零重读（`merge/cursors.ts` 开头列了四种游标的不对称性）→ 一张"不可推断删除"名单：`observations/meta.json`、`statements.json`、三个 `*.jsonl` 墓碑与日志。它们的删除只接受显式墓碑，树级差分对它们无效。
9. **两个迁移相撞（坑 236）** → 桌面跑完迁移、目标同步到 iPad，iPad 的源没走、闸门恒为真 → 持有清单让"目标树已到、源树未走"可检出；闸门按 §4 改成读自己设备的树差分。一般规则不变：闸门读哪份数据，处理它的代码就不许有跳过。
10. **agent 在一趟同步进行中写** → 裁决结果和这趟的合并撞车 → 裁决走 store 的原子写，引擎的 `selfWrites`/`dirty` 机制（`engine.ts:338-357`）照常把它算成本地编辑，最坏多跑一趟。裁决被禁止直接写 `sync-base/`、`snapshot`、持有清单。
11. **两台同时裁决同一个冲突** → 两个 run 文件 → key 去重，run id 小者赢；两边都已写完则两侧都带 provenance，不再自动裁决，进 mailbox。
12. **持有清单被当成数据文件拉进 AppData** → 命名 `holdings-<deviceId>.json`，`listRemote` 按名字挑出去，reconcile 看不到；`inSyncRange` 不放行它。
13. **用户在 Drive 网页上手动删了一个文件** → 它不出现在任何清单的差分里 → 本地照旧持有，下次本地编辑重新上传。保持今天的性质：远端缺失从不导致本地删除。
14. **退出登录再登录，本地缓存清空** → 没有 `base_B`，不推断（§3 无 base 规则）；但远端独有的孤儿文件仍按今天的规则被拉回本地（docs/13 那条实测）。这一条没有改善，见 §10。

## 9. 没选的两条

**路二：op-log / CRDT。** 每个改动写成一条不可变的 op，设备各自追加、合并即并集，状态由回放得出。它确实一次解决全部三类撞车，而且删除天然是一条 op。不做的理由是迁移成本：今天全部数据都是"整份文件就是状态"，每个 store 都直接读写它；换成 op-log 要重写每一个 store 的读路径、要处理压缩、要处理"回放到一半的状态"，而且 Drive 一文件一请求的成本模型对"很多小 op 文件"最不友好。

**用真 git 对象（isomorphic-git over Drive）。** commit/tree/blob 天生就是这份设计想要的东西，三方合并、删除推断、原子提交全是现成语义。不做的理由是运行环境和成本：isomorphic-git 的存储层假设一个能随机读写的文件系统，把它架在"一次请求一个文件"的 Drive 上，一次 fetch 就是几十上百个 object 请求；packfile 又要求本地能跑 zlib 和 delta，iPad 的 WKWebView 里代价不明。真正想要的只是 tree 的那一层语义，持有清单就是那一层，几十行。

两条都不是错的方向，是现在不划算。等 op 的需求真的从别处冒出来（比如实时协作），再回头看路二。

## 10. 还没定的

1. **退出登录再登录留下的孤儿文件。** 远端有、任何一台设备的持有清单里都没有的文件，今天会被当新文件拉回本地，这份设计不改这条。倾向：等它真的咬人再处理，处理方式是 purge 队列点名，不是让推断去碰"谁都没声称持有"的文件——那正是无 base 规则要挡住的东西。
2. **"不可推断删除"名单谁维护。** 今天五个条目写死在代码里。加一个数据文件就要想一次它该不该进名单，而没人会记得。倾向：把名单和 `inSyncRange` 放在同一个文件里，并让 `tests/platform/sync/range.test.ts` 那类清单测试同时盯住它。
3. **三台以上设备。** 差分是两两做的，N 台设备就是 N-1 份缓存和 N-1 次差分；请求数不涨（同一次 listing 全枚举了），但"A 删了、B 没删、C 不知道"的三方状态没有推演过。倾向：档 2 落地时先按两台设备验，第三台进来之前把这个状态机补完。
4. **裁决用哪个模型、算谁的预算。** 裁决是后台发生的模型调用，用户不在等。倾向：走 `budget` 的后台档，和 dream 同一类；具体额度等第一批真实冲突的量出来再定。
