# 饮食规划

## 愿景

给忙碌的都市白领——在意吃得健康，但没时间也没心力天天想吃什么的人——排这周吃什么，每天一句「今晚吃什么」。

这是伙伴为用户做的第一件和读书无关、而且天天发生的事。读书是天天打开的习惯，伙伴长在上面；吃饭是把用户真正用起 info 的入口；PDB 是同一个行为往外扩到世界。内部它是一个 info 研究室（[63](../63-情报局：研究室、专项组与态势.md)），视野是用户本人；界面上不出现研究室、情报局这类词，用户只是在和伙伴说话。

它不是一个独立的饮食 app。独立的膳食计划 app 已经死了两个：Yummly 2024-12 关停，Mealime 2026-10 关停并进超市的 app，关的时候 App Store 4.8 分、5.4 万评价。计划这件事只能作为一个天天发生的习惯的附加功能活下来，这条线的习惯是读书。它同时是 info 反馈环的练兵场：一个用户每天都会验一次的题材，命中没命中当天就知道。

核心诉求不是决策疲劳（[饮食核心诉求调研](../research/都市白领饮食核心诉求调研.md)）。第一位是省事，买、洗、切、洗碗这套体力活和它占的时间；第二位是钱；「吃什么」是真痛点，但排在这两样后面，撑它的强数字来自零售商的问卷。它的真实形态是腻：人们本来就在十来道菜里循环，86% 承认反复吃同样几道，43% 一周之内就重复。健康是说得多做得少，只有收入过一条线之后才反过来，那条线上的人正是这个 app 的读者。

对这条线的用户，省事和健康都是硬约束，不腻是区别所在。健康先当过滤器：蔬菜多、全谷物、瘦蛋白，少油少盐少精制碳水（哈佛健康饮食餐盘、地中海饮食、DGA 2020-2025、NHS Eatwell 说的是同一件事），不数卡路里；过滤剩下的按省力排序。健康不当卖点，它只是个筛子。

主件是这周的计划加一张购物清单，六点那句「今晚吃什么」是从计划里取的一行。购物清单是膳食计划的用户一致夸过的那一样（采购整合）。排计划先定形态（做饭 / 出去吃 / 点外卖），依据是到家时间、累不累、有没有备好的；再定具体吃什么。

宏观形态是一个环里的三件事：

- 一周的计划变成一张购物清单，带用户去店里买，清单按保质期排序。
- 每天从计划里取一道菜；有的日子做，有的日子热昨天的底再加一把绿叶，有的日子出去吃或点外卖，三种模式都在计划里。
- 吃完和伙伴说一句：照做没有、改了什么、腻没腻。多数日子没什么要说，说了的改下周。

和膳食计划 app 的区别只在第三件。Mealime 有前两件，没有记得住的对话，每周的计划都从零开始，用户两周内就走了；这里的计划长在用户上周说过的话上，几周之后计划就是用户自己那套循环。对到 info 的环上：买菜是采集，计划和那套循环是态势，今晚这道菜是简报，那句话是反馈。

功能型 app 先把屏幕定下来，数据让用户自己维护；这里是 soul 开一个研究室，排这周，把用户的菜和常去的店从观察攒成记忆，按 legion 的钟把今晚那句发出去，要改就收一句话。agent-native 买到三样：不用录入（只在偏离时说一句）、不用配置（问两句就开始）、不用每周从零排（有记忆）。独立 app 死掉就是死在这三样上。它不等于一切都是对话：两样产物形态固定、必须做扎实，购物清单（在店里单手勾）和今晚那句（按点到手机），其余归 soul。

计划就是记录。默认用户照计划吃了，只有偏离才说一句「吃了别的」，多数日子零输入。购物清单在店里勾掉的条目同时就是冰箱里有什么。

不腻靠记忆，不靠菜谱库：记住用户自己那十来道菜和常点的那几家，排这周不重样，每周加一道新的，用户不接受就撤掉。外卖是平等的一种模式，排进这周的计划，从用户自己那几家里选，不劝也不贴「清淡营养」的标签。

语音只在灶台前是前提。六点那个决策发生在回家路上，打字或者一句语音就够，第一片不需要做饭那种长会话语音。

读书在 iPad 和桌面，吃饭在手机。今天缺三样：从手机把一句话或一张照片送进这个研究室、六点前把「今晚」那句话按时段推到手机、对话之外的反馈通道。手机交、PC 蒸、六点推回手机，这条线也是手机与 PC 联动的练习。

带引导的烹饪电器（Thermomix 那类）已经被证明是门生意，它在这条线的下游：要结构化的菜谱和一周的计划，正是这条线攒的东西。现在不做。

不做：菜谱数据库、餐厅搜索、卡路里记账、营养优化器、代下单。

## 做一次吃两顿

单位是今晚加明天，不是周日一锅吃五天：风味和营养的损失随存放天数涨，放一天没问题。计划里每道菜带一个属性，耐不耐放一天。炖菜、焖菜、烤根茎、豆子和谷物打底耐放；清炒绿叶菜、炸物、面条、拌好的沙拉不耐放，只做一顿的量。两段组装：耐放的底一次做好，绿叶和生的部分吃的时候现加，五分钟。

省事的约束写死：一口锅、动手时间 ≤15 分钟、要洗的东西不比做一顿多。两顿的量要多洗一个盆，就不算省事。

半成品是正当手段：烤鸡、沙拉包、冷冻蔬菜、罐头豆子、净菜（即烹预制菜购买率 48.8%）。分量按人头算，一个人就是两道菜各两份，或者做完冻一半。一个人分量难控制容易浪费是国内不做饭的第四大障碍（32.3%），一锅吃五天正踩在上面。

一周只买一次，只有整周按保质期吃才成立（冷藏 ≤4°C，下面按 USDA FoodKeeper）：

- 1–2 天：生鸡肉、肉糜、鱼虾。当天不做的当天就冻，冻三个月没问题。
- 3–4 天：做好的熟菜。
- 3–5 天：猪牛整块（这周的后一半买回来就冻）、绿叶菜、鲜菇、豆芽、嫩香草、浆果。绿叶和浆果排前半周。
- 一周左右：西兰花、花菜、彩椒、黄瓜、番茄；葡萄、桃、李。排周中。
- 两周以上：胡萝卜、圆白菜、萝卜、洋葱、土豆、南瓜，土豆洋葱不进冰箱；苹果、柑橘、梨、猕猴桃两到四周。排后半周。香蕉室温。

山姆、盒马的真空包装肉按标签日期算，通常比散装多两三天；冷冻蔬菜和罐头豆子填后半周。计划因此不是按天分配，是按保质期排序：周一周二绿叶和鱼，周四周五根茎和买回来就冻的肉；购物清单标出哪几样一到家就冻。水果一样进计划和清单。

## 源分三类

按 [69](../69-源模型：索引、叙事源、用户带来的与快照.md) 的源模型分，没有一类要商务合作，也没有一类要爬。

世界数据，能吃什么：

- 菜谱不内置库。两条路：用户贴一个菜谱链接（Budget Bytes、Serious Eats、BBC Good Food、NYT Cooking 这类），走现有的网页摄入管子抽里面的 schema.org Recipe JSON-LD——几乎每个英文菜谱站都埋了，含配料、时间、份数、每份营养；或者模型按上面那组约束直接生成简单菜，主方向是西式和地中海做法，中式家常（HowToCook）降为可选参考。配料表是事实不受版权保护，存用户自己收的菜谱正是 Paprika 在做的事。
- 营养用 USDA FoodData Central（CC0），西式食材覆盖完整。[饮食规划调研](../research/饮食规划调研.md) 里「中式菜品和国内预包装食品无源」那个缺口因此基本消失，何况这条线本来就不数克。
- 出去吃和外卖没有菜单数据，美团、饿了么、大众点评都是封闭的，也不爬。唯一的外部源是地图 POI：中国用高德（个人认证开发者可用），两国都能用 Apple Maps Server API，给店名、品类、距离、评分。到店级，不到菜级。

买菜先做离线，两国都是（[买菜渠道调研](../research/都市白领买菜渠道调研.md)）。清单按通用品类分组就能用，不要任何零售商的数据；地图 POI 只解决「你常去哪家店」。美国的 Kroger Public API 能按门店给价格和货架位，是后面的加分项，不是地基。中国的即时零售没有消费者侧接口，清单列出来，用户自己去 app 里搜。

用户数据，他会吃什么：吃过什么、常去的那几家（说过一次「楼下那家米线」就记住）、忌口、这周外卖几次，以及他实际买得到什么——常去的店（山姆、盒马、Ole'）定义了可行的食材集合。没有外部源，全靠用户带进来。这是主源，推荐质量由它决定。

当日数据：天气、日历、位置。已经有了。

要加的是三个源插件（按 69 的插件模型，一个源一个文件）：网页摄入管子里加 Recipe JSON-LD 抽取，接用户贴的菜谱链接（下厨房这类中文站不埋，退回现有的正文抽取）；USDA FoodData Central 索引插件，只取 Foundation 和 SR Legacy，只用来做每周的模式核对（蔬菜份数、蛋白、全谷物），数字从数据来不经模型；地图 POI（中国用高德 Web 服务，两国用 Apple Maps Server API），把「楼下那家」解析成一家店，出去吃那种模式列附近的选项，到店级，缓存和展示的条款接之前还要读。不加：美团、饿了么、薄荷健康、任何菜谱库、把 HowToCook 当主库、Kroger（暂时）。

## 现在的位置

第一片已按 [73](../73-晚饭：周计划、采购单与偏离.md) 落地并随 v0.20.5 发出，默认关，内容是周计划、程序推的采购单、偏离一句话、配料图和菜品图；六点推送、上面说的三个源插件、手机到 PC 的联动还没做。

第一步是项目发起人自己用一周，先验做一次吃两顿：做两个耐放的底、每个两份，今晚一顿明天一顿，第二顿现加绿叶，然后说腻不腻、麻不麻烦。批量做饭没有任何一份全国性调查测过，只有这么一条路能知道。

要验的前提不是「会不会维护冰箱库存」，也不是「吃完会不会说一句话」。饮食记录第一个月脱落 50–70%，Cal AI 撑得住靠一张照片加一个减重目标，这条线没有那个外部目标，所以记录反过来做：验的是「偏离了会不会说」。第一指标是录入摩擦，推荐质量第二。命中率（今晚那句话用户照做没有）和落空记录（改吃了什么、为什么）是第一批能量化的反馈数据。

## 已知的事实

底账在 [饮食规划调研](../research/饮食规划调研.md)，2026-08-28。形态结论按本文修订，下面这些事实仍然成立。

- 代下单不通。十二家生鲜和外卖平台没有一家有消费者侧接口，开放面全朝商家、服务商、供应商，都要企业资质。逆向不做：最高检 2025-06 的口径里「绕过官方客户端让对方系统执行指令」是刑事定性，且 App Store 5.2.2 要求随时出示第三方授权。
- 唯一对个人身份开放的正规下单口子是京东联盟 CPS，次日达，配不上「今晚吃什么」。
- 跳转到对方 app 的收益很小：已知 scheme 只有小象超市和多点两家，2022 年的社区数据，只能到首页不带搜索词。清单的价值靠清单本身做好。
- license 雷已经点名：GitHub 上那份中国食物成分表 JSON、聚合数据那份、Open Food Facts（ODbL share-alike 污染闭源）、Edamam（缓存条款等于不能建本地库）、下厨房豆果美食杰的逆向接口、CC-BY-NC 的中文菜谱数据集。
- 一旦承诺数字精确，App Store 1.4.1 会按健康数据准确性更严格地审，要披露数据和方法并给就医提示。这是不数克的第二个理由。
- UI 自动化替用户在 app 里点按钮：iOS 非越狱做不到，Android 真机加 ADB 可行，但那是个人自动化不是产品能力，且卡在支付确认那一步。
- HealthKit 的 39 个膳食营养标识符加身体指标现在就能读写，做不做另说。
