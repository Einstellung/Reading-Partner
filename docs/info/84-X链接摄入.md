## 要什么

用户在任意一个对话里贴一个 X 链接，app 把内容取出来，做成能读的东西：在阅读器里打开、划线、全文搜、备课、引用。推文多半只是引子，用户要的是它指向的东西（PDF、GitHub 仓库、文章、论文），所以产物是外链背后的内容，推文作为来源信息（作者、时间、正文、链接）一并存下，以后 AI 可以拿它判断哪些值得读，这一步不做。推文本身就是内容的（X Article、没有外链的长帖）照样落成文档。这一步只做内核：给一个 X 链接，产出可读的文档。归进哪个 topic、分享扩展这些入口放在后面。

现状：书内对话的 `ingest_url` 用不带登录的普通请求取 X，拿到的是 JS 空壳。抽取只拦空正文，不拦短正文，所以很可能落成一本只写着「JavaScript is not available」的 EPUB。这条是读代码推断的，没有实跑。

## 按形态落成什么

| 形态 | 落成 |
|---|---|
| 没有外链、自己也不成内容的短推文 | 只留一条来源记录（正文、作者、时间、原链接、图），不成文档 |
| 长帖、作者自己接成的 thread、X Articles | 一篇 EPUB 文档，走 67 的文章构建，和网页文章同等 |
| 带外链的推文 | 自动顺着链接，目标内容落成文档（PDF 直接入库，GitHub 仓库取 README，网页走 67）。推文作为来源信息附在文档上，不放进正文 |
| 指向书稿类 GitHub 仓库（README 只是目录，章节是 md 文件） | 取全书：按 `SUMMARY.md` 或 README 的章节列表（没有就按 md 目录树）逐章从 `raw.githubusercontent.com` 取，按顺序拼成一篇文档 |
| 引用推文 | 被引用的那条一起带上，放在引用的位置 |
| 图片和视频 | 图片下载后嵌进去，视频只留链接 |

## 取材

两条路，按平台叠加：

1. 嵌入接口。X 给网页嵌入推文用的 syndication 接口（`cdn.syndication.twimg.com/tweet-result`，按推文 id 算一个 token 参数），不用登录，所有平台都能调。预计能拿到单条推文的全文、图片和引用推文，拿不到整串 thread，Articles 拿不拿得到不确定。
2. 用真浏览器读永久链接页。桌面上已有的隐藏 webview（`webview_fetch`，Linux 和 macOS）。57 实测过：不登录时永久链接页能给出全文，WebKit 也能读 x.com。thread 后面的回复和 Articles 大概率要登录，登录照 57 的做法：用户自己在一个看得见的窗口里登一次，cookie 留在本机。手机上贴的链接交给采集端处理，结果经 Drive 送回手机。

不用第三方镜像，不用付费 API。

取回来的正文太短，或者内容是登录墙的提示，就不落文档，回执里说明取不到和原因。

三条路都没有被限流，没有挑战页或锁定，没有 429。嵌入接口 8 次全是 200。浏览器两列的耗时是从发起导航到推文出现：未登录 11.0-12.5s，登录 10.8-13.1s。之后再滚动数回复，整页约 17-26s，取材本身用不着这一步。

发现：

1. 嵌入接口只可靠地给元数据，正文不可靠。长帖在 `display_text_range` 处截断（4 条全截了，字数从 160 到 304），返回里的 `note_tweet` 只有一个 id；Article 推文只给标题、预览和封面，没有正文。回 200，不报错，直接取 `text` 会落一份看着完整的残文。判断规则很简单：返回里有 `note_tweet` 或 `article` 字段，就只用它的元数据（坑 493）。它的长处是展开后的外链、卡片、图都是结构化字段，0.6 秒，所有平台都能调。

2. 不登录的浏览器就够了。长帖全文、Article 全文和文内的图，未登录永久链接页全给，和登录后的内容一致，字符数差在界面数字上。57 里「Articles 大概率要登录」「thread 后面的回复要登录」的预期，前一半被推翻：这 8 条里没有任何一条需要登录才拿得到正文。

3. 未登录页是另一套前端，没有任何 `data-testid`（57 已测到，这次仍然成立），只有 tailwind 类名；登录页有 `tweetText`、`twitterArticleRichTextView` 等 testid，但 Article 推文没有 `tweetText`，按它等会白等 8 秒。抽取按 `article` 元素：第一个就是目标推文，取 `innerText` 再切掉开头的名字和结尾的互动数字；类名选择器会随前端改版失效，不要依赖。Article 正文是逐步渲染的，0xMovez 被引用的那篇在 3 秒里从 27 489 涨到 28 540 字符，要等长度连续两次不变再取。另有一次未登录读取时 `innerText` 里混进了一段 1.7 万字符的 `<style>`（Article 正文容器里自带），重读两次没复现；读之前统一去掉 style 和 script。

4. 引用推文：嵌入接口给被引用那条的结构，但被引用的是 Article 时只有 t.co。浏览器页里只有 Article 的标题和两行预览。要正文就把被引用那条的 id 再读一次永久链接页（实测 0xMovez/2106761689123139973，未登录 28 540 字符、20 张以上的图）。普通推文的引用只有这一个样本，且是 Article，没有测到。

5. 外链：嵌入接口的 `entities.urls` 和 `card` 给展开后的 URL，但长帖被截掉的部分里的链接不在其中（manorgw 文末的 GitHub 链接就是丢的）。浏览器页里，登录态的正文链接 href 是 t.co，未登录页有的是目标地址（kirkdborne、manorgw），有的仍是 t.co（卡片）。所以外链两边合着用：嵌入接口给卡片外链，浏览器页给正文里的链接，t.co 由取材端跟一次重定向展开。

6. 图片：URL 带 `name=small/medium/large` 参数，未登录是 webp，登录是 jpg，没有测换成 `name=orig` 后能不能下原图。视频只有 `amplify_video_thumb` 缩略图，符合「视频只留链接」。

7. 回复和 thread：未登录页只显示目标推文加 1 到 3 条回复，然后是登录弹层，滚不下去；登录页滚几次能读到 6 到 54 条（回复本来就少的推文读不出更多）。8 条里只有 0xmovez 有作者自己接的一条回复（带 PDF 链接），未登录就能看到；其余的作者回复是回别人的评论。所以「作者自己接成的 thread」未登录能拿到多少条、登录后能不能拿全，这次没有样本，没测到。

8. 登录态的页面自己有后台请求回 403，内容不受影响，别把它当限流（坑 494）。

## 外链实测

2026-10-08，同样 8 条链接，看推文指向的东西能不能不登录取全。t.co 用普通 GET 取 301 的 Location 展开（7 个，各约 1 秒，没有限流）。Drive、GitHub、网页都是普通 HTTP 请求，不带 cookie，逐个串行。网页走现成的入口：`ingestArticleUrl` → `bind` → Readability/defuddle，在 bun 里用 jsdom 的 DOMParser 跑，没有别的改动。PDF 用 `pdftotext` 抽文本。

8 条里 5 条是引子，真正的内容在外链里：2 个 Drive 上的 PDF、3 个 GitHub 仓库。2 条 X Article 自成一体。jiangkoumo_ 的帖子本身就是内容，它说的几个项目没有给链接。

发现：

1. 真实内容在外链里的占多数（5/8），推文正文只是 100-370 字的推荐语。所以「带外链的推文」不是边角，是主要形态。目标全部不登录就能取，X 本身的登录与否不影响这一步。
2. Drive 要单独处理。分享链接 `drive.google.com/file/d/<id>/view` 返回 200 的 JS 壳，正文只有「Loading…」，现成入口会拒收（「the body is only 8 characters」）。改写成 `https://drive.google.com/uc?export=download&id=<id>`：303 跳到 `drive.usercontent.google.com`，200，`application/octet-stream`，开头是 `%PDF`，现成入口的魔数嗅探能认出是 PDF。文件名在 `Content-Disposition` 里，现在落成的标题是「uc」（URL 里没有名字），要从响应头取。没权限或文件不存在是 404 的 HTML。大文件会先出病毒扫描确认页，这次两个都是几百 KB，没有样本，没测；`drive.usercontent.google.com/download?id=<id>&export=download&confirm=t` 在小文件上同样直接给出 PDF，大文件可以先试这个地址。
3. PDF 不用 OCR。两个都是 LaTeX/WeasyPrint 生成的，每页都有文本层，逐页字数 263-3 693，没有空页。现成入口对 PDF 是原样入库，不抽文本，所以这一步只是确认入库后能读。
4. GitHub 仓库的通用网页路能取到 README，但标题是「GitHub - a b c …」（`/` 和 `:` 被换成空格），而且只到 README。README 就是目标的（lcu、PraisonAI）这样够用；README 只是目录的（pi-durable-book，书稿仓库）只拿到不到 2%。加一个 GitHub 站点适配器：用 `api.github.com/repos/<o>/<r>/readme` 取 README（默认分支不用猜）；README 里目录式地列出 md 章节、或仓库几乎全是 md 时，按 `SUMMARY.md`/目录树取全书。未登录的 API 每小时 60 次（实测 10 次调用后剩 50），`raw.githubusercontent.com` 没有这个配额，取文件走 raw。
5. 找外链要三处合着用：嵌入接口的 `entities.urls` 和 `card`；浏览器页正文里的链接（长帖被截掉的部分）；作者自己的回复（0xmovez 的 PDF 只在那里）。X 上的卡片不一定是目标：jiangkoumo_ 的卡片是 fly.io 首页，与内容无关。
6. X Article 里的外链是引用和背景，不是要读的内容；这 2 篇都不用跟。Article 末尾那类「往期文章」目录是同作者的别的 Article，也不跟。
7. 取不到的几种长相要在回执里分开说：登录页（muse.ai 根地址、claude.ai/login）、JS 壳（Drive 分享页、muse.ai/s/…）、404（Drive 无权限）。现成入口对 JS 壳已经会拒收，不会落成残文。

## 建议

登录对这一步不是必需的，先不做。

| 形态 | 走哪条 |
|---|---|
| 短推文（无 `note_tweet`、无 `article`） | 只用嵌入接口，一次请求，所有平台，不起浏览器。有外链按下一行走，没有外链只留来源记录 |
| 带外链的推文 | 嵌入接口拿卡片和展开 URL，长帖和作者自己的回复里的链接从浏览器页补，t.co 跟一次重定向；自动跟，不问用户。只跟认得的类型：Drive 文件改写成 `uc?export=download` 直链、GitHub 仓库走 API 取 README（书稿类取全书，见下一行）、PDF 直接入库、arXiv、文章页按 67；首页、产品页、登录页不跟。回执列出抓了什么、没抓什么。推文存为来源信息。X Article 里的外链不跟 |
| 书稿类 GitHub 仓库 | README 只是目录、章节是 md 文件的，取全书：按 `SUMMARY.md` 或 README 的章节列表（没有就按 md 目录树）逐章从 `raw.githubusercontent.com` 取，按顺序拼成一篇文档。取不全的章节在回执里列出，不落缺章的书 |
| 长帖（有 `note_tweet`） | 嵌入接口拿元数据和图，正文用未登录的隐藏 webview 读永久链接页 |
| X Article（有 `article`） | 同上；webview 取全文和文内图，落成 EPUB 文档 |
| 引用推文 | 被引用那条的 id 再走一遍上面的判断 |
| thread | 先按未登录读到的几条处理；要读全需要登录，等有真实 thread 链接测过再定 |

iOS 和 Windows 没有隐藏 webview。外链从嵌入接口的展开 URL 和卡片取，在设备上直接抓目标内容。设备取不到链接或取不到内容的，把链接交给采集端（36），采集端抓完经 Drive 送回设备。这几种情况交给采集端：

- 链接在长帖被截掉的尾部，或在作者自己的回复里。
- 推文本身就是内容（X Article、长帖），嵌入接口只有开头或预览。
- 设备直接抓目标失败。

回执里说明已交给采集端、等结果。任何情况下都不落截断的文档。

## 实现

2026-10-08，桌面先行。

- 代码：`src/info/x/`（`post.ts` 嵌入接口，`permalink.ts` 页面脚本和正文切分，`outbound.ts` 跟不跟，`read-post.ts` 按「建议」做判断，`store.ts` 来源记录），`src/reading/ingest/x-post.ts` 编排，`live.ts` 接线。书内对话的 `ingest_url` 收到 X 链接走这条，其余链接照旧。
- 扇出放在 bindery 之上，X 不注册站点适配器。bindery 的合同仍是一份材料出一份文档，不认识 X。info 把推文读成三样：来源记录、推文自身的内容（长帖、Article）、要跟的外链。reading 把自身内容作为 HTML 材料交给 bindery；每个外链按粘贴链接的原路走（`ingestArticleUrl`），由登记表找站点适配器，没有认领的走通用网页路。
- 来源记录存 `info-x-posts.json`，按推文 id，记录加产出文档的 hash，同步、按记录合并。不写进文档正文，不改书库条目。文档删了 hash 会留在记录里。
- 长帖既落成文档，也跟它的外链。作者紧跟在目标推文后的回复（未登录页能看到的那几条）接在长帖文档里，用分隔线隔开，回复里的链接也跟。短推文不读页面，它下面的 thread 不读。
- 引用推文走同一判断。被引用的不成文档时，它的正文以引用块放在引用它的长帖末尾。
- 跟哪些：登记表认领的、Drive 文件、`.pdf`、GitHub 仓库、其余有路径的网页；首页、登录页、产品页（单段路径是 pricing、download 这类）、视频站、X 自己的链接不跟，回执写原因。每条推文最多跟 6 个。Article 不跟。t.co 读一次 301 的 Location。
- 页面没读到推文就再读一次。读到的正文比嵌入接口的开头还短，算没读到。页面的 `status` 不看（坑 496）。
- 没有隐藏 webview 的设备（iOS、Windows），长帖和 Article 的正文不取，回执写需要桌面端；嵌入接口给的外链照跟。采集端交接没接：legion 有按能力标签选机器的机制（`requires: [WEBVIEW_FETCH]`），但 `ingest-url` 是 local run，入库和挂到书上都在发起的设备上，没有交给采集端再经 Drive 送回的通路。
- 回执是 run 的输出：先一句说读了谁的什么推文、跟了几个链接，再每个文档一句，最后每样没取的一句和原因。

## 还没测

- Drive 大文件（病毒扫描确认页）、文件夹链接、要登录才能看的 Drive 文件。
- GitHub 上 README 以外的形态：releases 里的 PDF、Wiki、GitHub Pages。
- Hugging Face、Notion、微信公众号这类外链目标，这 8 条里没有。
- thread：缺一个真实的 thread 链接，缺未登录和登录各能读到几条的数据。
- Tauri 的 `webview_fetch` 本身：引擎已在 WebKitGTK 里测过，这条命令连同它的 profile、超时后读页面的路径没有在应用里跑过。macOS 的 WKWebView 也没跑。
- headless Chromium 这次没跑（57 测过会被 X 拦）。
- 普通推文的引用、带视频的推文、Article 里的视频。
- 批量的限流：这次登录态总共 8 次页面加载，没有触到任何限制，量级上说明不了什么。
- iOS 和 Windows 上的嵌入接口调用。
