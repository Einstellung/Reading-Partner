## 流程

1. 起草：门口对话照 88 起草。Lumen 问用户手上有没有已经确定对路的论文，程序查到、用户认过的成为种子。学术题只搜 arXiv 和 Hugging Face，不读 X。卡片 Apply 就派第一次 run，没有另外一轮起草。
2. 第一版：快搜出一份 PDB 式简报，进 info 书架的各期一排，封面标「专题 · 只看这一次」。
3. 聊：用户开着书和门口对话，问哪条，Lumen 读原文、带页码回答。Lumen 把聊出来的意见收成几行，用户逐行定。
4. 更新：用户点「按这几条更新简报」，同一份简报出下一版，最上面写这次改了什么、因为用户哪句话。没有自动更新。
5. 结束：用户说可以了，Lumen 提议移进阅读，确认后这份简报成为阅读里的一本书，主题停掉。钉住、判断和记下的几行留作这个题的标签。

## 起草与种子

起草照 88「起草：来回问」。专题调研多两件事。

种子。用户说只看这一次时，Lumen 在起草中问一句有没有已经确定对路的论文，一两篇就够。用户报名字（标题、简称、作者加年份都行），Lumen 调 `find_seed_paper`，程序去查，在对话里立一张种子卡：每个候选一行，标题、作者、日期、编号都是程序写的，带「是这篇」「不是」。一个名字最多给 3 个候选；查不到就说查不到，请用户给链接或更完整的标题。认过的种子由 `propose_topic_search` 带上起草卡（卡上「种子 · 钉住」一段），Apply 时写进主题配置的 `seeds`，在标签库里各记一条 `pinned` 和一条 `yes`，第一版起就钉在简报最前面。

来源。见下一节。起草卡上写一行「来源：arXiv、Hugging Face 论文。X 不翻：学术题」，再一行「只看这一次：不每晚跟。出一份简报，聊着改，你说可以了就移进阅读」。

## 来源开关

主题配置加 `sources`：这个主题读哪些源（`pace.ts` 的 `RunSource`）。起草时 Lumen 判这个题是不是学术题，学术题默认不含 `x`，写在卡上让用户纠正；不是学术题照旧全读。旧配置没有这个字段，按全读算。对所有主题都有效，不只专题调研。

不含 `x` 的主题：第一次 run 不分两段（88「第一次分两段」），只有快段，一段读完，结果文件不写 `awaiting`；夜跑不进 X 的排队；`planRetry` 不列 X；源健康不写 X 那几行；开场和卡片不说「X 还在读」。

## 一份简报

一个专题调研只有一份简报，各版是它的不同版本。第一版就是第一次 run 的那一期（键照旧 `first:<searchId>`），在 info 书架的各期一排，不在专题册一排。封面版头写「专题 · 只看这一次」，和每日简报的「每日简报」分开，边框用苔绿；书架卡下写「调研中 · 第 n 版 · m 条」。

书的结构照 88「简报书」，几处不同：

- 封面后第一页：题名、日期，一段「这份简报回答一件事：……」（模型按 scope 和 judgments 写），一行来源和回看窗口（程序写，「arXiv、Hugging Face 论文，回看一年。X 没有翻，学术题」），条数（正文几条、札记几条、钉住几篇），一句「哪条有想法就在 Lumen 对话里说，你确认的意见会让这份简报原地更新」。
- 第二版起，「这次更新」放在最前面，目录之前（见「更新」）。
- 目录先列钉住的，再列正文，最后札记（Notes 在专题调研里叫札记）。
- 每条的版头标签：钉住的写「钉住 · 你给的种子」或「钉住 · 你钉的」；读深写「读了原文」或「只读了摘要」；本版变动写「新增」「改写」「降到札记」「新钉」。
- 每一条的原文都挂成这本书的辅助资料（88 每期最多 12 份的上限对专题调研放开到全部条目）。

## 条目格式

每条按这个顺序写，用不懂这个领域的人也读得懂的中文（书的语言照 88 跟界面语言；下面说的是中文版）：

1. 背景：这件事为什么要做。
2. 之前的工作：以前怎么做，点名代表工作。
3. 不足：以前的做法缺什么，用论文自己的说法。
4. 这篇做了什么：讲成一个能读的故事，每一步写明是谁（大模型、算法工具、人）做什么。
5. 成果：精确数字，带比较对象（「75%，PySR 40%」）。
6. 和你的目标的关系：分「帮得上」和「碰不到」两段，对着主题的 scope、want、judgments 说。
7. 把握：读到多深（读了全文 / 读了正文开头 / 只读了摘要，由程序按 `facts.depth` 写）；「论文自己承认」的局限；「我们看到」的问题（比如准确率由同一个模型判、对照的数字没有重跑）。

术语第一次出现时在句子里用一个分句解释（「符号回归，也就是直接从数据里找显式的数学式子」），解不解释由「读者懂什么」定。

每句论断带原文出处 `[M3.§2]`（88「材料登记」的节编号），书里画成一个小章节号（「§3.3」），点了在同一个阅读器里打开那份辅助资料并翻到那一节。程序校验每个编号存在。成果一段的每个数字必须出现在它引的那一节里（88 的数字核对收紧到逐句对所引的节），对不上重写一次，再不对这一句不印，该条把握里写「成果的数字没核对上」。作者、日期、编号、链接照 88 硬规则 1 由程序写。

只读了摘要的条目照样分七段，摘要没给的那几段写「摘要里没写」，成果里摘要没给数字就写「具体数字摘要里没给」，不许从别处补。

篇幅（初值）：读了原文的条目在手机上半页到一页，正文不超过 1200 字；只读了摘要的不超过 400 字。读深篇数沿用 88 的 `DEEP_READS.first`（5 篇），每次更新给新加的条目另 3 篇（初值）。

## 读者懂什么

写条目那一步除了主题和候选材料，还拿到读者懂什么的 statement，逐个术语决定解释不解释；拿不准就在句子里短短解释一句。

D 片之前：statement 只有 `profile` 和 `concern` 两种 kind（`memory/statements/types.ts`）；48 把「懂了什么、卡在什么上」算在 profile 里，dream 只写 profile（`memory/dream/proposals.ts`）；写稿已经拿到全部 profile 的文字（`build-live.ts` 的 `profile`，`compose.ts` 的 `ComposeInput.profile`）。D 片加的（已进 main）：

- `STATEMENT_KINDS` 加 `known`：读者懂或不懂某个东西，一条一句（「熟悉强化学习和 AlphaZero」「不熟悉符号回归」）。profile 只留讲法。
- dream 的提议可以写 `known`，证据是 `understood-concept` 和 `stuck-point` 观察（`memory/observations/types.ts`）。
- `statement_write` 的 kind 说明加 `known`，回执「Noted about you」和 profile 一样。
- 写稿的 `ComposeInput` 加 `known`（没被取代的 known 文字），提示词写明按它决定解释，拿不准就解释。
- dream 的 known 只能挂这两种观察，程序校验；dream 自己写的 profile 里讲懂不懂的，可以 supersede 时带 `kind: known` 挪过去。
- 读者自己说的排在 dream 的前面：`build-live.ts` 按这个顺序交给写稿，提示词写明两条冲突时前面的算数；dream 照旧不许 supersede 读者写的。
- 阅读对话的记忆段（`memory/live/memory-section.ts`）和 info 侧的读者段（`memory/statements/section.ts`）也印 known：前者接在同一作者的 profile 后面，后者单独一块。

对话里写回：用户问「符号回归是什么」，Lumen 答完调 `statement_write` 写一条 reader 的 known（「不熟悉符号回归」，evidence 是那条问话）；用户说「这个我清楚」，写「清楚 X」。statement 是猜测，对话里的纠正用同一个工具带目标下标取代旧条（48「读者自己写」）。

## 对话里改

用户读简报时对话窗在旁边：手机是整屏 sheet（68「卢明的对话窗」），iPad 和桌面是书旁的小面板。问法照 88「简报的对话」：选中一句 Ask，或直接说。Lumen 用简报的读工具（`read_pages`、`search_topic`、`read_supplement`，`reading/issue-desk.ts`）读原文回答，带 `[p.N "原话"]` 和原文的节号。

聊出来的意见不当场生效。Lumen 觉得说到了可以记的地方，先用一句话复述自己的理解，再调 `propose_study_lines` 立一张确认卡，每行一条：

| 种类 | 例子 | 记到哪 |
|---|---|---|
| 不要 | 只从现成数据拟合方程、不回头设计下一轮实验的符号回归 | 主题配置的 `avoid` |
| 我的理解 | 先验怎样进入归纳和实验设计是重点，排序时优先 | 主题配置的 `judgments` |
| 钉住 | LLM-IDEA | 只动这份简报，标签库记 `pinned` |
| 降级 | The AI Scientist 降到札记 | 只动这份简报，标签库记 `borderline` |
| 改写 | KeplerAgent「和你的目标的关系」写重了，它不设计下一轮实验 | 只动这份简报 |

每行下面一行小字「你说：『……』」是用户原话（程序按 propose 的 `readerLines` 找到那条消息做锚），一行写记到哪。每行三个按钮：对 / 改一下 / 别记。「改一下」就地改那句，改完算对。全部定完，卡片底部的「按这几条更新简报」才可点；点了才写配置、写标签、派更新。用户在对话里说「对，更新吧」时 Lumen 调 `update_study_brief`，对本对话最新那张确认卡做和按钮同一个动作（做法同 `confirm_topic_search`）。别记的行什么都不写。

写配置走 `update_topic_search` 同一条路（`changeTopicSearch`，`revision` 加一，原话进 `answers`）。钉住、降级、改写只进这一次的更新请求和标签库，不进主题配置。

## 更新

更新是一种新的 run，kind 照旧 `topic-search`，brief kind `update`，idempotencyKey `topic-search:<id>:update:<n>`，n 是要出的版本号。上一次更新还在 pending/running 时不派，Lumen 说还在改。和别的 run 一样在桌面采集端跑，`background_status` 能查。

一次更新做三件事：

1. 重判候选池。池子是这个调研所有 run 读到的东西：第一次 run 和之前每次更新的 run 目录里的 `arxiv-read.json`、`hf-read.json`（有 X 时连 `x-read.json`），沿用 88「判不了」里 `carry` 读别的 run 目录的那套，只是对专题调研每次都带上全部之前的 run，不只没判过的。重排的提示带上更新后的主题配置、确认过的几行（编号 `L1`、`L2`…）、种子和标签库里的 yes / no 条目（各最多 6 条，标题加一句理由，当示例）。模型每个候选多回一个可选的 `because`，填让它进来或出去的那行编号；程序据此把每处改动挂到用户原话上。
2. 补搜。`update_study_brief` 可以带补搜查询（同 `QUERY_SCHEMA`，最多 3 条，初值），追加进主题配置的 `queries`，只跑 arXiv 和 Hugging Face，窗口同第一次。更新不读 X。
3. 重写。没变的条目原样搬，不调模型；新加的条目照「条目格式」写；有改写行的条目按那行重写指定的段；降到札记的条目只留一句和事实行。钉住的条目不会被更新去掉，也不会被降级，除非用户自己降。全景那段每版重写。

arXiv 和 Hugging Face 的限速、冷却照 88 不变。更新碰到冷却，进度行写「arXiv 限流冷却，约 N 分钟后接着搜」，run 在 `read` 相位里等到冷却结束再发剩下的查询（`run.ts` 现有的 `deps.sleep`）；冷却剩下超过 60 分钟（初值），先用已有的候选出新版，没跑的查询记在这一版上，「这次更新」末尾写一行「补搜还有 2 条没跑，arXiv 在冷却，下次更新接着搜」，下次更新先跑它们。

更新期间书照常能读。阅读器顶上一条状态「正在更新到第 2 版，几分钟。现在看的是第 1 版，可以接着看」；门口对话里一张 run 卡列三步（重判几篇候选、补搜几条查询、重写变了的条目）。新版出来，盒里放一项（kind `brief-issue`，body 是新版的书，封面程序写「<题名> · 第 2 版：加 3 · 去 2 · 降 1 · 改 1」），Lumen 在当天门口对话里说一句新版好了、哪一两条值得先看。开着的那本如果是刚才的当前版，换成新版，停在同一条上（那条还在的话）。

## 这次更新

第二版起，书的最前面一块「这次更新」，程序写，不经模型：

- 标题行：「这次更新 · 10月21日 15:41 · 从第 1 版」。
- 分组：加 n 条、去 n 条、降 n 条进札记、改 n 条、新钉 n 篇。每组下面每条一行：条目标题（点了跳到那条，去掉的画删除线、不能点）、页码、「因为你说：『……』」。原因取自 `because` 指的那行的用户原话；模型没给 `because` 的不写原因行。
- 有没跑完的补搜就加一行说明。

每条的版头标签（新增、改写、降到札记、新钉）只在它变动的那一版上有，下一版就没了。

## 版本

阅读器顶栏在标题右边一个「第 n 版」按钮，点开版本列表：每版一行，版号、时间、一句改动（「加 3 · 去 2 · 降 1 · 改 1」），当前版标「当前」，正在看的标「正在看」。每行两个动作：

- 打开：在阅读器里看那一版，只是看。顶上一条「你在看第 1 版，不是当前的第 2 版」和「看当前」。
- 回到这一版：先确认一次（「这本书换回第 1 版的内容，别的版本留在列表里。你确认过的几条不撤，要撤跟 Lumen 说」），确认后当前版指回那一版。不新出版本号，版本列表不变；下一次更新从当前版改起，版号接着最大的往后。

回到旧版不撤已经写进主题配置的「不要」和判断，也不撤标签。

划线跟着版本：新版出来时，旧版上的划线按那句原文搬到新版，那句在新版里还在就搬，不在就留在旧版上。

## 结束

用户说可以了（「可以了」「就这样」），Lumen 调 `end_study`，在对话里立一张移进阅读卡：标题「移进阅读 · <题名> · 第 n 版」，reading 主题列表（建议照 68「收链接」的标法），末行新建主题，一行小字「移进去以后不再更新，主题记成结束」，按钮「移进阅读，结束调研」和「再看看」。确认后：

- 当前版的书走 88「info 书架与专题册」的 Move to…：第一次移入 `addFileToTopic`；之后它是一本普通的书（课堂、划线线程）。info 书架不再显示它（书架本来就不显示已在某个 reading 主题下的书）。
- 主题 `stopFollowing`：记 `stopped`，concern 标 `lapsed`。
- 旧版的书走删书联动删掉，版本记录留着。
- 标签库、种子、主题配置里的「不要」和判断都留着。卡片回执写「这次调研已结束，不再更新。你钉住的 n 篇和记下的 m 条留着」。

用户也可以从书架菜单 Move to… 直接移，效果相同。

调研中的专题简报不过期（`info/issue/expiry.ts` 跳过调研中的那一行）。

## 攒着问

照 88「攒着问」：每期最多 3 个，已定的不再问。专题调研多一种问题：对某一条的标注问题（「AutoSINDy 算对路吗？」），快捷回答「对路」「不对路」「说不准」，回答写进标签库（`yes`、`no`、`borderline`），原话作理由。问题由程序挑：不在标签库里、这一版分数在中间（初值：最终分 40 到 60）的条目，每版最多 1 个，算在 3 个之内。`questions.ts` 的 `ResultQuestion.template.code` 加 `label-item`，参数是条目键和标题。专题调研每一版都可以带问题，打开那一版时 Lumen 问。

## 标签

每个主题一个标签库 `topic-search-labels-<searchId>.json`，随账户同步，按记录合并（`palace/kinds.ts` 登记），只追加：

```ts
interface TopicLabel {
  id: string;                 // "tl-" + 8 hex
  searchId: string;
  item: string;               // 条目身份：arxiv:<id>，或 info/rank/link-identity.ts 的事件键
  title: string;              // 程序写
  label: "yes" | "no" | "borderline" | "pinned";
  reason: string;             // 用户原话
  source: "seed" | "line" | "question";
  evidence: string;           // 那句话的消息锚点
  at: number;
  brief: { version: number; place: "pinned" | "main" | "note" | "absent"; rank: number | null; score: number | null } | null;
  criteria: number;           // 当时主题配置的 revision
}
```

同一条目后来的标签盖前面的（按 `at` 取最新），旧的留着。`brief` 记当时这条在第几版、在哪、第几位、几分，没进简报的（种子、对话里提到但不在书里的）记 `absent`。`criteria` 现在用主题配置的 `revision`，以后有判据表（调研第 1 条）换成判据版本。

这些标签是这个题的金标集。离线重放脚本 `scripts/topic-labels-replay.ts`（待写）：读标签库和这个题各 run 目录里存下的读取，把打分管道（本地相关度、RRF、重排）重跑一遍，报三个数：yes 条目进没进候选池（召回）、yes 条目在最终排序里的位置、no 条目有几条进了简报。检索和打分有改动时拿它比前后。

它们也是 [decision-data](../north-star/decision-data.md) 说的决策数据的原料：带上下文（主题配置、当时的版次和位置）、有显式理由。只留本地和账户同步，不上传；上传要另行征得用户同意，流程归 decision-data。

## 数据

主题配置（`info/topic-search/types.ts`）加：

```ts
interface TopicSearch {
  // …88 的字段
  once?: boolean;              // 专题调研：不派夜跑，第一次送达后不停，end_study 时才 stopped
  sources?: RunSource[];       // 读哪些源；缺省全读
  seeds?: TopicSeed[];
}

interface TopicSeed {
  key: string;                 // arxiv:<id> 或 doi:<doi>，link-identity 的键
  title: string;               // 程序查到的
  said: string;                // 用户报的名字，原话
  at: number;
}
```

结果文件：专题调研只有一份，就是第一次 run 那份，每次更新照 `mergeRetry` 的接法并进去：新条目和改写后的条目接着编号（改写的是新编号、同一个键，旧的留给旧版），材料接着编号，正文进这次 run 的目录，`retries` 记一条，`ResultRetry.part` 加 `"update"` 并带版号。文件多一个字段：

```ts
interface TopicSearchResult {
  // …88 的字段
  study?: { versions: StudyVersion[] };
}

interface StudyVersion {
  n: number;                   // 1, 2, 3 …
  at: number;
  runId: string;
  base: number | null;         // 从哪一版改出来
  entries: { item: string; place: "pinned" | "main" | "note"; tag: "new" | "rewritten" | "demoted" | "pinned" | null }[];  // item 是文件里的条目号（E7），改写后同键换号，各版指各自的文字
  removed: { key: string; title: string; line: string | null }[];
  changes: { kind: "add" | "remove" | "demote" | "rewrite" | "pin"; item: string; line: string | null }[];  // item 是条目键
  lines: string[];             // 促成这一版的确认行
  skipped?: string[];          // 冷却没跑的补搜查询 id
  overview: TopicSearchResult["overview"];
}
```

一版是这份文件上的一张视图：`versionPart(result, n)`（`result-types.ts`，照 `firstPart`、`retryPart` 的写法）取出那一版的条目（按 `entries` 的顺序）、材料、全景和问题，出书用它；那一版的 `StudyVersion` 挂在返回值的 `studyVersion` 上（不进文件），版头标签和位置从这里读。第 1 版的问题是第一次 run 自己的，之后各版的是 `part: "update"`、`version: n` 那条 `retries` 记录的。条目加 `parts`（七段，每段的文字里带 `[M3.§2]`），旧条目没有就按 `summary` 加 `body` 印。

调研记录 `topic-study-<searchId>.json`，同步，按记录合并，任何设备都写：

```ts
interface StudyFile {
  version: 1;
  searchId: string;
  lines: StudyLine[];                                  // 按 id 合并
  rollbacks: { to: number; at: number }[];             // 只追加
}
```

`rollbacks` 在盘上是以 `rb-<at>` 为键的 map，读出来按时间排成数组：同步的按记录合并只按 id 合并 `lines`，旁边的字段按字段合并，数组两边都加了会丢一边，map 按键合并两边都留（`info/topic-search/study.ts`）。

```ts
interface StudyLine {
  id: string;                  // "L" + n
  kind: "avoid" | "judgment" | "pin" | "demote" | "rewrite";
  text: string;                // 卡上那句，用户改过就是改后的
  said: string;                // 用户原话
  evidence: string;            // 消息锚点
  item: string | null;         // 钉住、降级、改写指的条目键
  state: "confirmed" | "dropped";
  at: number;
  usedIn: number | null;       // 用在哪一版
}
```

当前版是最新的那个事件：最新一版出来的时间和最新一次回到旧版的时间里晚的那个。

书架索引（`info/issue/types.ts` 的 `IssueEntry`）加 `study?: { current: number; versions: { n: number; bookId: string; at: number; line: string }[] }`，那一行的键仍是 `first:<searchId>`，期号不随版本变。每版的书单独入库（kind `issue`），各版组装记在 `info-issue-state.json` 的 done 里，键 `study:<searchId>:v<n>`，组装照 88 按键幂等。

## 门口工具

工具在 `info/topic-search/`，经 `info/topic-search/live.ts` 的 `topicSearchDoorTools` 挂上：

| 工具 | 做什么 |
|---|---|
| `find_seed_paper` | 参数是用户说的名字。程序用 arXiv 插件的标题搜索、Hugging Face 论文搜索，查不到再问 Semantic Scholar 的标题匹配（`info/sources/plugins/s2.ts`），最多 3 个候选，立种子卡（kind `study-seeds`）。只读 |

| `propose_study_lines` | 参数是几行：种类、那句话、用户原话（程序找锚）、条目号（`E3`，钉住、降级、改写用）。立确认卡（kind `study-lines`），不写盘 |

## run 和出书的改动

`info/topic-search/run.ts`：

- `TopicSearchRunKind` 加 `update`，`encodeBrief`、`parseBrief`、`topicSearchRunKey` 跟着加 `update:<n>`。
- `open`：专题调研在 `active` 时放行更新。`read`：只跑这次请求带的补搜和上次没跑完的补搜，冷却按「更新」等。`build`：调构建函数的更新路径。`deliver`：`once` 不再在第一次送达后 `stopOnce`。`wrap`：告诉 `info/issue` 关了，kind `update`、版号。
- 按 `sources` 决定读哪些源、分不分段（`pace.ts` 的 `sourcesOf` 和 `splitsFirstLook` 加主题参数）。

`info/topic-search/build-result.ts`：`makeResultBuilder` 加更新路径。`BuildTopicSearchResultArgs` 加 `update`（基准版号、确认行、钉住、降级、改写、种子和标签示例）。`carry` 对专题调研传全部之前的 run id。重排（`rank-pool.ts`）多收确认行和标签示例，多回 `because`。选件（`select.ts`）先放钉住的，降级的直接进札记。写稿（`compose.ts`）加专题调研的条目格式、`known`、逐句出处和逐句数字核对，只写新的和改写的。最后用 `mergeRetry` 并进文件，写 `study.versions`。第一次 run 也写 `study.versions` 的第 1 版（钉住的种子作为条目）。种子不在这次读到的候选里时，程序按键补一个候选（arXiv 走 abs，DOI 走落地页），照常看原文。

`nightly.ts` 和 `info/issue/assemble.ts` 等「当晚所有 active 主题」的地方跳过 `once`（共用 `topic-searches.ts` 的 `nightlyTopicSearches`；组装等的主题列表在 `info/issue/live.ts` 的 `activeSearchIds` 里取）。`run-worker.ts` 加 `askUpdateRun`（同 `askRetryRun` 的挡法），`run-status.ts` 认得更新 run（标题「第 n 版更新」，三步进度）。

`info/issue/`：`plan.ts` 和 `render.ts` 出专题调研的书（封面版头、首页、这次更新、钉住一段、版头标签、七段、节号），`assemble.ts` 按 `study:<searchId>:v<n>` 组装并改那一行的 `study`，辅助资料对专题调研不设 12 份上限，`expiry.ts` 跳过调研中的。

## 待定

- `find_seed_paper` 从一个名字怎么查准：简称（「AlphaFold 那篇」）、非 arXiv 的期刊论文、同名多篇，arXiv 标题搜索和 S2 标题匹配各自的命中率要拿真名字试。
- 读了原文的条目到底多长合适，1200 字是初值。
- 一次更新的花费：重排一次、写新条目一到两次、读深最多 3 篇，加 arXiv 和 Hugging Face 最多各 3 条查询；没量过，第一次真用后记下来。
- known statement 起步从哪来：dream 要有 `understood-concept`、`stuck-point` 观察才写得出，新用户和刚开始用的题没有；是起草时顺口问一句，还是先全按「拿不准就解释」写。
- 划线搬到新版只按原句匹配，改写过的那段上的划线留在旧版；结束时旧版删掉，那些划线跟着没了。
- 回到旧版之后再更新，「这次更新」的原因行要不要提回滚这件事。
- 主题配置的「不要」写进去后，这个题以后再起一次调研时是否沿用。
