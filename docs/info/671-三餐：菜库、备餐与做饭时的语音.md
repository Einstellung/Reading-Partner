## 目标用户

上班、也在健身房练的人。时间紧，对吃得健康很讲究。稍微复杂的菜不是给他们的：想吃花哨菜的人去看 YouTube 和抖音，不看我们的菜谱。所以菜库不收复杂菜，每道菜的做法概述也只有一两句。

默认厨具：平底锅、锅（加蒸架当蒸锅）、电压力锅、电饭煲、豆浆机、微波炉、水壶。豆浆机是最省事的豆类来源：前一晚把豆和水放进去、设好定时，不用看着，机器好洗。烤箱不在默认里（要翻面，常常烤不透），慢炖锅、空气炸锅、烤面包机也不在。也没有厨房秤、煮蛋器、电蒸锅：蒸就是锅或平底锅里放蒸架。种子库每道菜都只用默认厨具；用户在对话里说了有烤箱等，模型才可以为他选需要的菜，做法类别表里的烤、焗烤、慢炖照留。

## 形态

一个计划覆盖 1 到 3 天（`MAX_PLAN_DAYS`），从用户说的那天起，默认今天，一趟采购、一次备餐。备餐可以在第 1 天的前一天（备餐日，草稿里的第 0 天），备餐日不算计划日，早饭午饭不归计划；在晚饭前做的，当天晚饭可以吃这次的锅，所以一个计划最多 7 顿午晚（3 天加备餐日晚饭）。要排更长，吃完这个计划再排一个、再做一次饭。新计划从它的第一天起顶掉旧计划里重叠的日子，之前的日子不动；过去的日子不能改照 73。

自己做的饭分两种。备餐是在用户能做饭的某天某个时段一次做一锅或几锅，分给之后的几顿；现做是那一顿当场做，走 73 的做法页，费事档位也只管现做的这种。早饭是组装模板（见菜库），不备；加餐照 73，另外午晚吃不满一天热量时程序补一份（见「克数」）。

计划默认偏备餐：大部分午晚吃备好的锅，现做的那几顿是快手组装；一次备餐动手合计默认一小时左右。两条都是默认值，用户在对话里说了就照他的。用户要某一顿好好做照 73 的 `proper`：不限时，不进菜库。

## 调味

调味靠现成的复合调料和酱：管装蒜蓉姜蓉、各种调味粉、瓶装酱。不用鲜蒜、姜、葱、辣椒，用户要了才用。调料的钠按克数算进参考份，钠上限把用量压小。

## 对话

排之前模型先问它不知道的：排几天（1 到 3 天，用户想排更长就说先排 3 天，吃完再排）、哪天哪个时段能做饭、装不装盒、最近想吃和不想吃的、厨具（默认厨具见「目标用户」，用户没提就不问，说有烤箱等才记进档案）。档案里已有的不再问。「明天晚饭后备餐，吃后面三天」「前一天晚上做」是备餐日晚上做、计划从后一天起；「今晚做今晚就吃，再吃三天」是备餐日下午做、当晚吃锅（`prepDinner`）、计划从明天起。计划从今天起时没有备餐日，备餐放在第 0 天的草稿退回，让模型把计划改从明天起。长期的几项（能做饭的时段、装不装盒、厨具、灶眼数、买不到的食物）用 `update_meals_profile` 记进档案；这一次的口味只跟着这份草稿。

然后模型交草稿（`propose_meal_plan`），对话里出一张草稿卡：每天每顿吃哪道菜，哪几顿吃同一锅，备餐在哪天哪个时段、做哪几锅、动手和总共多少分钟，前一晚要做的事。草稿没有克数。卡上的名字、锅的字母（按第一次吃它的那顿排）、分钟都由程序从检查过的草稿写（`build-draft-card.ts`），模型只交 id。备餐在备餐日时，卡上第 1 天前面多一块「前一天」：备餐那行，和当晚吃锅的晚饭（有的话），以及当晚给第 1 天准备的事。

模型只挑要口味的：每天午晚的主菜（哪一锅的哪种吃法，或现做哪道）、哪些主菜做成锅、备餐在哪天哪个时段，菜系搭配和这次的口味来自对话。早餐、现做主菜的主食、配菜、水果由程序从菜库补（`planner/fill.ts`）：先按钠最低给每天一份不重样的早餐，现做主菜优先挑全谷物、和计划那锅米饭不冲突的主食，水果按放得住的整个水果轮着排，配菜先由补蔬菜那步加；然后按最好优先搜索改动（换早餐、换主食、加减换配菜、换一锅某顿的吃法）：每处改动都跑一遍草稿检查（不排存放），按剩下问题的条数和各自差多少打分，在所有查过的草稿里先展开分最低的那份，比上一份差、又没消掉任何一条问题的改动不再往下走，剩下同样几条问题的草稿只展开 2 份，叠加最多 6 处改动、最多查 400 份；找到能过的就停，再把改动逐处撤回，撤了分不变差就撤。这样两处改动合起来才能过的组合也找得到，3 天的计划在 1 秒内补完。整包剩一半就加用这样东西的配菜，豆类不够就换豆浆早餐或加豆腐配菜，缺钙来源就换有奶的早餐、加上海青配菜或换带上海青的吃法（先排早餐时，主菜不带钙来源的那天先挑有奶的），钠超了就换咸度低的早餐、主食、配菜，出现两种米饭就换主食或一锅某顿的吃法。同样的主菜补出同样的计划，没有随机。模型交了的吃法或主食，只在改它就能过某条规则时才改，改了写进给模型的说明。早餐只在用户点名要某一种时由模型写，程序原样保留。用户对整个计划说了早餐或主食（「早餐都吃燕麦」「主食想吃面」），模型写进 `asked`（`breakfast`、`staple`），程序拿它当每天的早餐、每道能配它的现做主菜的主食，和模型逐天写的一样对待。

补不齐才退回，什么都不显示。退回的每条由程序写：哪条规则、哪样食材或哪一顿、要换模型的哪一项，钠超了列出这天早餐、每顿主菜和主食各多少 mg，整包剩余列出用它的那几顿和库里还有哪些主菜用它，热量不够列出这天每顿主菜连主食多少 kcal、哪顿没主食和库里热量高的主菜。一个回合最多退回 4 次（`MAX_DRAFT_ROUNDS`），满了工具不再收，模型用大白话告诉用户卡在哪、能改什么。回合本身的上限（`DEFAULT_MAX_ROUNDS`，8 轮）高于它，说明那一轮一定轮得到，测试盯着。

模型读的菜库只列主菜和早餐。按这位用户今天的目标算份量，每种吃法后写一顿（主菜加这种吃法的主食）的钠，现做主菜写主菜本身的钠，开头一句给出一天 2000 mg 减去早餐后午晚两顿还能用多少；另列「只有主菜用得完的整包」：没有配菜、早餐用到的易坏整包（豆腐、鲜面条、四季豆、蘑菇、香菇、鲜荞麦面），每样写包装克数、可接受的剩余和每道用它的主菜一顿用多少。别的整包由程序靠配菜用完，不给模型看。

用户在对话里改，模型交整份新草稿。对话回放只带文字不带卡片，所以卡还没确认时，三餐的说明里附上卡上那版的主菜、锅和备餐（`draftOnCard`，和 `propose_meal_plan` 的参数同形），连同模型当初逐天写的早餐、现做主菜的主食和 `asked`（卡上存着这版是从哪份选择补出来的，`picks`），模型只改用户说的那处；其余早餐、主食、配菜、水果不附，程序重补。同一对话里还没确认的草稿卡原地换成新版：卡 id 是 `meals-draft-<draftId>`，新版沿用 draftId、版本号加一，对话里不加新行；哪几顿「已改」由程序比对上一版算，按菜和吃法比，不看模型起的锅 id。已确认的卡不再改，下一份草稿是一张新卡。

长期的忌口和买不到（「我不吃西兰花」）不走新草稿，走 `update_meals_profile`。存完档案，程序拿新档案查卡上那版：有它的话从卡上的选择重补（同存盘计划的重补，见数据模型），补得过就原地换成下一版、标出改了的那几顿，结果里逐顿写「第几天哪顿：原来 → 现在」并附新版的 `draftOnCard`；补不过就不动卡，结果里写哪几顿还有它、要模型换哪几道主菜再交草稿。结果里没写改了的，模型不许说改了。

确认有两条路，写的是同一件事（`apply.ts` 的 `applyDraft`）：点卡上的「就这样」直接写；用户在对话里说一句确认，模型调 `apply_meal_plan`。写之前按当前档案重查一遍草稿，这时才解克数，计划和采购单一次写进去。卡折成「计划已排好」加查看计划、采购单两个链接。点按钮确认时，给模型留一行屏幕上不画的说明（带 `draft` 字段的 `meals-applied` 卡）。

## 菜库

菜从菜库里选。种子库内置在代码里（同食物表），收中餐、日餐、东南亚、美式、墨西哥、意大利、地中海，意大利和地中海分开算，不收韩餐和印度菜。种子库由模型按下面的字段起草，过 `checkDish`，再由用户在列表页审；先做约 120 道：主菜 80（多数能备）、早餐 20、主食 10–15。中餐参考 HowToCook（Unlicense）和 YunYouJun/cook（MIT），其他菜系取常见家常菜；只存配料和属性，不抄做法原文。种子菜避开用剩半包就坏的易坏食材（见「整包与开封」）：不用鲜香草，不用椰浆、菲达和马苏里拉这类开了就剩的罐装和软奶酪，高汤用罐装浓缩高汤膏（一小匙约 6 g 兑 240 ml 水，开封后冰箱放数月），不用盒装高汤，盒装开了就剩半盒，配方里不写水，只写膏的克数；鲜菜小量配料只留各菜共用的几样，罐头番茄和罐头豆按一锅三份正好一罐来写。种子库的豆腐加肉的菜，豆腐是大头：用北豆腐，备餐锅每份约 145–150 g、肉约 50 g，三份正好一整块（约 400 g）；现做的每份约 165 g、肉约 45 g。这靠入库检查里多个蛋白行的下限放宽（见入库检查）。豆腐加蛋、豆腐加豆类和毛豆的菜照旧。冷冻毛豆放得住，米饭碗、炒菜、凉面里常用。主菜、吃法和配菜里不放水果，水果单独成一项（见多样性）；早餐照旧可以带水果。一个计划里菜系每天随便混；不从用户的语言、地区推他吃哪个菜系、什么口味，口味只来自他说过的话和档案里的忌口。

每道菜带：

- 角色：主菜（午晚）、早餐、主食（一锅谷物这类要做的主食）、配菜（一盘蒸西兰花这类蔬菜菜）。
- 配料模板：食物表 id、一份参考份里各自的克数、各行的角色（蛋白、蔬菜、主食、油、调味、水果、点缀）。油、盐、酱油、味噌按克数写进模板。点缀是少量奶酪、酸奶、坚果、种子、香草：不受蛋白食物的克数下限管，脂肪算加的脂肪，钠和蛋白照算。
- 菜系、做法类别、要用的厨具、动手分钟、总分钟。
- 能备，还是只能现做。只有不用一直守着、动手时间不随量涨、回热不走味的做法能备：默认厨具里是炖煮、卤、压力锅、蒸、煮（汤、白煮肉、手撕肉）、煮谷物；用户有烤箱或慢炖锅时再加烤、焗烤、慢炖。炒和煎只能现做。鱼和海鲜一律现做，不备：回热发干发腥，而且鱼十来分钟就熟。
- 现做的主菜配哪几样主食（食物表里的主食或主食类的菜）。
- 能备的主菜带 2–3 种吃法，一锅吃三顿每顿味道不一样（牛肉豆子炖菜盖饭、卷进玉米饼、浇在微波土豆上）。一种吃法是：中英文名、配的主食（自带主食的写无）、可选的现配行（蔬菜、点缀，克数按一份参考份写；种子库不放水果），开饭时 5 分钟内配好。吃法的名字是菜名加主食加一两样它真带的蔬菜，中文不超过 14 个字，不出现两个「和」，英文不出现两个 and。吃法里的蔬菜在常见深色名单里轮换，同一种蔬菜最多出现在四分之一的吃法里；圆白菜只作菜本身的配料，不做吃法的现配行。主食写在吃法上，不写在菜上。

手撕鸡、一盘蒸蔬菜、一锅谷物都是库里的正经条目，搭成不同的顿：手撕、白煮的肉是带吃法的能备主菜，谷物是主食，蔬菜是配菜。批量做的主要是肉和蛋白，蔬菜每顿现做。

早餐不是一道做的菜，是组装模板：至少一样蛋白（蛋、牛奶、酸奶、豆浆、即食鸡胸、奶酪……）、至少一样主食（面包、吐司、馒头、卷饼皮、麦片……），蛋白和水果的样数不限（牛奶加蛋、酸奶加蛋都是常见搭法），一份合计蛋白不少于 15 g，可以加点缀和调味。只用组装、煮（煮蛋）、微波、蒸热、平底锅煎热面包，只能现做。

豆浆机早餐是早餐模板里的一类：前一晚把干豆（黄豆，可加黑豆、红豆、燕麦、小米、核桃、红枣）和水放进豆浆机、设好定时，早上倒出，配现成的蛋、馒头、吐司、水果。种子库有四种：黄豆浆、五谷豆浆（黄豆加燕麦、小米、红豆，豆浆里已有主食，馒头只要半个）、黑豆核桃豆浆、红枣豆浆。早上动手不超过 5 分钟，加上前一晚放豆的两三分钟也在 5 分钟内；这几道都算豆类（见多样性）。

冷藏几天不存在菜上，由程序按做法类别算（见「一锅」）；熟食不排冷冻，生肉生鱼的冷冻见「盒与存放」。

参考份是模板按比例缩放到主菜蛋白 25 g（73 的正常量）、主食 200 kcal、配菜蔬菜 150 g 的那一份；早餐不缩放，模板的克数是起点，按日常单位写（鸡蛋按整个、一个 50 g，牛奶豆浆 250 ml，酸奶 150–200 g，吐司一两片，馒头卷饼各一个，水果一个或一小把），每人的量由程序按日常单位再往上长（见「克数」）。能备的主菜按每种吃法各算一份：参考份加上这种吃法的现配行，现配行不跟着缩放。

### 入库检查

程序从配料模板和食物表算参考份，模型自报的数不算。以下全过才入库；能备的主菜每种吃法都要过：

| 参考份（早餐按模板原样） | 主菜 | 早餐 | 主食 | 配菜 |
|---|---|---|---|---|
| 蛋白占热量 | 不带主食 ≥ 30%，自带主食 ≥ 20% | ≥ 20% | 不查 | 不查 |
| 加的脂肪（油、黄油、酱、坚果、奶酪、点缀的脂肪） | ≤ 10 g | ≤ 10 g | ≤ 5 g | ≤ 5 g |
| 钠 | ≤ 600 mg | 不查 | ≤ 200 mg | ≤ 200 mg |
| 加糖（糖、蜂蜜、味醂、甜酱的碳水） | ≤ 10 g | ≤ 10 g | ≤ 5 g | ≤ 5 g |
| 蔬菜（配菜按所有蔬菜行） | 不查，见下 | 不查 | 不查 | ≥ 150 g |
| 真蔬菜 `real_veg` | ≥ 150 g | 不查 | 不查 | 不查 |
| 深色占真蔬菜 `deep_veg` | ≥ 一半 | 不查 | 不查 | 不查 |

主菜的蔬菜按真蔬菜算：参考份加这种吃法的现配行里，蔬菜行去掉不算的那几样，合计至少 150 g，其中深色的克数至少占一半（现做的主菜没有吃法，菜本身要达标）。不算真蔬菜的是香料和酱底：洋葱、紫洋葱、大蒜、姜、小葱、大葱和番茄碎罐头；它们仍是蔬菜行，只是克数不计入。深色蔬菜按《中国居民膳食指南》：深绿、红、橙、紫色的蔬菜，如菠菜、上海青、西兰花、罗马生菜、四季豆、青椒、番茄、胡萝卜、红彩椒、南瓜、紫甘蓝；白菜、卷心菜、黄瓜、西葫芦、芹菜、蘑菇、豆芽、豆类和黄彩椒不算。种子菜里深色蔬菜只用这些常见的：菠菜（含冷冻）、西兰花（含冷冻）、上海青、罗马生菜、四季豆（含冷冻）、青椒、胡萝卜、番茄、小番茄、红彩椒、南瓜、紫甘蓝，在中国和美国的超市都好买；模型写新菜时，用户提到别的深色蔬菜也可以用。

动手时间：能备的菜一锅不超过 20 分钟（等待不限），现做的不超过 15 分钟，早餐不超过 5 分钟，吃法的现配不超过 5 分钟。

另外：配料全在食物表里，每行的角色和食物表对得上，吃法的现配行只能是蔬菜、水果、点缀；做法类别在类别表里（类别表没有油炸），能备只限上面那几类，蛋白行是鱼或海鲜（食物表的蛋白品类 `seafood`，含鱼罐头）的主菜不能备；能备的主菜正好 2–3 种吃法，别的菜没有吃法；只有现做的主菜列配的主食，吃法的主食是食物表里的主食或主食类的菜；早餐至少一样蛋白、一样主食，合计蛋白不少于 15 g，做法在早餐那五样里；不收成品绞肉：肉末、肉馅、肉糜这类成品食物一律拒收，要做肉丸、肉糕就在蛋白行上标「现绞」，指名一块整块的瘦肉（猪后腿瘦肉、牛后腿肉、鸡腿肉这类肉和禽），营养按那块肉算；带现绞行的菜，中英文概述里都要写明现绞（现绞 / ground fresh），采购单据此提醒买整块瘦肉当天绞；每道菜都要有一句话的做法概述（中文不超过 40 字，另有英文），说清主料怎么做、做多久；参考份里每个蛋白行的克数在它的上下限内；主菜有两个或更多蛋白行时，每行的下限放宽为食物下限的一半（鸡腿肉、猪肉、北豆腐 80 g 变 40 g，鸡蛋 50 g 变 25 g），上限不变，只有一个蛋白行的主菜和早餐仍按完整下限。两样蛋白共享 25 g，各自仍要在盘里有分量，所以下限是一半而不是更低。

数字的来处：主菜蛋白 25 g 是 73 的正常量，早餐合计蛋白 15 g 是日常一份（一个蛋加一杯奶加一片吐司）的下限；配菜 150 g 是 73 的 V 格；蛋白占热量对着调研里高蛋白方案占 25–30%，自带主食的菜放到 20%；加的脂肪 10 g 是调研第 9 步每顿油酱坚果合计的约定；加糖每顿 10 g 是调研第 7 步（DGA）；钠按一天 2000 mg（中国居民膳食指南 2022 盐不超过 5 g，WHO 钠 2 g）照 73 的分顿比例分到一顿，再给主食和配菜留出余量；早餐不设单顿钠上限（钠超标主要出在午晚），它的钠照样算进一天的合计；主菜真蔬菜 150 g 取自指南每天 300–500 g 蔬菜、一半深色，午晚两顿合起来 300 g。

种子库每道菜都要过这套检查，由单测守着。

用户要一道库里没有的菜，模型用 `write_dish` 写一道（同样的字段），程序跑同一套检查。过了进用户自己的菜库，以后和种子菜一样选；没过就退回模型，标出哪几项没过，模型改配料再交，或者告诉用户这道菜按这套标准不健康、是哪一项。

模型可以为这次计划改一道菜的比例（多放菜、少放油），改过的版本跟着这份计划存，同样要过检查，不改菜库。

### 克数

程序按人解：

- 早餐从模板起，按日常单位往它的热量份额长：一个蛋、一杯 250 ml 的牛奶或豆浆、一片面包、半个馒头、一袋 30 g 的燕麦。先加主食再加蛋白，一次一个单位，只在更靠近份额时加，每行最多翻倍、不超过食物的克数上限。比一天钠上限按热量摊下来更咸的单位（蛋、面包），只在早餐的钠仍在它的热量份额内时加。水果和没有日常单位的行照模板。
- 主菜整道按模板比例缩放：一天的蛋白目标减去早餐、水果和配菜的蛋白，平分到午晚两顿的主菜；不低于参考份，不超过蛋白食物的克数上限。
- 主食补这顿的热量，夹法照 73；一天碳水不低于 130 g。主食的上限按 2000 kcal 的一天写（`STAPLE_REFERENCE_DAY_KCAL`），一天热量更高时按比例放大，低于 2000 不缩。
- 一顿没主食（锅的吃法不配主食）、补不满它那份热量时，差的那部分记到另一顿的主食上，仍在主食上限内。
- 午晚的主食都到上限、一天的热量仍不够时，程序加一份加餐：先一杯牛奶或酸奶，再一小包坚果；不用豆浆。只在更靠近目标、一天钠不过 2000 mg 时加，用户不能吃的跳过。加了的写进给模型的 `notes`。加餐后还不够，早餐越过它的份额接着按日常单位长（每行仍不超过模板的两倍和食物上限），一天钠不过 2000 mg。
- 主菜按蛋白放大时，调味行只按放大倍数的平方根长（肉翻 2.25 倍，酱翻 1.5 倍）。一天的钠仍超 2000 mg 时，把这天主菜的倍数每次降 0.1，一锅连同它喂的每一天一起降，只在这些天的蛋白都还在目标的九成以上（`DAY_PROTEIN_FLOOR`，和检查同一条线）、热量在下限以上时才降；降不下来的照常由钠检查报出。
- 油不用来补热量。一天脂肪低于下限时照 73 给每顿正餐加 5 g 油再解。
- 吃同一锅的几顿份量相同（蛋白目标每天一样）。主食每顿各解各的，一锅主食分盒时各盒克数不同。
- 克数按用户本人，几个人吃照 73 乘在采购单和备齐清单上。

### 给用户看的量

不用厨房秤。超市的包装上标着克数，用户看到的量是盒、锅和日常单位：采购单写「鸡腿肉 1 盒（约 500 g）」，一盒整盒下锅，一锅分 3 盒，一碗饭，一把菠菜，两片鱼。整盒下锅和分盒带来的几十克误差摊在计划里不影响营养，不为它多称一次。克数留在程序里，只用来算营养、蛋白够不够和钠；备齐清单、备餐页、做法页和日卡上都不出现要称的克数。

## 一锅

一锅是一道能备的菜做一次，分给 1 到 3 顿（`POT_MEALS`），做的那顿当顿吃也算一顿。只有能备的主菜做成锅，只给午晚，每顿用它的一种吃法；一锅吃几顿就用几种不同的吃法，吃法不够就用满它有的。配菜和米饭以外的主食按顿配，不做锅；米饭见下。同一道菜一个计划里只做一锅，同一天午晚不吃同一道菜。

一个计划只有一次备餐（`MAX_PREP_SESSIONS`），所有的锅都在这一次里做，在计划的某一天或第 1 天的前一天（备餐日）。备餐日只有晚饭能吃锅，而且备餐要在上午或下午；锅不能排备餐日的午饭。备餐日和时段在档案里能做饭的时段（档案没记就不限）；菜要的厨具在档案的厨具里，档案里没记厨具的按默认厨具算。

米饭一个计划只煮一锅。计划里所有电饭锅主食（米饭、糙米饭、五谷杂粮饭、小米饭）必须是同一种，用了第二种的那顿退回（`one_rice`，`planner/rice.ts`），哪种为准看哪种顿数多，一样多取先出现的。这锅饭在备餐时和锅一起用电饭锅煮，量是备餐之后所有吃米饭的顿解好的克数之和乘人数，现做的那几顿（比如第 3 天的鱼）也算；备餐之前的顿当顿自己煮。计划里没有备餐时，这锅饭在第一顿吃米饭的时候煮。主食的变化靠米饭以外的主食（馒头、饼皮、面条、土豆、面包）；全谷物要够，就把糙米饭或五谷杂粮饭定为这锅饭。

存放只排冷藏，由程序按做法类别定：

| 做法类别 | 冷藏 |
|---|---|
| 炖煮、卤、压力锅、慢炖、烤、焗烤、蒸、煮、煮米饭和谷物 | 做好当天和之后 3 天（`FRIDGE_DAYS_AFTER_COOK`） |
| 煎、少油炒、凉拌、醋渍、腌泡、绿叶菜、沙拉、微波、烤面包、不开火的组装 | 只能现做，不备 |

熟菜剩菜 FoodKeeper（USDA）给的是冷藏 3–4 天，取 3 天；熟米饭是 4–6 天，计划的窗口在它之内。锅里每一顿都要落在做好当天到之后 3 天以内，也不能早于备餐的时段，否则草稿退回。备餐日晚上做、吃后面 3 天，最后一顿正好是之后第 3 天。熟食不排冷冻：计划最长 3 天，一锅都在冷藏期内吃完。鱼和虾不进锅，当顿现做；生肉生鱼和冷冻鱼的存放、化冻见「盒与存放」。

偏离照 73「一锅」最后一段：没做的锅挪到剩下的第一顿做或删掉，做好的锅记备用盒；冷藏期换成这里的 3 天。

## 盒与存放

存放由程序从草稿、解好的克数和采购单算（`planner/storage.ts`），不存，读时算；时间用计划第几天加哪一顿，不写日期，备餐日写「前一天」。备餐在备餐日时，采购在备餐日或之前做完：采购单上锅要的东西和第 1 天要的东西都写备餐日前用到，保质期从备餐日算，当晚的事（豆浆机、化冻）记在备餐日晚上。

- 一次备餐，熟食只进冷藏，一锅在最后一顿之前吃完。
- 盒装锅里一顿的那一份；这顿的主食是这锅米饭时，饭也装进这个盒（「盒里有：锅里那份 + 米饭」）。蔬菜（吃法的现配行、配菜）和米饭以外的主食不装盒，吃时现做。盒数 = 锅的顿数减去备餐那顿吃掉的（备餐时段之后当天的第一顿午或晚餐），乘人数。盒约 750 ml、带盖、能进微波炉，玻璃的最好。
- 档案里说了不装盒：每锅有剩的配一个有盖大容器，连汤装，每次舀一份热透。没说就按装盒。
- 米饭：现做的那几顿的饭装一个有盖容器，算进容器数；不装盒的用户，留着的饭全装这一个容器。备餐那顿的饭当顿吃。饭摊开晾凉，1 小时内进冷藏，吃前热到冒热气；冷藏里一行写饭几份、怎么装、哪顿前吃完（最后一顿吃米饭的那顿）。意面、藜麦、面条这类不用电饭锅的主食照旧当顿煮。
- 生肉生鱼：保质期撑得到做它那天的，原包装放冷藏下层到那天；撑不到的，买回当天按顿分装冷冻。一包用不完的剩量（不少于一包的 20% 且不少于 50 g），平铺装冷冻袋，写日期，4 周内用（`RAW_FREEZER_WEEKS`）。每一份冷冻的配一个冷冻袋。
- 买来就是冻的继续冻着。吃鱼的前一晚拿到冷藏化冻，来不及就冻着下锅多煮几分钟；买回当天分装冷冻的生肉那份也前一晚拿到冷藏。
- 开封易坏的包装：用完日 = 第一次用到它那天加开封天数（`pack.openDays`）；豆腐泡在清水里加盖冷藏，面包袋口夹紧常温放，鲜菜折紧袋口放蔬菜格。酱和膏里开封要进冷藏的（`CHILL_AFTER_OPENING`）放冷藏，洋葱土豆和香蕉苹果柑橘这类常温放的（`ROOM_TEMPERATURE`）不进冰箱，其余干货、罐头、油和香料回橱柜。
- 前一晚提醒：豆浆机放豆和水、化冻。从第 1 天晚上排到倒数第二天晚上，每条写明是哪一顿。

备餐页（下一节）把这些摆成：先备齐·容器、分装、收进冰箱（冷藏、冷冻、常温三处）、早餐和晚上的事。

## 多样性

一个计划里程序查。随天数变的几项：

| | 1 天 | 2 天 | 3 天 |
|---|---|---|---|
| 红肉主菜（午晚）至多 | 1 顿 | 1 顿 | 2 顿 |
| 鱼虾至少 | 不要求 | 不要求 | 1 顿 |
| 蛋白品类至少 | 2 类 | 2 类 | 2 类 |
| 蔬菜种类（整个计划）至少 | 3 种 | 4 种 | 5 种 |

不随天数变的：

- 红肉（牛、猪、羊）：每 7 天最多 3 顿按天数折算，上限是 3 × 天数 ÷ 7 向上取整，即上表。一锅分三顿就是三顿；早餐不算。程序读主菜蛋白行食物的 `proteinCategory`：`meat` 就是牛、猪、羊（表里现在没有羊肉，加的时候同样记 `meat`），不加新字段。
- 蛋白品类：禽、畜、鱼虾、蛋、豆制品、奶、罐头杂豆，按计划里所有蛋白行算。
- 鱼虾：每周 2 次折算下来，3 天的计划 1 顿，更短的不要求；用户的忌口和买不到把鱼虾全排除时不查。罐头鱼也算，当顿现做。
- 同一样蛋白食物最多是 3 顿午晚的主菜蛋白（`SAME_PROTEIN_MAX_MEALS`）。
- 豆类：整个计划里至少一次（计划最长 3 天，等于任意连续 3 天里至少一天）。豆类是任何一顿（含早餐）里行角色为蛋白或主食、食物的 `proteinCategory` 是 `soy` 或 `legume` 的那一行：豆腐和豆制品、干豆和罐头豆、扁豆、自磨和买的豆浆，不管它是主蛋白还是配的一行，所以豆浆机早餐、豆腐汤、豆子炖菜都算。豆芽（蔬菜行）和酱油、味噌（调味行）不算。
- 蔬菜量：每天午餐加晚餐的真蔬菜（算法同入库检查，去掉洋葱、大蒜、姜、小葱和番茄碎罐头）至少 300 g，其中深色至少一半。不够时程序先补快手配菜，一天最多补两道（种子库有七道：微波菠菜拌芝麻、蒜蓉快炒菠菜、清蒸胡萝卜片、酱油四季豆、番茄黄瓜沙拉、醋拌紫甘蓝丝、生菜小番茄沙拉，动手都在 5 分钟内；配菜加在真蔬菜少的那一顿，换成用户厨具里做得出的），补了仍不够才退回，补了哪道写进给模型的 `notes`。
- 蔬菜种类：每天正餐和早餐里至少 2 种；整个计划不少于天数加 2（上限 8），上表。
- 全谷物：整个计划里，主食的份数至少一半（`WHOLE_GRAIN_SHARE`）是全谷物。主食的一份是一顿里的一个主食（主食行，或配的主食菜；一顿有两个主食就是两份），早午晚都算；豆类上的主食行不计份数。全谷物是糙米、杂粮饭、黑米、小米、藜麦、燕麦、全麦和含全谷的吐司面包、全麦面食和饼皮、荞麦面、玉米（鲜玉米、冷冻玉米粒、玉米饼皮）；白米饭、白面食、白馒头是主食但不算全谷物，土豆、红薯也不算。食物表里这一列是 `wholeGrain`（见数据模型）。
- 水果：不放进主菜、吃法和配菜里，单独成一项，列在一顿之后或当下午加餐。一天 2 到 3 份（早餐里的水果也算）；一份是一个 100 g 以上的整个水果（一个苹果、两个橘子），不按个数的按 125 g。挑放得住的整个水果（苹果、香蕉、橙子、橘子、冷冻莓果）。水果不计入蔬菜量。
- 钙：每天至少一个钙来源，早午晚、水果和加餐都算，备餐那天的晚饭不归哪一天。来源和算一个来源的克数：牛奶 200 g、酸奶 100 g、奶酪 20 g、茅屋奶酪 200 g；北豆腐、冻豆腐 100 g，豆干、五香豆干 50 g；带骨的沙丁鱼罐头 50 g、三文鱼罐头 60 g；芝麻酱 15 g；上海青、小白菜、芥蓝 100 g。一天里各样按克数折成份数相加，满一个就算。不算：豆浆（表里没有强化豆浆）、嫩豆腐（这一行也代表内酯豆腐）、豆腐皮（这一行也代表油皮）、茄汁鲭鱼罐头（来源记录没说带不带骨）、菠菜（草酸）、整粒芝麻、杏仁。食物表还没有钙这一列，所以先做成规则（`calciumSourceG`，读它的只有 `planner/checks.ts` 的 `calciumSources`）；以后按 USDA FoodData Central 这类逐行营养数据算出每天的钙，不只靠中国食物成分表，到时换掉 `calciumSources`。
- 一天的钠合计不超过 2000 mg。
- 一天的蛋白和热量都不低于目标的九成（`DAY_PROTEIN_FLOOR`；蛋白按各菜最大份量也够不到时退回）。

73 其余的整计划检查照旧：忌口、只用表里的食物。

## 整包与开封

采购单按零售整包买。易坏食材一包的量远大于一道菜用的量：一盒小番茄 250–500 g，一袋菠菜约 300 g，一个西兰花，一把香菜，一罐开了就要在几天内吃完的番茄碎或椰浆。

- 食物表的包装列 `pack`：典型零售包装克数、包装种类（盒、袋、块、盒装奶、颗、把、条）和开封后的保质天数。包装克数取中国和美国超市常见规格；开封天数取 USDA FoodKeeper 冷藏开封后的数字，有区间取低端。只给易坏食物填（保质期档 `d1-2`、`d3-5`、`w1` 的鲜品、豆腐、鲜面条、牛奶酸奶、面包饼皮）。
- 草稿交上来，程序把各顿的需求按食物累加、乘人数，向上取整成整包写进采购单，再算每包用剩多少、第一顿用到它是哪天（锅里的菜按备餐那天算）和开封后坏在哪天。
- 查的是这几样：按整包买的 `d1-2` 和 `d3-5` 食物（鲜菜、豆腐、鲜面条）。剩下的量不少于一包的 20% 且不少于 50 g，就是草稿问题，原样退回模型并点名：哪样食物、剩多少、哪天开封、哪天坏。低于这个容差的是取整的零头，不算。查之前程序自己先把整包对齐（`packFit`，解完克数再解一遍）：一样东西的用量超出整包不到 15%（`PACK_TRIM_SHARE`）时，用它的各行按比例减到整包，不多买一包——268 g 蘑菇和一盒 250 g 做出来是同一锅，多买的那盒要剩 85% 以上，锅里的蛋白已经允许为整盒挪 30%，单样食物挪一半；减完照常查蛋白、热量和蔬菜。买的包有剩，就把剩的按各顿余量分给用它的配菜和吃法的现配蔬菜（开封后、坏之前的那几顿），每顿不超过这样食物的单顿上限。分不完的，搜索再试着把它加到别的顿当配菜、换早餐和主食；只有主菜用得上的东西（见「对话」）用不完才退回，点名用它的那几顿。
- 不查：`w1` 的包（牛奶、豆浆、酸奶、面包、饼皮）一包能撑到下一个计划，剩了不算问题；食物表把无糖豆浆归成 `d3-5`（按现磨算），一升装开封后冷藏能放 7–10 天，和牛奶一样改记 `w1`（`KEEPS_OVERRIDES`）；按个买的散装蔬果（番茄、彩椒、黄瓜）按个取整，剩的不到一个，不查；`w2plus` 和 `pantry` 的食物（酱、香料、浓缩高汤膏、干货、鸡蛋、冷冻蔬菜、硬奶酪、柠檬青柠、洋葱胡萝卜土豆）不查。盒装高汤开了几天就坏，属于要查的一类，所以种子菜不用它（食物表里留着 `low_sodium_stock`）。生肉、鱼和虾不算开封易坏包装，存放见「盒与存放」；采购单上，做得比保质期晚的鲜肉鲜鱼写「买回当天分装冷冻」，买来就是冻的写「买回直接冷冻」。
- 鲜菜鲜果也查，但菜库里的小量配料（小番茄、菠菜、生菜）都是很多菜共用的，查的是整个计划有没有把一包用完。
- 采购单的用量是整包、整个、整盒，克数只在括号里写「约」：「鸡腿肉 1 盒（约 500 g）」。

配菜蔬菜的整包由程序排：同一种蔬菜跨几顿复用，一盒小番茄分在三顿，一袋菠菜分在几顿。只有主菜用得上的东西，模型照菜库里那张整包表搭配主菜。豆腐不在此列：北豆腐在中国和美国的超市都好买、便宜、蛋白高，种子库有多道菜用它；备餐锅整锅用一块（约 400 g，三份，每份约 145–150 g），现做的菜每份约 130–170 g，剩下的由计划里别的豆腐菜用掉，用不掉照上面的规则退回。拿不准一样东西会不会剩，就看它在计划里另外几顿的菜里有没有。

## 替换组

用户住在不同的国家，至少中国和美国，同一样东西在一边到处有、在另一边买不到：红腰豆、鹰嘴豆、黑豆罐头在美国欧洲超市随处可见，在中国只在进口货架上；干黄豆、干黑豆在中国好买。口袋饼、玉米饼皮、荞麦面、馒头同理。所以一样东西买不到时必须有替换。

规则：

- 能互相顶替的食物同属一个替换组。组由程序定，在 `nutrition/swap-groups.ts` 一张表里；食物表每个成员的 `swapGroup` 从这张表盖章，一个食物最多一组。
- 「买不到」「不想要」的食物由用户在对话里说，存进档案的 `unavailable`，和忌口并列，计划之外长期有效。忌口的食物不换：配料行或主食列表里有忌口食物的菜整道不可选；只在某种吃法的现配行或这种吃法的主食里有的，只这种吃法不可吃（`lib.wayBlocked`），这锅的其他吃法照旧，模型读的菜库不列它，补草稿时程序把落在它上面的那顿换到这锅别的吃法；一锅的吃法全不可吃，整道不可选。
- 忌口按名字认：食物 id、中文名（带不带（…）注）、别名、英文名都算，一个名字对上几行就全算，同一样菜的鲜品和冻品（中文名前缀「冷冻」「冻」配对，如冷冻西兰花和西兰花）算一样（`nutrition/foods.ts` 的 `foodsNamed`）。档案存用户说的那个词，查的时候展开。`update_meals_profile` 收到既不是标签、也对不上任何食物的新忌口不存，结果里点名说没记下；档案里原有的照留。
- 一道菜用了不可得的食物（配料行、吃法的现配行、主食），程序逐个换，不经模型。候选是同组的其他成员：先同梯队，再后面的梯队，最后前面的梯队，去掉同样不可得和忌口的。每个候选先算出换完的整道菜，再跑这道菜的入库检查（`checkDish`，钠也重算：罐头豆带钠，干豆几乎没有），第一个通过的就用，没通过的换下一个。
- 换算的克数：蛋白行保持原来的蛋白克数，主食行保持原来的热量，蔬菜行保持重量；行的角色优先于组的基准。豆类同时是蛋白和主食角色，按它在这道菜里的那一行的角色算。
- 菜名跟着换：红腰豆牛肉炖菜换成干红芸豆，菜名里的食物名随之换，吃法名同理。换了什么，程序写进给模型的 `notes`，模型告诉用户。
- 换成干豆时（`soak`），做法页加两步：前一晚泡豆，电压力锅煮（泡过的豆约 20–25 分钟，红芸豆必须煮透）。备餐的总时间和费事档位按加上的步骤重算。
- 食物不在任何组，或同组里没有一个成员让这道菜过检查，这道菜对这位用户不可选，草稿里用了它就点名退回，模型选别的菜。组外不换。

初始七组，括号里是组 id 和组的换算基准（都是食物表里现有的 id）：

- 罐头豆（`beans`，蛋白）：`canned_kidney_beans`、`canned_chickpeas`、`canned_black_beans`。第二梯队是干豆加电压力锅：`kidney_beans_dry`、`chickpeas_dry`，中国另有 `black_soybean_dry`（黑豆罐头的本地替代；脂肪和蛋白都高得多，按蛋白换算克数小很多）。兜底是 `frozen_edamame` 和 `firm_tofu`。梯队在组内有先后，程序先挑同梯队，没有再往后。
- 饼类（`flatbread`，热量）：`whole_wheat_pita`、`corn_tortilla`、`whole_wheat_tortilla`、`steamed_bun`。
- 面条（`noodles`，热量）：`soba_dry`、`whole_wheat_pasta_dry`、`pasta_dry`、`rice_noodles_dry`。
- 全谷物（`whole_grains`，热量）：`brown_rice_cooked`、`multigrain_rice_raw`、`quinoa_cooked`、`millet_raw`。
- 白身鱼（`white_fish`，蛋白）：`cod`、`frozen_tilapia_fillet`、`basa_fillet`。
- 罐头鱼（`canned_fish`，蛋白）：`canned_tuna_water`、`canned_salmon`、`canned_mackerel_tomato`、`canned_sardine`。
- 深色叶菜（`leafy_greens`，重量）：`spinach`、`bok_choy`。
- 其他组只在明显可换时再加，不凑数。

没有黑豆的干豆：干黑龟豆（black turtle bean）没加，食物表上限 260 要留一个空位，黑豆罐头买不到的用户走干红芸豆、干鹰嘴豆或 `black_soybean_dry`。

## 备餐页

> 状态（2026-10-27）：七段都已做（`info/meals/screen/prep-view.ts`、`prep-timeline.ts`、`MealsPrep.tsx`、`MealsTimeline.tsx`），语音见「时间线与语音」。点「做完了」只记 `planner.preppedAt`，跑着的时间线随之结束（不再计时、屏幕不再常亮），`prepRun` 留在计划里；规划器排的那几顿还没有旧的 `pots`，做法页不写取盒热透。
>
> 入口：Meals 页顶部的备餐卡和手机首页的 Meals 磁贴（`screen/batch-cook.ts` 一份状态：没计划时「Plan a batch cook」，备餐没做时写哪天哪个时段、动手和总共分钟、点开进备餐页，做完以后写下一顿，计划吃完了「Plan the next batch cook」）。规划对话里点 Apply 以后直接进备餐页，计划没有备餐就落到 Meals 页。

计划里备餐那天的日卡上有一行备餐卡（「备餐 · 下午 · 动手 72 分 · 共 95 分」），点开推到备餐页，手机是导航栈的一层 `meals-prep`，带这次备餐的 id。顶栏是返回、「备餐 · 周日 11/1」、动手和总共分钟；开始以后加预计几点结束。从上到下七段，整页没有勾选框：做饭的人腾不出手。

1. 这次做什么：一锅一张卡，菜名，做法和设备一行（「电压力锅 · 高压 15 分」），菜系标签，配料小图条（73「图片」兜底那排），吃它的几顿（做的那顿标「当顿」），每份蛋白和热量。这锅米饭是窄一些的卡：几份、什么时候煮、分给哪几顿。
2. 先备齐·容器：这次几锅的配料合并成一张单，按组（肉和蛋、蔬菜、罐头和干货、调味），每行是名字、给哪道菜、几盒或几个（见「给用户看的量」）、一句备注。单后面列要备的容器：食盒几个、或有盖大容器几个，装饭的有盖容器，冷冻袋几个。
3. 时间线：见下一节。
4. 分装：装盒才出，一顿一个格子：哪顿、盒里有什么（锅里那一份，主食是这锅米饭时加上饭）、吃时现配什么（蔬菜、米饭以外的主食）、吃到哪顿前。做的那顿当顿吃不装盒。
5. 收进冰箱：分冷藏、冷冻、常温三组。冷藏组开头一句「晾到不再冒热气，2 小时内盖好放进冷藏」，然后是锅（盒或大容器）、米饭、原包装的生肉生鱼、开封易坏的包装和用完日、开了的酱；冷冻组是分装的生肉生鱼、剩量和买来就冻的；常温组是橱柜里的和不进冰箱的蔬果。
6. 早餐和晚上的事：第二天早餐用豆浆机的写「放哪几样干料，加水，定好时」，用量杯或勺，不称重，水加到机器的水位线（通常一小把干豆对应约 300 ml）；要从冷冻拿到冷藏的鱼与肉，按晚列出。这几条和备餐页的语音分开，不开语音。
7. 做完了：点了以后通话结束，计划里这几顿改成「吃备好的」，那几顿的做法页按 73 写取盒热透。没点也照计划算做了（73「计划就是记录」）。

## 菜品图

菜库自带的菜有预先画好的图：批量主菜每种吃法一张，现做主菜一张（配它的第一个主食），早餐一张，共 226 张。id 是 `<菜>--w<第几种吃法>-<主食>`（吃法不配主食写 `plain`）、`<菜>--<主食>`、`<菜>--breakfast`，清单在 `info/meals/photos/dish-art-ids.ts`。

图不进安装包，放在单独的公开仓库 Einstellung/lumen-assets 的 release `dish-art-v1` 附件里（主仓库将来转私有）：`https://github.com/Einstellung/lumen-assets/releases/download/dish-art-v1/<id>.webp`，768 px WebP，质量 88，平均 60 KB，共 13.9 MB。同一个 tag 下的文件不改；换图就发新 tag，同时换代码里的 tag 和清单。

一顿饭按 `searchName`（吃法或菜的英文名）找图：批量主菜按吃法，现做主菜和早餐按菜。食材被替换过的菜名字跟着改了，找不到图，照旧显示。第一次显示时下载，走 Tauri http 插件（和应用其他二进制下载同一条路，不受 webview 的 CORS 和 CSP 管），存到 `meals-art/<tag>/<id>.webp`，以后只读盘。缓存每台设备自己下，不同步。release 上没有的图这次运行不再请求；连不上的下次刷新再试。

卡片上先用菜库图，没有再用模型画的图，都没有就是配料图条；下载失败或还没下完也是图条。菜库有图的菜不再交给模型画。

步骤在后台提前写，时机、失败退避和当场补写都照 73「做法页」：每次备餐一份，输入是这次几锅的菜、解好的份量和厨具，模型交每步一句话、属于哪个设备、动手分钟、等待分钟、要等哪几步做完才能开始。一台设备被前一锅占着时，后一锅不用这台设备的动手活（煎肉上色、炒香料、调酱）放到灶上或台面上趁等的时候做，设备一空就直接下锅；值不值得多刷一口锅、这道菜要不要这步由模型判断。模型不写钟点、不写分装和存放；最后那步（分装或收冰箱、晾凉）由程序写。存在 `info-meals-recipes.json` 同一张 `recipes` 表里，条目带 `kind: "prep"`，键是这次的锅、每锅的克数、米饭、厨具、灶眼数和语言的哈希（`prepStepsKey`）。整份回复有一步不合格就整份不收，留着上一份。步骤写好以后，各处显示的动手和总共分钟改用时间线的（`timelineMinutes`，含程序那步）；没写好之前是同一个排程器按每锅一步、菜库分钟估的（`planner/prep.ts`）。

## 时间线与语音

> 状态（2026-10-28）：已做排程、步骤写手、进度状态（`info/meals/timeline/`、`recipe/prep-steps.ts`、`prep-progress.ts`）和界面：备餐页第 3 段的提交图（`screen/prep-graph.ts` 算、`MealsTimeline.tsx` 画，开始以后每分钟重读一次）、跑着时顶栏下的「现在」卡、「开始备餐」、每步的「开始了」「做完了」「慢了 +5 / +10 分」、顶栏的结束钟点、跑着时屏幕常亮。备餐页打开时步骤还没写就当场写（chat 档），写的时候其余几段照常显示；步骤写好以后 Meals 页的卡片、日卡的备餐行和手机磁贴都用时间线的分钟。语音也已做（2026-10-27，分支 `meals-prep-voice`）：三餐对话的 `start_prep`、备餐页的「开始备餐」都开三餐线程上的通话（已在通话里就沿用那通），跑着时前台多 `prep_step`、`prep_say`，「所在地方」带步骤清单，到点提醒走前台的 `say`（念程序拼的句子，不经模型），挂断后「接回语音」，通话和备餐页共用一把常亮锁，`meals-prep` 卡片开始时放进三餐对话、每个事件原地换。设备不能语音时开始照走，页面一行说明。没验：真机出声和收音、WKWebView 里的常亮、前台模型会不会按说明调这两个工具。交接见 `docs/research/meals-timeline-handoff.md`。

程序排时间线：一个人一双手，动手段不重叠；一样设备同时只做一件事，灶台按档案里的灶眼数；等待段里手空出来做别的；就绪的步里先排后面挂着的链最长的。

界面照 `git log --graph` 画：左边每口锅一条轨（`step.pot`，饭也算一口），右边是字，窄屏优先。轨按第一次动手的先后排，短名从锅的菜名取（主料的头一两个字，重了取最短不重的前缀），饭用 i18n 的短名，颜色是 `styles.css` 的 `--rail-1` 到 `--rail-5`。`pot` 为空的步（洗锅）落在它后面那步的轨上；`after` 来自别的轨就画一条汇入曲线，meta 写「汇入 鸡 → 牛」。程序加的装盒步落在最后结束的那条轨上，把其余轨全部汇入。

有动手时间的步是一个提交，按开始先后编号，点越大动手越久。只等不动手的步不编号，挂在前一个提交下面写「接着：等 15 分，到第 41 分」，它的按钮也在这一行。线型三种：手在这口锅上是实线，锅自己走是斜纹，锅停着等别的锅是点线。锅做完的地方画一道封口，那一步后面挂「<菜名>完成」，整张图在最后一步下面封口。手换到另一口锅时，那一行上方是「手转到：牛」小标签加一条虚线箭头。手空的时段单独成一行（最矮 64px）：「手空 12 分，可以走开」（不到 5 分只写前半句），下面写后台每口锅几时好、几时回来做哪一步。不弹详情，全文照写。

跑着时顶栏下面多一张「现在」卡，和顶栏一起吸顶：第几分和钟点、手上在做哪步还剩几分（手空就写可以走开）、后台每口锅的状态（还剩几分、停着几时接着做、几时开始、好了）、下一次动手是哪步、几分后。顶栏那行的「HH:MM 结束」不变。

开始之前只有时长：每步写「第 N 分」和「动手 N 分」「等 N 分」，图上的时刻也是分钟，没有钟点。用户点「开始备餐」，或对卢明说「开始备餐」（三餐对话的工具 `start_prep`），程序记下开始的时刻，从这一刻起所有步骤、手空行和「现在」卡换成钟点。

开始的同时开一通语音（68 的通话形态），挂在三餐那条常驻对话上，每句写进这条对话，`focus` 是这次备餐；已经在通话里就沿用这通。通话一直开到「做完了」，期间屏幕常亮（`platform/app/wake-lock.ts`）。备餐页留在屏幕上，用户对着角上的卢明说。中途挂断，时间线照走、到点不出声，「开始备餐」的位置换成「接回语音」。

前台（136 的 `voice-front`）在这通电话里多两个工具：

- `prep_step({ step, event, minutes? })`：`event` 是 `done`（「切完了」）、`started`（「开始煮蛋了」）、`more`（「我慢了，还没切完」）。`more` 时用户说了几分钟就带上，没说程序按 5 分钟算。
- `prep_say({ what })`：`next` 下一步、`now` 现在该干什么、`left` 还要多久。句子由程序从排好的时间线拼，走 136 `read_out` 那条路直接进 TTS，不经模型。

前台上下文里「所在地方」那一段是这次备餐的步骤清单：编号、一句话、设备、状态（做完、在做、在等、没开始），不带钟点和分钟。编号和页面上的一样（`timeline/numbers.ts` 一处定，页面、语音、对话里的卡片共用）：只给有动手时间的步编号，只等不动手的步写成它所挂那一步下面的「after N:」行。`prep_step` 收到编号 N，记在 N 和它下面那几个等待里第一个还没做完的上：第 3 步动手做完、锅在泄压时说「3 好了」，记的是泄压那一步。

程序每收到一个事件就把剩下的步重排，写进这次备餐的状态，再用 `patchPart` 按 id 原地更新卡片：这次备餐在三餐对话里是一张卡（kind `meals-prep`，id 是备餐 id，开始时放进去），备餐页和卡片读同一份状态。当前步高亮，做完的变淡，钟点跟着重排变。动手步超了预计时长不自动算完，后面的步跟着顺延。等待步由程序计时，到点自动算完，程序在下一个空档念一句「压力锅到点了，下一步……」：只等自己和用户都没在说，不等 136 的 2 s。除此之外卢明不主动开口。

## 事实不经模型

程序算：入库检查的每个数、冷藏天数、每份克数、备齐清单的量、时间线的排法、开始以后的每个钟点、还要多久、到点提醒、分装格子和怎么放。模型交：选哪道菜、改比例、新菜的配料、步骤的文字和时长估计、进度事件。日子照 73 按编号交，从不写日期和钟点。

## 数据模型

食物表加列：深色蔬菜（`deepColor`，深绿、红、橙、紫色的蔬菜）和香料酱底（`aromatic`，洋葱、大蒜、姜、小葱、大葱、番茄碎罐头，入库检查不把它们算作真蔬菜），每 100 g 的钠（台湾库「鈉」、USDA Sodium、调味品标签），蛋白品类，不宜冻，加糖，蔬果按个数的每个克数（只给清单显示，不参与取整）。另有三列：包装 `pack`（`{ grams, kind, openDays }`，只给易坏食物填，见「整包与开封」）、全谷物 `wholeGrain` 和钙来源 `calciumSourceG`（见多样性）、替换组 `swapGroup`（见「替换组」）。加糖：调料取同一来源的总糖，来源没有糖数的取碳水，蜂蜜、味醂、白糖取碳水，单一香料记 0。新列在 `nutrition/food-columns.ts`（替换组表在 `nutrition/swap-groups.ts`），复合调料在 `nutrition/seasonings.ts`，菜库要的其他食物（盐、柠檬、青柠、低脂椰浆、扁豆、番茄碎罐头、干鹰嘴豆、干红芸豆、低钠高汤（盒装，种子菜不用）、浓缩高汤膏、菲达奶酪、玉米饼皮、面包糠、芝麻、鲜香草、玉米淀粉、干黑豆、干红豆、干红枣、冷冻龙利鱼）在 `nutrition/added-foods.ts`，生成的 `food-table.ts` 不动。菜的类型、做法类别、存放、参考份和入库检查在 `src/info/meals/dishes/`。

菜名给中文读者看得懂：外国菜用说明做法的中文名，通行的外文名放括号里，如美式牛肉黑豆炖菜（chili）、意式番茄炖牛肉块，不音译不硬译（chili 不叫辣酱）。

不用成品肉末：成品绞肉不知道是哪个部位、含多少脂肪，保质期只有一两天，撑不过一锅吃三顿。种子库的菜用整块肉切块、切片、切丁或炖软撕开；肉丸、肉糕、kofta 这几道用整块瘦肉当天现绞，现绞完当天做熟，做好后的存放照菜算。

豆浆机早餐不单设类型：豆浆是配料行加水，行上写干料的克数（黄豆 25 g、燕麦 15 g、核桃 8 g），水不是一行（水没有营养），营养由干料和食物表算；整豆浆不滤渣，干料的营养全部算进这一份。装备值是 `soy_milk_maker`，在默认厨具里；这类早餐的装备写它，做法类别按早上那一步（组装或煮蛋）。

滑蒸：蒸鸡用鸡腿肉，或鸡胸肉切薄片；肉片拌酱油、姜蓉和少许淀粉再蒸，鸡胸蒸 8–10 分钟。不收整块白蒸的鸡胸，概述里要写切薄片和淀粉，单测守着。

鱼和虾的种子菜：用无刺、味道温和、美国好买的冷冻白身鱼片（鳕鱼、鲷鱼、龙利鱼，即 basa）、三文鱼、冷冻虾仁和罐头鱼，都是现做；不收扇贝、蛤蜊、带鱼、鱿鱼（腥、难处理或不好买）。任意两道鱼虾菜的主菜蔬菜搭配不重复，番茄加西葫芦最多一道，单测守着。罐头茄汁鲭鱼和油浸沙丁鱼各有一道不开火的菜，便宜、ω-3 高。龙利鱼的数据取自 USDA FDC 的品牌记录 2099832（SR Legacy 和 Foundation 没有 pangasius，记录里只有鱼一样配料）。

种子菜库在 `src/info/meals/dishes/seed.ts`。用户自己的菜在 `info-meals-dishes.json`，按菜 id 走 records 合并。

    Dish {
      id, name, nameEn,
      summary, summaryEn,   // 一句话怎么做，中文不超过 40 字，审阅页和菜卡上显示
      role: "main" | "breakfast" | "staple" | "side",
      cuisine, method, equipment[], activeMin, totalMin,
      prep: "batch" | "fresh", staples: foodId[],   // 只有现做的主菜有
      ingredients: { food, grams, role, ground? }[],   // role: protein veg staple oil seasoning fruit topping；ground: 这块肉现绞，只有肉和禽的蛋白行能标
      ways?: { name, nameEn,   // 菜的简称加吃法，读起来是一顿饭：牛肉黑豆炖菜盖糙米饭
               staple: id | null,
               addOns: { food, grams, role }[],   // veg fruit topping，按一份参考份
               activeMin }[],                     // 能备的主菜 2..3
      origin: "seed" | "user", createdAt
    }

草稿在 `src/info/meals/planner/draft.ts`，不带克数也不带日期，天从 1 编号。模型交的只有主菜、锅、备餐，和用户点名的早餐；`breakfast` 空、`sides` 和 `fruit` 空的地方由 `fillDraft` 补齐：

    PlanDraft {
      days: {                                  // 1..3
        breakfast: dishId,                     // 模型只在用户点名时写
        lunch, dinner: {
          main: { batch: batchId, way: 1.. }   // 吃某一锅的某种吃法
              | { dish: dishId, staple?: foodId | dishId },   // 现做的主菜；staple 由程序挑，用户点名时模型写
          sides: dishId[]                      // 程序补
        },
        fruit: foodId[]                        // 程序补，一个 id 一份
      }[],
      batches: { id, dish, session, meals: { day, slot: "lunch" | "dinner" }[] }[],   // meals 1..3；day 0 只有 dinner
      sessions: { id, day, part: "morning" | "afternoon" | "evening" }[],             // 至多 1 个；day 0 是备餐日
      prepDinner?: { main: { batch, way }, sides }   // 备餐日的晚饭，只在第 0 天上午或下午备餐时
    }

`checkDraft` 先查结构（菜在不在库里、角色对不对、锅和备餐的关系、冷藏窗口、厨具），再解克数、补快手配菜，最后查多样性和整包，问题一条一句英文、点名规则，带离通过还差多少（`over`）。`fillDraft` 拿它当判据补草稿，补不齐的问题改写成点名模型选项的那几句退回。

计划在 `info-meals.json`，存成 73 的 `WeekPlan`，日卡、采购单、做法页照旧读：每个计划日一个 `DayPlan`，每顿是 make，带解好的克数（`items` 和 `solved` 相同），吃锅的那顿用吃法名。有 `prepDinner` 时，备餐日也存一个 `DayPlan`，只排晚饭（`planned: ["dinner"]`），早饭午饭和加餐是 skip，日卡只显示晚饭、不算当天的营养；旧计划正好有这一天时只换掉它的晚饭。`startDate` 是存下的第一天，`planner.start` 仍是第 1 天。草稿跟着存在 `WeekPlan.planner`（`{ start, draft }`，`planner/to-week.ts`），取代 73 的 `pots`。新计划顶掉旧计划里从它第一天起的日子；旧计划的最后一天正好接上新计划时，前面的日子留着，`id` 和 `startDate` 沿用旧的，否则整份换掉。

改档案时用这份草稿走同一套核心重解（`resolvePlannerWeek`），偏离过的顿（不是 make 的）原样留着。新档案拒掉了草稿里的东西（新加的忌口或买不到），程序从当初的选择重补一遍（`planner/redraft.ts`：模型的主菜、锅和备餐，卡上存的 `picks` 里点名的早餐、主食和 `asked`；`planner.picks` 跟着存，之前的计划没有就让程序重挑早餐和主食）：补得过就写新草稿，结果里逐顿列出改了什么；补不过（模型挑的主菜本身有它）就保持原样，结果里按日期列出哪几顿还有它，只有新草稿能换。`plan/` 不 import planner，`planner.draft` 存成 unknown，读回走 `parseDraft`；读到不合格的 `planner`（缺 `start`，或 `draft` 没有 `days`）只丢这一项，日子照读。之前排的周没有 `planner`，照旧读，照旧用周解算器重解。

备餐进度存在 `WeekPlan.planner.prepRun`（`{ key, startedAt, steps }`），跟计划一起同步，不加 `revision`。`key` 是它跟着的那份步骤，步骤换了旧进度就不认。每步记开始、动手结束、整步结束，以及「还要几分钟」说出来的动手或等待截止，都是从开始算的分钟；状态（做完、在做、在等、没开始）和钟点每次读时从这几项和排程算出来，不存。做完仍是 `preppedAt`。整个文件后写者赢，两台设备几乎同时点会丢掉一边的那一下；现在只有一个用户，先这样。备餐页回到前台时重读计划，另一台设备上的进度这样显示出来。

档案（`Profile`，`update_meals_profile` 写）加四项，都可缺省，缺省是没说过：

- `cookSlots`：能做饭的时段，`{ weekday: 1..7（周一为 1）, part: morning | afternoon | evening }[]`。morning 在午饭前，afternoon 在晚饭前，evening 在晚饭后。
- `boxes`：装不装盒。
- `burners`：灶眼数。
- `unavailable`：买不到或不想要的食物 id，和忌口并列，见「替换组」。

冷藏天数、检查结果、存放计划、钟点都不存，读时算。

- 不能出声的设备怎么报进度。
