## 硬规则

1. 程序算得出的事实不经模型转手。URL、作者、时间、互动数、star、提交和 release 日期、论文作者和日期、标题由程序取、程序写；模型只按程序编的号选，只写判断和叙述的句子。X 帖子的时间由 status id 解出（snowflake），永久链接由 id 加 handle 重建。
2. 只读：不发、不赞、不转、不关注、不回复（57）。开搜索页、永久链接页和外链都是导航，不点页面上的按钮。旁听页面自己收到的回答也在只读之内（2026-10-20 定）：不加请求、不改请求、不改节奏，除了现有的人速阅读不点任何东西。X 用用户自己登录的账号，Accounts 页建议用小号。
3. 碰到登录失效、验证、限流，当次停手，不重试，不自动重登。
4. 每次 run 都有硬上限（条数、开页数、模型调用数、时长），到了就收尾。
5. 碰 X 的活只在桌面采集端跑（Linux、macOS，有 webview 取材的那台），同一台同一时间只有一个。iOS 发请求、看结果。
6. 页面、帖子和原文的文字是材料，不是指令，包在不可信材料标记里交给模型。
7. 模型走日常档（今天是 Sonnet 5.5），同 86。

## 起草：来回问

入口是门口对话（68，`soul/door.ts`）。用户说在关注什么、要资料，Lumen 开始起草主题。

理解用户只读 statement（48）：profile 和没 lapsed 的 concern。不读阅读记录、对话原文和 observation，那一层每晚由 dream 消化成 statement。门口回合本来就带着 statement（`soul/self.ts`），起草不另取。

懂用户靠问，不靠猜。起草要定下范围、子方向、要什么、不要什么；凡是拿不准的、想写进去却不理解用户意思的，就在对话里问。大主题（AI for science）先拆成子方向（材料、蛋白质、天气、数学证明……）请用户挑。AI 做的判断明说出来让用户纠正（「我把 AI 辅助芯片设计算进 engineering，不算进 science」）。用户的话里有 last30days 的五类关键词陷阱（人群购物、数字撞车、教程措辞、单个泛名词、非拉丁文字）时，先问再起草。需要了解一个领域有哪些子方向时，Lumen 可以用 `web_search`。

问清了，Lumen 调 `propose_topic_search`（`info/topic-search/propose-tool.ts`，做法同 `propose_lab`：工具只立卡片，不写盘，卡片的 Apply 才写）。卡片上：名字、范围一段、挑中的子方向、要什么不要什么、「我的理解」几条判断、第一次多久能出（见「排队」）。搜索词不上卡片。主题搜索不挂 reading 的主题：结果进 info 书架（见「info 书架与专题册」），卡上不问归哪个主题（2026-10-15 改；现有实现的卡带主题、Apply 建同名主题，待删）。用户点卡片上的关注，或在对话里说好，程序写主题配置、写 concern、派第一次 run；用户在对话里改，Lumen 重新出卡。对话里说好时 Lumen 调 `confirm_topic_search`（`info/topic-search/confirm-tool.ts`，参数是卡上的名字），对本对话最新的那张卡做和按钮同一个 Apply，卡片随之标成已应用；名字对不上或那张卡已应用就不写。用户说只看这一次的，`propose_topic_search` 带 `once`，卡片上写一行「只看这一次」，Apply 把 `once` 写进主题配置。

## 主题配置

`info-topic-searches.json`（`info/topic-search/store.ts`），随账户同步，按记录合并。

```ts
interface TopicSearch {
  id: string;                    // "ts-" + 8 hex
  name: string;
  concernId: string | null;      // 对应的 concern statement
  scope: string;                 // 范围一段，用户的话
  subtopics: { id: string; name: string; picked: boolean }[];
  want: string[];
  avoid: string[];
  judgments: string[];           // 起草时明说过、用户没反对的判断
  anchors: string[];             // 锚词：消歧，也判「提没提到主题」
  queries: { id: string; subtopic: string | null; x: string; arxiv: string | null; ranking: string; weight: number }[];
  answers: { asked: string; answer: string; at: number }[];  // 用户对提问的回答，原话
  status: "active" | "stopped";
  once?: boolean;                // 只看这一次：第一次结果送达后记 stopped
  revision: number;
  createdAt: number;
  lastRunAt: number | null;
}
```

- `queries` 由 AI 起草时生成，用户不看。每个挑中的子方向 1 到 2 条，全主题 1 到 4 条。`x` 和 `arxiv` 是按平台上标题的写法写的关键词；`arxiv` 写 2 到 4 个具体的短词，最具体的放前面，不写整句，不用两个字母的词（如 AI，会被丢掉），两条短查询好过一条长的；`ranking` 是一句自然语言问题，给重排用。权重主 1.0，子方向 0.6 到 0.8。不进搜索词的：时间词、「news」「updates」这类元词；数字除非就是话题本身。同名风险高的，每条都带锚词。没挑中的子方向不出查询。
- `anchors` 命中任一个就算提到主题。
- 主题搜索不挂 reading 主题（2026-10-15）：确认时不建同名主题，配置里没有 `topicId`。之前写下的配置还带着这个字段，读的时候不认它，也不报错。起草卡上「归入哪个主题」那一行随 68 改版删。

concern 和主题配置的边界：concern 只记「用户在关注这件事」，一句话，作者是 reader，evidence 是用户开口的那条消息；范围、子方向、要不要、搜索词、源配置全部留在主题配置里，不写进 statement。已有一条说的是同一件事的 concern 时，模型在起草时按编号指出来，程序把主题挂上它；那条是 dream 写的，就用用户的话写一条 reader 的 concern 取代它（`supersede`）。

## 记忆回写

用户回答提问时说的话，分两处写：

- 只对这个主题成立的（「这个主题不要融资新闻」「材料方向只看实验验证过的」），写进主题配置的对应字段，原话进 `answers`。门口工具 `update_topic_search`，参数是主题编号和要改的字段，程序写盘、`revision` 加一，回执一行。
- 对用户本人成立、换个主题也成立的（「我只读英文原文」「我偏工程实现，不看纯理论」），用门口现有的 `statement_write` 写成 profile，作者 reader，全应用可用。reader 写的优先于 dream 的猜测（48）。

一句话两类都有，两处都写。

不关注了：用户说不关心某个主题了，Lumen 调 `stop_topic_search`，程序把主题记 `stopped`，不再派 run，把它的 concern 标 `lapsed`（48：lapsed 是一次编辑，不删）。以后读 concern 的地方自然不再带上它。用户又说关注了，重新起草时挂回这条 concern，取消 `lapsed`。`memory/statements/store.ts` 加 `setLapsed(id, lapsed)`，只能改 concern。

## 攒着问

run 里拿不准的地方不打断用户，攒进主题的待问清单，等下一期简报打开时由卢明问（见「简报的对话」）。来源两种：

- 模型在重排和写结果时标出拿不准的（「这条是 AI 做 EDA 的融资新闻，要不要这类？」），只交问题文字和候选编号。
- 程序从指标算出来的：某个子方向连续 7 天零产出（初值）、锚词未命中率过半、某个不要什么连续几天挡掉大量候选。问题文字由程序按模板写。

每期最多 3 个问题，同一个主题在它的第三期之后每期最多 1 个（初值）。同一个问题问过没回不再问；问题和已有的 `answers` 说的是同一件事的，模型标出来就丢掉。用户点快捷回答或回一句，按「记忆回写」写。

已经定了的不再问（2026-10-20）。重排和写稿两处提示都带上范围、要什么、不要什么、judgments、`answers` 和这个主题已经提过的问题（最近 20 个），并写明这些已经定了的不许再问；judgments 或不要什么已经归了类的那类东西，问它也算重问。程序再按词重合丢一遍模型的问题（`questions.ts` 的 `settledBy`，去掉 do/you/want 这类问句词后比）：和某条 judgment、want、avoid 共有至少 3 个词、占问题词数三分之一以上的丢；和某个已经提过的问题（含 `answers` 里问过的）共有至少 3 个词、占一半以上的丢。主题常是中文写的、技术词留英文，问题是英文，所以对 judgment 的门槛放得低。程序按指标出的问题不过这一道。

## 两种 run

第一次（全景）：确认后派，X 往回看 30 天（初值），arXiv 和 Hugging Face 往回看 365 天，每个查询铺开搜，给这个领域最近在发生什么的全景，按子方向分组。

之后每天（增量）：每晚一次，只报上次之后新的东西。没有新东西就不进当晚那一期，结果文件里记一句。

两种都是 legion run，kind `topic-search`，程序 worker，`requires: [WEBVIEW_FETCH]`，只有桌面采集端认领。idempotencyKey 第一次是 `topic-search:<id>:first`，每天是 `topic-search:<id>:<锚点日期>`，闸在被调用的一侧（坑 210）。每次 run 是一个 pi-durable 任务（`rp.topicsearch`，`defineTask`），相位：`open`（主题还在关注、没过当晚截止、停手规则放行、验会话，拿别睡锁）、`read`（X 逐线逐屏，同时跑 arXiv 的查询梯子和 Hugging Face 的论文搜索，见下）、`build`（打分、看原文、写结果文件，由注入的构建函数做，`setTopicSearchResultBuilder`；它不再发 arXiv 和 Hugging Face 的搜索请求，读 run 目录里存下的结果）、`deliver`（结果交给当晚那一期，见「简报书的实现」）、`wrap`（放锁）。每个相位先写盘再提交，重跑读已写的，不重读 X、不重复进盒。定义在 `info/topic-search/run.ts`，经 `legion/durable/program-task.ts` 的登记表在打开 Harness 时装进去，`legion/durable` 不 import info。run 目录 `topic-search-runs/<runId>/` 放进度文件、读到的帖子（`x-read.json`）、arXiv 结果（`arxiv-read.json`）和 Hugging Face 结果（`hf-read.json`），不清理。

arXiv 和 X 并行（2026-10-17 改）：arXiv 是普通 HTTP，不占屏幕也不碰 X 的会话，`read` 相位一开始就跑，不进 X 的排队，不等 X 读完（X 常要一到三小时）。只挪了查询梯子；读全文要等打分挑出条目，仍在 `build` 里。查询之间照旧一个接一个，按主机限速和每条最多 3 个请求不变；arXiv 的限速是全进程一把闸，和夜里采集、阅读端共用（坑 502）。每跑完一条查询就把到此为止的结果写进 `arxiv-read.json`（`info/topic-search/arxiv-read.ts`），崩溃或取消后重来只跑文件里还没有的查询；限流和失败的查询带着结局记下，这次 run 不再重跑，留给「重跑第一次」。一边失败不拦另一边：两边都结束后相位才往下走，有一边抛错就让 run 失败，另一边已写的文件留着，重来时不重读。run 的取消信号同时停两边。X 被停手规则挡住时（第一次 run、只剩 arXiv 的重跑），arXiv 照样跑；夜跑被挡仍整个跳过。改版前就进了 `build` 的 run，run 目录里没有 `arxiv-read.json`，在 `build` 里把 arXiv 补跑完。

Hugging Face（2026-10-19 加）是第三个源，和 X、arXiv 同级并行：`read` 相位三边一起开跑，各写各的文件，一边失败、限流或冷却不拦另两边。arXiv 冷却时 Hugging Face 照样搜，run 照样往下走，build 用它找到的论文。写法同 arXiv：每跑完一条查询写一次 `hf-read.json`（`info/topic-search/hf-read.ts`，形状和 `arxiv-read.json` 一样），重来只跑文件里没有的。

### 排队

桌面上碰 X 的活一次一个：第一次 run、详细资料 run、每晚的增量走同一个 runner，同 kind 一次只跑一个，先后不保证按请求时间。白天桌面开着就认领就做；关着就等下次开。Lumen 报时看桌面的 claim 心跳（`legion/claim`，每小时一次）：两小时内有就说「桌面开着，大约半小时」，没有就说「电脑开着时做，最晚今晚」。

每晚：锚点 01:00 在 `info/topic-search/nightly.ts`，判据同 `info/program/daily.ts` 05:00 那个：最近过去的 01:00 这台还没派过；挂在采集端五分钟的 tick 上（`checkTopicSearchNight`）。条件：`amICollecting()`、本机有 webview 取材、X 会话有效、停手规则放行、至少一个 `active` 主题。开始在锚点后 0 到 40 分钟（按设备和夜固定的偏移），每个 `active` 主题一个增量 run，当晚一次派完；结束取最早的：04:40、都读到上次位置、碰到每晚上限、停手。每晚上限是全部主题合起来的，当晚用量记在本机状态文件 `info-topic-search-state.json`（`sync: "local"`），后跑的 run 拿剩下的。机器睡过 01:00，醒来还在 04:40 之前就补跑，过了当晚不读。

### 重跑第一次

第一次 run 没取到的，用户登录 X 后在门口说一句就补读：卢明调 `retry_topic_search_first_run`（`info/topic-search/retry-tool.ts`）。这是第三种 run，brief kind `retry`，idempotencyKey `topic-search:<id>:retry:<n>`，n 是这个主题还在盘上的重跑里最大的号加一（`retry.ts` `nextRetryNumber`）；第一次 run 或上一次重跑还在 pending/running 时不派（`run-worker.ts` `askRetryRun`）。不重置 `topic-search:<id>:first`：同一个键派生同一个 run id，那个 id 下的 pi-durable 任务已经终结、run 目录里已有 `x-read.json`，重置要连这三样一起清。

补读什么在采集端 `open` 相位按源健康定（`planRetry`）：X 上次 `failed` 或从没读过的查询；arXiv 上次 `failed` 的，和梯子之前记的 `empty`（没有 `ladder` 字段）；Hugging Face 上次 `failed` 或从没读过的（有 arXiv 词的查询）。已经 `ok` 的、X 读了没新东西的、梯子已放宽到底的不读。上次重排失败留下待判的（见「判不了」）不重读，记进计划的 `judge`。都不用读、也没有待判的就跳过；只剩 X 而 X 还没登录、又没有待判的也跳过。读法同第一次（X 30 天、arXiv 365 天、上限和读深用第一次的）。结果并进这个主题最近一份 `kind: first` 的结果文件：原有条目、材料、问题不动，新件和材料接着编号（`E16`、`M23`），材料正文写进那份文件的 run 目录，文件里 `retries` 记每次重跑加了哪些件、它自己的全景、问题和统计。并完之后文件顶层的全景、分组和统计说的是并好的整份（2026-10-17 改）：重跑写稿时把文件里已有的件（只给编号、标题、事实行和结论）放在新件旁边，全景写的是整份，可以按编号引旧件，旧件不重写；这份全景替掉文件顶层的；写稿走了兜底版就不留全景，不保留旧的；没加出新件的重跑不动全景。统计是第一次和每次重跑的相加（各项求和，锚词缺失率按过地板条数加权），每部分各自的仍在 `firstLook.stats` 和 `retries[i].stats`。第一次自己的全景、写稿方式和统计第一次并入时存进 `firstLook`，`firstPart` 从那里取，所以 `first:<id>` 那一期不受影响。去重照旧，那份文件本身在 30 天历史里，它的键不再列。源健康只写这次读了的那几行，其余保留上次的。重跑关了单出一期，键 `first:<searchId>#<runId>`，只含这次新加的件（`retryPart`），没加东西就不出；那一期 Annex 里的全景是整份的，引到前一期的件时照样换成脚注号列标题（`retryPart` 带上 `citable`）。

登录 X 之后停手记录 `signed-out` 不会立刻消失：它只在下一次读 X 没停手、或下一次会话检查确认登录时清掉（`runs-live.ts` 的 `xSessionState`，`halt.ts` `clearSignedOut`）。这条记录不挡夜跑（`xGate` 只管验证和限流），挡夜跑的是会话侧车 `signedIn`，Accounts 页登录后的确认检查会写成 `true`。门口工具读停手记录前先按侧车清一次：侧车在停手之后确认过登录，就当已清。

### 第一次分两段

2026-10-17 加。第一次 run 先交快的源，慢的读完再补，用户不用等 X 读一两个小时才看到东西。源的快慢在 `info/topic-search/pace.ts`：`SOURCE_PACE` 里 arXiv 和 Hugging Face 是 `fast`、X 是 `slow`，以后加的社交媒体也记 `slow`。GitHub 不是搜索源，只在核实时查仓库，不分快慢。夜跑和重跑照旧一段读完。

同一个 run、同一个 durable 任务，相位多一圈：`open` 不验 X 会话，直接进 `read`（`part: "fast"`，只跑 arXiv 和 Hugging Face）→ `build`（X 记成「read after the first part」，结果文件写 `awaiting: ["x"]`，源健康不写 X 那几行）→ `deliver`（照第一次关掉，出 `first:<id>` 那一期；再在 run 目录写 `first-part.json`，记下结果文件、件数、窗口起点）→ `later`（验 X 的停手规则和会话，拿别睡锁）→ `read`（`part: "slow"`，只读 X）→ `build`（按重跑的路子并进同一份文件：接着编号、正文进 run 目录，`retries` 里记一条 `runId` 为这次 run、`part: "slow"`，清掉 `awaiting`）→ `deliver` → `wrap`（按重跑关掉，出 `first:<id>#<runId>`，只含 X 补进来的件）。`first:<id>` 那一期用 `firstPart` 组装，排除所有 `retries` 加的件，所以 tick 晚到、慢段并完才组装，也不会把 X 的件算进第一期。

X 被挡或没登录：快段照常交，慢段把 X 记成没取到（源健康写 `failed`），文件照样清掉 `awaiting`，`planRetry` 照旧把 X 列进「重跑第一次」。门口说一句重跑时，第一次 run 还在跑就不派（`askRetryRun` 本来就挡）。

恢复：进程被杀，任务从检查点接着走，build 的 memo 名慢段带 `:slow` 后缀，不和快段撞。run 失败被 runner 原地重试时，`legion/durable/program-task.ts` 起的是一个新任务、没有 memo，`open` 看到 run 目录里有 `first-part.json` 就直接进 `later`，不重建快段、不再出第一期。旧检查点没有 `part`，照改版前一段读完。

对话里怎么说：`guidance.ts` 的 `FIRST_LOOK_IN_TWO_PARTS` 进起草指引，提议搜索和第一次开跑时各说一句：先到的是 arXiv，X 像人一样慢慢翻，常要一个小时以上，读到的另出一期，以后加的社交媒体也慢；不许许诺什么时候完。`confirm_topic_search` 的工具结果带同一句。起草卡在预计时间后加一句（`info.cards.topicSearchSlowSources`）。第一期目录末尾按 `awaiting` 写「某主题：X 还在读，读到的另出一期」（`info.issue.book.awaiting`，9 种语言）。

以后要合回一段：把 `SPLIT_FIRST_LOOK` 设成 `false` 就回到一段读完，再删掉读 `RunPart` 的分支、`first-part.json`、`awaiting` 和 `part: "slow"` 那几处。

### 进度

2026-10-17 加。用户问第一次、重跑或夜跑回来没有、做到哪了，卢明先调门口的 `background_status`（[55](../soul/55-legion.md)「门口查进度」，`about` 填主题名或 id），不拿搜对话当 run 状态的来源，照样不许许诺什么时候完；重跑和恢复 X 的工具结果里也提醒这一句。主题搜索的描述器在 `info/topic-search/run-status.ts`，`registerTopicSearchRuns` 时登记。标题写哪个主题、第一次 / 第几次重跑 / 哪一夜；完成但汇报以 `skipped:` 开头的算跳过。细节：

- X：本机就是跑它的那台时，读 run 目录的进度文件，数出第几个查询共几个、读了几屏、找到几条不同的帖子（有回答盖到的帖子时注明几条来自回答、几条只来自页面）、开了几个帖子页、停手和收尾状态、相关度和旁听两条警告；不读帖子正文。run 在 `read` 相位把 X、arXiv、Hugging Face 三边的进度拼成一行汇报进 run 文件（如「reading X: ...; arXiv done: 2 queries searched (2 direct), 6 papers; Hugging Face done: ...」；`run.ts` 包一层进度文件，runner 30 秒一写），所以别的设备从同步来的 run 文件也能看到这一行。
- 每个查询的结果：本机有 run 目录里的源健康文件就逐查询写 X、arXiv 和 Hugging Face（后两个带梯子结局）；还没 build 完，按 `arxiv-read.json` 和 `hf-read.json` 写两边各跑了几条、各自的梯子结局和论文数，跑完的注明「结果等 X 读完才建」（第一次 run 注明「第一段不等 X 就建」），这样 X 还在读时也能说 arXiv 已经完了；文件还没有就写「arXiv 和 X 并行，还没写下结果」（第一次 run 写「arXiv 先搜」，X 写「第一段交了才读」）。不在跑它的那台上，在跑的写明进度文件和逐查询结果留在那台；跑完的用那台 claim 里带的源健康（每个查询最近一次读它的结果），写明是那台多久前报的。
- 结果文件（同步）：重跑看第一次那份文件 `retries` 里这次加了几件、现在共几件；第一次和夜跑看这次 run 的结果文件有几件、有没有新东西；第一次带 `awaiting` 时说第一段交了几件、X 还在读（run 已结束就说没等到 X 补进来），慢段并进后说第一段几件、X 补了几件。
- 简报（`info-shelf.json`，同步）：第一次 `first:<id>` 加慢段的 `first:<id>#<runId>` 两期分开说，重跑 `first:<id>#<runId>`，夜跑 `night:<日期>` 且 topics 里有这个主题；没加东西的重跑写明不出期。
- X 登录与停手：本机是跑它的那台（或没人认领、本机能跑）时读本机停手记录和会话侧车；否则用那台 claim 的 `sites` 和 `halt`，写明是那台多久前报的，都没有就说只有读 X 的那台知道。

防电脑睡眠：开始时拿一把别睡锁，收尾时放。Linux 走 logind 的 `Inhibit("sleep:idle")`，macOS 走 `IOPMAssertionCreateWithName`（`PreventUserIdleSystemSleep`）。宿主能力 `platform/app/keep-awake.ts`，Rust 侧 `src-tauri/src/keep_awake.rs`。合盖或手动睡眠不拦。

X 的动作按设备每天一份总额度，所有 run 共用（初值：搜索页 60 次、永久链接页 80 次）。

## 取材

### X

每条查询开 `x.com/search?q=<x> -filter:retweets&…`。第一次用热门排序加 `since:<30 天前>`；每天用 `f=live`（按时间倒序），读到上次位置就停。运算符在第一期实测核对。

读到上次位置：每条（主题、查询）记上次读到的最上面一条 status id 和 30 天内见过的 id。往下读时连续 8 条见过、或比那条早，这条线就停。

节奏（初值，跑一周后按进度文件调）：

| 项 | 值 |
|---|---|
| 每次上限 | 第一次每主题读入 300 条、开搜索页 12 次；每晚全部主题读入 400 条、开搜索页 30 次、开永久链接页 40 次、有效阅读 150 分钟 |
| 分段 | 2 到 3 段，每段 30 到 60 分钟，段间歇 10 到 30 分钟 |
| 视口 | 1440×2420（竖放的 1440×2560 显示器减去 140 像素窗口栏）；不高于页面读到的 `screen.availHeight` 减 140 |
| 每屏停留 | 新进视口的帖子，正文连同引用帖正文（不算名字、时间、计数、卡片）按每秒 12 到 20 字算，再加 2 到 6 秒随机，一屏最多 3 分钟 |
| 长停 | 每 5 到 10 屏一次，30 到 120 秒 |
| 滚动 | 每次 0.6 到 0.9 屏，拆成几次小步 |
| 线的顺序 | 每次打乱，线之间停 20 到 60 秒 |
| 一条线读完 | 连续 8 条见过或比上次最上面一条早；连续 4 屏没有新帖；连续 2 次滚不动 |

2026-10-14 实测（"AI for science"，Xvfb）：探针那样按整条帖子算字、1440×900，每分钟 2.2 条；按上表，1440×2420 每分钟有效阅读 3.8 条（f=live）、3.5 条（热门），1440×1300 每分钟 3.6 条，150 分钟约 520 到 570 条，过得了每晚 400 条。产量主要来自只算正文，视口高度影响不大。

截断的帖子过了本地相关度地板才开永久链接页补全文，有上限。地板量的词和打分第 2 步同一份（`rank-pool.ts` 的 `relevanceBasis`：X 查询去掉运算符），不用 `ranking`：`ranking` 是用户语言写的问题，中文主题拿它比英文帖子全部得 0（坑 661）。整次 run 读入的帖子满 60 条后，九成以上相关度为 0 就算地板失灵：进度文件记一步 `relevance-collapse`（每次 run 一条），进度行、源健康的 X 行（`note`）和 background_status 都带这条警告；之后每条线地板放不过任何截断帖时，按页面顺序开前 3 条的永久链接页（已开过的算在内），已读完的线也补这一轮。永久链接页上这条帖子自己正文和卡片里的外链（引用帖里的不算）一起收进帖子的 `links`：t.co 的文字写出了完整地址的直接用，只写了开头的照搜索页那样展开，直接指向目标的锚点用 href；这些链接和全文一起写进那一步的进度记录（`permalink` 步的 `links`，2026-10-18 之前的进度文件没有这个字段，照常读）。帖子文字里只写出来、底下没有锚点的链接（`https://` 开头的地址、`arxiv 2605.24043` 这样的编号、不带协议的 `github.com/组织/仓库` 和 `goo.gle` 一类短链），在打分和看原文时从文字里取（`info/x/text-links.ts`），不带协议又以省略号结尾的只是开头，不取；旧的 `x-read.json` 也这样补。短链看原文时先读一次跳转（不跟随，同 t.co），按目标定键和读法，见「看原文」。每一步落一条进进度文件：步号、屏上帖子 id、动作和结果。

停手（坑 494：页面自己的后台请求 403 不算）：落地 URL 变成登录页或搜索页出现登录墙（登录失效）；落到挑战页（`/account/access` 一类）或出现验证提示（验证）；出现限流或「稍后再试」（限流；搜索页只显示 X 的通用错误「Something went wrong. Try reloading.」、没写明限流的，先隔 5 秒重开同一页一次，算一页，还是这样才算限流，断网时也是这一页，坑 664）；连续 3 屏解析出 0 条帖子而页面字数正常（结构变了）。当次立刻收尾，已读的照常往下走，原因写进进度文件、本机状态文件和采集端状态文件（36 的 `halt` 字段，下一次简报 run 结束时被覆盖；`sites`）。登录失效等用户在桌面重新登录才再派（夜跑，或门口说一句重跑第一次，见「重跑第一次」）；门口对话自己读不了 X，X 只在第一次 run、重跑和每晚 01:00 起的增量里读，卢明不许许诺什么时候读；验证和限流跳过下一晚，再下一晚试一次，再碰到就停到用户在对话里说恢复（门口工具 `resume_x_reading`，`info/topic-search/resume-tool.ts`；停手记录在碰到它的那台本机，要在那台的门口说）；结构变了只停当次，等改页内脚本。停手规则挡着 X 时，第一次 run 照样往下 build（X 记为没取到），每晚的增量直接跳过。这几种都往盒里放一项（`kind: "topic-search-halt"`，body `sources:x.com`），说是哪种；登录失效到设置的 Accounts 页重新登录 X。

读法：app 自己的隐藏 webview，和彭博全文共用 `webview_fetch` 的 profile 和 cookie 罐（坑 385）。登录走现有站点登录：X 搜索源的 descriptor 写上 X 的登录页，`site-session.ts` 把它折成一个站，设置的 Accounts 页那一行就能开窗登录、查会话、退出（17、36、[accounts](../north-star/accounts.md)）；X 是注册表账户，不管有没有主题搜索都有这一行。登录是全程唯一的可见窗口，用户自己点。取材要一个长命的页：Rust 侧加 `webview_fetch/browse.rs`，开一个隐藏 webview，前端能让它导航、跑页内脚本、按像素滚、后退、关；页面要真渲染，否则 IntersectionObserver 不回调、无限滚动不加载，Linux 上把 WebKit 控件挪进离屏窗口（坑 600）；前端门面 `workshop/extract/webview-browse.ts`（capability，不认识 X）。搜索页脚本和解析放 `info/x/search-page.ts`，和 `permalink.ts` 并列。判稳定看脚本读没读到帖子，不等 load 事件（坑 496）。滚动用页内 `scrollBy`。

旁听回答（2026-10-20，[X搜索响应被动捕获可行性](../research/X搜索响应被动捕获可行性.md)）：X 读法开会话时带一段 document-start 脚本（`info/x/search-capture.ts` 的 `X_CAPTURE_SCRIPT`，经 `openBrowse` 的 `initScript`、`browse_open`、`build_window` 的 `page_script` 注入主框架；彭博全文、登录窗和别的会话不带）。脚本只在 x.com、twitter.com 上生效，包住 `fetch` 和 `XMLHttpRequest`，页面自己发的 `SearchTimeline`、`TweetDetail`、`TweetResultByRestId` 回答成功时留一份副本（fetch 用 `clone()`，XHR 读它自己读完的文本），页面那份不动，最多留 40 份。交回只走一个具名全局 `window.__readingPartnerXCapture`，读法每屏读完 DOM 后用 `X_CAPTURE_DRAIN` 取走并清空，开永久链接页后也取一次。脚本不伪装：包装是普通函数，全局是普通属性。解析在 `info/x/graphql-post.ts`：在整份回答里按帖子对象（`rest_id` 加 `legacy.full_text`）找，每条取作者、全文（`note_tweet` 优先，否则 `legacy.full_text` 按 `display_text_range` 截，t.co 换成 `expanded_url`）、外链、引用帖（自己的 id、全文和外链，链接只归引用帖）、转发和回复对象、计数（赞、转、回复、引用、浏览、收藏）、有没有媒体、是不是 X Article（只有 id、标题和 `preview_text` 那段开头，正文不在回答里）。

DOM 仍是主路径和兜底。读进来的帖子在回答里有同一个 id 的，用回答的全文、外链和精确计数盖住搜索卡片（`withCaptured`），不再算截断，于是不开永久链接页；X Article 的搜索卡片没有文字（坑 662），用回答里帖子自己的话、标题和预览当文字，帖子上记 `articleId`、`articleTitle`，仍算截断；回答里没有的帖子照旧走永久链接页。永久链接页的 DOM 没读到全文、这一页的 `TweetDetail` 回答里有，就用回答的（`permalink` 步记 `source: "captured"`）。卡片和回答比作者和开头 40 字（去掉链接和 emoji 变体选择符 U+FE0F/U+FE0E、合并空白、忽略大小写），对不上记一步 `capture-mismatch`，不停；作者不同就不用这份回答。`read` 步的 `captured` 记这一屏哪些帖子用了回答。整次 run 读入满 20 条、没有一条被回答盖到（钩子没注入、X 改了形状），记一步 `capture-silent`（每次 run 一条），之后照旧读，和没有钩子时一样。

### arXiv

两条路。

- 主动搜：arXiv 插件实现 `search` 槽（69），包现有的 `searchArxivTopic`，加时间窗（`submittedDate` 区间，不排序，坑 72）。第一次窗口从今天往回 365 天，每天从上次 run 起。每条查询的 `arxiv` 词按下面的梯子跑。

查询梯子（`info/topic-search/arxiv-ladder.ts`，程序的确定性逻辑，不经模型）。export API 把每个词当 `all:` 子句 AND，词多窗口窄就几乎搜不到。一条查询最多 3 个请求，按下面的顺序一个接一个发，不并发：

1. 取 3 个最具体的词（`arxivQueryTerms` 取出可搜的词；一份固定泛词表里的词，如 machine、learning、model，排到最后，其余保持原顺序），在 run 的窗口里搜。
2. 命中不足 3 篇，去掉最后一个词再搜，最少留 2 个词。
3. 还不足，用最前面的 2 个词、窗口起点再往回放宽（第一次 365 天，每天增量 7 天）。

每一步累计的论文凑够 3 篇就停；按先后顺序保留，窄步找到的排前面。请求之间按主机限速，arXiv 一次一个、上一个回来后隔 3 秒，全 app 共用一把闸。arXiv 的某个主机回 429（或 403「Rate exceeded」）后这个主机冷却 10 分钟起（export API 和 arxiv.org 分开记，export 限流时 arxiv.org 的 HTML 和 PDF 照读，坑 502），连着再被拒翻倍，封顶 4 小时，记在本机，重启不清；冷却期间这次 run 剩下的查询不发请求。某一步请求失败，梯子到此结束，保留前面步骤已找到的。查询没有可搜的词，不发请求。梯子在 run 的 `read` 相位和 X 并行跑，见「两种 run」。3 篇、2 个词、365 天和 7 天都是初值。

结果记成六种之一：`direct`（第一步就够）、`widened`（往后的步骤才找到论文）、`exhausted`（所有步骤跑完仍空）、`rate_limited`（429，或 arXiv 同样用来限流的 403「Rate exceeded」）、`cooling_down`（还在上次限流的冷却期里，没发请求）、`failed`（其他失败）。空和限流分开记，每一步的词、窗口、命中数一并记。`rate_limited` 和 `cooling_down` 的源健康都是 `failed`，「重跑第一次」会补；冷却没过就重跑，照样一个请求不发。

读原文时同一篇论文的 arXiv HTML 会读两次（开头一次、读深一次），第二次用 30 分钟内存下的那份，不再发请求（`fetch-memo.ts`）。
- 顺链接：帖子里的 arXiv 链接由 arXiv 站点适配器认领，读出 id、标题、作者、日期、摘要（export API）。

### Hugging Face

2026-10-19 加，和 X、arXiv 同级的检索源。Hugging Face 插件实现 `search` 槽，调 `huggingface.co/api/papers/search?q=…&limit=120`：不用登录，按相关度排，不分日期，一次最多 120 篇；`sort`、`since`、`skip` 这类参数不认，时间窗在本地筛。每行带 arXiv id、标题、摘要、作者、`ai_summary`、`upvotes`、`githubRepo`、`githubStars`、`projectPage`，插件把后五样放进条目的 `signals`。

日期：行里的 `paper.publishedAt` 不一定是 arXiv 第一版的日期，有的是 Hub 收录那天。程序用 arXiv id 的年月校正（`paperDay`）：落在 id 那个月里就用它，晚于那个月取月末，早于取月初，没有取月初。

每条有 arXiv 词的查询搜一次（`info/topic-search/hf-ladder.ts`），用 arXiv 梯子的取词规则取最具体的 4 个词，按查询里的原顺序拼成一句。只发一个请求，窗口是放宽后的（第一次往回再放 365 天，每天 7 天），拿到的答案本地读两遍：run 的窗口里凑够 3 篇是 `direct`；不够就看放宽后的窗口，有就是 `widened`，没有是 `exhausted`，窗口内的排前面。Hub 的搜索是语义的，尾巴会跑题（问 self-driving lab 会出自动驾驶），标题、摘要和 `ai_summary` 里一个具体词都没有的丢掉。每条查询最多留 20 篇。结局和 arXiv 一样六种，`rate_limited` 和 `cooling_down` 在源健康里都是 `failed`。

限速：Hub 对论文搜索单独计数，每 5 分钟 50 次，只在回答头里写着，和别的 API 不共用。闸里 `huggingface.co` 一组间隔 1 秒，论文搜索单开一道（`HF_PAPER_SEARCH_LANE`），间隔 6 秒、冷却单独记，搜索被 429 不停 Hub 的其他请求。冷却规则同 arXiv：10 分钟起翻倍，封顶 4 小时，冷却中不发请求；一次失败最多重试一次，冷却中不重试。发描述性 UA。Hub 的回答不压缩（一次 650 到 900 KB），Tauri 的 http 插件没开 gzip。

和 arXiv 的合并：两边找到的同一篇按 arXiv id 并成一个候选，用 arXiv 那条（日期、摘要），Hub 的 repo、star、upvotes、项目页、`ai_summary` 挂在候选上（`PaperInfo.hub`）。只有 Hub 找到的照样是论文候选，读原文走同一套 arXiv abs/HTML。

Hub 事实给模型当参考，不进最终分（2026-10-19；upvotes、star 要不要算分，看过真实结果再定）。重排和写稿里这篇论文的材料多一行「Hugging Face: N upvotes; GitHub repository owner/repo (S stars); has a project page」，`ai_summary` 另起一行，标明是 Hub 机写、未核对，截 240 字（`info/topic-search/hub-line.ts`）；两处的 system 都说 upvotes 和 star 只说明关注度，不说明质量或切题，机写摘要里的事实和数字不许用。写稿的数字核对认那一行的计数，不认 `ai_summary`。URL 不进提示词，模型只按编号引；Hub 给的仓库是这篇论文的原文候选，排在论文之后，照「每件最多 2 份原文」的规矩读（件里另有一篇论文时让位）。结果文件的件多一个可选字段 `hub`（件领头论文的 Hub 事实，没有就取件里第一篇带 Hub 事实的），旧文件没有这个字段照常读。

## 打分

移植 last30days 的打分（MIT，保留版权声明），放 `info/rank/`，纯 `.ts` 配单测。`rank` 相位每个主题跑一遍：

1. 规范化：每条帖子成一个候选，程序写 status id、重建的永久链接、由 id 解出的时间、作者、正文、原始互动数（赞、转、回复、引用、浏览）、命中的查询、帖内链接（t.co 由程序先展开）。id 解出的时间和页面显示的差一天以上，丢。arXiv 的每篇论文也是一个候选。
2. 本地相关度（`relevance.ts`）：`0.55·coverage^1.35 + 0.25·informative + 0.20·precision`，整句短语命中加分，只命中低信号词封顶 0.24。低于 0.15 丢。同义词表和低信号词表换成我们的。
3. 加权 RRF：X 的每条（查询、源）流取前 40，arXiv 和 Hugging Face 的各取前 12（两边都找到的一篇两条流各算一份），`Σ weight/(60 + rank)`，归一到 0 到 100。同一作者最多 3 条。进重排的池按 RRF 取，但先给帖子留 10 个位、给每个选中子方向的查询找到的候选各留 4 个位（`POOL_RESERVE`），池内仍按 RRF 排。
4. 重排：候选池前 40 条（第一次 60 条）一次发给模型。每条带程序编号 `c1`、`c2`…，正文前 420 字、作者、时间、命中的查询、帖内链接的编号 `c1.a`、`c1.b`；外加主题的范围、子方向、要什么不要什么、judgments、`answers`、已经提过的问题、各查询的 `ranking`、用户的 profile statement。模型只回 `{c, score, main, subtopic, doubt?}`：`score` 0 到 100；`main` 是这条真正的内容，`self` 或某个链接编号，由模型判断（86：帖子大多是引子，有时帖子或 X Article 本身就是正文）；`subtopic` 按编号；`doubt` 是拿不准时的一句问题，进待问清单。编号不存在的答案丢掉。
5. 最终分（初值）：帖子 `0.65·score + 0.20·RRF + 0.15·engagement`，论文 `0.80·score + 0.20·RRF`。`main` 指向 arXiv 论文的帖子按论文的公式算，不计 engagement（2026-10-19 加：荐论文的多是小号，互动近 0，重排 80 的帖子只得 60 左右，掉出前列）；它和那篇论文候选同一个 arXiv id，第 6 步并成一件，只占一个位，帖子留在件里当引子。engagement 照 last30days 的 X 刻度：`log1p` 加权（赞 .55、转 .25、回复 .15、引用 .05），参照值 9.2，归到 0 到 100。没提到锚词由程序判（正文、卡片标题、论文标题摘要里都找不到），扣 20；`score` 低于 20 的乘 0.3。重排漏答的单条用 `0.7·相关度·100` 代替 `score`，没提到锚词扣 25；整次重排失败见「判不了」。
6. 并成事：`main` 指向同一个规范化 URL、同一个 arXiv id 或同一个仓库的候选并成一件事，原文当主体，帖子是引子，事的分取成员最高分加 `min(10, 3·(帖子数−1))`。再按字符三元组和词 Jaccard 取大、阈值 0.48 贪心并簇。
7. 取若干件进看原文：第一次 15 件，每天 8 件（初值）。按分数取，先留两种位（`info/topic-search/select.ts`，2026-10-16 定）：帖子件最多 3 件（`POST_QUOTA`），条件是件里有一条帖子自己的最终分不低于 40（`RESERVE_FLOOR`）；每个选中的子方向只要有一件不低于 40，至少进一件，不要求进正文。其余按分数补，但最终分低于 20（`ITEM_FLOOR`，初值）的不成件，凑不满就少列（2026-10-17 加；重跑和慢段池子小，之前会把重排判成推广的帖子补进来），列表仍按分数排。帖子件指件里有过线的帖子：帖子和它引的论文、仓库、网页并成一件时也算，论文领头不影响，看原文时拿帖子的说法对原文。留位的候选在去重之前就要进候选单，不受前 `3×件数` 的截断。

### 判不了

2026-10-20 加。重排那次调用失败（断网、回答不是 JSON、一条都没答），这批候选就没被模型判过：不按本地相关度的兜底分列件，也不往下看原文、写稿。结果文件不列件，记 `unjudged`（run id、时间、原因、候选数；重跑和慢段记在它那条 `retries` 里），源健康照读到的写，读到的留在 run 目录（`x-read.json`、`arxiv-read.json`、`hf-read.json`）。这个主题下一次 build（夜跑、门口说的重跑、同一次 run 的慢段）把这些 run 目录里读到的并进候选池一起重排；待判的是 30 天内的结果文件记了 `unjudged`、还没有哪份的 `judged` 记它的 run（`result-types.ts` `pendingJudging`）。判成了就在自己的文件或 `retries` 那条记 `judged`；源健康只说自己读的。`planRetry` 把待判的 run 列进 `judge`，只剩它也派重跑，重跑不重读 X。那一期简报不列这批候选，目录下写一行「打分那一步没做完，N 条候选没有列出，这个主题下一次运行时再判」；一期里只有这一行也照出，卢明开场话不调模型。

模型调用因网络失败（`ai/provider-failure.ts` 认成 offline 的：Connection error、fetch failed 一类）就地重试两次，隔 3 秒、6 秒（`model-io.ts` `retryingModel`），重排、去重、比对、写稿都走它，其他失败不重试。写稿失败照旧用兜底版：那些件已经被重排判过。

## 看原文

推文常有夸张。每件事出结果之前，程序先读它的原文：`main` 指向的链接，加帖子里其余指向论文或仓库的链接，每件最多 2 份原文，论文先、仓库次、网页最后；帖子本身（最多一条）在这 2 份之外另读（2026-10-18 定：帖子链到的原文比帖子要紧）。所以每件最多 3 次读取，核对仍是一次模型调用，只对原文。读法用 86 的 `open` 路由（读法登记表、站点适配器、通用网页和 PDF；通用网页要注入 `extractReadable`，坑 658），每读到一份登记一份材料（见「材料登记」）。论文读摘要加 arXiv HTML 开头约 8000 字，没有真 HTML 就只读摘要。export API 限流、拿不到元数据时照样读正文：标题取 HTML 的文档标题 `h1`（去掉里面的脚注），没有才用 `<title>`，末尾的脚注号去掉；摘要取 HTML 里的 Abstract 节；没有 HTML 就读 PDF 文字层开头约 8000 字；HTML 和 PDF 都读不到才算没读到，原因写每一步的原话（PDF 取不到时带 HTTP 状态）。读深见下；仓库读 README 和顶层目录；网页读正文。README 和顶层目录都走 api.github.com（`/readme` 一次找到任何文件名和分支），这个 run 看到的 GitHub 剩余额度不超过 6 次时两个都不调 API：README 改到 raw.githubusercontent 依次试 `README.md`、`readme.md`、`README.rst`、`README`，顶层目录不读。

读到的东西按内容判是不是正文，不信状态码（2026-10-18，`workshop/bindery/gate.ts`）。抓来的网页先看结构：PDF 原始字节（`%PDF-`、`endobj`、`/FlateDecode` 中两个）、拦截页的专有标记（Cloudflare 挑战的 `_cf_chl_opt` 和 challenge-form、`Just a moment...` 标题、DataDome、PerimeterX、Imperva、Anubis，任意长度都算；普通页面也会带 Cloudflare 的 challenge-platform 脚本，这个不算）、同意页的表单（提交到 consent.google/yahoo/youtube）、带脚本而可见文字不到 50 字的脚本壳。抽出正文之后，正文不超过 1500 字时再看它说的是不是验证、Access Denied、cookie 同意或找不到页面；只看抽出的正文，不看整页，所以正文很短但页面顶上挂着 cookie 横幅的文章照样读。arXiv HTML 也先过同一道结构检查，再按坑 377 判。站点直接给的 PDF 按字节认，地址叫 `.html` 也一样，`open` 路由把字节交回，经 `readPdfText` 读文字层开头约 8000 字（和论文没 HTML 时读 PDF 的额度相同），不再重取一次；文本路由里读到 PDF 原始字节的，换 PDF 读法重取一次。没有文字层又没有摘要的算没读到（`no_text_layer`），不做 OCR。

同一份东西认成同一个键（2026-10-19，`info/rank/link-identity.ts`）。键之前先拆包装链接（`google.com/url?q=`、`l.facebook.com/l.php?u=`、`youtube.com/redirect?q=`、`out.reddit.com`、LinkedIn、Outlook safelinks 等），规范化 URL 合并 http/https 和 `www.`，追踪参数加 `ref`、`ref_src`、`_ga`、YouTube 的 `si` 等。论文：arXiv 的 abs/pdf/html、alphaxiv、ar5iv、`huggingface.co/papers/<id>`、SciRate 和 arXiv 自己发的 DOI（`10.48550/arXiv.<id>`）都是 `arxiv:<id>`；`doi.org`、`dx.doi.org` 和路径里带 DOI 的出版社页（`/doi/<doi>` 一类，Nature、Springer、APS、bioRxiv、Frontiers）是 `doi:<小写 DOI>`；OpenReview、ACL Anthology、IEEE Xplore 按站内编号成键。DOI 等论文页按网页读（就是落地页），排在 arXiv 论文之后、仓库之前，帖子里指向它们的链接也算原文候选；落地页的 `<meta>` 写了 arXiv 编号（`citation_arxiv_id`、指向 arXiv 的 `citation_pdf_url`、arXiv DOI）时改走论文读法，arXiv 读不到才用落地页。短链（goo.gle、bit.ly 等）读一次跳转定键，指到已读或已列的东西就不占名额。结果文件里旧拼法的 `url:` 键读入时按新规则重算，30 天去重照样认。普通 DOI 要查它的 arXiv 版本（`topic-search/doi-arxiv.ts`）：先看这次 run 的 arXiv 搜索结果里谁带着这个 DOI（条目的 `<arxiv:doi>`；Hugging Face 不带 DOI），没有再问 Semantic Scholar 的 `paper/DOI:<doi>?fields=externalIds`。S2 这一路在闸里单开一道（`S2_DOI_LANE`，间隔 1.5 秒，429 后冷却，冷却中直接跳过不发），最多重试一次；不带 key 的 S2 常 429，查不到就照旧当 DOI 页。打分前把候选池里所有 DOI 链接查一遍，查到的键改成 `arxiv:<id>`，于是按论文打分、和 arXiv 候选并成一件、走 arXiv 读法；读原文时新冒出来的 DOI 链接也这样查。每个 DOI 一次 run 只问一次，查到、查不到、出错都记下。不按 DOI 查开放获取地址（要 Unpaywall，没接）。

每份原文的每一步留一条记录 `{step, code, retryable, detail}`（`info/topic-search/read-failure.ts`），步有 `api`、`html`、`pdf`、`page`、`post`、`lookup`、`readme`。code 有 `not_found`、`no_such_format`（arXiv 没有 HTML 版）、`blocked`、`login_wall`（登录墙、付费墙、同意页）、`js_shell`、`too_short`、`no_text_layer`、`wrong_content`、`rate_limited`、`cooling_down`、`upstream_error`、`timeout`、`too_large`、`unsupported`、`budget_spent`（当天的 X 页数、GitHub 查询额度用完）；可以重试的只有 `rate_limited`、`cooling_down`、`upstream_error`、`timeout`、`budget_spent`。200 但写着找不到页面的记 `not_found`。一份原文的读法记成 `{url, outcome, steps}`，`outcome` 是 `read`、`partial`（读到了，但有一步失败，比如论文正文读到了、export API 没给元数据，或帖子全文页没打开、只有搜索页那段）或 `unread`，按尝试的先后存进结果文件的 `verify.reads`。`verify.reason` 照旧是各步原话拼成的一句话，写总结的提示和书里用它。2026-10-18 之前的结果文件没有 `reads`，`failuresOf` 把旧的 `reason` 读成一条 `unknown`、不可重试。重试的规划现在还不看这些。

`main` 是 `self` 的帖子先读它自己：搜索页被截断的（长帖、X Article）经 permalink 读全文。帖子里的外链要读到原文（论文、仓库、文章），帖子自己的说法不算来源。搜索页每条帖子只显示约 275 字，多数帖子的链接在截掉的那部分里（坑 657），所以 X 读取时开过永久链接页的帖子带着全文里的外链，看原文时再经 permalink 读全文的，X 读法交出的外链（t.co 已展开，去掉 X 自己和本站导航）也算，帖子文字里写出的链接同样算，都是这件事的原文候选：帖子领头的件先读帖子，它交出的论文和仓库可以排到件里已有的网页前面，补到 2 份原文为止。读到了非帖子的原文，`original` 记它、核对状态是「对过」，拿帖子的说法对它；一份都没读到才是「帖子即原文」，读不到的原因记进 `verify.reason` 并在写总结的提示里交代；截断的帖子全文页没打开、只用了搜索页那段的，打不开的原因也进 `verify.reason`。arXiv HTML 的节标题和论文标题一样去掉 LaTeX 脚注（`\thanks`）。写总结的数字检查除了材料各节正文，也认材料标题和节标题，因为提示里给模型看了它们。写总结时每件材料约 2400 字，有三份材料（帖子加两份原文）时 3600 字，每节最多 1200 字；每份材料都给后面的每份留 1200 字；只有一节的 X 材料（一条帖子、没有小标题的 X Article）可以用留完之后剩下的全部额度。

然后一次模型调用对一件事：给帖子正文（`p1`、`p2`…）和原文的节（`M3.§2`），模型回 `{claims: [{post, says, verdict, evidence}]}`：`says` 是帖子的一个说法，`verdict` 是对得上、对不上、原文里找不到；对不上的写一句差异（「推文说开源了完整训练代码，仓库里只有推理代码」），`evidence` 按编号指出原文哪节。差异句里的数字和日期必须出现在它引的帖子或原文节里，程序抽数字核对，对不上丢掉这条差异。没读到原文（登录墙、拒收）的，结果里写「没读到原文」和原因，不写差异。

读深是写总结那一步里的一轮：模型第一次调用可以只答 `{"deeper":["E2"]}`，在还没读全的论文里挑。程序读到本次 run 的上限后拒绝其余的并告诉模型：第一次 run 每个主题 5 篇，每天增量每个主题 2 篇（初值，`build-result.ts` 的 `DEEP_READS`；一个 run 对应一个主题，所以上限是每次 run 的，不是每晚合计）。读全文是整篇 arXiv HTML 去掉参考文献和致谢；没有 HTML 用 PDF 文字（到参考文献前为止）；都封顶 4.8 万字，登记成另一份材料，替换较短的那份。读不到的告诉模型，按已读的写。这一轮只发生一次，不算两次写稿尝试之一。

每篇论文记读到的深度：材料的 `facts.depth` 和结果里论文事实行的 `depth`，取 `abstract`、`head`、`full`。总结的提示里写明每件读到了哪一档，只能对读到的部分下结论，没读到的写进该条的 `unknown`。

star、日期、作者这些事实一律由程序从原文和 `lookup` 取，不让模型转述。

## 结果

`write` 相位每个主题写一份结果文件 `topic-search-<searchId>-<日期>.json`，随账户同步。结果文件保留：夜跑去重和跨天延续读它，简报书从它生成。

结果文件里有：

- 第一次：开头一段全景，模型写，按编号引事；下面按子方向分组，每组几件。
- 每天：只列新的事；见过的事只有帖子的互动数比上次进结果时涨到两倍以上、且赞多了 100 以上（初值）才再列，标「延续」，只说变了什么。每天用 f=live 读到上次停的位置就停，见过的帖子多半读不到，「延续」很少触发，先这样。
- 每件事：标题（原文标题，没有就作者加帖子第一句，截到 120 字，不改写）；一句结论（`summary`）和两三段正文（`body`），模型写；还不知道、无法核实的一句；事实行，程序写（论文：作者、日期、arXiv id；仓库：star、最近提交、最新 release；帖子：作者、时间、互动数）。书里印的是紧凑版（`topic-search/facts-line.ts`）：论文作者只列前三位，多于三位写「et al.」；论文、仓库最近提交、release、网页、帖子的日期一律只到日（YYYY-MM-DD）；标签（stars、likes 等）跟书的语言。给提示词和数字核对用的仍是完整版（`factsText`：全部作者、完整时间戳），紧凑版里的数字都是完整版里有的，所以核对不放宽也不收紧；差异行；链接（原文、引子帖）和材料编号。
- 待问的问题（见「攒着问」）。

写作规矩：跳过推广、活动吹捧、刷互动的帖；线程当一篇讲；引用帖连被引用的内容一起讲。事实和判断分开写，判断用分寸词（likely、probably、may 一类），不把推测写成事实。全景和每件的句子里的数字和日期必须出现在它引的材料里，程序核对，对不上重写一次，再不对用兜底版。兜底版由程序出：主题名、一句「这次的说明没写成」、每件事的标题、事实行和链接。

提示词缓存（2026-10-20，坑 663）：只有写稿带缓存断点。写稿重写那次照发上一次的 system 和正文，要改的问题（读深过的还有读深结果）另起块接在后面，于是读到上一次写进缓存的前缀；读深之后那次正文已经变了，从它重新写起。实测两次写稿是常态。重排、对照原文、去重判断和卢明开口每个只调一次，不带断点，写缓存的 1.25 倍没人读。

去重：每件事的键（status id、规范化 URL、arXiv id、仓库）在这个主题 30 天的结果里出现过就不再列，延续除外。键不同的，按 ARA 的跨源去重（`dedupe_headline_alerts.py` 的核心，MIT，移植到 `info/rank/dedupe.ts`，中文按二元组）：共享词 ≥ 4 且 Jaccard ≥ 0.5 算同一件；Jaccard 在 [0.35, 0.5)、共享词 ≥ 3 的交给模型，只回 `{id, verdict, confidence}`，只有 duplicate 且 high 才压掉，失败一律照发。

送达：结果不单独进盒，交给当晚那一期简报书，一期进盒一项（见「简报的对话」）。现有每日简报不变。

源健康按（主题、查询、源）记，写进采集端状态文件：上次取到的时间、读到条数、新条数、过地板条数，「没取到」（停手、解析失败、限流）和「没新内容」分开；X 行可带警告（`note`：相关度地板失灵、旁听没盖到任何帖子，两条都有时用分号连起来，`x-progress.ts` 的 `xReadNote`）；arXiv 和 Hugging Face 各一行，另记梯子的结果（`direct`、`widened`、`exhausted`、`rate_limited`、`cooling_down`、`failed`）和每步的词、窗口、命中数。源健康不在界面上显示（信息源页 2026-10-17 已去掉）。

## 简报书

2026-10-15 定。主题搜索的结果是一种特化的书，照 PDB。每晚一期，一期一本 EPUB，装用户关注的所有主题，不是一个主题一本。出了就不再改。当晚所有主题都没有新东西就不出。

结构：

- 封面：日期、期号、主题。走 67 的排版封面，程序生成。
- 目录页：每行「主题 / 小题：一句结论（Page n）」，只看这一页就知道全部。末尾一行 Notes，列出 Notes 里的小题，再一句指向 Annex。
- 正文：一条一页。小标题；斜体导语，和目录那句是同一句；两三段正文，事实和判断分开，判断用分寸词，写明还不知道、无法核实的；推文和原文不符时写出差异；程序给的事实（stars、日期、作者）单独一行；底部列原文链接。
- Notes：短条，条与条之间用 `* * *` 分隔。
- Annex：深度篇。

语言（2026-10-16 定）：书用应用的界面语言写。语言设置选了具体语言就用它；选 auto 就用系统语言匹配出的界面语言（`info/topic-search/book-language.ts`，`languageInstruction("auto")` 的全局行为不动）。写这一期的所有模型调用（结论和正文、全景、排序时提的待问问题、卢明开场话）都带这一个明确的语言指令；论文、帖子、仓库的原标题和引用的名字保持原样不翻。程序写的标签（目录、Notes、Annex、「还不清楚」、原文/经由、差异行、延续行）、期名、日期、封面、EPUB 的 `language` 都按同一个语言取自界面文案（`info.issue.book.*`、`info.issue.facts.*`），出书时定死，出了就不改。

跨天延续照 PDB：只写新增，用 yesterday、still、again 这类词带过，不重述以前写过的。新题第一次出现时写短，说清还不知道什么。题的轻重靠位置、篇幅、在正文和 Notes 之间升降来表现，不另加标记。

原文（论文、仓库、原帖）出书时挂成这本书的辅助资料（67「辅助资料」），Outline 横线下列出，点开在同一个阅读器里看。用的是看原文时登记的材料（见「材料登记」）。

简报书里没有 Learn 和课堂，也没有阅读器自带的对话（iPad 的对话卡、手机的 Learn sheet），空出的位置不补别的。唯一说话的是卢明（见「简报的对话」）。

## 简报的对话

简报的对话就是当天的门口对话（68，按天一条）。卢明是简报员：每晚出一期，第二天门口对话的时间线里出现一张简报卡（「Oct 15 brief · 4 items」，Open 打开这本书）。卡是程序放的，规矩见 68「卢明的对话窗」。

用户打开简报时，对话窗跟着出来，卢明先开口：今天哪几条值得看，引页码。开口时带上最多三个想问用户的问题（「攒着问」），每个问题下有快捷回答；回答后一行回执写明记到了哪里，主题配置或关于用户本人的 profile statement（「记忆回写」）。跨天的连续性靠卢明读以前各期的书和记忆。

划线：只 Highlight 时书上留线，对话里什么都不出现，卢明知道，下次说话时自然照顾到。选中后 Ask：问题带着引文进卢明的对话，回答也在那里。

上下文干净：用户开着哪一期、在第几页、划了哪几句，作为附注只给模型，做法同收链接（68：作为 app note 附在消息上，不进线程文件），不进对话文件，用户看不到。门口回合在开着简报书时把这本书摆上桌当材料，卢明能翻全文、读辅助资料里的原文核对。

点卢明回答里的页码：对话窗收起，书翻到那页并标出那段（同手机课堂点引文，77）；要接着聊再点卢明。

## 展开与全文

用户在简报的对话里：

- 「展开讲讲」第 n 件：Lumen 用已登记的材料详细讲（门口工具 `read_topic_material`，按结果件号和材料号读正文），用户不读全文。已有材料答不上的，Lumen 派详细资料 run，当场说多久能到，回来接着讲。
- 「我要全文」「好好读一读」：出专题册。这件事有详细资料就直接交给装订器；没有就派详细资料 run，结束后交给装订器。

Lumen 按用户的话判要的是听还是读；拿不准先讲，讲完一句话问要不要全文。

### 详细资料 run

kind `dossier`，agent worker，`synced` tier，`requires: [WEBVIEW_FETCH]`，排队同上。idempotencyKey 是 `dossier:<结果件 id>`：同一件还在排队或在跑时再要，Lumen 说已经在做；做完再要是新的一次（`dossier:<结果件 id>:<n>`）。参数里带用户要的是讲还是全文。

一个 agent 多轮调工具（`legion/subagent` 的 `runSubagent`），日常档。种子是那件事和主题搜索时已登记的材料：帖子只证明作者说了什么，要顺着它的链接和点到的实体到 X 以外找原始材料（ARA 推文种子模式）。读论文按需读全文，不止摘要。

开始前程序先查已有的专题册（info 书架上的和移进 reading 的，范围待实现时定）（移植 ARA 的 `prior_context.py`，MIT）：按标题 2 分、小标题 1 分对种子标题和正文首段打分，中文按二元组，阈值 2 取前 5，编号 `P1`…，每条给标题和开头 400 字；另把这些专题册里所有材料的来源 URL 规范化后建表。

工具，参数都只有编号和短文字：

| 工具 | 做什么 |
|---|---|
| `plan` | 开头调一次：4 到 8 个可回答的问题，每题写明什么算一手；2 到 3 个证伪问题（什么会推翻这件事的说法）。程序编号 `Q1`…、`F1`… |
| `x_search` | 查询词。程序在桌面 webview 按上面的节奏读一屏到几屏，回编号帖子，格式同重排的候选 |
| `arxiv_search` | 查询词，走 arXiv 插件的 `search` 槽，回编号论文 |
| `web_search` | 24 的工具，返回的来源由程序编成候选 |
| `open` | 读候选 #n，86 的 `open`：读法登记表、站点适配器（arXiv、GitHub、Drive）、通用网页和 PDF；X 帖子给出自身全文候选和全部外链候选。是引子还是正文，由模型判断 |
| `pick` | 选一份材料：编号、角色（一手、二手、评论、反方）、回答了哪些问题号 |
| `ask` | 在某个问题下加追问，挂在它下面（每题最多 3 个追问、最多两层） |
| `finish` | 一句说明，结束 |

每轮模型看到的进度由程序写：每个问题挂了哪些材料、还缺哪些。

够了的判据由程序数：每个 `Q` 至少一份一手材料；每个 `F` 至少一份反方材料，或用 `x_search` 和 `web_search` 各查过一次没找到（程序记下查过什么）；选中的材料 3 到 20 份。不满足时 `finish` 被拒，回缺的问题号。上限（初值）：工具调用 60 次、`x_search` 10 次、`open` 30 次、模型轮数 30、时长 60 分钟。到上限就按已选的交出去，缺的问题号写进交接。已经在这些专题册里的材料（规范化 URL 命中）不能 `pick`，要提它就写 `P` 编号。

结束后：要讲的，结果送达门口（`deliverTo`），Lumen 的答铃回合用 `read_topic_material` 读选中的材料接着讲；要全文的，写交接给装订器。一份材料都没选中，run 失败，盒里一项说没找到和查过什么。

### 材料登记

主题搜索的 `verify` 和详细资料的 `open` 每读到一份东西，程序登记一份材料，`info/dossier/registry.ts`，挂在结果件上：

| 字段 | 内容 |
|---|---|
| `id` | `M<n>`，同一规范化 URL 只登记一次 |
| `url`、`canonicalUrl` | 规范化移植 ARA `source_cache.py` 的 `canonicalize_url`：去 `utm_*`、`fbclid` 等追踪参数，query 排序；另拆包装链接、合并 http/https 和 `www.`（见「看原文」） |
| `title`、`author`、`publishedAt` | 读法和适配器读出来的 |
| `reader` | x、web、arxiv、github、drive、pdf |
| `facts` | 程序取的事实：star、最近提交、release、arXiv id 等 |
| `hash` | 正文内容哈希 |
| `facts.depth` | 论文的读到深度：`abstract`、`head`、`full` |
| `sections` | 按标题边界切的节 `M<n>.§k`：小标题、字数。整份 PDF 没有节 |
| 正文 | 可读稿（`Manuscript`）或整份文档的字节，缓存在 run 目录 |

模型在任何地方提到材料，只写 `M3`、`M3.§2`、`P2`；程序校验编号存在。

## 简报书的实现

- 生成（2026-10-15 做完，`src/info/issue/`）：每个主题 run 的 `deliver` 不再各自进盒，把结果交给当晚那一期；当晚各主题的 run 都收尾后（或到 04:40 截止），把各主题的结果 JSON 映射成分节稿（封面、目录、一条一节、Notes、Annex），用 bindery 现有的 `buildSectionedEpub` 出 EPUB，`importBook` 入库（新的 `LibraryKind`），挂辅助资料（`supplements-<bookId>.json`）。一期进盒一项。info 不能直接 import reading（会成环），入库和挂辅助资料照「reading 或外壳注入」的老规矩（同 86）。写这一期时，程序把前几期同一主题写过的结论句交给模型，供它只写新增。
- 何时出：run 收尾（含跳过的）时告诉 `info/issue` 关了，本机记进 `info-issue-state.json`（local，只有采集端写）。当晚所有在关注的主题（`status: active`）的 run 都关了就组装，否则采集端五分钟一次的 tick 到 04:40 把已关的组装。第一次 run 关了就立即单出一期，只含这个主题，不管白天还是夜里；分两段时快段交了就出这一期，X 补进来的另出 `first:<searchId>#<runId>`（见「第一次分两段」）。各主题都没有新东西就不出。组装按键（`night:<日期>`、`first:<searchId>`、重跑的 `first:<searchId>#<runId>`）幂等：期号取自书架索引、EPUB 字节由分节稿和期号决定，中途崩了再组装一次是同一本书、同一个盒项。
- 分节稿初值（第一期后调）：所有主题的件按分数排序，前 6 件（`MAIN_MAX`）且分数不低于 45（`NOTE_BELOW`）、有结论和正文的进正文，其中最多 2 个位留给带帖子的件（`MAIN_POSTS`，同样要过 45、写成、不是延续），其余进 Notes；延续件、兜底版（没写成的）进 Notes；正文一件都没有时把分最高的已写件提上来。第一次 run 的全景进 Annex，正文里的 `E3` 换成脚注号，下面列标题；每天的短全景不进书。
- 目录行不写页码：每行「主题 / 小题：结论」，「主题 / 小题」是指向那一节的链接。页码要阅读器分页后才有，出书时算不出。小题是子方向名，没有子方向就只写主题。每一节的小标题用原文标题。
- 一期进盒一项：`kind: "brief-issue"`，origin 是门口那一天，body 是书的 hash，封面一句程序写（「Oct 15 brief · 4 items」）。现在点开直接在阅读器里开这本书（`box-jump.ts` 加了一行），门口对话里的简报卡归 ③。
- 入库：`LibraryKind` 加 `issue`，不挂任何主题。入库和挂辅助资料默认用 platform 的 `importBook`、`addSupplement`，外壳可以用 `setIssueFiling` 换掉。
- 辅助资料：每件取第一份非 X 的材料，正文的件在前、Notes 在后，一期最多 12 份。组装时用 bindery 的 `bind({kind: "url"})` 重新取一次原文：论文按站点给的 PDF 原样入库，网页和 README 出 EPUB，入库为 `article`，不挂主题。取不到的只留正文里的链接。代价是每份一次请求加图片，夜里在采集端做。材料登记里缓存的只有纯文本节（论文前 8000 字，读全的到 4.8 万字），拿它出书会缺图缺格式，所以不用。
- 跨天延续：写一期时，把这个主题 30 天内的结果里最多 20 句结论（新的在前）交给模型。这些句子里的数字算可引用来源，延续件可以只写一句结论不写正文。
- info 书架索引：`info-shelf.json`，同步，整份合并（只有采集端写）。每期一行：键、期号、日期、主题、来源结果、件数、书的 hash、盒项 id；专题册一排只留了结构。
专题册起初不在任何主题，第一次移入走 `addFileToTopic`，不是 `moveFileToTopic`。
- 阅读器模式（④ 前半，2026-10-15 做完）：库条目 kind 为 `issue` 的书按简报模式开（`reading/issue.ts` 的 `readerModeOf`）。iPad/桌面顶栏没有 Learn，笔架没有 AI 笔；手机底栏没有 Learn；空位不补。桌面鼠标不拿笔时在字上拖动即选中，出同样的 Highlight / Ask（`epub/paged/mouse-select.ts`，只在简报里；书里拖动仍是翻页）。选中后 Ask 不建划线线程：引文挂在门口对话输入框上方（可移除），发出时是一行 Markdown 引文加问题（`chat/quoted-question.ts`），对话里画成引文块。Highlight 照常存标注。阅读器开着简报时把它发布到 `lumen/issue-context.ts`，角落据此打开当天的门口对话，卢明隐藏时只出对话窗；同一期再发布不再弹。手机上点简报盒项直接在阅读器里开；简报不在任何主题下，离开时不记 opened。
- 门口回合开着简报书时，`openDoorTurn` 的 `desk` 摆上 `issue` 桌面项（`reading/issue-desk.ts`），history 仍是门口线程；带 history 的项摆到门口直接报错。整本估算不超过 12k token 就内联全文，每页带 `[p.N]` 锚；挂 `read_pages`、`search_topic`（连辅助资料一起搜）、`read_supplement`；不带 memory 和 origin。附注由 `issueDoorTurn` 拼：期名、第几页/共几页、这期上的划线（最多 12 条，按页排）、引文在哪一页；接在用户这行后面，只进发给模型的那份。标注没有时间戳，附注列这期上全部划线，不只当天的。
- 门口对话里的页码引文 `[p.N "原话"]` 在开着简报时按这本书校验（`createQuoteCheck`）；点了对话窗收起，书翻到那页并标出那段（iPad/桌面 `ViewInstance.highlightQuote`，手机 `jumpInBook`）。没开简报时门口不接管引文。
- 卢明开场话（④ 后半，2026-10-15 做完）：出书时写好，打开时说。组装一期时（`info/issue/assemble.ts`）程序先挑这期的问题：取当晚各主题结果里带的问题（每个结果已按自己主题的上限挑过），按主题轮流各取一个，一期最多 3 个；放不下的在 `info-topic-search-questions.json` 里退回待问（`askedIn` 清空，不算问过）。再让日常档模型写两三句判断：哪几条值得看、为什么，条目用编号 `[n]` 指（正文在前、Notes 在后，从 1 数），不写日期和条数，不问问题；同时给模型自己那类问题每个两三个快捷回答。程序模板的问题不要模型给回答，快捷回答按模板来（留着/去掉之类），说出时按用户的界面语言措辞。模型失败、没配、回的不是 JSON，判断句为空，只说程序那句。结果记在这一期书架索引那一行的 `opening` 字段（`info/issue/opening-record.ts`），跟着这行一起过期。
- 说出来（`info/issue/opening.ts`）：门口对话因打开某期而起、线程载入后，`use-door-chat.ts` 调 `speakIssueOpening({ bookId, date, threadId, pageOf })`。先查 `info-issue-spoken.json`（同步，按书 hash 记录合并）：这期说过就什么都不做，换台设备同步过来也一样；没说过先记下再说，宁可崩在中间少说一次，不说两遍。往当天门口线程追加一条卢明的消息：程序写的「Oct 15 brief: 4 items.」（界面语言），接模型那几句；`[n]` 换成 `[p.N "小标题"]`，页码由阅读器分好页的全文按小标题找（`reading/issue.ts` 的 `headingPage`：以这句开头的那页是正文那一节，否则跳过目录页取第一处，是 Notes 里那条），找不到就写成带引号的标题、不做链接。点了走前半做好的引文跳转：对话窗收起，书翻到那页标出小标题。每个问题一张卡（kind `issue-question`，`info/issue/question-card.ts`，组件 `lumen/IssueQuestionCard.tsx`）：问题、快捷回答、「In my own words」。
- 回答：点快捷回答就是以用户身份说出这句；点「In my own words」卡片等着，用户下一句话就是回答。卡片记下回答和那句话的时间，画成「You said: …」，写回线程文件。这句话发给模型时附一条 app note（只进模型那份），写明回答的是哪个主题搜索（名字和编号）的哪个问题，要它按「记忆回写」写：只对这个主题成立的走 `update_topic_search`，问题和回答原话进 `answers`；对用户本人成立的走 `statement_write` 写 profile；都有就两处都写。回执用工具自己的：主题那边是「Saved to this topic」加主题名，profile 的回执改成「Noted about you」（其他 kind 照旧「Wrote down a …」）。问题在出书时已经标了问过，回不回都不再问。
- info 书架（② 2026-10-15 做完）：`ui/components/info/InfoShelf.tsx`，逻辑在 `info-shelf.ts`。平板/桌面侧栏 Briefing 下面一项 Briefs，手机首页一张 Briefs 卡。各期是日期卡，新的在前，写期号、日期、主题、件数；当天的、或本机没有阅读位置的标 New。专题册另一排，菜单 Open / Move to… / Delete。
- 专题册 Move to… 复用 `MoveToTopicDialog` 和 `move-to.ts`，第一次移入调 `addFileToTopic`。移动和删除不改索引（只有采集端写 `info-shelf.json`）：书架不显示已在某个 reading 主题下的专题册，也不显示书已不在库里的期和专题册。
- 回收：garbage marker `info-issue-expiry`（`info/issue/expiry.ts`），日期早于今天 30 天（`ISSUE_KEEP_DAYS`，初值）的期过期，没打开过的也过期，专题册不过期。只在采集端跑。housekeeper 加了 `flow` 动作（80）：marker 用 `carryOut` 自己执行，这里先走注入的 `deleteBook` 联动，再从 `info-shelf.json` 删掉那一行，和组装走同一条串行队列。
