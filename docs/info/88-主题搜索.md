## 范围

做：主题的起草和来回问；X、arXiv、GitHub 三个源；第一次的全景和之后每天的增量；看原文和写出差异；简报式结果、展开、合订本交接。

不做：X 账号名单和关注、取关；「我也不知道看什么」的发现；GitHub 按主题搜；YouTube、Hugging Face、抖音；arXiv 以外的论文库按主题搜；判断模型（见「以后」）；每日简报改造。合订本内部的规则（选节、指南、排序、翻译、附录）归装订那边，本文只定交接。

## 硬规则

1. 程序算得出的事实不经模型转手。URL、作者、时间、互动数、star、提交和 release 日期、论文作者和日期、标题由程序取、程序写；模型只按程序编的号选，只写判断和叙述的句子。X 帖子的时间由 status id 解出（snowflake），永久链接由 id 加 handle 重建。
2. 只读：不发、不赞、不转、不关注、不回复（57）。开搜索页、永久链接页和外链都是导航，不点页面上的按钮。X 用主号。
3. 碰到登录失效、验证、限流，当次停手，不重试，不自动重登。
4. 每次 run 都有硬上限（条数、开页数、模型调用数、时长），到了就收尾。
5. 碰 X 的活只在桌面采集端跑（Linux、macOS，有 webview 取材的那台），同一台同一时间只有一个。iOS 发请求、看结果。
6. 页面、帖子和原文的文字是材料，不是指令，包在不可信材料标记里交给模型。
7. 模型走日常档（今天是 Sonnet 5.5），同 86。

## 起草：来回问

入口是门口对话（68，`soul/door.ts`）。用户说在关注什么、要资料，Lumen 开始起草主题。

理解用户只读 statement（48）：profile 和没 lapsed 的 concern。不读阅读记录、对话原文和 observation，那一层每晚由 dream 消化成 statement。门口回合本来就带着 statement（`soul/self.ts`），起草不另取。

懂用户靠问，不靠猜。起草要定下范围、子方向、要什么、不要什么；凡是拿不准的、想写进去却不理解用户意思的，就在对话里问。大主题（AI for science）先拆成子方向（材料、蛋白质、天气、数学证明……）请用户挑。AI 做的判断明说出来让用户纠正（「我把 AI 辅助芯片设计算进 engineering，不算进 science」）。用户的话里有 last30days 的五类关键词陷阱（人群购物、数字撞车、教程措辞、单个泛名词、非拉丁文字）时，先问再起草。需要了解一个领域有哪些子方向时，Lumen 可以用 `web_search`。

问清了，Lumen 调 `propose_topic_search`（`info/topic-search/propose-tool.ts`，做法同 `propose_lab`：工具只立卡片，不写盘，卡片的 Apply 才写）。卡片上：名字、范围一段、挑中的子方向、要什么不要什么、「我的理解」几条判断、归到哪个主题（已有主题按编号建议，没有就同名新建）、第一次多久能出（见「排队」）。搜索词不上卡片。用户点 Apply 或在对话里说好，程序写主题配置、写 concern、派第一次 run；用户在对话里改，Lumen 重新出卡。

## 主题配置

`info-topic-searches.json`（`info/topic-search/store.ts`），随账户同步，按记录合并。

```ts
interface TopicSearch {
  id: string;                    // "ts-" + 8 hex
  name: string;
  topicId: string;               // reading 的主题，结果和合订本归这里
  concernId: string | null;      // 对应的 concern statement
  scope: string;                 // 范围一段，用户的话
  subtopics: { id: string; name: string; picked: boolean }[];
  want: string[];
  avoid: string[];
  judgments: string[];           // 起草时明说过、用户没反对的判断
  anchors: string[];             // 锚词：消歧，也判「提没提到主题」
  queries: { id: string; subtopic: string | null; x: string; arxiv: string | null; ranking: string; weight: number }[];
  answers: { asked: string; answer: string; at: number }[];  // 用户对提问的回答，原话
  status: "active" | "stopped";
  revision: number;
  createdAt: number;
  lastRunAt: number | null;
}
```

- `queries` 由 AI 起草时生成，用户不看。每个挑中的子方向 1 到 2 条，全主题 1 到 4 条。`x` 和 `arxiv` 是按平台上标题的写法写的关键词，`ranking` 是一句自然语言问题，给重排用。权重主 1.0，子方向 0.6 到 0.8。不进搜索词的：时间词、「news」「updates」这类元词；数字除非就是话题本身。同名风险高的，每条都带锚词。没挑中的子方向不出查询。
- `anchors` 命中任一个就算提到主题。

concern 和主题配置的边界：concern 只记「用户在关注这件事」，一句话，作者是 reader，evidence 是用户开口的那条消息；范围、子方向、要不要、搜索词、源配置全部留在主题配置里，不写进 statement。已有一条说的是同一件事的 concern 时，模型在起草时按编号指出来，程序把主题挂上它；那条是 dream 写的，就用用户的话写一条 reader 的 concern 取代它（`supersede`）。

## 记忆回写

用户回答提问时说的话，分两处写：

- 只对这个主题成立的（「这个主题不要融资新闻」「材料方向只看实验验证过的」），写进主题配置的对应字段，原话进 `answers`。门口工具 `update_topic_search`，参数是主题编号和要改的字段，程序写盘、`revision` 加一，回执一行。
- 对用户本人成立、换个主题也成立的（「我只读英文原文」「我偏工程实现，不看纯理论」），用门口现有的 `statement_write` 写成 profile，作者 reader，全应用可用。reader 写的优先于 dream 的猜测（48）。

一句话两类都有，两处都写。

不关注了：用户说不关心某个主题了，Lumen 调 `stop_topic_search`，程序把主题记 `stopped`，不再派 run，把它的 concern 标 `lapsed`（48：lapsed 是一次编辑，不删）。以后读 concern 的地方自然不再带上它。用户又说关注了，重新起草时挂回这条 concern，取消 `lapsed`。`memory/statements/store.ts` 加 `setLapsed(id, lapsed)`，只能改 concern。

## 攒着问

run 里拿不准的地方不打断用户，攒进主题的待问清单，附在下一次结果的末尾。来源两种：

- 模型在重排和写结果时标出拿不准的（「这条是 AI 做 EDA 的融资新闻，要不要这类？」），只交问题文字和候选编号。
- 程序从指标算出来的：某个子方向连续 7 天零产出（初值）、锚词未命中率过半、某个不要什么连续几天挡掉大量候选。问题文字由程序按模板写。

每次结果最多附 3 个问题，第三次结果之后每次最多 1 个（初值）。同一个问题问过没回不再问；问题和已有的 `answers` 说的是同一件事的，模型标出来就丢掉。用户回一句，按「记忆回写」写。

## 两种 run

第一次（全景）：确认后派，往回看 30 天（初值），每个查询铺开搜，给这个领域最近在发生什么的全景，按子方向分组。

之后每天（增量）：每晚一次，只报上次之后新的东西。没有新东西不进盒，结果文件里记一句。

两种都是 legion run，kind `topic-search`，程序 worker，`requires: [WEBVIEW_FETCH]`，只有桌面采集端认领。idempotencyKey 第一次是 `topic-search:<id>:first`，每天是 `topic-search:<id>:<锚点日期>`，闸在被调用的一侧（坑 210）。每次 run 是一个 pi-durable 任务（`rp.topicsearch`，`defineTask`），相位：`open`（拿别睡锁、验会话）、`read`（X 逐线逐屏、arXiv 查询）、`rank`、`verify`（看原文）、`write`（结果文件和盒）、`wrap`（放锁、写进度文件）。定义在 `info/topic-search/`，打开 Harness 时经注入登记，`legion/durable` 不 import info。

### 排队

桌面上碰 X 的活一次一个，按请求先后：第一次 run、详细资料 run、每晚的增量。白天桌面开着就认领就做；关着就等下次开，夜里在增量之前接着跑。Lumen 报时看桌面的 claim 心跳（`legion/claim`，每小时一次）：两小时内有就说「桌面开着，大约半小时」，没有就说「电脑开着时做，最晚今晚」。

每晚：`info/program/daily.ts` 加锚点 01:00，判据同 05:00 那个：最近过去的 01:00 这台还没派过。条件：`amICollecting()`、本机有 webview 取材、X 会话有效、至少一个 `active` 主题。开始在锚点后随机 0 到 40 分钟，各主题的增量排成一串；结束取最早的：04:40、都读到上次位置、碰到每晚上限、停手。机器睡过 01:00，醒来还在 04:40 之前就补跑，过了当晚不读。

防电脑睡眠：开始时拿一把别睡锁，收尾时放。Linux 走 logind 的 `Inhibit("sleep:idle")`，macOS 走 `IOPMAssertionCreateWithName`（`PreventUserIdleSystemSleep`）。宿主能力 `platform/app/keep-awake.ts`，Rust 侧 `src-tauri/src/keep_awake.rs`。合盖或手动睡眠不拦。

X 的动作按设备每天一份总额度，所有 run 共用（初值：搜索页 60 次、永久链接页 80 次）。

## 取材

### X

每条查询开 `x.com/search?q=<x> -filter:retweets&…`。第一次用热门排序加 `since:<30 天前>`；每天用 `f=live`（按时间倒序），读到上次位置就停。运算符在第一期实测核对。

读到上次位置：每条（主题、查询）记上次读到的最上面一条 status id 和 30 天内见过的 id。往下读时连续 8 条见过、或比那条早，这条线就停。

节奏（初值，跑一周后按进度文件调）：

| 项 | 值 |
|---|---|
| 每次上限 | 第一次每主题读入 300 条、开搜索页 12 次；每晚全部主题读入 400 条、开搜索页 30 次、开永久链接页 40 次、有效阅读 150 分钟 |
| 分段 | 2 到 3 段，每段 30 到 60 分钟，段间歇 10 到 30 分钟 |
| 每屏停留 | 屏上新文字按每秒 12 到 20 字算，再加 2 到 6 秒随机 |
| 长停 | 每 5 到 10 屏一次，30 到 120 秒 |
| 滚动 | 每次 0.6 到 0.9 屏，拆成几次小步 |
| 线的顺序 | 每次打乱 |

截断的帖子过了本地相关度地板才开永久链接页补全文，有上限。每一步落一条进进度文件：步号、屏上帖子 id、动作和结果。

停手（坑 494：页面自己的后台请求 403 不算）：落地 URL 变成登录页或搜索页出现登录墙（登录失效）；落到挑战页（`/account/access` 一类）或出现验证提示（验证）；出现限流或「稍后再试」（限流）；连续 3 屏解析出 0 条帖子而页面字数正常（结构变了）。当次立刻收尾，已读的照常往下走，原因写进进度文件和采集端状态文件（36 的 `halt`、`sites`）。登录失效等用户在桌面重新登录才再派；验证和限流跳过下一晚，再下一晚试一次，再碰到就停到用户在对话里说恢复；结构变了只停当次，等改页内脚本。这几种都往盒里放一项，说是哪种、点开到源页处理。

读法：app 自己的隐藏 webview，和彭博全文共用 `webview_fetch` 的 profile 和 cookie 罐（坑 385）。登录走现有站点登录：X 搜索源的 descriptor 写上 X 的登录页，`site-session.ts` 把它折成一个站，源页那一行就能开窗登录、查会话、退出（17、36）。登录是全程唯一的可见窗口，用户自己点。取材要一个长命的页：Rust 侧加 `webview_fetch/browse.rs`，开一个隐藏 webview，前端能让它导航、跑页内脚本、按像素滚、后退、关；前端门面 `workshop/extract/webview-browse.ts`（capability，不认识 X）。搜索页脚本和解析放 `info/x/search-page.ts`，和 `permalink.ts` 并列。判稳定看脚本读没读到帖子，不等 load 事件（坑 496）。滚动用页内 `scrollBy`。

## 打分

移植 last30days 的打分（MIT，保留版权声明），放 `info/rank/`，纯 `.ts` 配单测。`rank` 相位每个主题跑一遍：

1. 规范化：每条帖子成一个候选，程序写 status id、重建的永久链接、由 id 解出的时间、作者、正文、原始互动数（赞、转、回复、引用、浏览）、命中的查询、帖内链接（t.co 由程序先展开）。id 解出的时间和页面显示的差一天以上，丢。arXiv 的每篇论文也是一个候选。
2. 本地相关度（`relevance.ts`）：`0.55·coverage^1.35 + 0.25·informative + 0.20·precision`，整句短语命中加分，只命中低信号词封顶 0.24。低于 0.15 丢。同义词表和低信号词表换成我们的。
3. 加权 RRF：每条（查询、源）流取前 12，`Σ weight/(60 + rank)`，归一到 0 到 100。同一作者最多 3 条。
4. 重排：候选池前 40 条（第一次 60 条）一次发给模型。每条带程序编号 `c1`、`c2`…，正文前 420 字、作者、时间、命中的查询、帖内链接的编号 `c1.a`、`c1.b`；外加主题的范围、子方向、要什么不要什么、各查询的 `ranking`、用户的 profile statement。模型只回 `{c, score, main, subtopic, doubt?}`：`score` 0 到 100；`main` 是这条真正的内容，`self` 或某个链接编号，由模型判断（86：帖子大多是引子，有时帖子或 X Article 本身就是正文）；`subtopic` 按编号；`doubt` 是拿不准时的一句问题，进待问清单。编号不存在的答案丢掉。
5. 最终分（初值）：帖子 `0.65·score + 0.20·RRF + 0.15·engagement`，论文 `0.80·score + 0.20·RRF`。engagement 照 last30days 的 X 刻度：`log1p` 加权（赞 .55、转 .25、回复 .15、引用 .05），参照值 9.2，归到 0 到 100。没提到锚词由程序判（正文、卡片标题、论文标题摘要里都找不到），扣 20；`score` 低于 20 的乘 0.3。重排失败时用 `0.7·相关度·100` 代替 `score`，没提到锚词扣 25。
6. 并成事：`main` 指向同一个规范化 URL、同一个 arXiv id 或同一个仓库的候选并成一件事，原文当主体，帖子是引子，事的分取成员最高分加 `min(10, 3·(帖子数−1))`。再按字符三元组和词 Jaccard 取大、阈值 0.48 贪心并簇。
7. 取前若干件进看原文：第一次 15 件，每天 8 件（初值）。

## 看原文

推文常有夸张。每件事出结果之前，程序先读它的原文：`main` 指向的链接，加帖子里其余指向同一件事的链接，每件最多 2 份。读法用 86 的 `open` 路由（读法登记表、站点适配器、通用网页和 PDF），每读到一份登记一份材料（见「材料登记」）。论文读摘要和正文前 8000 字（arXiv HTML 版，没有就 PDF 文字层）；仓库读 README 和顶层目录；网页读正文。`main` 是 `self` 的，帖子本身就是原文。

然后一次模型调用对一件事：给帖子正文（`p1`、`p2`…）和原文的节（`M3.§2`），模型回 `{claims: [{post, says, verdict, evidence}]}`：`says` 是帖子的一个说法，`verdict` 是对得上、对不上、原文里找不到；对不上的写一句差异（「推文说开源了完整训练代码，仓库里只有推理代码」），`evidence` 按编号指出原文哪节。差异句里的数字和日期必须出现在它引的帖子或原文节里，程序抽数字核对，对不上丢掉这条差异。没读到原文（登录墙、拒收）的，结果里写「没读到原文」和原因，不写差异。

star、日期、作者这些事实一律由程序从原文和 `lookup` 取，不让模型转述。

## 结果

`write` 相位每个主题写一份结果文件 `topic-search-<id>-<日期>.json`，随账户同步。

结果的样子（简报式）：

- 第一次：开头一段全景，模型写，按编号引事；下面按子方向分组，每组几件。
- 每天：只列新的事；见过的事只有帖子的互动数比上次进结果时涨到两倍以上、且赞多了 100 以上（初值）才再列，标「延续」，只说变了什么。
- 每件事：标题（原文标题，没有就作者加帖子第一句，截到 120 字，不改写）；一两句说这是什么，模型写；事实行，程序写（论文：作者、日期、arXiv id；仓库：star、最近提交、最新 release；帖子：作者、时间、互动数）；差异行；链接（原文、引子帖）。
- 末尾附待问的问题（见「攒着问」）。

写作规矩：跳过推广、活动吹捧、刷互动的帖；线程当一篇讲；引用帖连被引用的内容一起讲。全景和每件的句子里的数字和日期必须出现在它引的材料里，程序核对，对不上重写一次，再不对用兜底版。兜底版由程序出：主题名、一句「这次的说明没写成」、每件事的标题、事实行和链接。

去重：每件事的键（status id、规范化 URL、arXiv id、仓库）在这个主题 30 天的结果里出现过就不再列，延续除外。键不同的，按 ARA 的跨源去重（`dedupe_headline_alerts.py` 的核心，MIT，移植到 `info/rank/dedupe.ts`，中文按二元组）：共享词 ≥ 4 且 Jaccard ≥ 0.5 算同一件；Jaccard 在 [0.35, 0.5)、共享词 ≥ 3 的交给模型，只回 `{id, verdict, confidence}`，只有 duplicate 且 high 才压掉，失败一律照发。

送达：结果进盒一项，`kind: "topic-search"`，origin 是门口那天，body 指结果文件；run 带 `deliverTo` 门口（68），结果在那天的门口对话里是一张结果卡（卡片注册表），点盒里那项打开到这张卡。第一次和每天的结果都这样。现有每日简报不变，持续主题的每日增量在合并之前是这个主题自己的一项。

源健康按（主题、查询、源）记，写进采集端状态文件，源页显示：上次取到的时间、读到条数、新条数、过地板条数，「没取到」（停手、解析失败）和「没新内容」分开。

## 展开与全文

用户看结果卡时：

- 「展开讲讲」第 n 件：Lumen 用已登记的材料详细讲（门口工具 `read_topic_material`，按结果件号和材料号读正文），用户不读全文。已有材料答不上的，Lumen 派详细资料 run，当场说多久能到，回来接着讲。
- 「我要全文」「好好读一读」：出合订本。这件事有详细资料就直接交给装订器；没有就派详细资料 run，结束后交给装订器。

Lumen 按用户的话判要的是听还是读；拿不准先讲，讲完一句话问要不要全文。

### 详细资料 run

kind `dossier`，agent worker，`synced` tier，`requires: [WEBVIEW_FETCH]`，排队同上。idempotencyKey 是 `dossier:<结果件 id>`：同一件还在排队或在跑时再要，Lumen 说已经在做；做完再要是新的一次（`dossier:<结果件 id>:<n>`）。参数里带用户要的是讲还是全文。

一个 agent 多轮调工具（`legion/subagent` 的 `runSubagent`），日常档。种子是那件事和主题搜索时已登记的材料：帖子只证明作者说了什么，要顺着它的链接和点到的实体到 X 以外找原始材料（ARA 推文种子模式）。

开始前程序先查本主题已有的文档（移植 ARA 的 `prior_context.py`，MIT）：按标题 2 分、小标题 1 分对种子标题和正文首段打分，中文按二元组，阈值 2 取前 5，编号 `P1`…，每条给标题和开头 400 字；另把主题里所有文档的来源 URL 规范化后建表。

工具，参数都只有编号和短文字：

| 工具 | 做什么 |
|---|---|
| `plan` | 开头调一次：4 到 8 个可回答的问题，每题写明什么算一手；2 到 3 个证伪问题（什么会推翻这件事的说法）。程序编号 `Q1`…、`F1`… |
| `x_search` | 查询词。程序在桌面 webview 按上面的节奏读一屏到几屏，回编号帖子，格式同重排的候选 |
| `arxiv_search` | 查询词，走 arXiv 插件的 `search` 槽，回编号论文 |
| `web_search` | 24 的工具，返回的来源由程序编成候选 |
| `open` | 读候选 #n，86 的 `open`：读法登记表、站点适配器（arXiv、GitHub、Drive）、通用网页和 PDF；X 帖子给出自身全文候选和全部外链候选。是引子还是正文，由模型判断 |
| `pick` | 选一份材料：编号、角色（一手、二手、评论、反方）、回答了哪些问题号 |
| `ask` | 在某个问题下加追问，挂在它下面（每题最多 3 个追问、最多两层） |
| `finish` | 一句说明，结束 |

每轮模型看到的进度由程序写：每个问题挂了哪些材料、还缺哪些。

够了的判据由程序数：每个 `Q` 至少一份一手材料；每个 `F` 至少一份反方材料，或用 `x_search` 和 `web_search` 各查过一次没找到（程序记下查过什么）；选中的材料 3 到 20 份。不满足时 `finish` 被拒，回缺的问题号。上限（初值）：工具调用 60 次、`x_search` 10 次、`open` 30 次、模型轮数 30、时长 60 分钟。到上限就按已选的交出去，缺的问题号写进交接。已经在本主题里的材料（规范化 URL 命中）不能 `pick`，要提它就写 `P` 编号。

结束后：要讲的，结果送达门口（`deliverTo`），Lumen 的答铃回合用 `read_topic_material` 读选中的材料接着讲；要全文的，写交接给装订器。一份材料都没选中，run 失败，盒里一项说没找到和查过什么。

### 材料登记

主题搜索的 `verify` 和详细资料的 `open` 每读到一份东西，程序登记一份材料，`info/dossier/registry.ts`，挂在结果件上：

| 字段 | 内容 |
|---|---|
| `id` | `M<n>`，同一规范化 URL 只登记一次 |
| `url`、`canonicalUrl` | 规范化移植 ARA `source_cache.py` 的 `canonicalize_url`：去 `utm_*`、`fbclid` 等追踪参数，query 排序 |
| `title`、`author`、`publishedAt` | 读法和适配器读出来的 |
| `reader` | x、web、arxiv、github、drive、pdf |
| `facts` | 程序取的事实：star、最近提交、release、arXiv id 等 |
| `hash` | 正文内容哈希 |
| `sections` | 按标题边界切的节 `M<n>.§k`：小标题、字数。整份 PDF 没有节 |
| 正文 | 可读稿（`Manuscript`）或整份文档的字节，缓存在 run 目录 |

模型在任何地方提到材料，只写 `M3`、`M3.§2`、`P2`；程序校验编号存在。

### 交给装订器

```ts
interface DossierHandoff {
  runId: string;
  topicId: string;                                   // 主题配置的 topicId
  seed: { resultItemId: string; material: string };  // 种子材料的 M 编号
  plan: { id: string; text: string; kind: "question" | "falsify"; parent?: string }[];
  materials: RegisteredMaterial[];                   // 程序登记的全部材料，含没选的
  picks: { material: string; role: "primary" | "secondary" | "commentary" | "opposing"; answers: string[] }[];
  prior: { id: string; documentHash: string; title: string }[];
  discrepancies: { post: string; says: string; evidence: string }[];  // 看原文时对不上的
  gaps: string[];                                    // 没答上的问题号
}
```

装订器怎么接、合订本内部怎么排，归装订那边。装订出的文档入库挂到主题配置的 `topicId`，入库由 reading 注入（同 86），文档经同步到手机。盒里来一项，`kind: "dossier"`，origin 指那张结果卡，标题由程序写「全文：<种子标题>」，点开进阅读器。
