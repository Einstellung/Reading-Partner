## 一、信息架构的第一性设计：顶层容器是"主题"，不是"书"

用户的真实场景是主题阅读（syntopical reading）：带着一个问题读一批材料——几篇论文 + 几本书。

所以建的不是书架，是"主题项目"，里面挂多份 PDF/EPUB。由此推出几条结构性结论：

- AI 的记忆和笔记都长在主题上，不是书上，跨材料连续。AI 能说出"这篇的做法和你上周读的那本第三章矛盾"这种话。
- 最终产出是主题级的一份，不是每本书一份。
- 与微信读书 AI、NotebookLM 的差异就在这里。

## 二、陪读闭环

### 读之前（开题）

新建主题时用户说明：为什么读、想回答什么问题。AI 据此生成阅读问题清单。这一步必须足够轻（一句话也行），否则会变成没人用的仪式。

### 读的过程中：内容进入 AI 的四条通道

按动手成本从低到高：

1. 划线——用户的自然动作，AI 自动可见；
2. 划线 + 批注（打字）——AI 可针对用户的批注回应，不只是原文；
3. 选中 →"问 AI"（划词菜单入口）——即问即答；
4. 圈选问 AI（Pencil 圈一块区域）——对付 PDF 图表和公式。技术上是临时手势层，不存墨迹。

> 通道 3 已落地为"AI 笔"（模式在前、选区在后）。通道 4（圈选问 AI）于 2026-07-13 废弃：替代方案是系统截图 + Pencil 标记 + 粘贴进对话，表达力更强，且是 iOS 原生肌肉记忆。见 [03-陪读交互-通话模型.md](./03-陪读交互-通话模型.md)。

AI 始终知道上下文——当前页码、刚划的内容、主题、memory。用户问一句"这里没看懂"就够，零复制粘贴。这是"陪读"与"开着聊天窗口"的区别。

### AI 行为原则

AI 默认不主动插话，只在被划线/提问时响应，读的心流不能打断。"主动模式"（如读完一节主动提问检验理解）可做成开关，默认关。

## 三、核心机制：三层记忆模型（三版演进）

### 被否的第一版：逐条审批制

AI 每条回答下带"存入笔记"按钮，人逐条筛选进笔记。否决理由：把沉淀成本摊到每次对话上，读得越投入打断越多。

### 被否的第二版：自动合并制

AI 定期把对话自动"改写合并"进人类可见的主题笔记，人用 diff 提示 + 直接编辑保持掌控。否决理由：AI 直接写人的笔记，需要 diff 提示、编辑权限规则等一堆补丁机制，且笔记的最终形态不应由 AI 单方生成。

### 定稿的第三版：三层模型

映射 Claude Code 的 transcript / MEMORY / 交付文档三件套。

第一层：对话流——原始记录，完整保留，不加工。

第二层：AI 自己的笔记（memory）——给 AI 自己用的，不是人类交付物。AI 持续维护：读到哪、用户卡在哪些概念、⭐（标记"这段值得记住"，见第四节）过什么、每份材料核心立场、用户与材料的分歧点。

- 存在目的是跨会话的陪读连续性。主题横跨几周、几本书、几十场对话，原始对话流放不进上下文；有 memory，三周后翻开第三本书，AI 仍记得"你读第一篇论文时对这个假设持怀疑态度"。
- 人可随时点开查看（建立信任、排查理解偏差），但按 AI 自己好用的方式组织，不追求文笔。
- 更新时机完全自动化：会话结束后台静默更新，无需确认、无需 diff 提示。不是人的交付物，第二版里的那些补丁机制整个不需要。
- memory 记错了，人不直接编辑，在对话里纠正（"你记错了"），AI 自己修正。memory 归 AI 所有。

第三层：最终笔记（人触发，人机共创）。

作废 2026-08-21：整层已被 [31](./31-读完之后的梳理与讲.md) 的"梳理对话 → 一场讲 → deck"取代，代码里从未有过共创路径。以下正文留作历史。

用户想整理时才整理（读完一本书、主题读完、或某天有感觉了）。触发后进入共创会话：AI 基于 memory + 划线批注 + ⭐对话起草稿骨架，然后人机在编辑器里一起迭代（"这段展开""这两点合并""这个观点不对，我的理解是……"）直到满意。笔记每条带出处锚点（哪本书哪页哪条划线，可跳回原文）。PPT 从这份笔记生成。起草稿的输入就是第五节那份痕迹列表——划线、批注、⭐、AI 对话——加上 memory。

### 该结构的红利

最终笔记诞生于用户全程在场的共创，每个字都过目，笔记不会变成 AI 话语堆积场；memory 不面向人，可以自由混乱。

AI 核心选型（pi）与第二层 memory 的设计定稿，见 [02-AI核心与memory设计.md](./02-AI核心与memory设计.md)。

## 四、人的信号：⭐重点关注

⭐是一个手动标记，语义是"这段值得记住"。设想中它同时喂两头：memory 中权重最高，共创起草稿时优先采用；并和划线、批注一样显示在第五节的痕迹列表里。

落地状态：⭐ 从未实现。annotation 上的 `starred` 只是引擎适配层的遗留透传字段（`src/reading/engine/convert.ts`、`wire-engine.ts`），没有 UI 调用点，蒸馏也不读它。今天人的信号只有划线、批注和对话。

划线和批注天然是高权重信号（用户亲手留下的思考痕迹），沉淀权重高于 AI 自己的话。

## 五、界面布局

2026-07-13 修订：AI 不是常驻侧栏。AI 通话展开时聊天接管整个窗口、阅读缩成画中画卡片，全端统一（含桌面），见 [03](./03-陪读交互-通话模型.md) 跨端一节。

```
阅读时                          通话主画面态
┌──────────────┐              ┌──────────────┬────┐
│   阅读区      │      ⇄       │  聊天(全窗,   │📖卡│
│ (reader引擎)  │              │  ChatGPT式)  │片  │
│ 笔架/AI笔     │              │              │    │
└──────────────┘              └──────────────┴────┘
```

痕迹列表在左，对齐 Zotero 的 Annotations 面板位置，但它是浮在阅读区之上的抽屉、不占一栏，全端默认关闭（PC 也是），顶栏按钮开合。抽屉顶上三个 tab：Outline、Marks（痕迹）、Prep（[09](./09-学习机模式.md)）。AI observations 不在这里，它是主题级的，在主题侧栏。搜索框仍未做。

痕迹列表平时不是笔记：用户在书上留下的所有东西按顺序排着——划线、批注，以及"这条划线下面跟 AI 聊过"的小标记（AI 星标）。形态上就是一个 annotation 列表，不发明新概念。AI 笔的划线和普通划线是同一类 annotation，星标只是它的一个属性，不是单独的分类。实现上列表由壳自己画：引擎不提供侧栏，annotation 数据本就存在壳这边（见 [04-reader对接备忘.md](./04-reader对接备忘.md)）。

AI 的对话内容本身不进这个列表。点星标打开的是那条划线的独立聊天线程（见 [03-陪读交互-通话模型.md](./03-陪读交互-通话模型.md) 线程模型），原文和问答都在，可以接着聊。长篇解释混进列表会把人的痕迹淹掉。

共创那部分（把痕迹列表织成一份人类笔记文档、独立的共创工作模式）随第三层一起作废，见 [31](./31-读完之后的梳理与讲.md)。

iPad 竖屏走的也是"通话模型"——书与 AI 画中画互换，详见 [03-陪读交互-通话模型.md](./03-陪读交互-通话模型.md)。语义层跨端一致（接通 / 通话中 / 挂断），表现层也跨端一致：都是主画面加画中画互换，没有"桌面 AI 栏常驻展开"那一版（2026-07-13 否）。

## 六、完整闭环一句话

读（划线/批注/提问）→ AI 默默维护观察 → 读完发起梳理对话 → 一场讲 → PPT，见 [31](./31-读完之后的梳理与讲.md)。

人的管理负担全程为零，掌控点只在梳理那一场对话。
