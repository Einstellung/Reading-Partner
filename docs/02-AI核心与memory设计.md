> 补记（2026-08-06）：本文第二部分的 memory 更名为 AI observations（AI 观察），正文照旧不改。改名的理由是叫法一直是歪的——这套东西记的不是 AI 自己的经历，而是 AI 对读者的观察：读到哪、卡在哪、他信什么、他有什么背景。适配器的方法名 `listObservations` 本来就是这么写的。改完之后判据也清楚了：AI 自己说过什么不算观察，读者留下的痕迹才算；而且观察天然可以被读者反驳（"你这条看偏了"），和"纠错走对话"是同一件事。代码搬到 `src/observation/`，模型看见的工具改叫 `observation_search` / `observation_read` / `observation_update`。盘上不动：`memory-<topicId>/` 目录名、`meta.json` 的字段名、同步范围按文件名匹配的规则全部保持原样（Drive 里已有真实数据，改名要迁移，风险大于收益），读写这些路径的代码处有注释说明这是历史名。事件日志里的 `distill-run` 等类型名同理不动。本文件名里的 memory 也照旧。模块后来搬回 `src/memory/`，观察这一类材料落在 `src/memory/observations/`，那次改名的理由在那一层继续成立；顶层叫 memory 是因为模块还装着 `user-profile.md` 和 `info-feedback.jsonl`，这两样不是观察。盘上的 `memory-<topicId>/` 目录名、`meta.json` 字段名、事件类型名照旧不动。

# 第一部分：AI 核心选型——pi（badlogic/pi-mono）

## 选什么

只采用 pi 的 `pi-ai`：统一 LLM 接口，30+ provider、流式输出、工具调用、TypeBox schema 校验。agent 循环走的是下面注意点 4 的兜底方案，自己写，落在 `src/ai/agent.ts`（479 行，只用 pi-ai 的 `Provider.stream` 和 `validateToolCall`）。

不用 `pi-agent-core`（原计划采用，最终没引），也不用 `pi-coding-agent`——后者是一个 Node 终端产品，不是我们要的库。

## 采纳理由

1. pi-ai 明确支持浏览器环境（核心代码无副作用，可打进前端 bundle）。我们零后端，AI 循环必须跑在 Tauri webview 里，iPad 无 Node 是死约束。
2. MIT 协议，与壳的许可证（PolyForm-NC）兼容。
3. 模型可插拔（Claude/GPT/Gemini/DeepSeek/Kimi/Ollama）：陪读可用便宜模型，重活用最强模型。
4. 我们的 AI 是 agentic 形态，回答前可能要调工具取上下文、检索材料。

## 分工架构

```
你的 AI 层
├─ 陪读 persona 和 prompt（开题、解释风格）             ← 自己写
├─ 上下文装配：每轮自动注入页码/选区/最近划线/memory   ← 自己写
├─ 工具集：读取阅读上下文、检索主题材料、查批注、
│         读写 memory、生成出处锚点                    ← 自己写
├─ agent 循环（src/ai/agent.ts）                       ← 自己写
└─ pi-ai（模型接入、流式、工具调用校验）                ← 白拿
```

与阅读引擎完全对称：引擎是白拿的核，pi-ai 是白拿的模型接入，产品长在连接层上。

## 已知注意点（如实记录）

1. 凭据放客户端，本地应用模式：Anthropic 和 OpenAI 走订阅 OAuth，DeepSeek 走 API key，细节见 [05](./05-AI接入备忘.md)。将来若公开发行再加代理后端。
2. CORS：webview 直连各家 API 可能受限。解法是 HTTP 请求走 Tauri Rust 侧发出，这是第一个要碰原生层的地方，量很小。
3. pi 项目年轻、API 会变：锁版本应对；MIT 协议下最坏情况 vendor 进来自维护。
4. pi-agent-core 的浏览器兼容性需实测（pi-ai 已确认支持浏览器）。兜底方案：基于 pi-ai 自写精简 agent 循环——这条后来就是实际走的路。

## pi 自带什么、不带什么

自带会话持久化（append-only JSONL 树，支持恢复/fork/分支）和上下文压缩（compact），可作为三层记忆模型第一层"对话流"的实现参考。不带跨会话长期 memory；memory 本就该是产品层设计而非框架功能（Claude Code 的 memory 也只是文件目录 + prompt 规则 + 读写工具）。

>
> 落地状态（2026-07-19）：蒸馏新增"上次以来的安静划线"输入——按 `meta.json` 的 `lastAnnotationDistillAt` 取本书此后创建的批注（页/选中文/批注，最多 40 条最近的，超出在 prompt 里标注），作为独立块喂给蒸馏，prompt 指示判断这些多为静默的划线是否成一个值得记的 PATTERN（读者反复划什么、在哪些主题/页停留），成则写一条聚合 memory（通常 understood-concept / belief / stuck-point，锚到这些批注 id），绝不一划一条，可以不记；蒸馏成功后才推进时间戳。过滤与格式化是纯函数，单测。另：开场上下文装配在本书有 overview.md 时加入"读者笔记的全书框架"块（按段落边界截到约 1500 字）。
>
> 落地状态（2026-07-30）：蒸馏改跑在子 agent capability 上（`src/ai/subagent/`）。蒸馏什么、怎么策展、两个触发点都不变；不完成的 pass、时间戳纪律和 `evidence: "optional"` 的理由见 [25](./25-子agent与上下文隔离.md)。
>
> 落地状态（2026-08-06）：梳理对话接上蒸馏（`src/memory/observations/retell.ts`，[31](./31-读完之后的梳理与讲.md)），和读书蒸出来的写进同一个观察池。判据是贵且久——要读很多才能得出、一段时间内还成立的判断才写下来。观察类型加到七种，新增 `can-explain` / `cannot-explain`（读的时候没懂是 stuck-point，懂了但张嘴讲不出来是 `cannot-explain`）。两条纪律写死在提示词里：一是不采信考官自己在对话里下过的结论，只从读者说的话判断；二是每次蒸馏第一步是拿整份观察索引对账，这段对话解决掉的旧观察就地更新（可以跨类型），正文加时间线保留演变，绝不新旧两条并存。增量游标只管输入的消息，不管输出的观察。
>
> 落地状态（2026-08-10）：触发点从"挂断 + 裁剪兜底"改成欠账模型（`src/memory/observations/arrears.ts`）。读书不聊天的一整本书原先一条观察都蒸不出来，因为两个触发点都长在对话上。现在欠账从盘上的数据推出来——本书 `annotations-<bookId>.json` 里晚于该书游标的标记数，和线程里晚于该线程游标的读者消息数——所以断网、退出、崩溃都不丢账。app 开着时每 30 分钟看一眼，另加启动、回前台、关书/切书各看一眼；每次最多跑一趟，选欠账最多的那个 topic，topic 内对话优先于纯划线。闸门是时间和量都要够：距上次蒸馏 ≥ 30 分钟，且新增划线 ≥ 5 条或有新的读者消息 ≥ 1 条。游标进 `meta.json`：`distilledMessages` 每线程已蒸的消息数（和梳理共用，线程 id 不重叠），`distilledMarks` 每本书已蒸到的最新标记时间——按书而不按 topic，否则一个 topic 里 A 书跑一趟就把 B 书更早的标记埋到游标底下。纯划线没有对话可读，走自己的提示词（不复用 transcript 那套）：如实说这次没有对话，让蒸馏器从标记的分布读——读到哪、注意力落在什么上、是否反复回到同一主题；并写死"划线只证明注意力不证明理解"，禁止只凭标记记 understood-concept。选哪个 topic、跑不跑，是纯函数，单测。

## 决策背景：否掉重型 memory 引擎路线

曾调研过 Hindsight（vectorize-io）、LangMem 等开源 memory 引擎（该调研文档已删除，此处记录结论以免重新踩坑）：

- Hindsight 的机制与需求匹配度确实高——bank 映射主题、observation 自动合并、证据锚点、矛盾修订，几乎条条对上。但它是自托管服务端（Docker/K8s + Postgres/pgvector + 后台 worker，无嵌入式/浏览器模式），采纳它等于推翻三条既定架构决策：零后端、纯 TS 单语言（LangMem 更是 Python）、iPad 平权。
- 规模也错配：那套机制（事实抽取、向量召回、时态矛盾追踪）是为平台级多用户海量事件设计的；我们是单用户、单主题作用域，一个主题几十场会话、几百条划线，Claude Code 式的文件方案够用。
- 决议：第一版自建轻量 memory 引擎；重型引擎降为二阶段候选——将来若因多端同步等原因后端反正要出现，再做对照 PoC，用数据证明值得再换。

### 从该调研保留下来的引擎无关原则（照单全收）

1. 边界纪律：原始记录是事实源（业务库，完整不可丢）、memory 是可随时重建的派生视图、最终笔记是人的作品，memory 引擎坏掉不应损坏另外两层。
   作废 2026-08-19：第三层不再是人的作品，写出来的东西读者是 lecture 入口不是人（`src/reading/prep/chapters/chapter.ts`），v1 那批给人读的章笔记已被 `purge.ts` 在启动时从盘上和 Drive 删除，见 [31](./31-读完之后的梳理与讲.md)。前两层的边界纪律照旧。
2. Memory Adapter 窄接口（retain/recall/listObservations/correct/rebuild）：业务层不感知引擎，使引擎可替换。
3. 两条写入通道：高信号事件即时写——划线、批注、⭐（"这段值得记住"的手动标记，见 [01](./01-交互设计.md) 第四节，从未实现），以及用户在对话里明确表达的观点；会话 transcript 在挂断时批量蒸馏，不逐条触发。
4. 两段式读取：进主题时注入短快照，提问时按需召回。
5. 四段式上下文装配：当前阅读上下文（实时取，不进 memory）/ 主题短快照 / 按问题召回的 memory（带来源 ID）/ 原始证据（按需回查）。
6. 不采用的捷径：
   - 纯向量 RAG——不会维护"用户以前信 A 后来纠正为 B"的演变，也分不清用户观点/材料观点/AI 回答；
   - 全量 transcript 常驻 prompt——成本加注意力稀释；
   - 让 memory 直接当最终笔记——重新引入已否决的"AI 单方写人的笔记"（见 01 第三节被否的第二版）。

## 定稿方案：结构学 Claude Code，管线学 OpenClaw，领域层自己做

参考了两个主流 agent 的 memory 机制。两者均属"文件型、agent 自维护、prompt 驱动"流派，且都不是可安装的库，抄的是设计不是代码。

### 从 Claude Code 抄结构

- 按主题隔离的记忆目录（对应它的按项目隔离）；
- 索引 + 明细两段式：索引常驻（限制行数），明细文件按需读；
- 每条记忆带类型/元数据、一事一文件、去重纪律（有相关就更新不新增、错了就删）——memory 是"当前理解的最新版"，不是日志堆积。

### 从 OpenClaw 抄管线

- 分层蒸馏：transcript 存档 → 会话笔记 → 定期蒸馏进长期 memory、清过期条目；
- 会话收尾静默写入：触发静默 agent 回合，把值得留的写进 memory，即 01 中"合上书，AI 后台消化"的实现机制。触发点是挂断，即用户点 ✕ 结束本次对话（见 [03-陪读交互-通话模型.md](./03-陪读交互-通话模型.md)）；补充触发点是上下文将压缩时，因为一通对话可能长达数小时横跨多本书，只靠挂断触发太晚；
- 时间衰减：带日期记忆衰减、常青文件不衰减。"读到第几页"类进度信息该衰减，"用户对某假设持怀疑"类理解立场该常青；
- 混合检索（memory 长大后）：切块 embedding + BM25 + MMR；社区已抽出独立库 memsearch 可评估。第一版数据量小，可只用 BM25 关键词检索甚至纯快照。

### 两家都没有、属于我们领域层的

- 证据锚点一等公民：每条 memory 指回划线/批注/消息 ID，可跳回原文。锚点由交互天然给出——AI 笔划出的划线就是对话的宿主，一条划线上同时挂着颜色、批注和一场 AI 对话（见 03）；
- 领域 schema：读到哪、卡住的概念、每份材料核心立场、材料间冲突、用户与材料的分歧、用户信号权重高于 AI 回答；
- 产品化的"看看 AI 记了什么"查看面板；
- 纠错交互：人不直接编辑 memory，对话里说"你记错了"，AI 自己修正（memory 归 AI 所有，同 01 第三节的定稿）。

### 实现落点

纯文件 + 本地存储，零后端，TS 实现。通过 pi 工具暴露给 agent：`memory_read` / `memory_update` / `memory_search`。embedding 来源待定（API 调用，或第一版直接 BM25 绕开）。

## 为什么是"结构学一家、管线学另一家"

两家面对的遗忘问题不同。Claude Code 是项目协作者，仓库随时能查，真正会丢的只有查不到的那一小撮（用户是谁、纠正过什么、隐性约束），所以它在写入端做功：一事一文件、类型标签、重复就更新、错了就删、明确的"不该记什么"清单；读取端就一个常驻索引，没有向量、检索和衰减。OpenClaw 是常驻助理，活在消息流里，没有仓库兜底，事后才知道哪条重要，所以它写入宽松、复杂度全堆在读取侧：embedding + BM25 混合检索、MMR 去冗、30 天半衰期、后台蒸馏，外加上下文将被压缩时的静默保命回合。

我们的数据两种性格都有：划线、批注、⭐、用户的明确观点在发生那一刻价值就定了，适用写入端策展；陪读对话的 transcript 哪句将来有用当场说不准，适用先存档、收尾静默蒸馏、长大了再上检索。
