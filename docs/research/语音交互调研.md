# 语音交互调研

> 上游：[companion/27-实时语音](../companion/27-实时语音.md)、[info/33-语音简报](../info/33-语音简报.md)。调研日期 2026-10-14，只查资料没跑。原稿在 [../assets/voice-interaction-survey/](../assets/voice-interaction-survey/)：[01 现有链路](../assets/voice-interaction-survey/01-current-pipeline.md)、[02 端到端模型](../assets/voice-interaction-survey/02-e2e-models.md)、[03 级联与提速](../assets/voice-interaction-survey/03-cascade.md)、[04 噪声与多人](../assets/voice-interaction-survey/04-noise.md)。标「厂商」「自报」的数字没有第三方复现。

## 现状

info 语音通话从用户说完到 AI 出声的端到端延迟从没量过。按代码推算，不含模型的三段（端点判定、ASR 收尾、TTS 首句）下限约 2.2 s、典型约 3.2 s，加上模型，用户感受到的大概是 5–8 s。做得好的级联是 0.8–1.3 s（Pipecat 指南的预算合计 1293 ms，目标 1500 ms 以内）。这是推算，要真机量过才算数。

差距按项列（01 第 2、4 节，03 延迟预算）：

- 端点判定：能量 VAD 加固定静音 `hangoverMs` 1250 ms，业界用模型判停是 200–400 ms。
- TTS 整句合成完才交给播放器：iPhone 直连 12 句，请求到首帧 p50 628 ms，到整句收全 p50 1853 ms。改成首帧开播，第一句约省 1.2 s。
- 语音回合用文字聊天的同一个模型、思考档（默认 low）、全套工具和整条线程历史，没有语音专用的快档和短提示词。文字聊天一轮模型调用地板约 5 s。Claude 各档首 token（Pipecat voice-readiness 基准，2026-08-18，P50/P95）：Haiku 4.5 637/1615 ms，Sonnet 4.6 850/4126，Sonnet 5 1204/2465，Fable 5 3956/6496。该基准定 700 ms 为上限，Claude 里只有 Haiku 4.5 进线（[基准](https://www.pipecat.ai/benchmarks/voice-readiness)）。
- 第一句要等模型写出句号类标点再多一个字才能进 TTS，软边界提前发被冻结规则架空；英文 `.` `?` `!` `,` 都不是边界，英文回复要等换行或整轮结束。
- 说话期间 volatile 文本一直在出，模型却要等 hangover 和强制定稿之后才起。
- `prepareInfoTurn`、`quiet()`、工具构建都在 `speech-end` 之后才开始，没有前移到用户说话期间。
- 开场句预合成 `OpeningCache` 写了没接生产路径，「853 ms 变成 0」不成立。

噪声问题按项列（01 第 3 节，都是从代码推出来的）：

- 判据只有 -35 dBFS 的单缓冲 RMS，是在安静房间、手持 iPhone 16 上拟合的，不随底噪调整，不区分人声和噪声，不认人。
- 持续底噪超过阈值时 hangover 一直被刷新，轮次不收尾，AI 永远不答，也没有轮次时长上限。
- 底噪在阈值上下波动时反复 duck，播放音量一直在抽。
- 噪声持续 300 ms 就判成打断，当场停播。
- AI 还在思考、没出声时来噪声，会 abort 正在跑的模型回合；识别器没出字则 `speech-end` 为空串，不再发问，用户问了一句，AI 一直不吭声。
- 旁人说话只要够响就和用户一样开轮、打断、进转写；不够响但落在用户轮次窗 ±300 ms 内的会拼进用户那句。
- 回声余量只有 3.5 dB（-38.5 对 -35），09-05 换摆位后识别器写下了手机自己的声音。
- iPad 上一条都没测过。

## 结论一：延迟差距在级联自己的工程上

不换架构就能收回大半。按收益排：

1. TTS 首帧开播。句首即时裁静音、句尾边收边播。
2. 语音回合专用快档：不开思考，短提示词，固定前缀（系统提示、书的上下文）放前面走 prompt cache。受控研究里 prompt cache 让首 token 快 13–31%（[arXiv 2601.06007](https://arxiv.org/html/2601.06007v2)）。
3. 端点判定换神经 VAD 加 Smart Turn：VAD 用 200–300 ms 短静音触发，Smart Turn v3.2 判完没完，判未完再等，兜底 2–3 s。预计省 0.8–1 s。
4. 投机与预热：静音 300–500 ms 时用 SpeechAnalyzer 的 volatile 文本先发请求，用户续说就撤；Deepgram Flux 的同类做法中位省约 150 ms，尾部 5% 省约 350 ms（Telnyx，2026-01）。用户一开口就建好 LLM 和 TTS 连接，新建连接比复用连接首帧慢 180–240 ms（实测 536–754 对 355–515 ms）。装配（`prepareInfoTurn`、`quiet()`、工具）前移到说话期间。
5. 首句切到第一个逗号就送 TTS；中英文都按逗号和句末标点切。

小米 TTS 只收整句，不支持流式输入文本。要再压首包得换一家能流式收文本的，候选见 03「流式 ASR 和 TTS」表：阿里 `qwen3-tts-*-realtime`、CosyVoice WebSocket、讯飞超拟人、Cartesia、ElevenLabs。换之前先用 [docs/info/33](../info/33-语音简报.md) 的测试台量首包。

框架不换。Pipecat 和 LiveKit 都要一台服务器串三段，我们是端上直连各家 API，搬进去等于重做架构。能直接用的只有 Smart Turn（BSD-2）、Silero VAD（MIT）和 Pipecat 的做法。LiveKit turn detector、自适应打断的权重和 TEN 的 VAD、轮次模型，许可证都不能用，TEN 的轮次模型还明文禁止部署在终端设备。

| 框架 | 要服务器 | 许可 | 对我们 |
|---|---|---|---|
| Pipecat | 要 | BSD-2 | 看做法，不搬 |
| Smart Turn v3.2 | 不要，8 MB int8，CoreML 16.8 MB | BSD-2 | 用，毫秒级 |
| LiveKit Agents | 要 | 代码 Apache；turn detector 只许在 LiveKit Agents 里用 | 不能用 |
| TEN | 要，加声网账号 | Apache 加附加条款 | 不能用 |

## 结论二：噪声和多人换端到端也解决不了

端到端全双工在噪声和旁人说话下并不比级联稳，问题都出在把非语音或旁人语音当成插话（04 第 6 节、02「嘈杂环境与多人说话」）：

- FD-Bench（[2507.19040](https://arxiv.org/abs/2507.19040)）：Moshi 噪声下成功回复率约 60%，噪声触发的误打断 38-48%；Freeze-Omni 误打断只有 4-7%，成功回复率只有 10-15%。
- Moshi 在静音集误触发 168 次、噪声集 64 次（[2603.24144](https://arxiv.org/abs/2603.24144)）。
- MSI-Bench（[2609.24812](https://arxiv.org/abs/2609.24812)，多人场景 1152 例中英各半）：最强系统全通过率英文 66.8%、中文 54.5%，最强开源权重 34.0% / 19.3%。
- HumDial 总结（[2604.21406](https://arxiv.org/abs/2604.21406)）：多人说话和瞬态噪声仍导致误激活或漏检。

前端（VAD、声纹、打断规则）在两种架构下都要做。做法，按先后：

1. 能量 VAD 换 Silero v6（MIT，v6.2.3 于 2026-09-23 发布），同时拿 FireRedVAD 的 CoreML 版（Apache-2.0，2.2 MB）在自录的咖啡馆、电视、旁人说话素材上 A/B 定选型。FireRedVAD 自报误报 2.69%，Silero 在同一测试集 9.41%，但那个测试集是干净朗读语音。
2. 降噪只放在判定支路：原始 VPIO 音频给 ASR，GTCRN（MIT，48K 参数）处理过的副本给 VAD 和打断判定。通用增强会伤现代 ASR（[2512.17562](https://arxiv.org/abs/2512.17562)、[2603.04710](https://arxiv.org/abs/2603.04710)）。
3. 声纹：CAM++ 中英版（sherpa-onnx，Apache-2.0，28.3 MB）逐段验证。用户最初几轮在安静处说的话自动攒 10-20 s 算 embedding，存本地，之后每段和每次打断比对一次，不像本人就不送 ASR、不触发打断。阈值中英各标一次。帧级 personal VAD 没有中文模型，排后面。
4. 打断规则化：播放期提高阈值；连续人声至少 0.5 s；先暂停不停止；2 s 内没出字就从断点续播；转写够 3–4 个字且不在「嗯/对/好/是/哦」词表里才算打断，附和只记不停；打断时把助手消息截到已播出的部分，撤掉在飞的 LLM 和 TTS。耳机时放宽。
5. 核对 TTS 是否走同一个 VPIO 引擎（AEC 要播放信号做参考，录放分两个 audio unit 会留回声）。
6. 产品兜底，几家成熟产品的共同做法：用 `AVAudioSession.currentRoute` 检测耳机切策略；加静音键（Gemini Live 2025-12 把暂停键换成了静音键）；嘈杂时按住卢明说话，松手即结束一轮；首次进语音读 `preferredMicrophoneMode`，不是 voiceIsolation 就用 `showSystemUserInterface(.microphoneModes)` 弹系统面板（app 不能直接设置，[文档](https://developer.apple.com/documentation/avfoundation/avcapturedevice/preferredmicrophonemode)）。

TEN VAD、TEN Turn Detection、LiveKit turn detector 的许可证不能用。

## 结论三：Anthropic 仍无实时语音 API

纯端到端换掉 Claude 不成立：中文好的全双工模型推理不如 Claude，推理强的 StepAudio 3 三方 TTFA 8.83 s。值得做一次对照实验的是混合架构，前端全双工模型管轮次和附和，Claude 留在后端。

中英可用的开源全双工只有 MiniCPM-o 4.5（Apache-2.0，全双工端侧要 M4 Max 24GB，iPhone/iPad 做不了）。Moshi 系、NVIDIA 系、KAME 都只有英文。

| 方案 | 前端 | Claude 怎么接 | 部署与价格 | 要测的 |
|---|---|---|---|---|
| A. qwen3.8-omni-flash-realtime | 托管全双工，semantic_vad 过滤附和和背景噪声，中文强 | 做成它的 function：`ask_claude(transcript)`，拿到结果照读，Claude 原文存为检查点 | 只有 API，iOS 走 WebRTC/WebSocket，几天能接起来。阿里官方价每百万音频 token 输入/输出：新加坡 0.93/1.87、北京 0.848/1.696 美元；三方换算同系 Qwen3.5 Omni Realtime 约 0.16/0.82 美元每小时 | 中英混说识别、噪声和旁人说话下的误打断、首响、调 Claude 期间填充语是否自然、结果被改写的程度 |
| B. Gander（腾讯，Apache-2.0） | MiniCPM-o 4.5 当小脑，每秒出 listen/speak/interrupt/tool 控制 token | Brain 是 provider 注册表，把自带的 Codex 换成 Claude（Agent SDK 或直连 API） | 自托管，发布配置 3 张 GPU，可压到 1-2 张 24GB 卡；iPad 走 WebRTC。FDB v3 轮次 100%、过早打断 8%、工具 pass@1 0.40 | 同 A，另加小脑自答的比例和质量、交给 Claude 后追问或改口时任务能否正确续接 |

两路用同一套录音脚本（安静 / 背景人声 / 街噪 × 中文 / 英文 / 中英混，每格 20 回合），和改进后的级联比三个数：首响 p50/p90、误打断率、该停不停率。若两路在噪声下都不比改进后的级联好，就只做级联。

其余模型对比（延迟、许可、星数、更新时间）见 [02](../assets/voice-interaction-survey/02-e2e-models.md)，框架和轮次模型全表见 [03](../assets/voice-interaction-survey/03-cascade.md)，VAD、降噪、声纹、成熟产品做法全表见 [04](../assets/voice-interaction-survey/04-noise.md)。

## 待定

- 语音回合换快档要发起人定。Haiku 4.5 这类档位和 model-tiers 里「用户实时在等走对话档」的口径有关。
- Smart Turn 和 FireRedVAD 在中文上的准确率没公布，要用自己的中文朗读和讨论录音量；读书场景停顿比客服电话长，阈值要调松。
- VPIO 下 iPad 控制中心有没有麦克风模式，要真机看一次。
- 端到端延迟的基线要先在真机上量：`turn-log.jsonl` 有模型 `first-byte`，原生侧有 `RP-CALL` 日志，两边时钟没对上。
