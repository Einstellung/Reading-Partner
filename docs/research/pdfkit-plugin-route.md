# 手机 PDF：PDFKit 插件路线评估

2026-09-22。回答一个问题：手机上的 PDF 走 iOS 原生 PDFKit、经 Tauri 插件接进 app，要做多少东西、和现有 PDF 阅读能力差多少。只读调研，未改文件、未跑构建。

路线已关，见 [north-star/phone-reading](../north-star/phone-reading.md)。

## 1 现有 PDF 阅读器用到的引擎能力

引擎接口面是 `src/reading/engine/types.ts`（`EmbedPdfHandle` / `EmbedPdfViewProps`），壳侧的引擎无关契约是 `src/platform/app/reader-contract.ts:182`（`ViewInstance`）。`EmbedReaderPane.tsx` 把前者翻成后者，`wire-engine.ts`（1081 行）是全部命令式接线。

| 能力 | 今天怎么来的 | 手机续读下 |
| --- | --- | --- |
| 页面光栅 | EmbedPDF `RenderLayer` + `TilingLayer`，PDFium WASM 在 worker 里 | 必须 |
| 缩放 | `ZoomPlugin`，档位 0.5–3，竖排锁 fit-width、翻页锁 fit-page（`layout-modes.ts`） | 必须（393pt 上不缩放读不了） |
| 布局模式 | `vertical` 连续滚 / `paged` 一屏一页横翻，每本书存一份 | 翻页可以先没有 |
| 滚动与翻页手势 | 自研，`engine/gesture/` 3045 行：触摸路由、橡皮筋、惯性、双指缩放、滚动指示条 | 必须（滚 + 捏） |
| 文本层与选区 | `SelectionPlugin`；阅读区 `user-select: none`，选区由插件画 | 可以先没有（手机不复制、不查词） |
| 标注创建 | `AnnotationPlugin`，工具表 `ToolType`（`reader-contract.ts:156`）：highlight / underline / ink / eraser / note / text / image / navlock | 只要 highlight（EPUB 手机版就只有它） |
| 标注持久化 | 壳侧 `annotations-<bookId>.json`，zotero schema；`convert.ts` 双向翻译 | 必须，格式不能变 |
| 标注选中与弹窗 | `onAnnotationAnchor` 量视口矩形 → `annotation-selection.ts` 决定开不开编辑器 | 删除弹窗必须，编辑器可以先没有 |
| AI 引文高亮 | `highlightQuote`，Tier A 用引擎 `searchAllPages` 定位画紫框，Tier B 退回横幅 | 可以先没有（AI 在手机上全置灰） |
| 书内搜索 UI | 不存在。引擎的搜索只被引文高亮调用 | 可以先没有 |
| 大纲 | 不走引擎。壳侧 pdf.js `getOutline()`（`src/fulltext/extract.ts:27`） | 可以先没有 |
| 全文提取 | 不走引擎。壳侧 pdf.js `getTextContent()`（`src/fulltext/extract.ts`） | 可以先没有 |
| 图片提取与裁图 | 不走引擎。壳侧 pdf.js 渲染（坑 25：EmbedPDF 适配层没有区域截图） | 可以先没有 |
| 封面 | 走引擎。`covers.ts:51` → `engine/raster.ts` → `engine-singleton` | 已经在手机上跑着 |
| ViewState | `pageIndex` + `pageX/pageY`（未缩放页坐标、原点左上）+ `scale` + `layout` | 必须 |

两条落在前提上的事实：

- 全文、大纲、图片提取全部不经阅读引擎，用壳里另一份钉住的 pdf.js。换不换引擎都一样，手机上要不要它们只由「AI 上不上手机」决定，和 PDFKit 无关。
- 封面经 PDFium。`PhoneShelf` 的 `CoverBand` → `useCovers` → `covers.ts` → `raster.ts`，所以 PDFium WASM 今天已经在 iPhone 上被初始化（书架上有 PDF 时），[70](../70-手机读EPUB.md) 的「PDF 的封面照常渲染」就是这条路。「WASM 在 iPhone 上没验过」只对阅读器成立，对引擎启动不成立。

## 2 标注文件和坐标互认

盘上形状（`convert.ts:26` 的 `ZoteroAnnotation`，[64](../64-epub纸页.md)「标注」）：

| 字段 | 内容 |
| --- | --- |
| `position.pageIndex` | 0 基页号 |
| `position.rects` | `[left, yBottom, right, yTop]`，PDF 点、原点左下 |
| `position.paths` / `width` | 墨迹，每笔 `[x0,y0,x1,y1,…]`，同一套 PDF 点左下 |
| `sortIndex` | `makeSortIndex(pageIndex, topY, x)`（`convert.ts:105`），topY 是距页顶的距离 |
| `pageLabel` / `text` / `comment` / `color` / `tags` / `aiThreadId` / `starred` | 壳自己的字段 |

`convert.ts:112`/`:121` 的 y 翻转只因为 EmbedPDF 的 `Rect` 是原点左上。PDFKit 的 `PDFAnnotation.bounds`、`PDFPage.bounds(for:)`、`PDFSelection.bounds(for:)` 用的就是 PDF 用户空间、原点左下、单位点，和盘上格式同一个约定，不需要翻转。这是 PDFKit 路线唯一明确占便宜的地方。

需要为 PDFKit 重写一遍的：

| 东西 | 为什么 | 写在哪 |
| --- | --- | --- |
| zotero ↔ 原生标注对象的映射 | `convert.ts` 整份是对 `PdfAnnotationObject` 写的 | Swift 里再写一份（`PDFAnnotation(bounds:forType:.highlight)`、`quadrilateralPoints`） |
| `sortIndex` 生成 | 现成实现吃 topY（左上），PDFKit 给左下，要 `pageHeight - yTop` | 换算一行，但要和现有实现逐字节一致，否则 iPad 和手机排序不同 |
| 高亮的多行分段 | 现在是 rects 数组；PDFKit 高亮用 `quadrilateralPoints` | 映射规则要保证 iPad 画出来一模一样 |
| 墨迹 | PDFKit 的 ink 标注存 `PDFAnnotation` 的 paths（`UIBezierPath`），和 `position.paths` 的扁平数组不是一个形状 | 手机不画墨迹，但读到墨迹要显示，否则 iPad 画的线手机上消失 |
| 单测 | 现有 `convert` 的等价物在 bun 下测；Swift 那份只能在 Mac 上测 | 纯函数那半可以留在 TS、Swift 只做几何搬运，代价是每次标注都过一次桥 |

ViewState 互认：

| 现有字段 | PDFKit 对应 | 能不能直接换算 |
| --- | --- | --- |
| `pageIndex` | `PDFDocument.index(for: PDFPage)` | 能 |
| `pageX/pageY`（未缩放页坐标、左上） | `PDFDestination.point`（页坐标、左下） | 能，`y' = pageHeight - y` |
| `scale` | `PDFView.scaleFactor` | 能，但两边 fit-width 的基准（版心、页边、viewportGap）不同，同一个数字落地不是同一个视觉尺寸 |
| `layout` | `PDFView.displayMode` + `displayDirection` | 能，两个枚举拼一个 |

格式不必改，互认可行；要新写的是转换层，不是新格式。

## 3 Tauri iOS 插件的模子

`plugins/voice` 是仓库里唯一一个自建 Tauri 插件。照它的模子，一个 PDFKit 插件要这些文件：

| 文件 | voice 里的样子 | PDFKit 插件要做什么 |
| --- | --- | --- |
| `plugins/pdfkit/Cargo.toml` | `links = "tauri-plugin-voice"`（名字要和 `lib.rs` 的 `Builder::new` 和 ACL 命名空间一致，无编译期检查） | 照抄 |
| `plugins/pdfkit/build.rs` | `COMMANDS` 常量逐条列命令，生成 `permissions/autogenerated/`，要提交进仓库 | 每个命令一行 |
| `src/lib.rs` | `Builder::new("pdfkit")` + `generate_handler!` | 照抄 |
| `src/ios.rs` | `ios_plugin_binding!(init_plugin_pdfkit)`，每个命令一个 `run_mobile_plugin` | 照抄；参数结构体必须 `rename_all = "camelCase"`（Swift 用裸 `JSONDecoder`） |
| `src/fallback.rs` | 非 iOS 的空实现 | 必须有，否则桌面编不过 |
| `src/commands.rs` / `models.rs` / `error.rs` | 命令签名和 DTO | 新写 |
| `permissions/default.toml` | 手写 | 新写 |
| `ios/Package.swift` | 静态库，依赖 `../.tauri/tauri-api`，平台 iOS 26 | 照抄 |
| `ios/Sources/*.swift` | `class VoicePlugin: Plugin` + `@_cdecl("init_plugin_voice")`；每个命令带显式 ObjC selector（Tauri 按 `<command>:` 构选择器） | 新写：Plugin、PDFView 宿主、标注映射、手势/选区 |
| `src-tauri/Cargo.toml` | `tauri-plugin-voice = { path = "../plugins/voice" }` | 加一行 |
| `src-tauri/src/lib.rs` | `.plugin(tauri_plugin_voice::init())` | 加一行 |
| `src-tauri/capabilities/ios.json` | `"permissions": ["voice:default"]` | 加一条 |

编译验证：`scripts/ios-swiftcheck.sh --dirty` 把 commits 打成 git bundle scp 到 Mac，按 iPhoneOS SDK 编到 .o 为止，四秒出错误行号。只管类型，不管运行时、链接、签名、资源。脚本里 `PKG="plugins/voice/ios"` 是写死的，加第二个插件要改这一行。

### 原生视图盖在 WKWebView 上

voice 插件一行 UIKit 都没有。本仓库没有原生视图叠放的先例，这条路的每一个几何问题都是第一次。

| 叠法 | 做法 | 坑 |
| --- | --- | --- |
| 全屏盖住 | 插件从 `Plugin` 基类拿到宿主 viewController，present 一个装 `PDFView` 的控制器 | 顶栏、笔架、Aa 全部看不见。要么用 UIKit 重画一套（和 webview 里那套并行维护），要么 PDF 阅读屏在手机上长得和 EPUB 阅读屏不一样 |
| PDFView 在 webview 之上、只占阅读区 | JS 每次布局变化把阅读区的 CSS 矩形报给 Swift，Swift 设 frame | 顶栏和笔架只要在 PDFView 矩形之外就还能用；Radix portal 的 Outline / Aa sheet 贴底、会被 PDFView 盖住，必须在开 sheet 时把 PDFView 藏起来或缩小。滚动惯性、旋转、键盘、sheet 动画期间两层不同步会漂（原生 frame 是即时的，webview 布局是异步的） |
| PDFView 在 webview 之下、webview 透明开洞 | `webView.isOpaque = false`、`backgroundColor = .clear`，阅读区 CSS 透明 | sheet 和弹窗自然盖在上面，层级对了；但 WKWebView 整块是一个 UIView，hit-test 不按 CSS 透明度走，阅读区的触摸全被 webview 吃掉，PDFView 收不到手势。要么在 webview 上覆写 `hitTest` 按 JS 报来的矩形放行（要和 JS 的滚动状态同步），要么把手势识别器挂在 webview 上再转发。这一条没有现成方案，是这条路最大的未知 |

只有「PDFView 只占阅读区」的两种叠法能保住顶栏、笔架和 Aa，`PhoneReaderBar`、`PenToolbar`、`PhoneDisplaySheet` 不用重写；全屏盖住则要重写一套 UIKit 的。另外 Aa 对 PDF 无意义（PDF 不重排，改不了字号行距边距），手机 PDF 屏的那一格要换成别的。

## 4 两条路对照

| | PDFium WASM（现有引擎上手机） | PDFKit 插件 |
| --- | --- | --- |
| 新写代码量级 | 4–6 个新文件 + 改 3–4 处：手机 PDF 屏（`PhoneReader` 的 PDF 分支或兄弟组件）、手机版打开流程（`open-epub.ts` 的 PDF 对应物）、书架撤闸（`shelf-list.ts:141` 的 `PDF_ELSEWHERE`）、手势参数按 393pt 调（`engine/gesture/` 复用，不重写）。引擎、`convert.ts`、`wire-engine.ts`、标注层全部原样复用 | 15–20 个新文件，跨 Rust / Swift / TS 三种语言：插件 8 个骨架文件 + Swift 3–5 个（Plugin、PDFView 宿主、标注映射、手势转发）+ TS 侧实现 `ViewInstance` 的适配器 1–2 个 + 手机 PDF 屏 + 视图叠放的壳改动。`engine/gesture/` 那 3045 行在这条路上作废（PDFKit 自带滚动和捏合） |
| UI 要不要为 393pt 重排 | 要，但只是壳：iPad 的顶栏/侧栏/笔架布局不能直接用，和 EPUB 手机屏共用 `PhoneReaderBar` + `PenToolbar` 就行 | 一样要，且多一层：原生视图和 web 壳的几何要对齐 |
| 正文字号问题 | Letter 612pt 宽，393pt 屏 fit-width 是 0.64 倍，10pt 正文渲染成 6.4pt | 一样。PDFKit 没有重排（Apple Books 的重排不是 PDFKit API）。两条路都不解决这件事 |
| Android | 不变。同一份前端产物，Android 有 PDF 就有 PDF | PDFKit 无 Android。三选一：Android 继续不给 PDF，从此两端阅读能力永久分叉；Android 走 WASM，两套引擎并存（两条标注写入路径、两套 ViewState 生成、两套手势，测试面翻倍，`tests/layering.test.ts` 要给插件适配层登记新目录）；Android 上用系统 `PdfRenderer` 再写第三套（无文本层、无标注，等于重做） |
| 离线 | 全离线 | 全离线 |
| 包体 | 4.6 MB（`public/pdfium/pdfium.wasm`），已经在包里 | 系统框架 0 增量，但 WASM 不会因此从包里去掉：桌面和 iPad 的阅读器、以及所有端的封面渲染都还要它。除非给 iOS 单独裁一份前端产物（现在没有这种分叉）。PDFKit 不省包体 |
| 已知风险 | iPhone 上 WASM 的启动时间、内存峰值、滚动帧率，见 [pdfium-on-iphone](./pdfium-on-iphone.md)。坑 21 已解，坑 118 说 iPad 模拟器上 PDFium 和触摸都是真的 | webview 与原生视图的 hit-test 与层级，无先例、无成方案。Swift 那半在本机只能靠 `ios-swiftcheck.sh` 编类型，运行时只能在 Mac 或模拟器验，迭代回路比 TS 慢一个量级。PDFKit 的高亮样式、选区、ink 绘制行为都由系统决定，和 iPad 上现有的画法对不上就是「同一条线两台设备长得不一样」。Tauri 的 iOS 插件文档薄，`gen/apple` 是生成物、本机没有，工程文件的改动只能在 Mac 上试 |
| 顺带得到 | 无 | 系统级选区菜单、查词、分享、VoiceOver、自动滚动这些 PDFKit 白送；但它们都在「可以先没有」那一列 |

两条路共同要做、和引擎无关的：手机 PDF 屏的壳、书架撤闸、打开流程、ViewState 读写、标注读写、进度显示。这部分在两条路上都是同一批文件。
