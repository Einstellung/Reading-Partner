# 趋势雷达调研：new-term-radar 及同类项目

2026-10-13 对 zhuyansen/new-term-radar 及同类项目的调研。起因是希望将来不再自己刷 X 等信息渠道，由 AI 自己查、过滤、筛选；这里看这类项目怎么发现新冒头的名字，哪些机制能搬进 info 侧。

## 一、zhuyansen/new-term-radar

**基本情况**
- 572 星、249 fork，MIT。
- 仓库 2026-10-12 创建，7 个 commit 全在当天，是从作者 agentskillshub.top 背后的 radar 抽出来的。
- Python 标准库，约 2300 行，74 个离线单测。

**它解决什么问题**：给做 SEO、导航站、newsletter 的人每天报"刚冒头的专名"（新模型、产品、仓库），赶在关键词工具收录之前。目标是"名字"，不是话题或观点。

**数据从哪来，各信号怎么判新**（以源码为准）

| 信号 | 怎么抓 | 判"新"的规则 | 依赖 |
|---|---|---|---|
| X | 经 AIsa 中转调 `get_twitter_user_last_tweets`，每个账号取最近 20 条 | 见下方"名字抽取"和"X 的判新" | AIsa key（付费，$0.003/账号/次） |
| Hugging Face | 公开 API `api/models?sort=trendingScore`，取前 100 | 本轮前 50 里、上轮前 100 快照里没有的。`base_name()` 用正则剥掉 gguf/awq/fp8/instruct/27B 之类后缀，同一底座的量化和微调版归成一条 | 无 |
| GitHub | Search API 查 `created:>=14天前 stars:>=300`，2 页 | 日均星数 = stars/age ≥200，或比上次快照多 ≥400。另取 owner 的显示名生成搜索变体（"niko strata"） | 无 |
| Sitemap | 读配置里的站点 sitemap，和上次的 URL 快照做差 | 新 URL 的 slug 切词，按"不同 URL 数"计数，`lift = n / (基线URL数 × 新旧比 + 1)`，至少 3 个 URL | 无 |
| 新域名 | DataForSEO whois（经 AIsa） | 注册且首次收录都在 90 天内、有排名关键词的域名 | 约 $0.13/查询。README 自己承认目前坏着 |
| Search Console | 用户自己站点的数据 | 自家站首次出现展示量的查询 | Google OAuth |

**名字抽取**（`terms.names()`）：
- 首字母大写、带数字（Qwen3.8）、词内大写（HyperFrames）、三个以上大写字母的词，都算"像名字"。
- 后跟的数字并入（Opus 5.5），相邻名字词最多连三个，遇标点或中文断开。
- strong 模式只保留含"确定是名字"那类词的短语。

**X 的判新**：维护一个 60 天词表（所有账号共用）。本轮出现、词表里没有的名字，满足以下之一才算：
- 至少 2 个不同账号用过；
- 或只有 1 个账号用过，但必须是 strong 名字，且那条帖子 ≥100 赞。

单条爆帖最多贡献 3 个名字。

**判"是不是名字"**（`judge.py`）：
- 每 25 个候选一次 chat 调用（默认 gpt-4.1-mini，也走 AIsa），每个候选带最多 3 处出现位置当证据。
- 模型打 0–1 分，过 0.5 算名字。提示词是正反例式的（"opus 5.5" 是名字，"dashboard" 不是）。
- 调用失败也照样出报告，只是不排序。

**去重和打分**：
- 各信号的候选按字符串合并。
- 排序依次看：过不过名字线、命中几种信号、最早那个信号的先后（X > HF > GitHub > sitemap）、名字分。
- `_drop_nested` 去掉被更长短语包含的子词，比如有 "opus 5.5" 就去掉 "5.5"。
- `known_terms` 用子串匹配标"已覆盖"。

**事后核验**（`review.py`，这个仓库最值钱的设计）：
- 每个入库的 lead 在 14 天后用 Google Trends 回查。
- 判"涨了"的标准：峰值 ≥ 自身基线 × 2，且比基线高 ≥10。
- Trends 最后两天的数据没定型，读之前一律丢掉。
- 按信号统计命中率和提前天数，回答"哪个信号可信"。

**附加的关键词表**（`usecases.py`）：Sonnet 读帖子和 README，提出"人们用它做什么"的通用搜索词；再用一次模型复筛，查 Google Ads 量和 Trends 曲线，给出 prioritize/watch/skip。纯 SEO 用途。

**输出、调度、成本**：
- 每次出 Markdown 报告和 report.json，leads 存进 SQLite（`state/radar.db`），可选用 Resend 发邮件。
- 用 GitHub Actions 跑：sources 每 8 小时、daily 每天一次，状态放在 Actions cache 里。cache 丢了，复盘历史就从零开始，README 自己说了。
- 示例配置 35 个 X 账号一天读三次，约 $15/月（X $10，关键词表 $5）。所有付费调用都走 AIsa，README 里的注册链接是作者的推荐链接。

**README 和代码对不上的地方**
- Known issues 写"Search volumes are not in the report"，但关键词表明明有 Ads 量和每日搜索估计，这条过期了。
- 说 X 是"60 天里第一次用的名字"。实际词表只来自 radar 自己抓过的帖子（每账号每轮 20 条），所有账号共用，旧帖也会进表。头几周的实际含义是"radar 开跑以来没见过"。
- 自称"first eight names"、"a real run" 的效果数据，git 历史里看不到，没法复核。命中率它自己也承认还没有。
- 每个信号的命中率统计里，一个 lead 会同时记到它命中的每一种信号上，多信号 lead 会抬高各信号的数字。
- `known_terms` 用双向子串匹配，短词会误伤（配个 "ai" 就几乎全中）。

## 二、同类项目

**sansan0/TrendRadar**（6.3 万星，GPL-3.0，10-10 还在更新）
- 数据来自第三方非官方的 newsnow 聚合 API（微博、知乎、抖音等热榜），加 RSS。
- 过滤分两层：
  - 关键词文件：词组、正则、`+` 必含、`!` 排除、全局过滤。
  - AI 过滤：用户用自然语言写兴趣，模型先抽出 5–20 个带描述的标签（顺序就是优先级）；再按标题把每条归入一个标签并打 0–1 分。兴趣文件一改，旧分类全部作废重来。
- 跨榜排序：`0.6 × 排名分 + 0.3 × min(出现次数,10)×10 + 0.1 × 高位占比`。
- 三种推送模式：当日汇总、当前在榜、只推增量。
- 需要常驻（Docker 或 Actions）。GPL，只能借思路。

**wildlifechorus/condenseit**（90 星，MIT）：自托管的新闻摘要，偏好学习做得最完整（`learning/preference_engine.py`、`reranker.py`）。
- 显式评分加隐式信号：读过轻微加分，稍后读强加分，忽略轻微减分；隐式信号权重默认 0.5。
- 所有信号按半衰期做指数衰减。
- 分数由几部分叠加：类别和来源的平均分、TF-IDF、embedding 质心相似度、LLM 抽取的话题重合。
- 最后一次 LLM rerank，按 0.4 的权重混进经典分，模型乱答也压不过统计分。
- 需要常驻服务器。

**AutoLLM/ArxivDigest**（468 星，MIT，2024 年后停更）：兴趣写成一段话，按批让模型给 1–10 分加一句理由，≥8 才推。和我们现在的粗筛同构，没有新东西。

**AdrienGuille/pyMABED**（MIT，2019 停更），学术法 MABED：
- 每个词每个时间片的 anomaly = 实际提及数 − 按当片总量摊下来的期望提及数。
- 用最大连续子序列和找爆发区间，区间内 anomaly 之和就是事件强度。
- 再按时间序列相关性合并同一事件的词，去重叠事件。
- Kleinberg 爆发检测（双态自动机）是同一路数，需要较大的语料量。

**BERTopic `topics_over_time` / `partial_fit`**（MIT），以及 TopicGPT（MIT）：
- BERTopic 用 embedding 聚类，再按时间片算 c-TF-IDF，看话题规模随时间的变化。Python 加 HDBSCAN，搬不到 TS 和 iOS。
- TopicGPT 让模型先生成话题分类体系再归类，思路和 TrendRadar 抽标签一样。

另外 pingcap/ossinsight（Apache）的 trending 接口从 2026-03 起回空表，我们[坑 322](../pitfall/network/322-ossinsight-trending-answers-empty-with-a-data-quality-note.md) 已经记过。

## 三、搬什么，接到哪

我们现在的粗筛（`src/info/collect/screen.ts`）只问一个问题：这条命中哪个研究室的哪条 observable。缺三样东西：这个词以前见没见过（新颖度）、几个独立源同时在说（汇聚度）、数量在不在加速（速度）。这三样都是程序算得出的事实，按"不经模型转手"的规矩，应该由代码算好，作为一行事实放进粗筛提示词。[docs/65](../info/65-加工手册：常态模型、日更列表、滚雪球与稿.md) 的"信号强度 = 偏离常态幅度 × 普遍性"和 [docs/69](../info/69-源模型：索引、叙事源、用户带来的与快照.md) 的"第 3、14 天回头重打分"，已经给这些机制留了位置。

**适合搬的**（radar 是 MIT，可以直接移植成 TS）

1. **名字抽取加新颖词表**
   - 把 `names()` 移植成纯 `.ts`（约 60 行），配单测。
   - 在采集端按设备维护"名字 → 最后出现日期"的 60 天词表，生命周期和 `info-pool-marks.json` 同类。
   - 条目入池时算出它带的新名字。
   - 放在 info 领域目录（例如 `src/info/collect/novelty.ts`），不放 capability。

2. **跨源汇聚规则**
   - 同一个新名字在 30 小时内出现在 ≥2 个不同 descriptor，算候选；只出现在一个源的，要求是 strong 名字加该源自己的热度数。
   - 数到的源个数正是 [docs/65](../info/65-加工手册：常态模型、日更列表、滚雪球与稿.md) 说的"普遍性"。
   - 产出就是 [docs/65](../info/65-加工手册：常态模型、日更列表、滚雪球与稿.md) 的第四类候选（日更列表里的小异常）。

3. **GitHub 和 HF 的速度信号**
   - GitHub：加一份 stars 快照，算出 `starsPeriod`（比上次多几颗）和 stars/age，填进 `ItemSignals`。trending 失效后 search 查询缺的正是这个。
   - HF：做"新进 trending 前 50（对照上轮前 100）"的差分，再用 `base_name` 正则把量化和微调版归到底座名下，正好处理 [docs/69](../info/69-源模型：索引、叙事源、用户带来的与快照.md) 说的"九成是转换版"。
   - 插件按设计是纯模块，快照放在采集层，由它补算差值后再交给粗筛。
   - 刷星核验沿用 [docs/69](../info/69-源模型：索引、叙事源、用户带来的与快照.md) 已有的三条。

4. **sitemap 差分作为新的发现方式**：给没有 RSS 的站点（目录站、公司博客）用。URL 快照做差，slug 词按"不同 URL 数"算 lift。按 [docs/17](../info/17-信息源系统.md) 的 descriptor 格式加一种 kind，配好 `pause`，遵守 robots。

5. **"是名字还是普通词"的判官**：只对新颖候选跑，25 个一批，用便宜模型。提示词是 MIT，可以照着改。它是粗筛之前的一道窄门，不改粗筛"绝对判断、不设配额"的规矩。

6. **事后核验和逐源命中率**
   - 这是 [docs/69](../info/69-源模型：索引、叙事源、用户带来的与快照.md) 第 3、14 天重打分的具体做法：首次见到时记下当时的信号，14 天后用我们自己能拿到的后续信号判它有没有"涨"，比如又出现在几个源、星数还在不在涨、用户开没开盒、批注了没有。
   - 按 descriptor 汇总命中率，显示在源页面上，用来淘汰没用的源。
   - 不用 Google Trends。
   - 一并搬上"最后两天数据没定型就丢掉"的规矩，任何快照差分都适用。

7. **隐式反馈衰减**（借 condenseit 的思路，MIT）：开盒、忽略、批注当隐式信号，按半衰期衰减。只用在分拣排序和管家的口径上，不进粗筛，粗筛仍是绝对判断。按"对话就是纠错界面"，不加星级评分界面。

8. **兴趣抽标签**（只借 TrendRadar 的思路）：用户一段话交给模型拆成带描述、带优先级的标签，兴趣一改旧判断全部作废。可以作为"新建研究室时起草 scope 和 observables"的一个工具，现有结构不动。

**不适合的**
- **AIsa 和它背后的整套付费链路**（X 读取、Google Trends、Ads 量、whois、Search Console）。这些都是 SEO 用途，对阅读没意义。按账号列表读 X 是唯一真正有用的一项，但要么付费第三方（约 $0.003/账号/次），要么走采集 PC 上的登录态 Chrome（[docs/57](../info/57-登录态浏览器取材与computer-use.md)），iOS 上都跑不了。这两条路选哪个待定。
- **TrendRadar 的代码**（GPL-3.0）和它依赖的 newsnow 非官方 API：只能借思路，接口随时可能没。
- **常驻服务器和 Actions cache 调度**（radar、TrendRadar、condenseit 都是）：我们有采集端轮询加条目池（[docs/35](../info/35-简报漏斗.md)、[docs/36](../info/36-采集端与阅读端.md)），用不着。
- **BERTopic 和 MABED 这类统计爆发检测**：一个人一天几百条的量太小，撑不起；BERTopic 还要 Python 和 embedding 聚类。按不同源计数的 lift 已经够用，以后池子攒到几十天、量上来了，再考虑 MABED 的 anomaly 公式（MIT，只是一个公式）。
- **ArxivDigest**：没有比现有粗筛多出来的东西。

**一个绕不过的缺口**：radar 抓"新名字"最早、最强的信号来自一张 X 账号表；我们今天的 X 只有用户手动贴链接（[docs/84](../info/84-X链接摄入.md)、[docs/86](../info/86-AI驱动的链接摄入.md)）。要实现"不再自己刷 X"，得先定 X 的持续取材怎么做。上面第 1–6 条只接现有的 arXiv、GitHub、HF、RSS 源，不需要等这件事定下来。
