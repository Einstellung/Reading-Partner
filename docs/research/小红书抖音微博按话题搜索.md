# 小红书、抖音、微博按话题搜索

2026-10-13。用户希望 agent 按话题替他去各平台搜新闻和舆情，以英文世界媒体为主、要支持好，中文只做小红书、抖音、微博。[舆情监测agent调研](./舆情监测agent调研.md)之后，这份拆 OpenCLI 和 xiaohongshu-mcp 的源码（外加 yt-dlp 的提取器），写这三个平台在我们隐藏 webview 里按关键词搜索的做法。

没登录过任何平台，没请求过这三个平台的搜索页。下面的选择器和行为都出自开源项目的源码，没在我们的 WebKitGTK / WKWebView 上验过。

## 0. 先要知道：我们现有的取页函数有三处限制

取页函数是 `src-tauri/src/webview_fetch/page.rs` 的 `fetch_page_via_webview`，前端入口是 `src/workshop/extract/webview-page.ts`。

- **只能跑同步脚本。** 页面加载并稳定后（`Phase::Page`，即 DOM 不再变化），只跑一次调用方的脚本。Linux 用的是 `run_javascript`，macOS 用的是 `evaluateJavaScript`，都不会等 Promise 返回。`script.js` 会直接把脚本的返回值 `JSON.stringify`，返回 Promise 时只会得到 `{}`。
  - OpenCLI 三个适配器的等待逻辑（MutationObserver 包在 Promise 里）和滚动采集逻辑都是异步的，不能原样搬进来，必须改写成同步读取。
- **一次调用就是一次加载。** 窗口用完即销毁，所以做不到"点筛选 → 等结果刷新 → 再读"或"滚动 → 等加载 → 再读"。
  - 微博的翻页和筛选都在 URL 参数里，不受影响。
  - 小红书的排序和时间筛选只能靠点击筛选面板；抖音要下滑才能加载更多。这两件事要么接受只拿首屏，要么给宿主加多步能力。多步能力可以是 `steps`（每段脚本之后重新等页面稳定），也可以是"脚本把结果挂到 `window` 上、宿主再轮询读取"。
- **拦截页识别只认英文。** `policy.rs` 的 `BLOCK_MARKERS` 全是英文；"安全限制"、"验证码"、`300017` 这类页面会被判成 `ok`，风控信号只能在我们自己的脚本里识别。

## 1. 小红书

**打开的 URL**
- OpenCLI：`https://www.xiaohongshu.com/search_result?keyword=${encodeURIComponent(q)}&source=web_search_result_notes`
- xiaohongshu-mcp 只是 `source=web_explore_feed` 不同。

**取数方式。** 两个项目的做法不一样，建议两条都写：先读页面状态，读不到再退到 DOM。

**做法 A：读 `__INITIAL_STATE__`（xiaohongshu-mcp `xiaohongshu/search.go`）。** 先等 `window.__INITIAL_STATE__ !== undefined`，然后：

```js
const feeds = window.__INITIAL_STATE__.search.feeds;
const feedsData = feeds.value !== undefined ? feeds.value : feeds._value;
return JSON.stringify(feedsData);
```

- 结果要过滤，只留 `modelType === "note"` 的条目（列表里混着直播卡片 `live_v2` 和搜索热词 `hot_query`）。
- 能拿到的字段（`types.go`）：
  - `id`、`xsecToken`
  - `noteCard.type`：`normal` 是图文，`video` 是视频
  - `noteCard.displayTitle`
  - `noteCard.user.{userId,nickname,avatar}`
  - `noteCard.interactInfo.{likedCount,commentCount,collectedCount,sharedCount}`
  - `noteCard.cover.{urlDefault,urlPre,infoList}`
  - `noteCard.video.capa.duration`
- 没有正文和时间。
- OpenCLI 注释说"Pinia store + XHR 拦截的路子坏了，API 现在返回空 items"；xiaohongshu-mcp 10-09 仍在用这条。两边说法冲突，未验证。

**做法 B：读 DOM（OpenCLI `clis/xiaohongshu/search.js`）。** 等待和判断状态的代码原文：

```js
const findNoteCard = () => document.querySelector(
  'section.note-item, section:has(a[href*="/search_result/"]), section:has(a[href*="/explore/"])');
if (/登录后查看搜索结果/.test(bodyText) || document.querySelector('#login-btn')) return 'login_wall';
if (/请求太频繁|访问频次异常|安全限制/.test(bodyText)) return 'security_block';
```

逐卡解析的原文：

```js
// cards: section.note-item, fallback a[href*="/search_result/"],a[href*="/explore/"] .closest('section'); skip .query-note-item
const titleEl = el.querySelector('.title, .note-title, a.title, .footer .title span');
const nameEl = el.querySelector('a.author .name, .author-name, .nick-name, .name');
const likesEl = el.querySelector('.count, .like-count, .like-wrapper .count');
const detailLinkEl = el.querySelector('a.cover.mask') || el.querySelector('a[href*="/search_result/"]')
    || el.querySelector('a[href*="/explore/"]') || el.querySelector('a[href*="/note/"]');
const authorLinkEl = el.querySelector('a.author, a[href*="/user/profile/"]');
// 标题为空时取 detailLinkEl.querySelector('span')
```

- 能拿到的字段：标题、作者、点赞数、详情链接（`a.cover.mask` 的 href 带 `xsec_token`）、作者主页。
- 发布时间：笔记 id 的前 8 位十六进制就是 Unix 秒，换算成北京时间即可，`noteIdToDate` 可以直接搬：

```js
const match = url.match(/\/(?:search_result|explore|note)\/([0-9a-f]{24})(?=[?#/]|$)/i);
const ts = parseInt(match[1].substring(0, 8), 16);
return new Date((ts + 8 * 3600) * 1000).toISOString().slice(0, 10);
```

**排序和时间筛选。** URL 里没有参数，两个项目都是悬停 `div.filter` 展开面板，再按文字点选项：
- 面板：`.search-layout__top > .filter > .filter-panel`
- 分组：`.filters`，组名是它直接子元素里的 `span`
- 选项：`.tag-container > .tags`（mcp 写的是 `div.tags`），选中后带 `.active`

可选值：

| 分组 | 选项 |
|---|---|
| 排序依据 | 综合 / 最新 / 最多点赞 / 最多评论 / 最多收藏 |
| 笔记类型 | 不限 / 视频 / 图文 |
| 发布时间 | 不限 / 一天内 / 一周内 / 半年内 |
| 搜索范围 | 不限 / 已看过 / 未看过 / 已关注（要求登录） |
| 位置距离 | 不限 / 同城 / 附近 |

- 点完不能马上读：站点会先把 `feeds` 清空再灌入新数据，xiaohongshu-mcp 的 `waitFeedsChanged` 是比较前后两次的 id 列表来等。
- 在我们这边要做筛选就需要多步能力；只有一次加载的话，只能拿"综合"排序的首屏。

**翻页。** 下滑加载。OpenCLI 每次滚 900px，连续两次没有新卡片就停（`buildScrollHarvestJs`），注释说每次滚动约多出 5-7 条。xiaohongshu-mcp 不滚，只取首屏。首屏条数未验证。

**OpenCLI 的一个修补。** 后台标签页里瀑布流会塌成一条：多张卡片 `top` 全相同，且 `.feeds-container` 的高度为 0。

```js
diag.cardCount > 1 && diag.feedClientHeight === 0 && diag.distinctCardTops === 1
```

它的做法是换一个新标签页再试一次。我们的窗口创建时就是隐藏的，很可能遇到同样的问题，未验证。

## 2. 抖音

**打开的 URL。** `https://www.douyin.com/search/${encodeURIComponent(q)}?type=video`（OpenCLI `clis/douyin/search.js`）。

**取数方式。** 读服务端渲染出来的 DOM，不拦 XHR。注释写明：直接调 `/aweme/v1/web/general/search/single/` 会因为缺 `a_bogus`/`msToken` 签名返回 `verify_check`。卡片类名是混淆过的，每次构建都会变，所以只认稳定钩子：

```js
const lis = document.querySelectorAll('[data-e2e="scroll-list"] li');
const a = li.querySelector('a[href*="/video/"]');
// 收集 li 内所有叶子元素的 textContent，按形状认字段
```

按形状认字段的规则（`projectCard`）：
- `^\d{1,2}:\d{2}(?::\d{2})?$` 是时长
- 第一个 `^\d+(?:\.\d+)?[万亿]?$` 是点赞数
- `@` 后面那个文本节点是作者
- 剩下的过滤掉相对时间、日期和"合集/视频/作者"后，最长的那段是描述（`desc`）

判断状态的原文：

```js
if (/登录后查看|请先登录|登录抖音|验证码|验证|verify_check|安全校验/.test(text)) return { state: 'login_wall' };
if (/暂无相关搜索结果|没有找到相关结果|搜索结果为空|暂无结果/.test(text)) return { state: 'empty' };
document.querySelector('[class*="login-mask"], [class*="LoginMask"], [class*="login-modal"], dialog[role="dialog"]')
```

- 能拿到的字段：描述（就是标题文案）、作者昵称、点赞数、视频链接（`https://www.douyin.com/video/<id>`）、时长。
- 拿不到：播放、评论、分享数（适配器填 0），作者 id、封面、精确时间也没取。
- 上限 30 条，不滚动。
- **排序和时间：适配器没做。** 抖音 Web 接口有 `sort_type`、`publish_time` 参数（从 MediaCrawler 一类项目得知），搜索页 URL 认不认这两个参数未验证；不认就只能点"筛选"面板，那就需要多步能力。

## 3. 微博

**打开的 URL。** `https://s.weibo.com/weibo?q=${encodeURIComponent(q)}`。OpenCLI 等 2 秒后同步读 DOM（`clis/weibo/search.js`），是三个里最好搬的。原文：

```js
const cards = Array.from(document.querySelectorAll('.card-wrap'));
const contentEl = card.querySelector('[node-type="feed_list_content_full"]')
  || card.querySelector('[node-type="feed_list_content"]') || card.querySelector('.txt');
const authorEl = card.querySelector('.info .name') || card.querySelector('.name');
const timeEl = card.querySelector('.from a');
const urlEl = card.querySelector('.from a[href*="/detail/"]') || card.querySelector('.from a[href*="/status/"]') || timeEl;
// id: url.match(/weibo\.com\/\d+\/([A-Za-z0-9]+)/) 或 /(detail|status)\/([A-Za-z0-9]+)/
```

- 能拿到的字段：正文全文（`feed_list_content_full` 是"展开全文"后的完整文本，已经在 DOM 里）、作者、时间（"x分钟前"或日期原文）、链接、微博 id。正文就是文字，不用进详情页。
- 以下几项不是从这两个项目里来的，是我对 s.weibo.com 页面的了解，未验证：
  - 互动数在 `.card-act` 的转发/评论/赞三项里；
  - 图片在 `.media-piclist img`；
  - URL 参数：`&page=N` 翻页，`&xsort=hot` 按热度，`&scope=ori` 只看原创，`&timescope=custom:YYYY-MM-DD-H:YYYY-MM-DD-H` 限定时间，`&suball=1`。
- 如果这些参数成立，微博一次加载就能完成"最新/热门 + 时间窗 + 第 N 页"。

## 4. 风控

**登录要求**
- 小红书：未登录会出现"登录后查看搜索结果"墙（OpenCLI 把它当硬错误）；搜索范围这类筛选要求登录。
- 抖音：OpenCLI 注释写"匿名访问者只看到空骨架"，所以要登录。
- 微博：OpenCLI 的报错提示是"ensure you are logged into weibo.com"。当前未登录能看到几页，未验证。
- 结论：三个平台都按需要登录处理，复用现有 `site-session.ts` 的按站点登录流程（Linux 和 macOS 都有）。

**软封信号（OpenCLI `clis/xiaohongshu/risk-control.js` 原文节选）**

> XHS gates note-detail navigation behind velocity-based risk control: reading a run of notes back-to-back trips a soft block that redirects to `website-login/error?error_code=300017` / `300031` or renders "安全限制" / "访问链接异常" ... retry ONCE after a long randomized cooldown. The retry is deliberately capped at one: hammering a hot risk state is exactly what escalates it toward the account-violation / ban path (#842, #677). ... it does NOT cap request velocity across separate CLI invocations.

- 参数：详情页导航后等 2-5 秒随机；被拦后冷却 8-18 秒随机，只重试一次。
- 小红书搜索页另认三个词：`请求太频繁|访问频次异常|安全限制`。
- 抖音（OpenCLI issue #2308）：同一个已登录 profile，人手打开搜索页正常，CDP 驱动的导航却时而超时、时而 `document.body` 为空，作者判断是抖音对 CDP 导航单独风控。我们的 webview 没有 CDP，这可能是好事，未验证。
- 两个项目都没有微博的风控信号。
- 封号代价（xiaohongshu-mcp README，作者自述）：
  - 同一账号不能在多个网页端同时登录，否则会被踢下线。所以用户如果平时也在浏览器里用网页版，就会和 app 互踢。
  - 新号会被要求实名。
  - 稳定跑了一年没被封（未核实）。

**建议的节奏**
- 每个平台每个话题每天 1 次（最多 2 次），每次只取首屏或第 1 页（约 20 条）。
- 严格串行，同一平台两次搜索之间随机隔 30-90 秒，每平台每天总搜索不超过 20 次。
- 进详情页只给小红书分拣后的前几条，每天每平台不超过 5 个，间隔照 OpenCLI 的 2-5 秒再放宽。
- 一出现风控信号：本轮不重试，该平台停 24 小时，按 [57](../info/57-登录态浏览器取材与computer-use.md) 写进状态让用户处理，不自动重新登录。我们是定时任务，没必要学 OpenCLI 的即时重试。

## 5. 文字够不够、要不要进详情页、要不要转写

- **微博**：搜索页给的就是全文，不用进详情页。
- **小红书**：搜索页只有标题（`displayTitle`），正文在详情页。
  - 详情页地址：`https://www.xiaohongshu.com/explore/<id>?xsec_token=<token>&xsec_source=pc_feed`
  - 取 `__INITIAL_STATE__.note.noteDetailMap[id].note` 里的 `title`、`desc`、`time`、`ipLocation`、`imageList`、`video`（mcp `feed_detail.go`）；OpenCLI 用 DOM：`#detail-title`、`#detail-desc, .note-text`。
  - 视频笔记的字幕在 `note.video.mediaV2`（一个字符串化的 JSON）的 `video.subtitles` 里，xiaohongshu-mcp 已经在解。能拿到字幕就不用转写。哪些视频笔记带字幕，未验证。
  - 详情页正是速率风控盯得最紧的地方，只对筛后少数条进。
- **抖音**：搜索页只有视频文案（`desc`，通常一两句加话题标签），没有正文。
  - yt-dlp 的 `DouyinIE` 调的是 `www.douyin.com/aweme/v1/web/aweme/detail/`，缺 cookie 时报 "Fresh cookies (not necessarily logged in) are needed"（看的是 `s_v_web_id`）。也就是说要 cookie、但不一定要登录态，可以从 webview 的 jar 导出给它。
  - 我们现有的 yt-dlp 路线（[56](../info/56-YouTube访谈接入.md)）只取字幕；抖音视频在 yt-dlp 里一般没有字幕轨，要转写就得下音频再做 ASR。这超出了"够用就行"，建议第一版只用 `desc`。
- yt-dlp 的小红书提取器（`xiaohongshu.py`）也读 `__INITIAL_STATE__.note.noteDetailMap`，只取视频流，不取字幕。

## 6. 在 WebKitGTK / WKWebView 里跑：已知坑和未验证项

- **UA。** 两个项目都跑在真 Chrome 上（OpenCLI 用扩展加 `chrome.debugger`，xiaohongshu-mcp 用 go-rod，带指纹选项 `WithFingerprint`、`fingerprint-brand: Chrome`）。我们在 Linux 上发的是固定的 WebKitGTK 默认 UA `...(X11; Ubuntu; Linux x86_64) ... Version/60.5 Safari/605.1.15`，macOS 不设 UA。[坑 108](../pitfall/webview/108-a-modernised-user-agent-is-what-gets-you-blocked.md) 说明不能为了"像 Chrome"去改这个 UA，否则彭博 403。小红书和抖音见到 Linux Safari 60.5 这个少见的 UA 会不会降级或拦截，未验证。
- **隐藏窗口。** 页面可能被判为 `visibilityState=hidden`，导致 rAF 和定时器节流、IntersectionObserver 不触发、懒加载不出来；小红书瀑布流可能塌成一条（OpenCLI 在后台标签页里已遇到）。隐藏窗口有固定的 `policy::VIEWPORT` 尺寸，但卡片的 `getBoundingClientRect` 在里面是不是 0，未验证。OpenCLI 的 `isVisibleNote` 过滤会因为这个把卡片全扔掉，搬的时候建议先去掉可见性过滤。
- **CSS `:has()`。** WebKitGTK 2.42 以上支持，本机是 2.52.3，CI 的 ubuntu-22.04 运行库版本更低。建议改成 `a[href*=...].closest('section')` 这种写法，不依赖 `:has()`。
- **`load-failed`。** 抖音和小红书都会在页内改地址。[坑 370](../pitfall/webview/370-a-cancelled-load-is-reported-as-a-failed-one.md) 说被取代的那次导航也会报 `load-failed`，现有代码已经放过 `Cancelled`。
- **返回值编码。** [坑 371](../pitfall/webview/371-a-script-that-stringifies-comes-back-double-encoded.md)：脚本不要自己 `JSON.stringify`，否则会编码两层。
- **cookie 和登出。** [坑 110](../pitfall/webview/110-guessing-cookie-domains-misses-the-session.md)、[坑 111](../pitfall/webview/111-webkit-writes-the-cookie-jar-on-its-own-schedule.md)：登出要按 jar 里实际存在的域名删，抖音和小红书都有多个子域。
- 不确定的统一按未验证处理：xiaohongshu-mcp 的 `__INITIAL_STATE__` 在 WebKit 里是否有数据、抖音 `data-e2e="scroll-list"` 是否由服务端渲染给 WebKit、微博未登录的表现。

## 7. 许可证

两个项目都是 Apache-2.0，都没有 NOTICE 文件，版权行分别是 `Copyright 2025 jackwener` 和 `Copyright 2025 xpzouying`。搬进本仓库（PolyForm Strict）可以：保留原版权声明，附一份 Apache-2.0 全文（仓库里目前没有第三方许可证目录，需要新建），在改动过的文件里注明"修改自……"。

建议直接搬（改成同步脚本）的部分：
- OpenCLI 小红书 `search.js`：`extractSearchRows` 的选择器、`WAIT_FOR_CONTENT_JS` 里的墙和风控正则、`noteIdToDate`、`stripXhsAuthorDateSuffix`、`isCollapsedRender`、`SEARCH_FILTERS` 表
- OpenCLI 抖音 `search.js`：`projectCard`、`parseDouyinCount`、`extractDouyinVideoId`、`isSearchCardMetadataText`、`collectCards` 和状态正则
- OpenCLI 微博 `search.js`：整段 evaluate 脚本
- xiaohongshu-mcp：读 feeds 和 `noteDetailMap` 的那两段 JS、`onlyNotes` 的过滤规则、`mediaV2` 字幕解析的逻辑（Go 要翻成 TS）

不搬：xiaohongshu-mcp 的 humanize 鼠标轨迹（我们不点就用不上）和 MediaCrawler（非商业许可）。
