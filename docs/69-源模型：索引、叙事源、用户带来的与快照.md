# 源模型：索引、叙事源、用户带来的与快照

> 2026-09-13 定案。上游：[63](./63-情报局：研究室、专项组与态势.md) 定了源归注册表、研究室认领、招募员和两档源；[17](./17-信息源系统.md) 是源描述格式和引擎；[65](./65-加工手册：常态模型、日更列表、滚雪球与稿.md) 是加工。本文回答 63 没答的一个问题：供给侧哪些是固定的、哪些是开放的，以及论文和代码这类领域的源从哪来、怎么判质量。17 的描述格式多一种 discovery，其余不动。

## 四种源

按取法分四种，各自的固定与开放程度不同。

| 种 | 例 | 身份 | 查询 | 谁管 | 取法 |
|---|---|---|---|---|---|
| 索引 | arXiv、Semantic Scholar、GitHub（OSS Insight、OpenDigger）、Hugging Face、HN Algolia、官方统计与披露 | 固定，产品自带 | 开放，一个研究室几条 | 采集经理按可观测项配 | 查 |
| 叙事源 | 媒体、博客、newsletter、机构页面 | 开放 | 无 | 招募员找、评分、分层，用户只有否决和「加进来」 | 订（17 的 feed / listpage / json-api） |
| 用户带来的 | 登录态的彭博、订阅的 newsletter、手机上转来的一条 | 开放 | 无 | 用户 | 拿（57 的登录态浏览器、分享入口） |
| 快照 | DAS-2M、会议 proceedings、历史档案 | 半固定 | 无 | 起研究室时灌一次 | 灌 |

需求侧全开放：视野用户说，可观测项 AI 起草用户改，concern 从行为蒸出。供给侧照需求配：先查索引，索引查不到的缺口才招募叙事源，叙事源也没有的才提名付费或登录。今天的实现是反过来的，从用户配的几条 feed 出发看它们吐出什么。

「有的用户没这个需求」不需要开关。索引是能力，写在代码里；启用是数据，写在研究室的态势里。一个只关心宏观的用户，他的研究室推不出任何 arXiv 查询，arXiv 适配器就一次不跑。

## 索引是一种 discovery

17 的格式加一种：

```
{ kind: "index", provider: "arxiv" | "github" | "huggingface" | "s2", query: { ... } }
```

一份 index 描述就是一条查询：「arXiv cs.RO 近两天」「GitHub trending python 加 robotics」「HF 机构 lerobot 的新模型」。它和别的源一样是 `SourceDescriptor`，进注册表、被研究室认领、走漏斗、出 cable、有健康和轮询周期。用户在源列表里看到的是查询实例，不是 arXiv 本身。

`provider` 对应一个适配器，落在 `src/info/sources/index/`，一个 provider 一个文件，接口是 `provider.ts` 的 `IndexProvider`：校验查询、一句话描述查询、跑查询出条目。适配器只出标题层，不抓正文；正文按描述的 `fulltext` 走，和别的源一样。文献库的客户端（arXiv、S2、OpenAlex、PubMed）从 `reading/papers` 提到 `src/scholar/` 这个 capability，info 和 reading 共用，坑 72、73 随代码一起搬。

第一批四个适配器和各自的查询：

- arxiv：分类加检索词，时间窗用 `submittedDate` 区间过滤，不排序（坑 72）。摘要进 `summary` 和 `textContent`，`fulltext: none`。
- github：三种查询。trending 走 OSS Insight 的 API，按时间窗和语言；search 走 GitHub Search API 按 `created:>` 找新仓库；topic 按 topic 列近期活跃仓库。命中的仓库补 star、fork、created_at、topics，前几个再问 OpenDigger 的 OpenRank 和 activity 做核验。不抓 github.com/trending 的 HTML。
- huggingface：papers 走 `api/daily_papers` 按日期，带 upvote 和评论数；models 和 datasets 走 `api/models` `api/datasets` 按 `trendingScore`，可按 `pipeline_tag`、`author`、tag 过滤。
- s2：不做发现，做补字段。给已知 arXiv id 批量取 citationCount、influentialCitationCount、venue；坑 73 的 null 和限流照旧。

以后按同一形状补 FRED、EDGAR、统计局；一个适配器一个文件，不是一次重构。

## 信号

索引给的不只是条目，还有数：star、upvote、下载、引用。`InfoItem` 多一个 `signals`，cable 原样带着。粗筛看得到它，分析员读 cable 时也看得到。

质量按信号到达的时间分三段，同一篇论文的分要打几次：

| 时间 | 能看到什么 | 强弱 |
|---|---|---|
| 第 0 天 | 作者和机构的过往、声称（已知 benchmark 上的新数、放不放权重和代码）、实验室是否同时发博客 | 便宜，弱 |
| 第 1 到 7 天 | HF 点赞、代码库 star 增速和 OpenRank、几家媒体同时报、有人复现 | 中 |
| 一个月以上 | 引用数、influential citation、被别人当 baseline、录用和奖 | 强，但晚 |

再加一个只有我们有的维度：命中哪条可观测项、离用户 concern 多远。一篇平庸论文正好打在你在读的问题上，比一篇轰动的论文在隔壁领域值钱。

流程：第 0 天粗筛看标题摘要判命中，命中的进日更列表带第 0 天信号；第 3 天和第 14 天回头补注意力信号重打；两项都过线才提「该读」。月度再查引用，给合订本。第 0 天这一步本文落地，回头重打是 65 的 recurring 计数器在论文上的样子，后置。

论文、权重、代码要连成三角：README 里的 arXiv 链接、HF 论文页的 model 和 code 链接。连上之后一篇论文的分吃得到它权重的下载和它仓库的 star。第一版先各自出条目，连接后置。

## 机器之心这类叙事源的位置

它们的上游是同一批索引：arXiv 新增列表、作者在 X 上喊、实验室博客、HF Daily Papers、会议录用名单，加中国实验室直接投稿。站在索引下游一到三天，带自己的选择偏好。当确认信号用，不当发现源用。

## 坑，接之前先知道

- GitHub trending 没有官方 API，那一页是内部启发式的 HTML。刷 star 是真的：ICSE 2026 那篇研究，2019 到 2024 年约 600 万疑似假 star，2024 年中 50 星以上的仓库 16.7% 卷进过，AI 和 LLM 仓库最多；进过 trending 的只占 0.42%。核验三条：star 对 fork 和 contributor 的比例、创建到进榜的间隔、有没有论文链接或机构归属；OpenDigger 的 activity 不随 star 涨就是刷的。awesome 列表和教程仓库按有 release、有 CI、有 license 过一遍。
- HF 下载数是 HTTP 请求数，CI 和镜像都算，只看方向。trending 被刷过：2026 年 5 月一个恶意仓库 18 小时 24 万下载冲到第一，98.5% 是机器账号。模型列表九成是微调和量化版，按 `author` 限机构、按 tag 排掉转换版。
- arXiv 坑 72，S2 坑 73。S2 匿名额度极薄，补字段要批量、要能整体降级。
- GitHub REST 匿名 60 次一小时，补字段只给前几十个。
