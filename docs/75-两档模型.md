# 两档模型

2026-09-22 定。全app 只有两个模型档位，任务归哪一档由程序决定，设置里没有第二个入口。取代「一个默认模型 + 简报单独一个」的旧安排。

- 对话档（`defaultModelId`）：读者真在跟它说话的那些——阅读对话、Lumen、info 对话。
- 日常档（`everydayModelId`，null 表示跟随对话档）：没人等着看的例行活。

两档都只是模型 id，供应商永远是 `defaultProviderId`：凭据是单活的（`ai/credentials.ts`），写在另一个供应商下的模型 id 没有 key 可用。

## 谁归日常档

这一版的日常档是三餐线的全部（`info-meals` 这条会话的每一轮，加上 `info/meals` 里的无头调用——今天只有写做法那一次）和简报的两段（粗筛、分析）。备课、蒸馏、记忆和阅读侧的所有调用留在对话档。

归类写在 `src/ai/model-tier.ts` 的两张表里，只有那一份：`ThinkingKind → tier` 管无头调用，thread 的 file key → tier 管会话。要把一件新活挪去日常档，就是往那两张表里加一行。设置项只说日常档跑哪个模型，不说哪些活是日常档。

`ai` 是 capability，不能 import 领域，所以 `info-meals` 这个 key 在表里是字面量，和 `MEALS_BOOK_ID` 的一致由测试盯着。

会话的档位按整条 thread 定，不按单轮内容：三餐会话里问什么都是日常档。发起调用的四个地方（`soul/turn.ts` 量窗口、`soul/bell.ts`、`soul/recover.ts`、`ui/components/info/use-info-call.ts`）都过同一个 `modelIdFor`。装配时量的上下文窗口必须是真正要发过去的那个模型的。

## 旧字段

`briefingModelId` 改名成 `everydayModelId`。读盘时做一次迁移（`migrateSettings`）：文件里有 `briefingModelId` 而没有 `everydayModelId`，就按日常档读。旧 key 不从文件里删——老版本的设备读自己那份，fields 合并看到一侧少了个 key 会把删除同步过去（和 `autoNotes`、`backgroundCollect` 同一个理由）。`palace/kinds.ts` 的 fieldGroups 里两个 key 都在，模型 id 和供应商一起结算（坑 237）。
