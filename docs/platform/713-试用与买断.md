# 试用与买断

2026-11-27 定。C 端定价：3 个月免费试用，功能完整；试用期满一次性买断 4.99 美元，永久解锁。用户继续用自己的 AI API key，我们不代理也不垫付模型调用费。

## 规则

试用期满未买断，整个 app 锁住，不只是 AI。锁屏只有四项：购买、恢复购买、删除账号、退出登录。不提供数据导出，书和对话本来就在用户自己的 Google Drive（docs/platform/13）。

使用 app 必须登录，试用时钟因此跑在服务端。登录方式是 Google 和 Sign in with Apple，都走原生：app 拿到服务商的 id_token，调用 Supabase Auth 的 `signInWithIdToken` 换会话。Google 的 id_token 在 Drive 同步登录里已经在取（docs/platform/18）；Apple 在 iOS 上走原生 ASAuthorization。

强制登录写进审核备注的理由：授权跨设备生效，同步按账号进行。另备一个审核测试账号。

已有用户（发起人和一两个在用的人）在管理后台直接标为已购买。

## 后端

Supabase：Auth、Postgres、Edge Functions。先用免费档，收钱之前升 Pro（25 美元/月）：免费项目一周没有任何请求会被暂停，数据保留、90 天内可恢复，暂停期间登录和状态检查都失败。不用 Vercel，它的 Hobby 档只许非商业用途。授权接口放在 Supabase Edge Function。

665 的 users 表迁过来，增加 trial_started_at（用户首次登录时由服务端写入）、purchased_at、purchase_source、banned。devices 表原样迁过来。防一份购买被很多人共用：把 Drive 同步用的 Google 账号和登录账号对照，并盯每个账号下的设备数。

## 支付

RevenueCat，月跟踪收入 2500 美元以内免费，超出收 1%。RevenueCat 的 app_user_id 取 Supabase 的 user id，这样在 iPad 上买了，手机和桌面也解锁。RevenueCat webhook 调 Edge Function 写 purchased_at。

iOS：4.99 美元的非消耗型内购，加入小型企业计划，抽成 15%。苹果对非订阅 app 的限时试用要求做成一个 0 元的非消耗型项目，名字如「3-Month Trial」，照做；但试用是否到期以服务端时钟为准。Android：Google Play 一次性商品，经 RevenueCat。桌面：以后用 Stripe 或 Paddle，同样记入 RevenueCat。

app 侧是插件 `plugins/purchases`，iOS 经 SPM 引 RevenueCat `purchases-ios` 5.x，三个命令：`configure`（API key 加 Supabase user id，换账号时走 `logIn`）、`buy_lifetime`（取商品后购买，用户取消返回 `cancelled: true`，不算错误）、`restore`（返回 `lifetime` entitlement 是否生效）。Android 和桌面一律返回 `unavailable`。前端入口是 `src/platform/app/purchases.ts`：`REVENUECAT_IOS_API_KEY` 为空时整套关闭，不调插件，返回 `not configured`；商品 id `lumen.lifetime`，RevenueCat 后台的 entitlement 要命名为 `lifetime` 并挂上这个商品。StoreKit 内购不需要 entitlement 文件条目。

## 状态检查

app 启动时带 Supabase 会话问 Edge Function，答案是 trial、purchased、expired、banned 之一，附试用截止日期。答案带签名，缓存在本地。离线宽限 7 天：连不上服务器时，只要上次成功检查在 7 天内就沿用缓存的答案，超过 7 天锁住。

## 管理后台

起步不做自定义面板。用户、登录和设备看 Supabase 控制台，购买看 RevenueCat 控制台，再建一个 Postgres 视图做总览：今日登录数、即将到期的试用、购买数。需要手工操作（延长试用、封禁、退款）时再上自定义面板，Refine 或 Retool。

## 实施顺序

第一步只动后端，app 界面不变：建 Supabase 项目和 accounts、devices 两张表（`supabase/migrations/`），app 现有的 Google 登录上报改为拿 id_token 换 Supabase 会话再报设备，默认打开（docs/platform/665）。不加 `profile` scope，不收姓名。Vercel 后端 `server/` 删除，隐私政策和条款移到 `site/`。上架前苹果隐私标签照隐私政策列出收集的字段：邮箱、用户 ID、设备信息。

后续依次：Sign in with Apple、启动强制登录、锁屏、内购与 RevenueCat、升 Pro。

## 实现

代码已写完、默认关闭（2026-11-27）。两道开关都关着时，app 的启动和今天完全一样：不发状态请求、不出界面、不写文件。

客户端开关是 `src/platform/license/config.ts` 的 `LICENSING_ENABLED`，出厂为 false，测试盯着。同一文件里的 `LICENSE_PUBLIC_KEY` 为空、后端地址为空、或这个构建没有可用的登录方式时，检查也直接放行。服务端开关是 `public.app_config` 表的 `licensing_enforced`，默认 false；没开时 `license-status` 对所有人答 `open`，旧客户端打开开关也锁不住任何人。

状态值五个：`open`（服务端开关没开）、`trial`、`purchased`、`expired`、`banned`。服务端判定顺序：封禁优先，其次已购买，再看试用；试用截止 = `trial_started_at` + 3 个月，按 Postgres 加 interval 的方式（月底截到当月最后一天）。客户端把 `open`、`purchased` 和未到期的 `trial` 视为放行；`trial` 过了截止日期即使来自缓存也按 `expired` 处理。

答案是 `{ payload, signature }`：payload 是 `{ v, userId, status, trialEndsAt, issuedAt }` 的 JSON 原文，signature 是对这段原文的 ECDSA P-256 / SHA-256 签名（WebCrypto 的 r||s 64 字节，base64url）。客户端只验签收到的原文，不做规范化。不用 Ed25519，WKWebView 和 WebView2 的 WebCrypto 都稳定支持 P-256。

缓存是 AppData 下的 `license.json`，存签过名的原样答案，和 `account.json` 一样不在任何 palace kind 里，因此不同步；每次读都重新验签，改文件没用。离线宽限从服务端签发时间 `issuedAt` 算 7 天，不信本机记的检查时间；`issuedAt` 比本机时钟晚一天以上也不认（防把时钟往回调）。缓存只对签发给的那个账号有效。

会话：沿用 `account.json` 里的 Supabase 会话，access token 剩不到一分钟就刷新，刷新被拒再用 Google id_token 换，不看上报的同意标记。完全拿不到会话（没登录 Google）出登录页；连不上（没网、服务端出错、超时 10 秒、签名不对）走缓存。状态请求返回 401 时强制刷新一次再问。

检查时机：启动一次；回前台时，距上次检查超过 6 小时、或当前不是放行状态就再查；Google 登录状态变化时再查。

界面：`src/ui/components/license/`，两个外壳各挂一个 `<LicenseGate />`，放行时什么都不画。登录页只有 Google 按钮（复用设置里同一个登录流程），Apple 按钮受 `APPLE_SIGN_IN_AVAILABLE` 控制，现为 false。锁屏是盖住整个 app 的全屏页（`OVERLAY_Z.lock`，在所有浮层之上，确认框在 `lockDialog`）。试用到期：购买、恢复购买、删除账号、退出登录四个按钮；封禁：只有删除账号和退出登录，买了也解不开；离线超过宽限：重试和退出登录。删除账号先确认，调 `delete-account`，成功后本机退出 Google 登录并删 `license.json`。

购买和恢复购买现在接的是占位实现（`src/platform/license/store-handlers.ts`，答 unavailable），内购插件落地后在那一处接上，app_user_id 传 Supabase user id。购买成功后立刻重查，服务端还没收到 webhook 时提示稍等。

服务端代码在 `supabase/functions/`，未部署：`license-status`、`revenuecat-webhook`、`delete-account`，共用的判定和 webhook 映射是 `_shared/license.ts`、`_shared/revenuecat.ts`，不依赖 Deno，app 的 `bun test` 直接测（`tests/supabase/`）。webhook 只认 `LIFETIME_PRODUCT_ID` 的 INITIAL_PURCHASE、NON_RENEWING_PURCHASE（写 purchased_at 和 purchase_source，已有则不动）和 REFUND、CANCELLATION（清空），app_user_id 不是 UUID 的忽略；重放无害。沙盒购买的 purchase_source 带 `(sandbox)`。

打开的步骤：

1. `bun scripts/license-keygen.ts` 生成密钥对，私钥 JWK 不进仓库。
2. 在 SQL Editor 跑 `supabase/migrations/20261127010000_app_config.sql`。
3. 设密钥：`supabase secrets set LICENSE_SIGNING_KEY='<私钥 JWK>' REVENUECAT_WEBHOOK_AUTH='<随机串>' LIFETIME_PRODUCT_ID='<商品 id>'`。
4. 部署：`supabase functions deploy license-status`、`supabase functions deploy delete-account`、`supabase functions deploy revenuecat-webhook --no-verify-jwt`。RevenueCat 后台的 webhook 填 `https://<ref>.supabase.co/functions/v1/revenuecat-webhook`，Authorization 填同一个随机串。
5. 把公钥 JWK 填进 `LICENSE_PUBLIC_KEY`，`LICENSING_ENABLED` 改 true，发版。此时服务端仍答 `open`，客户端只验证链路。
6. 已有用户在控制台标 purchased_at，然后 `update public.app_config set value = 'true' where key = 'licensing_enforced';` 打开强制。
