# 560 iOS 开发验收环境

iOS 的构建、模拟器和真机验收有两套环境：租来的 Mac mini（2026-08 起用，2026-10 归还），和不需要自己的 Mac 的 Linux + GitHub Actions + USB 真机。本文写两套各自怎么搭、怎么用、能验什么，以及将来租云 Mac 时照着重建。

## 两套共用的

**包名。** 开发包一律 `com.xinyuan.readingpartner.dev`（ASC 资源 id `VW3G7LG4MS`）。正式包名 `com.xinyuan.readingpartner` 装上去会顶掉设备上的 TestFlight 版。包名只能经 CLI 的 `--config` 改，装机前从 ipa 的 `Info.plist` 读回 `CFBundleIdentifier` 校验；下面所有脚本都带这道闸。

**签名。** 付费团队 `HF6369DDYP`，用 App Store Connect API key 云签名（坑 47、197），profile 一年有效，Xcode 里不需要登任何 Apple ID。新设备要先 `POST /v1/devices` 注册，占每年 100 个名额之一、不可删。已注册：iPhone 16 `00008140-000C31641EEB001C`、iPad `00008120-001E78AC2EE00032`。新 entitlement 要先给 App ID 开 capability（坑 401）。

**密钥放在哪。** 不进仓库。Linux：仓库 `.env` 的 `ASC_KEY_ID` / `ASC_ISSUER_ID` / `ASC_PRIVATE_KEY_PATH`，`.p8` 在 `~/.appstoreconnect/private_keys/`。GitHub secrets：`APPLE_API_KEY_ID`、`APPLE_API_ISSUER`、`APPLE_API_KEY_P8_BASE64`、`APPLE_TEAM_ID`。Mac：`~/.asc-env`（600，导出 `APPLE_API_KEY`、`APPLE_API_ISSUER`、`APPLE_API_KEY_PATH`、`APPLE_DEVELOPMENT_TEAM`），`.p8` 在 `~/.appstoreconnect/private_keys/`。重建时从 Linux 拷过去。

**设备。** iPhone 16（iOS 26.5.2）、iPad15,7（iPadOS 26.7.1）。前提：开发者模式开、信任这台电脑、解锁、自动锁屏设永不；换了签名身份要在「设置 → 通用 → VPN 与设备管理」信任一次；每次重装 .dev 都要重新给本地网络权限（坑 567），国行 iPhone 还要重新给「无线数据」权限（坑 217）。iPad 上的 Shadowrocket 不许关。

**验收顺序。** Linux 上 xvfb 跑真 WebKitGTK → 模拟器 → 真机，不跳步。xvfb 那一步在用户的 Linux 上做，不开可见窗口；Mac 上开模拟器窗口不受这条限制。模拟器只有 Mac 版有。

## Mac mini 版

### 拓扑

Mac mini M4 / 16 GB / macOS 26.5 / Xcode 26.6（`/Applications/Xcode.app`）/ iOS 26.5 模拟器 runtime，用户 `mima1234`（uid 501）。Mac 在 192.168.110.x 的 NAT 后面，Linux（192.168.0.107）到不了它，所以由 Mac 上的 LaunchAgent `com.readingpartner.tunnel` 常驻一条 SSH 隧道连到 Linux（模板在 `scripts/macos/com.readingpartner.tunnel.plist`）：

- Linux `127.0.0.1:2222` → Mac sshd；Linux 的 `~/.ssh/config` 里 `Host macmini` 指 `127.0.0.1:2222`、`User mima1234`，免密。
- Linux `127.0.0.1:5900` → Mac 屏幕共享。
- Mac `17890`/`17891` → Linux 的 Mihomo 代理（HTTP/SOCKS）。

隧道里写死了 Linux 的地址，Linux 换 IP 就断（坑 202），日志在 Mac 的 `/tmp/rp-tunnel.log`。

代码：`~/Reading-Partner` 是独立 clone，remote `linux` 指 `ssh://xinyuan@192.168.0.107/<主 checkout>`，只 fetch（push URL 设成了 `DISABLED_no_push_to_users_workspace`）；`origin` 是 GitHub，Mac 到 github.com 走 HTTP/2 会断（坑 204）。每件活一个 `git worktree add --detach ~/rp-<活名> FETCH_HEAD`；`~/rp-flow` 是来回切版本用的那个；`~/rp-swiftcheck` 归 `scripts/ios-swiftcheck.sh` 用，它从 Linux 用 git bundle 经 scp 送代码。同步代码只 `git checkout FETCH_HEAD -- src tests`，整树 reset 会让 tauri 重启整条构建（坑 381、205）。

### 装机

1. 系统设置开「远程登录」和「屏幕共享」，并保持一个图形登录会话：codesign 和模拟器窗口都要它（坑 179、566）。
2. Xcode 26.6，然后 `sudo xcodebuild -runFirstLaunch`，装 iOS 模拟器 runtime。用 `mas get 497799835` 装 Xcode 时 App Store 的 `storedownloadd` 会在自己的安装步骤失败后删掉下好的 `.pkg`；办法是盯住 `$(getconf DARWIN_USER_CACHE_DIR)com.apple.AppStore/497799835/`，`.pkg` 一出现就硬链接到别处，下满后 `sudo installer -pkg <它> -target /`。
3. 无 tty 的 SSH 里 `sudo` 要 askpass：`~/.askpass.sh`（700，两行，echo 登录密码），`~/.zshenv` 写：

   ```
   export PATH="$HOME/.cargo/bin:$HOME/.bun/bin:/opt/homebrew/bin:/opt/homebrew/sbin:$PATH"
   export BUN_INSTALL="$HOME/.bun"
   export SUDO_ASKPASS="$HOME/.askpass.sh"
   ```

   不要在这里写 `http_proxy`：代理是隧道，隧道一断每条命令都挂。自己拼的 `ssh macmini '...'` 覆盖了环境时要再导一次 `SUDO_ASKPASS`。
4. 工具链（下载走隧道代理 `http_proxy=http://127.0.0.1:17890`）：
   - rustup stable，`rustup target add aarch64-apple-ios aarch64-apple-ios-sim`；bun。
   - Homebrew：`xcodegen cocoapods ios-deploy libimobiledevice ios-webkit-debug-proxy mas`，`brew tap facebook/fb && brew install idb-companion`。
   - `python3 -m venv ~/idbvenv && no_proxy='*' ~/idbvenv/bin/pip install fb-idb`（不要建在 `/tmp`，坑 374）。
   - `python3 -m venv ~/pmd3venv && no_proxy='*' ~/pmd3venv/bin/pip install pymobiledevice3 websocket-client`。
   - macOS 系统代理指着本机 7890（Clash Party，平时不跑），Python 系的网络命令都要加 `NO_PROXY='*' no_proxy='*'`；curl 不读系统代理，拿它判断通不通会误判。
5. 签名：放好 `~/.asc-env` 和 `.p8`。不往 Xcode 里加 Apple ID。
6. 隧道：Mac 的 `~/.ssh/id_ed25519.pub` 加进 Linux 的 `authorized_keys`，Linux 的公钥加进 Mac 的 `authorized_keys`；plist 改好用户名和 IP 后放进 `~/Library/LaunchAgents/`，`launchctl load`。
7. `git clone`，`git remote add linux ...`，`bun install`，`bun run wasm`。

2026-10 时的版本：Homebrew 7.0.9、bun 1.3.14、rustc 1.97.1、xcodegen 2.46.0、cocoapods 1.17.0、idb-companion 1.1.8、fb-idb 1.1.7、pymobiledevice3 11.26.1、ios-webkit-debug-proxy 1.9.2、libimobiledevice 1.4.0。

- GitHub Actions（`macos-26`，Xcode 26.5）出要 Xcode 的两样东西：workflow `.github/workflows/ios-linux-loop.yml`，现在只在 `exp/linux-ios-loop` 分支上。三个 job：`devices`（只读查 ASC 已注册设备，`scripts/ios-linux/asc-devices.py`）、`wda`（WebDriverAgent v16.14.2 `build-for-testing`，包名 `com.xinyuan.wda`，runner 是 `com.xinyuan.wda.xctrunner`，通配 profile 到 2027-10-12）、`devbuild`（.dev 的 dev 模式包，devUrl 写死 `http://10.42.0.1:1437`，做法见坑 561）。只推 `.github/workflows/ios-linux-loop.yml`、`scripts/ios-linux/**`、`src-tauri/**` 会触发，也可以手动 dispatch。产物是 artifact `wda-runner-ipa` 和 `rp-dev-ipa`。

### 静默语音测试

在真机上跑完整通语音对话、量延迟，不出声、不需要人说话。只在 debug 构建（`tauri ios dev` 出的 .dev 包）里可用：Rust 的 `harness` 命令和 Swift 的 `voice_harness` 在 release 里直接拒绝。

做法。开关打开后，通话不开麦克风：AudioFront 建一个 `.playback` 的栈，不碰 input node，`VoiceHarness.swift` 按真 tap 的节奏（48 kHz、4800 帧、每 100 ms 一块，底噪 -75 dBFS）把剧本里的 WAV 片段喂进和 tap 同一个 sink，后面的电平检测、轮次状态机、SpeechAnalyzer 一行没改。TTS 照常合成、照常进播放器；播放器接到一个自己的 mixer 再接 main mixer，main mixer 的 `outputVolume` 为 0，扬声器无声，自己那个 mixer 上的 tap 把实际送出的 PCM 录成 `output.wav` 并按 -50 dBFS / 300 ms 判出「可闻开始/结束」，时刻加上 `outputLatency + ioBufferDuration`。SpeechOut 的播放逻辑没改，只把 RP-TTS 那几行同时写进 `native.jsonl`。

时钟。Swift 写 `native.jsonl`，Rust 写 `rust.jsonl`，都用 `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)`（即 `mach_absolute_time`，AVAudioTime 的 hostTime 也是它），不用对齐。TTS 每句的 req/firstAudio/handed（Rust `mono_ms`、Swift `SpeechOut.monoMs`）也是这个钟，日志里的 RP-TTS 行和 jsonl 的 `tts-*` 行可以直接比。webview 的点经 `harness mark` 送到 Rust，带自己的 `performance.now()`；开跑前 20 次 `clock` 往返，分析时取 RTT 最小那次算偏移，把 webview 的点换到同一时钟上。打点的位置：

| 点 | 谁打 | 在哪 |
|---|---|---|
| 片段开始 / 说话结束 / 片段结束 | native | 喂入器，按 tap 语义（一块缓冲送达时，它装的是之前 100 ms） |
| `turn-end`（hangover 判停）、`finalized`（强制定稿返回） | native | `ConversationRun.verdict` 的 `.end` |
| `conv:*`（speech-start/duck/stop/end、spoken、state） | native + js | `VoicePlugin.emitConversation`；webview 侧 `traceSource` |
| `front:speech-end`、`front:request-sent`、`front:first-byte`、`front:first-sentence-to-tts`、`front:delegate-sent` | js | 级联前台的 `frontMarks`，每回合每个点第一次发生时（和 RP-FRONT 行同一组时刻） |
| `front:delegate-done`（带「task N」）、`front:cue`（过渡语播没播成）、`front:note`（后台结果回来）、`front:notify`（前台开口告知）、`front:read-out-start/end` | js | `cascade.ts` 的 `trace` |
| `model-ask`、`model-first-delta`、`model-done`、`tool-start/end` | js | `traceModel` 包前台的 model |
| `speak-push-first`、`speak-begin/stop` | js + rust | `traceSource`；`commands.rs` |
| `tts:started/firstAudio/ready/queued/...` | rust | 会话里原本丢掉的 relay timeline（`session.rs` 接到 `harness::watch_relay`） |
| `cues-primed`、`cue`（id、是否预合成） | rust | `SpeechSession::prime_cues` / `speak_cue` |
| `enqueue`（句子进播放器）、`speech:speaking` | native | `VoicePlugin.enqueueSpeech`、`emitSpeech` |
| `tts-first`（行时刻=排上节点，带 req/firstAudio/handed/startsInMs）、`tts-dry`、`tts-resumed`（silentMs）、`tts-played` | native | `SpeechOut`，和 RP-TTS 行同处 |
| `audible-start/end` | native | 播放器 mixer 的 tap |

剧本。`tests/fixtures/voice-scripts/<名>.json` 加同目录的 16 kHz WAV，素材用 `scripts/ios-linux/voice-fixtures.py` 拿 edge-tts 合成（男声 Yunxi / Andrew，和冰糖分得开）。每步：`clip`、`text`、`start`（`reply-end` 等上一段回复播完；`reply-start` 等 AI 开口，用来插话；`clip-end` 上一个片段一完就接；`next-reply-end` 等这一步之后才开始的一段回复播完，用来等后台结果念出来）、`offsetMs`、`timeoutMs`、`expect`（`turn` / `interrupt` / `none`），可选 `after`：一个 trace 点名（如 `front:notify`），本次跑里它发生过之后 `start` 才从它算起，用来等前台问完「念还是自己看」再答。剧本级可选 `finalAfter`：最后那几段回复从这个点之后算（如 `front:read-out-start`）。现有三个：`zh-chat-then-delegate`、`en-mixed`（en-US 识别，中英混说以英文为主）、`barge-in`（AI 说话中途一个 250 ms 的「嗯」，再一个「等一下」）。

每次跑的文件在设备的 `Library/Application Support/com.xinyuan.readingpartner.dev/voice-harness/<剧本>-<时间>/`：`rust.jsonl`、`native/native.jsonl`、`native/output.wav`（24 kHz，AI 实际送出的声音）、`native/input.wav`（16 kHz，喂进去的声音），拉到 `~/.cache/rp-ios-linux/voice-runs/<同名>/`，分析写 `latency.json`。拉失败时用 `voice-run.sh pull <run> <设备上的 dir>` 重拉。表的一行是一个用户片段，链是 `speechEnd`（片段里的话说完）→`turnEnd`（判停）→`finalized`（定稿）→`speechEndSent`→`frontHeard`（前台收到）→`request`（前台请求发出）→`firstByte`（首字节）→`firstSentence`（第一句送 TTS）→`ttsRequested`→`ttsFirstAudio`（TTS 首帧）→`ttsHanded`→`enqueue`→`scheduled`（排上节点）→`audible`（可闻），逐段毫秒数和 TOTAL；没发生的点跳过，下一段从上一个发生的点算。前台交出去的回合另给 `delegate`（说完→派出）和 `filler`（说完→第一声，标 `(cue)` 的是预合成过渡语），汇总表多一行「hard question→filler heard」。句中断流的回合给 `dry 次数 静音毫秒`。最后一张表一行一个后台任务：`sent→back`（派出→CallNote 回来）、`back→notify`（回来→前台开口告知）、`notify→heard`、`total`。`interrupt`/`none` 的步另给从片段开始算的 duck、stop、声音停下的时刻，和有没有被打断。`latency.json` 是 `{ turns, tasks }`。

前提和限制：app 要在前台、info 页、卢明在屏幕上（剧本起的是页面长按会起的同一通电话）；识别 locale 按剧本的 `locale` 覆盖设置，en-US 模型没装过时第一次会下载。iPad 上 `mainMixer.outputVolume = 0` 是否真的一点声都不出还没在真机上听过，第一次跑时让人在旁边确认一次。

## 将来租云 Mac 时怎么重建

云 Mac 只承担 Swift 检查、模拟器和需要 Xcode 的构建；真机仍插在 Linux 上走 USB 那套。

1. 选机：Apple silicon，能拿到图形登录会话（VNC 或自动登录），系统和 Xcode 至少和设备的 iOS 一样新（坑 521）。
2. 连法：云 Mac 一般 Linux 能直连，`~/.ssh/config` 里把 `Host macmini` 指过去即可，`scripts/ios-swiftcheck.sh` 认 `RP_MAC`。只有 Mac 在 NAT 后面才装隧道 plist。云 Mac 到不了 Linux 时，代码从 GitHub 拉，或像 `ios-swiftcheck.sh` 那样用 git bundle 送。
3. 照「Mac mini 版 → 装机」第 1–7 步做；有直连外网就跳过隧道代理和 `NO_PROXY` 那几条。
4. 从 Linux 拷 `.p8`，写 `~/.asc-env`。不注册新设备，不加 Apple ID。
5. 验收这台机器：`scripts/ios-swiftcheck.sh` 绿；按「日常循环」起一个 iPad 模拟器，`scripts/ios-sim.sh reader` 跑一遍对照 `scripts/ios-sim/baseline.md`；`scripts/macos/build-dev-ipa.sh` 出包，包名校验通过，ipa 拿回 Linux 用 `device.sh install` 装上真机。
