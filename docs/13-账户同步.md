# 账户同步

## 动机

跨设备接续：PC 上班时聊，回家 iPad 接着聊。数据一致性主张全量同步，包括 PDF 本身。

## 机制

Google 账户登录 + Google Drive 作用户自带存储，不搭后端。与"测试者自带 API key"同一哲学：数据和算力都在用户自己账下。

scope 用 `drive.file`，在用户 Drive 里建可见的 "Reading Partner" 文件夹。不用 `appDataFolder`：Google 文档明确说明用户断开应用授权时 `appDataFolder` 会被整个删除，把书和批注放进去会造成数据事故。可见文件夹用户能自行备份，断开授权也不丢数据。app 按 file id 追踪，用户重命名文件夹不影响。

## Drive 布局

```
Reading Partner/
  books/<contentHash>.pdf     内容寻址，不可变 blob，上传一次永不冲突
  data/                       各 JSON（reading-state、annotations、threads、topics、memory…）
                              rev / mtime / hash 写在每个文件自己的 appProperties 里，
                              远端状态由 data/ 的一次 listing 得出
  manifest.json               旧版索引，只在迁移时读一次用来回填 appProperties，
                              之后不再维护也不删（老版本设备还在读）
```

## 同步时机

- 本地写入 debounce 后 push。
- 启动时 + 周期数分钟拉远端状态，比对 rev，有新的下拉。
- 回到前台立刻跑一趟（30 秒内不重复），切走时本地有改动就立刻推一趟。周期定时器在手机后台根本不走，只靠它就是"回来还要再等五分钟"。
- 变没变看内容 hash，不看 mtime：app 会用同样的内容重写文件，按 mtime 判就是「只是重存了一次的设备赢下整个文件」。
- 两边都改过的文件走三方合并（base = 上次同步成功时的内容，存在本地 `sync-base/`），不选边。合并结果发布在远端 rev 之上，两台设备收敛到同一份。合并模块删掉的记录进 `sync-trash.jsonl`（只在本地，留 30 天）。
- 文件级删除仍然不传播。

## 手机不走 books 通道

手机形态永远不开 PDF、也没有导入入口（docs/22），books 通道整个关掉，上下都不走。`library.json` 照常同步——手机知道有哪些书，只是不存；手机上没有书架，没人读它。桌面和平板不变。

## 不同步

- fulltext / figures 缓存：按内容 hash keyed，另一端自动重建。
- events 日志：按设备各自追加。
- prep 下载的论文 PDF（`prep-<hash>/pdf/`）及其派生缓存：另一端凭 plan 重新下载，避免 prep 目录几百 MB 上云。prep 只同步 `state.json` 和笔记 md。
- 缩略图 / 对话粘贴的图片（`images/`）：v1 不同步；另一端显示为缺图，`readThreadImages` 已容忍。
- sync 自身：`sync-auth.json`（token）、`sync-state.json`（folder/file id 映射、上次同步快照、自动同步开关、上次同步成功时间和上次错误）、`sync-base/`（合并基线）、`sync-trash.jsonl`（合并删掉的记录）。

## 自动同步开关

开关值存 `sync-state.json`（不同步），不放 settings.json，从根上避免"关了同步却被同步回来打开"的怪圈。同步启用本就是每台设备各自的选择。

## AI 凭据不同步

`credentials.json`（含 Anthropic OAuth token / API key）不在同步范围：明文凭据上云会把暴露面从本地磁盘扩大到 Google 账号（盗号或误分享文件夹即泄露），且两设备共用 refresh token 有被轮换后互踢的问题。每台设备各自登录 AI 账号，只多输一次。settings.json 里的 Semantic Scholar key 价值低，保留同步。

## 设置页 Sync 区块

Google 登录按钮 → 登录后显示账户邮箱、自动同步开关（登录后默认开，可手动关）、Sync now、上次同步时间、登出。

上次同步时间是"最近一趟一个都没失败的同步"，只有干净的一趟才推进它（`engine.ts`）。它存在 `sync-state.json`，启动时读回来喂给引擎（`restoredLastSyncAt`），所以重启后显示的还是上次那个时间，不会退回 Never。写回磁盘只走 `recordPassResult`，它不接受 null 覆盖已有的时间戳——一趟同步开始时就会发一次状态，那时引擎还什么都没做。

## OAuth

- 桌面：PKCE + loopback，refresh token 落本地。复用 Anthropic 登录已有的 Rust 一次性回调监听器（`start_oauth_callback_listener`，`oauth_callback.rs`），不引 tauri-plugin-oauth——同一个固定 loopback 端口、按 state 匹配，少一套机制。client id/secret 从 `VITE_GOOGLE_CLIENT_ID` / `VITE_GOOGLE_CLIENT_SECRET` 读，Desktop client 的 secret 不保密（PKCE 才是保护）。
- iOS：custom URL scheme，单独的 iOS OAuth client，已落地（`authFlow.ts` 的 `AuthFlowKind = "desktop-loopback" | "ios-scheme"`，`auth.ts` 按它分支走 `captureSchemeCode`）。全过程见 [18](./18-iOS-Google登录.md)。
- Google Console 需两个 client：Desktop + iOS。

坑：OAuth consent screen 处于 Testing 状态时 refresh token 七天过期，必须发布 In production。非敏感 scope 可直接发布，代价是"未验证应用"警告，品牌验证可去掉。

## 前置

所有数据身份从 `hashPath`（绝对路径 hash）换成文件内容 hash，配套本地 library 导入模型。这也正是 iPad sandbox 需要的形态。

## 演进方向：按需与分批（2026-07-29 定）

全量同步在只有 PC 和 iPad 时成立，接进手机就不成立了。方向按 iCloud 的姿态改：不预先拉全部，让用户尽快用上手边要用的那部分。

两条轴。

**书按需下载。** 不再对齐整个 `library.json`。书架上一本没下载的书显示为在云端，点了才拉，带进度。桌面上新设备登录不必先等几百 MB；手机形态下书架入口根本不存在，等于永不拉。

**数据分批到达。** 先拉最近动过的，再往回补，先到的先能用。

分批的粒度只能按远端修改时间，不能按内容日期：`data/` 里每个文件的 rev/mtime/hash 已经写在 appProperties 上，一次 listing 就能排序；而按内容日期切只对 info 成立（`threads-info-<date>.json` 天然按天），reading 的对话是一本书一个 `threads-<bookId>.json`，没有天这个粒度。按 mtime 排序的效果是一样的——最近动过的先到。

分批要求同步状态从"全有或全无"变成"这批已到"。`health.ts` 现在的 `lastSyncAt` 语义是"这台设备持有的一切都已镜像"，分批之后这句话不成立，得跟着改，否则健康态会一直显示落后。
