## 目标

早上刷牙、吃饭、上厕所的那二十分钟，AI 把当天简报念出来。手机锁屏或 app 在后台，手是湿的或脏的，全程不点屏幕。用户在前台点一次"开聊"，之后一直处于对话状态：AI 念它的，用户随时开口打断，聊完接着念。全双工，不用唤醒词。

只做 info 线的每日简报播报。reading 线不做语音。

这条推翻 docs/22 "实时语音对话同时否掉"那一句。

## 形态：全原生

音频链路整体在 Swift：麦克风采集、回声消除、`SpeechAnalyzer` 识别、TTS 播放。TTS 的网络请求放 Rust 侧，音频字节直接进 Swift 播放，不经过 webview。webview 只剩界面和文本流。

不能只搬一半。WKWebView 无视宿主 app 的 AVAudioSession（WebKit bug 167788，2017-02 报，至今状态 NEW），反过来宿主把自己的 session 设成 `.playAndRecord` 会打断 webview 正在播的音频。而原生 ASR 必然要求宿主自己激活 session——`AVAudioEngine.inputNode` 的官方文档写着 category 和硬件决定 input 可不可用，不可用时 engine 抛异常。所以一旦有一段在原生侧，全部都得在原生侧。

另两条收益：采集和播放共用同一个 voice-processing 单元，AEC 的参考信号必然正确；只有原生 `SpeechAnalyzer` 拿得到 `AnalysisContext.contextualStrings` 热词表。

原生代码走 Tauri iOS 插件（`tauri plugin new <name> --ios`，`ios/` 是一个 Swift package）。Swift 侧继承 `Plugin`，命令是 `@objc public func foo(_ invoke: Invoke)`，参数用 `invoke.parseArgs(...)`，流式结果用 `trigger("partial", data: [...])` 推出去，JS 侧 `addPluginListener('voice', 'partial', cb)` 收。Tauri 生态里没有任何语音识别插件先例（仓库零 issue、零第三方插件），全部自己写。

## ASR

`SpeechAnalyzer` + `SpeechTranscriber`，iOS 26.0+，完全设备端，locale `zh-CN`。

preset 用 `timeIndexedProgressiveTranscription`（等于 `volatileResults` + `fastResults` + `audioTimeRange`）。打断时要按时间把助手消息截断到用户听到的位置，时间轴用得上；`fastResults` 偏响应速度、牺牲一点准确度，探针里要单独验它值不值。

结果从 `transcriber.results` 这个 `AsyncSequence` 出。`Result.text` 是 `AttributedString`，属性里带 `SpeechAttributes.TimeRangeAttribute` 和 `ConfidenceAttribute`，`isFinal` 区分 volatile 和定稿，`range` 给 `CMTimeRange`。

喂音频用 `AnalyzerInput(buffer:)`。格式必须先 `SpeechAnalyzer.bestAvailableAudioFormat(compatibleWith:)` 查出来自己转（`AVAudioConverter`）——官方明写 analyzer 不做音频转换。iOS 27 起有 `AnalyzerInputConverter` 和 `CaptureInputSequenceProvider` 能省掉 tap 和转换那一段，26 上自己写。

模型走 `AssetInventory`：`assetInstallationRequest(supporting: [transcriber])` 拿 downloader，`downloadAndInstall()`，进度在 `progress` 上，首次使用要有下载 UI。模型在系统存储、app 内存空间之外，不进包体也不占运行内存；但 reservation 有上限（`maximumReservedLocales`），系统会在长期不用后取消订阅，不能假设模型永远在。

推理跑在系统 XPC 服务里（`com.apple.SpeechRecognitionCore.speechrecognitiond`、`localspeechrecognition`），不在 app 进程——那个服务的沙箱 profile 里才有 `AGXAccelerator` 的 IOKit 通道。后台 CPU 预算（60% 平均值 over 15 秒窗口）按进程记账，大概率不算在我们头上，但 Apple 从未文档化 XPC 记账规则，要用 Instruments 钉死。

locale 相等性有坑：判定必须用 `SpeechTranscriber.supportedLocales` 的成员检查。不能拿 `Locale.current`（系统语言 en-US 加地区德国时 identifier 是 `en_US@rg=dezzzz`，直接构造报 unsupported），也不能信 `supportedLocale(equivalentTo:)` 的返回值——它对 `ru_RU` 会返回 `ru_RU`，而 `ru-RU` 根本不在 `supportedLocales` 里。

热词表：`AnalysisContext.contextualStrings` 收当天简报里的机构名、论文标题、人名，播到哪一条就用 `SpeechAnalyzer.setContext(_:)` 换成哪一条的词。它只在当前 locale 的语言内起作用，中文专名靠它，英文专名靠不上。

英文专名的纠正落到 ASR 之后：插问时正在播的是哪一条已经是确定的（见"交互"），那一条的机构名、论文标题、人名构成一个十几个词的封闭集合，在这个集合里做音近匹配，不是让润色模型漫无边际地猜。

排除的两条。`SFSpeechRecognizer`：框架会停掉超过一分钟的 task，还有不公开的每日配额（官方原文 "Individual devices may be limited in the number of recognitions that can be performed per day"），会话要长时间挂着的场景直接毙掉。`webkitSpeechRecognition`：底层就是 `SFSpeechRecognizer`（WebKit 用私有 `_setMaximumRecognitionDuration:` 设成 3600 秒绕开一分钟上限，我们不能用私有 API），用的是老引擎，且拿不到热词表。

## 探针第一轮实测

2026-08-13，iPhone 16（iPhone17,3）、iOS 26.5.2、本地签名的开发构建。三场都是 `SpeechAnalyzer` + `SpeechTranscriber`，`volatileResults` / `fastResults` / `audioTimeRange` 全开，VPIO 开，`sampleRate` 留空。两份原始导出留档在 [assets/voice-probe/](./assets/voice-probe/)（run 2 和 run 5），数字对不上时回去查。

`isAvailable` 为真。`supportedLocales` 30 个：中文四个（`zh-CN`、`zh-TW`、`zh-HK`、`yue-CN`），英文九个（`en-US`、`en-GB`、`en-AU`、`en-CA`、`en-IN`、`en-IE`、`en-NZ`、`en-SG`、`en-ZA`），另有 fr 四个、de 三个、es 四个、it 两个、pt 两个、`ko-KR`、`ja-JP`。`bestAvailableAudioFormat` 是 16000 Hz 单声道，麦克风给的是 48000 Hz，转换那一步躲不掉。`maximumReservedLocales` 是 5。模型首次使用时下载，装完 `modelInstalled` 为真。权限只弹麦克风一个，没有第二个"语音识别"弹窗。

跨语种是对称且彻底的：不是另一种语言差一点，是另一种语言不在解码空间里，按一个语言解码而不是逐词切换。

run 2，locale `zh-CN`，热词表 `["机器之心"]`，17.2 秒，输入电平峰值 -20.34 dBFS、均值 -36.88 dBFS（安静环境基线）。三条定稿：

```
conf 0.604  ow everthing going机器之心。
conf 0.797   how severything going
conf 0.411  机器之心。
```

run 5，locale `en-US`，热词表 `["机器之心", "how's everything going", "Claude"]`，17.3 秒，峰值 -14.04 dBFS、均值 -31.13 dBFS。四条定稿：

```
conf 0.727  How's everything going?
conf 0.068   This situation?
conf 0.859   How's everything going?
conf 0.271   Shenjian Wan Lo.
```

`This situation?` 和 `Shenjian Wan Lo.` 都是用户说的中文被英文模型解出来的结果，后者对应的原话是"机器之心"。反过来 run 2 里的英文也没解出来。中文专名在中文 locale 下每次都对。

`contextualStrings` 跨不过语种边界。直接证据是 run 5：热词表里明写着"机器之心"，输出仍是 `Shenjian Wan Lo.`。同语言内的提升也很弱——第三场 locale `zh-CN`、热词表里放英文词，`Claude` 仍被听成 `cloud`，`how's everything going` 比 run 2 略好但远不如 `en-US` 下（这一场只有口述结论，没有导出留档）。

置信度只能单向用。低置信度标得出跨语种垃圾（0.068、0.271），高置信度不保证正确——run 2 里错的英文是 0.797，对的中文是 0.411。做纠错判据时可以用它否定，不能用它确认。

## 探针第二轮实测：外放 AEC 与后台锁屏

2026-08-15，同一台 iPhone 16、iOS 26.5.2、本地签名的开发构建。三份原始导出留档在 [assets/voice-probe/](./assets/voice-probe/)（VPIO 开、VPIO 关、后台锁屏）。

外放 AEC 是两组对照，除 `voiceProcessing` 外参数相同：locale `zh-CN`，三个结果开关全开，采样率留空，热词空，硬件音量满格。探针自己当远端——先录用户十秒，再把这段人声从外放循环放出来，分四段：静默基线 5 秒、录制 10 秒、只播不说 15 秒、播着的同时用户插话 15 秒。

VPIO 开：

```
baseline  peak -56.65  mean -74.57  转写 0 条
record    peak -13.43  mean -27.16  哈喽哈喽哈喽，现在怎么样？听得到吗？……
echo      peak -38.48  mean -67.84  转写 0 条
barge     peak -12.46  mean -29.44  啊啊，我现在在说新的内容有没有什么。这个说法。
```

VPIO 关：

```
baseline  peak -69.34  mean -72.11  转写 0 条
record    peak -36.24  mean -44.77  这是第一部分的内容，然后让我们一起来去尝试一下……
echo      peak -56.69  mean -63.41  哈。这是第一部分的内容……（播放内容被原样转写，相似度 0.55）
barge     peak -35.46  mean -43.48  这是第二部分的内容，让我们尝试一下……
```

全双工成立。VPIO 开着，外放最大音量放连续人声，识别器 15 秒零输出；用户一开口立刻识别，识别文本里没有混进播放内容。VPIO 关掉，播放内容被识别器原样转写出来，docs/27 那句"模型听见自己，自己打断自己"在对照组里如实发生。

残留电平这个指标区分不出两组：echo 段相对基线抬了 6.73 dB（开）对 8.70 dB（关）。判据只能是有没有被转写出来。原因是 VPIO 顺带做自动增益——同样是用户说话，开着采到 -27.16 dBFS，关掉只有 -44.77 dBFS。人声相对回声残留的余量，开着 40.7 dB，关掉 18.6 dB，差 22 dB。VPIO 在这条链路上抬高人声比压低回声管用，以后复测别再盯残留电平。

后台锁屏是一场 44.8 秒的会话，播放关闭，locale `zh-CN`，按下 Start 后立即锁屏，全程锁屏说五句话，结束前解锁停止。五句全部定稿，逐字的 volatile 结果也一路在出：

```
[2880-7860]    conf 0.943  哈喽哈喽哈喽，现在能不能听得见我说话呢？
[13260-17340]  conf 0.981  第二次尝试能不能听见我说话呢？
[23280-27600]  conf 0.986  第三次尝试能不能听见我说话呢？
[30540-35460]  conf 0.972  第四次尝试能不能听见我说话呢？
[37200-42300]  conf 0.847  第五次尝试能不能听见我说话呢？
```

287 个电平采样贯穿全程，`droppedSamples` 为 0，没有中断事件，`run.error` 是 null。

证据边界：日志里没有 app 生命周期标记，"按下 Start 后立即锁屏"这个前提来自口述，这份数据本身证明不了锁屏发生在第几秒。会话只有 45 秒，更长的没测。

## 探针第三轮实测：停顿与定稿延迟

2026-08-15，同一台 iPhone 16、iOS 26.5.2。locale `zh-CN`，`volatileResults` / `fastResults` / `audioTimeRange` 全开，VPIO 开。

说话中途停顿不会被提前定稿。一场 11.7 秒，用户说"今天关于那个……嗯……那个模型的新闻是什么呢"，中间故意停约两秒，只出一条定稿，没有被切开：

```
[0-10140]  conf 0.58  今天关于那个。嗯。那个模型的新闻是什么呢
```

volatile 的轨迹看得到它在等：5614ms 时是"今天关于那个。"，之后空了将近两秒，7589ms 才补上"嗯"。

定稿延迟约 2.6 秒，当不了轮次信号。把定稿事件的到达时刻减去它自己的音频结束时刻，取已留档的两场会话，七次测量（毫秒）：

```
2446  2627  2847  2696  2316  2709  2601
```

均值 2.6 秒，波动很小，且与句子长短无关，像固定的内部超时。这是 `fastResults` 开着的成绩。

证据边界：停顿那场的定稿是在用户按下 Stop 之后才到的（stop_probe 在 11465ms，定稿在 11618ms），所以那一场本身证明不了自发定稿。自发定稿由后台锁屏那场证明——45 秒里五句话各自定稿，中途没人按停。

## 按住说话的启动延迟：定稿

2026-08-22，iPhone 16 / iOS 26.6，28 次真机按住。按下到 tap 交出第一个音频 buffer：

```
                  n   中位数   范围        转写完整
留着引擎           9    304ms   120-316     9/9
每次重建          13   1082ms   490-1277    2/13
```

丢头字（坑 166）就是这一秒。留着引擎之后它消失了。

那一秒里贵的是 `setVoiceProcessingEnabled(true)` 重建 IO 单元和随后的 `engine.start()`；读硬件格式不在里面（每次按住 0-12ms）。`stop()` 会释放 `prepare()` 分配的资源，`pause()` 不会，所以按住之间用 `pause()`。

不需要为速度牺牲回声消除。同一轮里开 VPIO 复用是 305ms、关 VPIO 复用是 277ms，分不出差别——VPIO 那几百毫秒只在第一次付。而且 `isEchoCancelledInputAvailable` 在这台 iPhone 16 上是 false，`setPrefersEchoCancelledInput` 那条路根本拿不到，代码已删。

定的形态：音频前端（session + VPIO + engine + tap）的持有者是一次语音模式。

- 第一次按住时建，不在切进语音模式时预热。橙点在 `engine.start()` 那一步亮（坑 167），预热等于用户还没开口橙点就亮。第一次按住仍付那一秒、仍可能丢头字，接受。
- 按住之间不释放，停多久都不释放。用户思考、读回答、滚屏，回来按住仍是 300ms。不加空闲超时——那会让"想一下再说"变成最容易丢字的情况。
- 切回键盘、离开聊天、组件卸载立刻释放，橙点跟着灭（`plugin:voice|release_microphone`）。

iOS 自己收走麦克风的窗口从一次按住变成整个语音模式，`AudioFront` 因此常驻订阅三件事：interruption 的 `.began`、输入路由变空、app 离开屏幕（锁屏只给这一条，坑 162）。空闲时任一条都把栈拆掉，下次按住重建；按住中只拒绝"留着"，拆除仍由 run 自己走。路由变空要在拿到锁之后重读路由，因为建 session 的过程中路由本来就会短暂为空。

分段埋点（`TimingLog` / `DictationTiming`）留着，走事件到 webview；`RP-DICT` 那些行只在 debug 构建里打。

## 系统要求

`src-tauri/tauri.conf.json` 的 `bundle.iOS.minimumSystemVersion` 从 `16.0` 抬到 `26.0`，全局抬，不做运行时能力开关。硬件下限 iPhone 14——`SpeechTranscriber.isAvailable` 在 8 核 Neural Engine 的机器上返回 false，社区实测 iPhone 11 和 SE2 不行、iPhone 12 起可以，我们留一档余量。README 和 TestFlight 的 What to Test 都要写清系统和机型要求。

模拟器上 `isAvailable` 是 false（不模拟 ANE），日常开发循环必须真机。开发条件是 Mac mini M4 16G + iPhone 16。

plist 改 `src-tauri/Info.ios.plist`（`gen/apple` 不入库、CI 现生成，手改会被覆盖，见坑 31）：加 `UIBackgroundModes = [audio]`，加 `NSMicrophoneUsageDescription`——它现在只在 `Info.plist` 里，靠合并顺序漏进 iOS 包，不该指望。`NSSpeechRecognitionUsageDescription` 不用加：探针实测只有麦克风一个弹窗，语音识别授权状态一直是 notDetermined，转写照跑。

## 后台与锁屏

`UIBackgroundModes` 含 `audio`，session 用 `.playAndRecord` + `.voiceChat` mode，前台 `setActive(true)`。

录音必须在前台启动。后台起或重启抛 `AVAudioSession.ErrorCode.cannotStartRecording`（561145187，`!rec`），iOS 12.4 起就封了。所以"开聊"那一下必须在前台按，之后才能锁屏。也没有"挂着待命但不录"的后台状态：`audio` 后台模式只在音频 I/O 真的在跑时保活。

任何中断等于会话死亡。来电、Siri、闹钟触发 `AVAudioSession.interruptionNotification` 之后，后台重启麦克风必然 `!rec`，不能自动恢复。中断处理要写对，恢复只能等用户回前台，界面上如实说"被打断了，点一下继续"。

iOS 26 不需要垫无声音频保活。Apple DTS 在 forums/thread/826462 里明说 iOS 26 不区分"只录音"和"录音加放音"，indefinite background microphone-only recording 是支持的，只要 session 保持激活。念完一条到下一条之间的静默不用垫静音。

后台常驻内存 DTS 给的指导值是 100MB 以下。`SpeechTranscriber` 的模型在 app 内存空间外，这一条正好有利。

锁屏控件用 `MPNowPlayingInfoCenter.default().nowPlayingInfo` 加 `MPRemoteCommandCenter`：`MPMediaItemPropertyTitle` 写当前这一条的标题，配 `MPMediaItemPropertyPlaybackDuration` 和 `MPNowPlayingInfoPropertyElapsedPlaybackTime`，`nextTrack` 绑"跳过这条"。

App Review 按"后台播放的语音助手"报，不按"后台录音"报。`audio` 后台模式的官方描述只写播放，有人只用它做后台录音被拒（forums/thread/776949）。我们的主行为就是播放，录音是打断手段；2.5.14 要求的录音可见指示由系统橙点自动满足。

后台识别行为 Apple 零文档，实测锁屏全程 volatile 和定稿都照出，见"探针第二轮实测"。实测只覆盖一场 45 秒，更长的会话还没跑过。

## TTS

主选小米 `mimo-v2.5-tts`（2026-08-27 定，依据是音质和读音实测，见"音质与读音实测"）。`POST https://api.xiaomimimo.com/v1/chat/completions`，`Authorization: Bearer`，OpenAI 协议兼容，但要合成的文本必须放在 assistant 消息里，user 消息是可选的风格指令、不会被念出来。SSE 流式，base64 PCM 在 `choices[0].delta.audio.data`，固定 24 kHz / 16-bit / 单声道——响应里没有采样率字段，这个值是拿与两家已知 24 kHz 的逐句时长交叉验证推出来的。中文音色四个：冰糖、茉莉、苏打、白桦。限额 100 RPM / 10M TPM，个人小米账号自助建 key，不用审核不用实名；要新起一套凭据，现有 STT 那把 key 是硅基流动的（`src/ai/voice/config.ts`）。限时免费，没有截止日期也没公布后续价格。

备选阿里 `qwen3-tts-flash`，¥0.8 每万字符，读音最稳，代价是单位一律拼字母、听感平。硅基流动 `FunAudioLLM/CosyVoice2-0.5B` 出局，两条独立理由（16 kHz 上采样冒充 24 kHz、三成句子随机损坏）在"音质与读音实测"。MiniMax `speech-02-turbo`（`POST https://api.minimax.chat/v1/t2a_v2?GroupId=`）的价格仍未查证，不进候选。

计费口径有三种，别混：按字符、1 汉字算 2 字符、按 UTF-8 字节。纯中文文本三者是 1 : 2 : 3，本轮语料（41% 的字符是数字和英文缩写）是 1 : 1.59 : 2.30。阿里那条"1 汉字 = 2 字符"是从选型第一轮继承下来的假设，两轮折算都在用它，没有独立验证过。硅基流动的定价页写的是"每千字符 UTF-8"，实际按字节算才对，当"字符"理解会把成本算便宜三倍。一份两千字简报在阿里是 ¥0.32，在小米是 0。

请求在 Rust 侧发，PCM 直接喂 `AVAudioPlayerNode`，不经过 webview。小米只给 PCM，没有 mp3 那条弱网退路；Rust 侧要先解 SSE 帧再 base64 解码，比 OpenAI 兼容的 `/v1/audio/speech` 多一层。第一版按句请求整段拿，首帧粒度实测够细（见"音质与读音实测"），真流式随时能开。

按句合成、按句接力。切句规则：硬边界是 `。！？；：` 和换行；软边界 `，、` 且累积长度超过 8–12 字才切，免得把 "OpenAI，" 切成碎句；第一句遇到第一个软边界就发，把首字延迟压到最小，后面的攒长一点让韵律连贯；不在英文缩写、数字、URL 中间切；先跑规范化再切句，否则边界不稳。

文本规范化自己做，不指望供应商。要处理的：日期 `2026-08-09` 念成"二〇二六年八月九日"；全大写缩写查表，未知的逐字母；URL 整条换成"链接"或域名主体，不念协议和路径；年份逐位读，数量按位数读；连字符和几个实测出来的词条见"小米落地要点"。这一层是无依赖纯函数，放 `src/info/briefing/` 下的 `.ts` 并配单测，换供应商它不动。各家对 "GPT-5"、"arXiv"、"2026-08-09" 的实际读法都没有公开说明，词条靠实测攒。

打断时播到哪个字：Swift 侧知道当前在播第几句，`AVAudioPlayerNode` 的 `playerTime` 给句内偏移，按"这一句共 N 字、总时长 T"线性插值到字符位置。中文语速均匀，误差一两个字，够用来把助手消息截断到用户真正听到的位置（docs/27）。字符级时间戳只有 ElevenLabs 给，不值得为它换供应商。

断网兜底用 Apple 的 `AVSpeechSynthesizer`：本地合成、免费、系统进程合成不占 app 的后台 CPU 预算，`speechSynthesizer(_:willSpeakRangeOfSpeechString:utterance:)` 直接给正在念的字符区间。音质是 default 档，enhanced 和 premium 要用户自己去系统设置里下载，app 没有 API 代下。

## Qwen3-TTS 复核

本节记的是 2026-08-27 上午的文献复核，只比了延迟、价格和工程量，没有量音质和读音。它和下一节得出的"不换供应商"当天就被音质实测推翻了，见"音质与读音实测"。

2026-08-27 复核，结论不换：第一版留硅基流动 CosyVoice2。原文在 [assets/companion-research/](./assets/companion-research/) 的 `round2-01-qwen-tts.md`。

延迟没有任何支持换的证据。qwen3-tts 那个 97 ms 出自技术报告（arXiv 2601.15621），测的是开源权重 Qwen3-TTS-12Hz-0.6B 单卡 torch.compile + CUDA Graph、并发 1 的模型侧首包（LM 93 ms 加 tokenizer 4 ms），不含网络；托管的 qwen3-tts-flash 现役快照是 2025-11-27，比那套权重开源（2026-01-22）早两个月，没有文档说是同一套。阿里托管侧唯一出现过的毫秒数在实时合成用户指南的 FAQ 排障段（"首包延迟：正常约 500ms"），是排障基线不是规格，同页还注明 SDK 量出的首包含 WebSocket 建连耗时。硅基流动一个数都没有。两家在"未实测"那一栏上是平的。

价格差可忽略。qwen3-tts-flash ¥0.8 每万字符、汉字按 2 字符计，折 ¥1.60 每万汉字；CosyVoice2 ¥0.05 每千 UTF-8 字节、汉字 3 字节，折 ¥1.50 每万汉字。两千字简报是 ¥0.32 对 ¥0.30，按下一节实测的语速约 10 分钟语音。realtime 版 ¥1 每万字符，贵 33%。

工程量差得明显。硅基流动是 OpenAI 兼容的 `POST {base}/v1/audio/speech`，key 和 base_url 与现有 STT 同源，`response_format: "pcm"` 给裸 PCM 且 `sample_rate` 可选 8/16/24/32/44.1 kHz，能挑一个和 VPIO 引擎对得上的。百炼没有 OpenAI 兼容的 TTS 端点，只有 DashScope 原生的 multimodal-generation，要新起一套凭据；HTTP 加 `X-DashScope-SSE: enable` 给的是 base64 包着的 PCM，24 kHz/16-bit/单声道且不可选（`format` 和 `sample_rate` 只存在于 CosyVoice 和 Qwen-Audio-TTS 的请求里），Rust 侧多一层 SSE 帧解析加 base64 解码。还有一件必须做对的事：400 `DataInspectionFailed`（内容审核）要从网络错误里单独拆出来，念新闻天然踩这个雷，当网络错误重试就是那一句永远静音的循环。流式文本输入只有 realtime WebSocket 有，第一版按句请求整段拿，用不上。

唯一真正的差距是音色：qwen3-tts-flash 51 个，含粤语、四川话、京片子、上海话、天津话、陕西话和一批角色音；硅基流动八个通用播音音色。当前范围是早上念新闻，播音音色正是要的。等陪读者人格那条路排上日程，再拿这条重新决策，那时候连带要决定的是声音复刻（qwen-voice-enrollment ¥0.01 一个音色，免费 1000 个）。

TTFB 要量，两家一起量。一个丢完就扔的脚本，从与手机同网络的机器对两家各发 40 句、每句 20 字左右中文，分段记 DNS、TCP、TLS、HTTP 首字节、第一帧可播 PCM（阿里那边是解完 SSE 帧和 base64 之后）、整句收全。另记两个派生量：第一帧里含多少毫秒音频——服务端整句缓冲后一次吐的话，"流式"对首字延迟毫无帮助，这是决定按句接力成不成立的那个数；以及 RTF（合成耗时除以音频时长），必须明显小于 1 否则接力会饿。p50/p90，WiFi 和蜂窝各一轮。若两家 p90 都在 500 ms 以上，要重新想的是按句接力这个形态，换不换供应商是次要问题。2026-08-27 按这个量法跑完了，结果在下一节。

## 首包延迟实测

本节只量延迟。它的"留硅基流动"结论已被"音质与读音实测"推翻；表里的速度数字仍然作数，句首静音是它漏掉的那一段，补在那一节。

2026-08-27，Linux 桌面机，两家各发 40 句，回答上一节留下的那个问题。原始数据、脚本和字段说明留档在 [assets/tts-probe/](./assets/tts-probe/)，数字对不上时回去查。

条件：40 句科技新闻语料，每句 20 字上下的中文，含机构名、数字、英文缩写混排；每句新建连接，这才是按句接力的真实情形；两家都取 24 kHz 16-bit 单声道（阿里固定不可选，硅基流动显式传 `sample_rate: 24000` 跟它对齐）；硅基流动用 `FunAudioLLM/CosyVoice2-0.5B:alex`，阿里用 `qwen3-tts-flash` 的 Cherry。脚本只用标准库自建 socket、自解 HTTP/1.1 chunk 和 SSE 帧，每一段都量在它真正发生的地方，chunk 边界是服务端实际 flush 的边界，不被客户端库的缓冲抹平。

限制：本机跑着 Mihomo TUN + fake-ip，`api.siliconflow.cn` 和 `dashscope.aliyuncs.com` 都解析到 198.18.0.0/15，全程走隧道。DNS 和 TCP 那两段被压成本地隧道的假象（0.1–0.4 ms），TLS 之后每个数都含上游中转，所以绝对值偏高、不能单独引用。两家是同一条隧道、同一时段交替发送，隧道加的是共同常数项，两家之间的相对比较站得住；首帧粒度和 RTF 是服务端行为，根本不经过网络。iPhone 上的绝对值还没量。

p50 / p90，毫秒（min / max 在留档里）：

| | 硅基流动 CosyVoice2-0.5B | 阿里 qwen3-tts-flash |
| --- | --- | --- |
| DNS 解析 | 0.3 / 0.4 | 0.4 / 0.6 |
| TCP 连接 | 0.1 / 0.1 | 0.1 / 0.1 |
| TLS 握手 | 88.8 / 101.4 | 78.2 / 85.7 |
| 请求→响应头 | 225.0 / 265.9 | 255.8 / 305.7 |
| 请求→首帧 PCM | 225.0 / 265.9 | 281.4 / 316.9 |
| 起点→首帧 PCM（端到端） | 317.7 / 350.9 | 360.2 / 394.8 |
| 请求→整句收全 | 558.6 / 653.3 | 1182.6 / 1453.9 |
| 首帧含音频 | 42.7 / 72.7 | 320.9 / 320.9 |
| 平均每帧音频 | 73.0 / 124.1 | 315.3 / 324.5 |
| 整句音频时长 | 4820.0 / 5480.0 | 4880.9 / 5696.9 |
| 首帧/整句 占比 | 0.009 / 0.016 | 0.066 / 0.077 |
| RTF（合成耗时/音频时长） | 0.118 / 0.130 | 0.243 / 0.271 |

表里阿里所有以 .9 结尾的毫秒数含 0.9 ms 的水分：那是 44 字节 RIFF 头被当成采样点算进去了（见"音质与读音实测"末尾），真值是整数——首帧 320.0 ms、整句 4880.0 / 5696.0 ms。占比和 RTF 不受影响。

硅基流动 40 句全成功，阿里 39 句成功、1 次 `TimeoutError`（第 27 句），在隧道条件下大概率是隧道抖动，不算阿里的账。硅基流动那两行"请求→响应头"和"请求→首帧 PCM"相等不是笔误：40 句里第一个 body chunk 每次都和响应头在同一次读里到达。

按句接力成立。两家都是真流式：首帧占整句的比例远小于 0.4，RTF 远小于 0.7。带着隧道劣化的条件下两家 p90 端到端首字都在 400 ms 以内，低于上一节定的"p90 超过 500 ms 就要重想按句接力这个形态"那条线，干净网络只会更低。

只按速度看，硅基流动每一项都不差于阿里，多数明显更好，那一轮据此判"供应商不换"。这条结论已被音质推翻。

最实在的差距是分块策略不是网络。阿里固定 320.9 ms 一块吐——39 句只有这一个值，24 kHz × 16 bit 恰好 15404 字节一块；硅基流动按合成节奏 flush，40 句里出现 6 种不同的首帧长度，最小 23.8 ms。哪怕两家网络延迟完全相同，阿里也要多等约 280 ms 才凑够第一块能播的音频。这是服务端行为，换网络不会变。

97 ms 那个数被实测否掉。它测的是开源权重 Qwen3-TTS-12Hz-0.6B 在单卡 GPU、torch.compile、并发 1 时的模型侧首包，不含网络，且托管的 `qwen3-tts-flash` 现役快照比那套权重开源早两个月。上一节写的是"不适用"这个怀疑，现在实测证实。

内容审核 0 拒绝。40 句最容易踩的语料（机构名、数字、英文缩写混排）阿里一句没拒，此前担心的 `DataInspectionFailed` 没出现。样本只有 40 句，不能推广成"没有风险"，上一节那条"必须把 `DataInspectionFailed` 从网络错误里单独拆出来"的做法照旧保留，只是它现在不是选型的减分项。

同一轮数据顺带量到了语速，用来修掉此前拍的 250 汉字/分钟。后来加进小米重跑一轮同语料（40 句，硅基流动 39 句成功），三家分别是硅基流动 197.8、阿里 192.4、小米 193.8 汉字/分钟（含数字标点分别是 341.2 / 328.0 / 330.4 字符/分钟）。三家基本一致，都比 250 慢两成。往后按 195 汉字/分钟算，或者直接用 192–198 这个区间；最初写的 199 偏快，对最慢的那家高估约 3%。

按实测语速折每分钟语音的价钱：阿里 ¥0.0416，一小时 ¥2.50（本轮 40 句计费 1739 字符，按 1 汉字 2 字符折，这个口径本身未验证，见"TTS"）；小米限时免费，没有单价。单价限定在这类语料——科技新闻里 41% 的字符是数字和英文缩写，同样的发音时长里塞进了更多计费字符；纯中文文本阿里每分钟 ¥0.031。上一节那份两千字简报按 195 汉字/分钟约 10.3 分钟，阿里 ¥0.32。阿里的 1 万字符免费额度按这类语料约合 19 分钟语音。

阿里唯一真正的优势仍是 51 个音色对 8 个，那是陪读者人格那个阶段才重新决策的事，与延迟无关。（小米中文音色四个，同样在那个阶段才重新算账。）

## 音质与读音实测

2026-08-27，回答上两节没回答的那半：三家的音质和读音。31 句科技新闻陷阱句加一段 375 字模拟简报，三家各合成一份，同一个 ASR（硅基流动 SenseVoiceSmall）回读做横向对照；可疑处换第二个音色重合成再回读一次，能复现的算真读错，不能复现的算解码器抖动。音色是硅基流动 alex、阿里 Cherry、小米冰糖，硅基流动另出一版 anna 做同性别对照。完整报告、判读规则和 ASR 的天花板写在 [assets/tts-probe/](./assets/tts-probe/) 的 `quality-report-2026-08-27.md`；音频样本太大，没有入库。

结论和前两节相反：硅基流动出局，小米 `mimo-v2.5-tts` 成为首选，阿里 `qwen3-tts-flash` 作备选。项目发起人在对齐响度后的 A/B 里亲耳选了小米的音色。

### 硅基流动出局

两条独立理由，各自都够。

一，它交付的不是真 24 kHz。频谱 99.5% 能量上限只有 3910 Hz，8 kHz 处一道 42 dB 的硬悬崖，底层是 16 kHz 采样再上采样——`sample_rate: 24000` 只买到重采样，买不到带宽。阿里 7147 Hz、小米 8437 Hz，两家到 12 kHz 都有正常能量。分频段能量（占总能量 dB，六段样本平均）：

| 频段 kHz | 硅基流动 | 阿里 | 小米 |
| --- | --- | --- | --- |
| 0–1 | -1.2 | -0.5 | -0.3 |
| 2–4 | -11.9 | -17.1 | -19.5 |
| 6–8 | -33.0 | -26.3 | -19.5 |
| 8–10 | -75.5 | -25.6 | -21.4 |
| 10–12 | -75.3 | -27.1 | -25.5 |

二，31 句陷阱句里 11 句内容级损坏，6 句整词被毁：

```
RTX 5090 首发售价公布   →  RTX 509式首发手加工部
传回首批地表图像        →  船回手PD表图像
月产能规划 5 万片晶圆   →  天越产能规划 5 万聘精元
OpenAI 宣布            →  欧克美艾宣布
服务器芯片             →  微负器芯片
新款电机峰值扭矩        →  新款舰机风式扭矩（并把 ·m 整个吞掉）
```

外加声调错：推理→退理、该→改、开源→开人。重新取样这几句全部变干净，所以这不是能靠文本预处理修掉的前端 bug，是随机的解码器抖动。对每天自动播报，随机比确定性糟得多——预防不了，也不知道今天哪一句会崩。阿里那 31 句一次抖动都没有。

还有第三条，它把上一节那点延迟优势也吃掉了：句首静音均值 375 ms（最大 520），是纯延迟，直接加在用户听到第一个字的时间上。

### 真正的首字延迟要把句首静音算进去

上一节只量到首帧 PCM 到达。句首静音在音频里不在网络里，但用户等的是第一个字出声，两段要加起来：

| | 首帧 PCM | 句首静音 | 听到第一个字 |
| --- | --- | --- | --- |
| 阿里 qwen3-tts-flash | 360 | 85 | 445 |
| 硅基流动 CosyVoice2 | 318 | 375 | 693 |
| 小米 mimo-v2.5-tts | 736 | 117 | 853 |

毫秒，首帧 PCM 是端到端 p50。阿里和硅基流动来自上一节那轮 40 句（全程走隧道），小米来自加了直连规则之后重跑的 18 句那轮；小米这一栏没有绕远的账还最慢，这个对比对它不占便宜。

### 小米 mimo-v2.5-tts

接入方式实测与文档一致，协议细节写在"TTS"那一节。

延迟（加了直连规则，18 句 17 成功，p50 / p90，毫秒）：TLS 74.6 / 79.5；请求→首帧 PCM 665.5 / 964.4；端到端首字 735.6 / 1041.7；请求→整句收全 1767.1 / 2006.6（最大 2401.9）。RTF 0.348 / 0.380。首帧固定 160 ms 音频，占整句 3.1%。

三条判据两条过。首帧占比 0.031，远小于 0.4，PASS；RTF 0.38，远小于 0.7，PASS；p90 端到端首字 1042 ms 超过 500 ms 那条线，FAIL。这条 FAIL 不否决小米，但那条线要重新理解：它是按"每句都要等"定的，而按句接力只有第一句要等。整句收全最慢 2402 ms，最短的一句音频 4320 ms，接力余量近两秒；第一句那 853 ms 用预合成抹平（见下一节）。

分块策略是三家里最激进的：首帧固定 160 ms，后续稳定 320 ms，首块特意减半提前吐。阿里首帧恒定 320.0 ms。小米在协议上是想抢首字的，被服务端本身的延迟盖住了。

客观音频指标三家里最好（31 句）：真 24 kHz（99.5% 能量上限 8437 Hz）、峰值均值 -2.37 dBFS、RMS 均值 -18.18 dBFS、无削波、直流偏移可忽略、句首静音 117 ms、句尾静音 451 ms（最大 580）、语速 4.41 字/秒。句尾那 451 ms 是要在客户端裁掉的，见下一节。

四个确定性读音 bug，两个音色都复现：

```
LLM     →  一千        （前端把 LLM 归一化成了数字，这个词每天要念）
18A     →  十八安培
GPT-5   →  GPT 杠 5
620N·m  →  620 N 米    （应为"牛米"）
```

另一面：`4.8TB/s` 三家里只有小米展开成"四点八太字节每秒"，另两家在拼字母；`RISC-V`、`5G-A` 也只有小米念对。百分比、小数、2026 年、1024 比特、第十二次、长数字、五句多音字全对。这些错的共同点是确定性——同一段文本每次错在同一处，一张替换表全消得掉，这正是它比硅基流动那种随机损坏可控的地方。

### 三家共同硬伤：连字符

`苏-27` 三家全部念成"苏负二十七"，两次取样六个音色无一例外。`RISC-V` 和 `5G-A` 上硅基流动和阿里把连字符念成"减"，小米念对；`GPT-5` 上小米念成"杠"，阿里念对。没有一家的连字符处理是对的，只是错的位置不同。不管选谁，这一类都要在送进 TTS 之前做文本预处理。

### 内容审核 0 拒绝

两轮语料合计 71 句（31 句陷阱句加 40 句延迟语料，机构名、数字、英文缩写混排），三家一句没拒，此前担心的 `DataInspectionFailed` 没出现。副作用是为小米写的错误帧解析分支只经过 dry-run 验证，没有被真实拒绝事件确认过，那条路径算未验证。

### 量阿里之前先踩了一个接口坑

qwen3-tts-flash 的 SSE 首帧不是裸 PCM，是一整个 WAV 文件：44 字节 RIFF 头（data size 填占位符 0x7FFFFFFF），后面才是采样点。按裸 PCM 拼起来，那 44 字节会解码成每条音频开头一个满刻度的咔哒声，31 句的全段峰值全落在前 5 ms，差点被当成阿里的音频缺陷写进结论。上面表里阿里的数字都是修正后的（修正前"削波 62 个样本"、峰值中位数 -0.0 dBFS，修正后归零、-7.3 dBFS）。另两家给的是真裸 PCM，没有头。详见 `docs/pitfall/` 里 DashScope 首帧那一条。

## 小米落地要点

一，句尾静音必须裁。451 ms 均值在按句接力时是每句之间凭空多出的空白，40 句就是 18 秒干等。Swift 侧拿到整句 PCM 后从尾部回扫到第一个超阈值采样点即可，句首那 117 ms 一并处理。阿里不需要做这件事（句首 85 ms、句尾 51 ms）。

二，文本预处理替换表：`LLM`→大模型、`GPT-5`→`GPT5`、`620N·m`→620 牛米、`18A`（原样送会被念成"十八安培"，替成什么要再试一次），加上连字符那一类。它属于 info 领域的简报生成侧，不属于 TTS 传输层，落点就是"TTS"那节说的 `src/info/briefing/` 下那个纯函数。

三，第一句预合成。简报生成完就把第一句合成好存着，853 ms 变成 0。和 `plugins/voice` 在两次按压之间不拆音频栈是同一个思路。

四，TTS 后端写成可切换的。小米的限时免费既没有截止日期也没公布后续价格；同平台 ASR 是 ¥0.5/小时，那是最可能的落点，按一天五分钟的用量就算收那个价一年也就一百多块，不用纠结，但别焊死。

五，iPhone 上的分流要先确认。`api.xiaomimimo.com` 不在 geosite 的 CN 列表里，手机挂着代理时会绕远——桌面上第一轮三家同跑就撞上了，小米的 TLS 881 ms、端到端首字 2235 ms，把域名加进直连规则重跑才拿到上面那组数。真机测之前先确认走直连。详见 `docs/pitfall/` 的"网络与 CSP"那一组。

## AEC 与音频路由

`AVAudioEngine` 开 `setVoiceProcessingEnabled(true)`（iOS 13+），或直接建 `kAudioUnitSubType_VoiceProcessingIO`。采集和播放共用同一个单元，参考信号就是我们自己播出去的那一路。官方明写：用了 chat mode 但不开 VPIO 的 app，系统不做回声消除和自动增益。

AirPods 走 HFP 窄带，无解。`.voiceChat` 自动带 `allowBluetoothHFP`，而设备同时支持 HFP 和 A2DP 时系统按官方仲裁规则必选 HFP。iOS 26 新增的 `bluetoothHighQualityRecording` 用不了：官方要求 mode 是 `default`（和 VPIO 需要的 VoiceChat 互斥），自己也说会增加输入延迟、不推荐实时通信场景，而且欧盟不支持。`prefersEchoCancelledInput`（iOS 18.2+）同样要求 `default` mode，且只支持内置麦加内置扬声器、仅部分 2024 年后机型——2026-08-22 在 iPhone 16 上实测 `isEchoCancelledInputAvailable` 是 false，这条路拿不到。结论是 ASR 端要能吃 8k/16k 窄带输入，检测到蓝牙输入路由时可以提示用户摘一只耳朵。

外放场景 VPIO 的实际效果没有任何可引用的实测报告，自己测了，见"探针第二轮实测"：外放满音量放连续人声，开着 VPIO 识别器一条都不出，用户插话立刻识别。探针的远端已经是没有天然停顿的连续语音，比 VoIP 苛刻；一米距离和嘴里有东西这两档还没试。

## VAD 和轮次检测

不做唤醒词。全双工下用户直接开口就行，KWS 这一层不需要，实测也确认了全双工成立（见"探针第二轮实测"）。半双工那条路（播的时候只跑关键词、命中才停播开全量 ASR）的做法是 sherpa-onnx `zipformer-zh-en-3M-2025-12-20`（Apache-2.0，约 13MB，iOS 有官方 xcframework，关键词纯文本自定义不用重训），技术记录留作备案，不实现。

VAD 和轮次检测要做，用来判断用户说完了没有。

定稿是准确性信号，不是时机信号。实测的 2.6 秒（见"探针第三轮实测"）之上再叠级联管线的 600–900 毫秒和模型思考时间，用户说完到听见回答超过三秒半。所以：

- 时机（何时判定用户说完）由独立的轮次检测给，不等定稿。
- 内容用 volatile。它紧贴说话实时更新（停顿那场一直更新到 11512ms）。轮次判定成立的那一刻，取当时最新的 volatile 送给模型。
- 定稿迟到但准，用于事后纠正记录。上下文里存的是定稿，不是 volatile。

打断的触发也走 VAD 检测到的语音起始，那是几十毫秒级，比等定稿快两个数量级。

范围只做"用户说完了没有"，不做"这句话是不是冲我说的"（2026-08-15 定）。第一版默认安静环境、说话人声音足够大且清楚。兜底是免费的：转写文本送到模型那一层，如果那句话根本不是在问它（电视里的半句话、旁人聊天），模型不作答，播报继续——级联管线自带，不需要额外机制。第一版的失败模式是无谓停顿一下，不是答非所问。

iOS 26 的 `SpeechDetector` 当不了通用 VAD：官方明写它只能与 `SpeechTranscriber` 或 `DictationTranscriber` 配套挂进同一个 analyzer，拿不到独立事件流。它是省电门控，可以挂着（`SensitivityLevel.medium`）省掉静音时的转写开销。

VAD 先用 Silero VAD（MIT，JIT 模型约 2MB，30ms chunk 单线程小于 1ms）。响应不够快再换 TEN VAD（RTF 0.0086–0.016，官方称收尾比 Silero 快几百毫秒）——它是 Apache-2.0 加声网的非竞争附加条款，禁止"以与 Agora 竞争的方式部署"，陪读 app 不构成竞争，但这不是标准 Apache-2.0，用了要单独记一笔。

第一版就是 VAD 加静音超时，超时 700–900 毫秒起步调手感。这不是将就：Apple 自己的定稿要 2.6 秒，比 docs/27 说的"将近一秒"代价大得多。smart-turn v3.2（BSD-2，8.28MB int8 ONNX，官方称最好情况 CPU 上 10ms、多数云机器 100ms 以内，23 种语言含中文）后置，等 VAD 加超时的手感确实不够时再上——它要自己接 ONNX Runtime（pipecat 没有 iOS 实现），有没有 CoreML 格式未查证。

这三样都跑在原生侧，webview 路线上那些坑（`@ricky0123/vad-web` 的 Safari SIMD 问题、AudioWorklet 改派渲染线程）都不存在。

## 旁证：OpenAI Realtime API

2026-08-15 查 OpenAI Realtime API 官方文档和公开报道。本节全是别人的做法和别人的数字，我们自己的实测在上面三节"探针第 N 轮实测"里。

轮次检测有两种判据。`server_vad` 按能量和静音切，参数 `threshold`（0-1）、`prefix_padding_ms`、`silence_duration_ms`。`semantic_vad` 用语义分类器判断用户说完没有，判据是已经说出来的词：概率低就等超时，概率高就不等，官方例子是尾巴拖着"ummm…"会拿到更长的超时。它只有一个参数 `eagerness`（low/medium/high/auto，auto 等于 medium）。出处 https://developers.openai.com/api/docs/guides/realtime-vad

`eagerness` 这个抽象要抄：抢话意愿不是固定阈值，应随场景调。念简报时低，用户已在提问来回中时高。

"检测到用户说完"和"打断正在播的回答"是两个独立开关（`create_response` 和 `interrupt_response`），印证上面把检测与动作解耦的做法。

打断时用 `conversation.item.truncate` 带 `audio_end_ms`，语义是"用户实际听到了多少毫秒"，服务端据此把超出部分的文字转写从上下文里删掉，保证上下文里不存在用户没听过的话。出处 https://developers.openai.com/api/docs/guides/realtime-conversations 。这印证 docs/27 的"把助手消息截断到用户真正听到的位置"，本文 TTS 那节按"这一句共 N 字、总时长 T"线性插值正是干这件事。

负面结论：公开资料里没有任何"这句话是不是冲我说的"的检测。语义分类器回答的是"说完了没有"，不是"是不是对我说的"。用户抱怨集中在相反的失败——停顿被抢话，OpenAI 2025-03 专门更新过一版来减少打断（https://techcrunch.com/2025/03/24/openai-says-its-ai-voice-assistant-is-now-better-to-chat-with ，社区帖 https://community.openai.com/t/feature-request-advanced-voice-mode-keeps-interrupting-me/962909 ）。推断（未经证实）：他们的典型用法是手机举在嘴边或戴耳机，靠距离本身滤掉环境音，而我们是一米外扣在台面上，声学处境更难。

## 交互

当前条在屏幕上有身份。播到哪一条，顶部就显示那一条的标题和进原文的入口，进度条按条打标记（Google News Audio Briefing 就是这么做的，9to5Google 2025-12-17：https://9to5google.com/2025/12/17/google-news-audio-briefing/）。这直接解决插问时的上下文识别：用户说"这条什么意思"，上下文是播放器的当前条，不靠语义猜。`Briefing` 的 `mustRead` / `oneLiners` / `outOfLane` 本来就是有序数组，当前条就是下标。

按住说话的手势兼作确认。"这条明天别再给我"这类动作用 Spotify DJ 那个骨架：按住 → 一声 beep → 说 → 立即生效 → AI 口头复述一句作回执（Spotify newsroom 2025-05-13：https://newsroom.spotify.com/2025-05-13/dj-voice-requests/）。beep 告诉用户从现在起录的话当指令，它就是语音里的确认卡。前提是副作用可逆且只影响眼下这一次；写进画像的长期偏好仍然走 docs/17 的 apply 确认卡。

不打断播放的持久化动作。"记一下这条"应该是一声 earcon 的成本，不该变成一次对话（Snipd 把耳机的上一曲键改成 snip 键，触发后一声音频确认，播放不停，https://support.snipd.com/en/articles/10225450-create-snips-with-your-headphones）。手机上没有耳机按键可改，落到锁屏 `MPRemoteCommandCenter` 的某个命令上。

播报中断后的恢复。中断后会话必死，回前台时界面上显示"念到第 3 条被打断了"，一点接着念。听到一半走开再回来是普通续播，进度和 `info-run-<日期>.json` 一样存成断点。

要避开的坑：

- 不做成两种播放模式。NotebookLM 的互动是独立入口，用普通播放键播了就不能提问，得退出去点挥手图标、等重新起播、再拖回刚才那个时间点（Android Police：https://www.androidpolice.com/notebooklm-interactive-audio-make-me-feel-like-i-have-a-private-tutor/）。我们的简报只有一种播放，随时可插问。
- 回答前的静默必须有交代。级联管线的 600–900ms（docs/27）加上思考时间，这段静默要有声音或视觉占位，否则用户以为没听见会重复问。NotebookLM 官方自己承认主持人会在回答前尴尬停顿（blog.google 2024-12-13：https://blog.google/technology/google-labs/notebooklm-new-features-december-2024/）。
- 保留破圈位。docs/16 那 0-1 条"重要但不在你日常关注"在语音版照样念。Daily Listen 只从既有兴趣里选题，被评测直接点名有回音壁风险（Android Police：https://www.androidpolice.com/google-daily-listen-setup-guide/）。

第一次构建是探针不是功能。只验三件事：

1. `SpeechAnalyzer` 的中文识别质量，含专名和中英混说。2026-08-13 跑完，见"探针第一轮实测"。
2. 外放时 AEC 压不压得住。2026-08-15 跑完，见"探针第二轮实测"。
3. 后台锁屏能不能持续。2026-08-15 跑完，见"探针第二轮实测"。

同一个探针后来加跑一轮，量出定稿延迟，把 M-voice-3 的轮次检测架构提前定了下来（见"探针第三轮实测"）。

参数从 JS 侧传，一次构建跑多组实验：locale、`fastResults` 开关、AEC 开关、采样率、`contextualStrings` 的词表内容。真机上改一个参数重发一次 TestFlight 太贵。

三件都过了，下面两个正式排：

- M-voice-2：原生插件骨架（采集 + VPIO + `SpeechAnalyzer` + 结果推 JS）、TTS 走 Rust 侧、按句接力播放、句尾静音裁剪、第一句预合成、文本规范化层加单测（见"小米落地要点"）。
- M-voice-3：VAD 和轮次检测、打断与截断、锁屏 Now Playing 与当前条身份、按住确认手势、中断恢复。

## 未实测

- VPIO 有没有不依赖 audio unit output bus 的系统级回声参考兜底，官方没说。
- iPad 上 `SpeechTranscriber.isAvailable` 未实测，社区报告只覆盖 iPhone 和 Mac。
- 麦克风常开加 VAD 的实际耗电，没有可引用数字，只能自己用 Instruments 的 Energy Log 测。
- `AssetInventory` 的模型体积 Apple 没公布（`maximumReservedLocales` 实测是 5）。
- 语音识别 XPC 服务的 CPU 算不算 app 的后台预算。
- iPhone 上的按句首包延迟绝对值。桌面上量到的三家各带各的网络条件（阿里和硅基流动那轮全程走 Mihomo TUN，小米那轮加了直连规则），接力成不成立这半已经有答案，剩下的是绝对值。
- 逐句合成再拼接的实际听感。音质那轮只合成了整段，头尾静音能预估，拼接处的音高和语速接不接得上要真拼一遍才知道。
- 长文本的音色漂移。试听样本只有 375 字约 70 秒。
- 小米限时免费之后的价格。没有截止日期，也没公布后续价格。
- 阿里"1 汉字 = 2 字符"的计费口径。两轮折算都在用它，没有独立验证过。
- 小米的错误帧解析分支。两轮语料一次内容审核拒绝都没有，那条分支只跑过 dry-run。
- MiniMax 的定价。
- 自动 MOS 打分没做。这类模型在中文上的可靠性存疑，一个不可信的分数比没有分数更糟；音质判断靠试听样本和客观指标。
- smart-turn v3 有没有 CoreML 格式，以及在 iOS 上接 ONNX Runtime 的实际延迟。
- 送给模型的 volatile 比定稿差多少。轮次判定那一刻取的是 volatile，这个差值决定第一版的回答质量，没量过。
- App Review 对"以播放为主、录音为打断手段"的实际态度，只有一个反面案例和条款文本。
