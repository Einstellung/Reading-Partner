# 三餐：周计划、采购单与偏离

> 2026-09-21 改定（原为「晚饭」，一天一顿）。上游：[north-star/diet.md](./north-star/diet.md)、[63](./63-情报局：研究室、专项组与态势.md)、[69](./69-源模型：索引、叙事源、用户带来的与快照.md)。

饭这条线：一周七天、一天三顿的计划，一张从计划推出来的采购单（一周一趟），每道菜的做法，偏离时说一句话。

## 形态

内部它是一个研究室（63），视野是用户本人。但它不落 `Lab` 记录：`sources: []` 的 lab 会被 `labsForSource` 派到每个无人认领的源上，饭不认领任何源，也不该进采集管线。它自己一份 store 在 `src/info/meals/`，和 labs 平级。界面上不出现研究室、情报局、lab 这些词。

`settings.json` 里一个布尔 `meals`，默认关，跟着账号同步。关掉只是不显示入口，数据留着。

界面是一页卡片（Meals）：采购单在最上面，然后是今天和明天，再往下是这周剩下的几天。点采购单进采购单详情，点某一天进那天的详情（三顿加做法）。对话只有一条常驻线程，看的是哪一屏就把 `focus` 挂在 desk 上（`mealsGuidance(state, today, { focus })`，`week` / `shopping` / `day`），不按屏分线程。

## 三餐

`DayPlan` 是 `{ date, breakfast, lunch, dinner }`，每顿一个 `Meal`：

    Meal = { mode, dishId?, reheatOf?: {date, meal}, freshAdd?, place?, note? }
    MealMode = cook | reheat | packed | out | delivery | bought | skip

七种平等。外卖不是次等选项，不吃也是一种安排。

早饭是习惯不是七个决定：`WeekPlan.breakfastLine` 一句话记用户自己说的模式（「燕麦酸奶和鸡蛋吐司轮着来，周五路上买」），但每天的早饭仍然是真的 `Meal`，做的那几天指向真的 `Dish`——否则燕麦和酸奶不会出现在采购单上。

做一次吃两顿写进菜的形态：每道菜分耐放的底（`base`）和吃的时候现加的那部分（`fresh`），带 `keepsADay`。一顿 `cook` 的晚饭后面可以接第二天中午一盒 `packed`，或者第二天晚上一顿 `reheat`，`reheatOf` 指向底是哪天哪顿做的。`packed` 要么有 `reheatOf`，要么在 `note` 里说清这盒是哪来的（上周炖的），两样都没有就退回让模型重写。

省事的约束是硬的：一口锅、要洗的东西不比做一顿多、动手时间午饭晚饭 ≤15 分钟，早饭 ≤10 分钟（`HANDS_ON_LIMITS`）。超了 `assembleWeekPlan` 退回。

健康只是过滤器：蔬菜多、全谷物、瘦蛋白，少油少盐少精制碳水。不数卡路里、不报克数、这一片里任何地方不出现营养数字。

## 采购单

一周一趟。不由模型写，由程序从周计划推（`deriveShoppingList(plan, today)`，纯函数）：

- 只有 `cook` 且有 `dishId` 的顿贡献配料，三顿一视同仁。`reheat` 和 `packed` 吃的是已经买过的底，`out` / `delivery` / `bought` / `skip` 不贡献。
- 同名同类的配料跨菜合并成一条，份量文本用 ` + ` 接起来，保质期取短的，`neededBy` 取最早用到它的那天。
- 分组按品类走一遍店（produce、protein、dairy、frozen、grains、pantry、other），组内按保质期档从短到长，再按 `neededBy`、名字。
- `freezeOnArrival`：`d1-2` 的 protein，`neededBy` 距采购当天两天以上的，标「一到家就冻」。

`ShoppingState` 把四份东西分开放，因为调整计划要重推导出的那一半，而用户自己加的洗洁精不能跟着没了：

    { items（推出来的）, reader（用户加的）, dropped, replaced, checked, doneOn }

`currentList(state)` 是唯一把它们拼起来的地方，纯函数：推出来的减掉 `dropped`，套上 `replaced`，接上 `reader`。勾选状态单独存在 `checked` 里按 key 索引，所以重推导之后勾还在（`reconcileShoppingList` 只换 `items`）。替换保留品类、保质期和 `neededBy`——用户换的是篮子里放什么，不是什么时候要。

单子靠说话改，三个工具直接写盘不出卡片：`add_shopping_items`、`remove_shopping_item`、`replace_shopping_item`。用户已经说了，再拿张卡请他确认自己说过的话就是在布置作业。

`markShoppingDone(date)` 把这一趟按完。按完之后单子就是冰箱里有什么：再要什么记到下周，`add_shopping_items` 什么都不写，只回一句让模型这么说；除非用户说今天反正要路过一趟（`today: true`），这时那条带 `afterDone` 加进来，算在「还要买」里，不算这趟漏掉的。这一片里没有任何东西能把按完的那趟重新打开。

## 偏离

计划就是记录。默认照计划吃了，零输入。只有偏离才在对话里说一句「中午没带饭，食堂吃的」。

`Deviation` 是 `{ date, meal, became, place?, said }`。`applyDeviation` 只动眼前一两顿，两种情况：

- 底没做成：那顿本来要做的菜改成实际发生的，所有 `reheatOf` 指着它的顿清掉指针和菜（模式留着），进 `attention`。
- 底没吃掉：本来要带的那盒还在冰箱里，放不住。今明两天里下一顿要做的饭进 `attention`，但不动它——那顿计划本身没问题，它只是该被换成先吃那盒。

`attention` 最多两条，交给模型用 `propose_meals_plan` 带 `adjustment` 重排这一两顿。别的顿一概不动，整周不重排。腻了、太麻烦不当场改，留到下次排。

## 做法

`Dish.method` 是 `{ steps, note?, writtenAt }`。不在排计划时写：一周里大部分菜没人点开，提前写七份步骤就是七份白花的 token。

`ensureDishMethod(dishId, ports)` 在用户第一次点开那天时问一次：无线程无卡片的一次 headless 回合，把菜、章程和硬约束（一口锅、动手 ≤15 分钟、洗的不比一顿多、底做一次现加的现加）给模型，要 `{steps, note?}` JSON。校验 1–10 步、每步 ≤200 字；不合格返回 null 什么都不存，下次点开再问。同一道菜并发只跑一次（in-flight map）。任何失败都是「这天没步骤」，不抛。

用户说「换成不用烤箱的做法」走 `write_meals_method`，直接写，不出卡片。

## 事实不经模型

日期、今天是哪天、采购单、「一到家就冻」的标记、偏离之后哪几顿要重排，全由程序算。模型只交菜、配料（`category` 和 `keeps` 从固定枚举里选）、模式和文字。日子按 1 到 7 的编号加顿别交回来，从不写日期。

## 图片

机制没变，只改了名。用户分不出蔬菜，所以每一行都要有图。配料图先取 TheMealDB 的 `<Name>-small.png`，按英文常用名：模型给每个配料填一个 `en`（单数小写），`images.ts` 拿别名表把它映到 TheMealDB 那 992 个名字之一（全量内置在 `mealdb-ingredients.ts`），不调 API 也不经模型；菜心、莲藕、金针菇、毛豆四样用 Spoonacular 图片 CDN 常量 slug 兜底。白底抠图比网上的照片更能认出是哪种菜，所以这一层始终排在搜索前面。

菜品图、以及两家图库都没有的配料图，走 Bing 图片搜索，在电脑的隐藏 webview 里跑（坑 372）。Apply 写完周计划之后起一个 `meals-photos` run（`requires: [WEBVIEW_FETCH]`、`local`、不可 delegate），把这周还缺的查询一次搜完：菜按 `searchName`，配料按 `<en> vegetable` 或 `<en> food`，一轮最多二十条。搜到一条写一条进 `info-meals-photos.json`（键是 `dish:<searchName>` 和 `ingredient:<en>`）。页面打不开就算这一轮失败，剩下的等下一轮，不记成「这道菜没有图」。

手机不搜：计划应用完立刻用配料拼图和品类图形显示，图等文件同步过来。用户说图不对就在对话里重搜整周（`refresh_meals_photos`，忽略缓存）。图注是 "Photo: 站点"，点开图片所在的那一页；这些图走 `img:` 代理时把那一页当 Referer 发（坑 30）。

兜底两级：菜有自己的图就用，16:9 一条；没有就画一排配料抠图小方块——最多四张，粗指针 44px、细指针 40px 见方，`object-contain` 加 4px 内边距，蔬菜和肉排在调料前面，一张都取不到就整排不画。横幅只属于照片：白底抠图 `object-cover` 拉满一条 160px 的横幅，出来的是一块生牛肉。采购单每行一张 40px 方图，取不到就画品类图形。任何时候不出现裂图标，也不留空盒子。

TheMealDB 条款要求标注来源并回链，所以页面底部有一行 "Ingredient photos from TheMealDB"；上应用商店要先买 supporter，发布前要处理。

## 数据模型

一份 JSON：`info-meals.json`，`src/info/meals/store.ts`，io 照 `labs/store.ts`（`readGuardedJson` + 原子写 + 版本号）。章程、当前这周、采购单、偏离清单互相依赖，拆开按字段合并会拼出没存在过的状态，所以 palace 里登记成 `sync: "data"` + `merge: "opaque"`：整文件最后写者胜。图片缓存是单独一份 `info-meals-photos.json`，同样整文件合并。

类型在 `types.ts`：`MealsCharter`、`Dish`（`base` / `fresh` / `keepsADay` / `handsOnMinutes` / `ingredients` / `method?`）、`DishMethod`、`Ingredient`、`Meal`、`MealMode`、`MealKey`、`MealRef`、`DayPlan`、`WeekPlan`（七天、菜、`breakfastLine`、`revision`）、`ShoppingItem`、`ShoppingState`、`Deviation`、`MealsState`。

旧名字（dinner、`info-dinner.json`、`dinner-photos`）没发过版，直接改名，不做迁移。
