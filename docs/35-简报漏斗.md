# 简报漏斗与条目池：Reading-Partner

> 本文是 [16](./16-信息陪读与分诊.md)（分诊）和 [17](./17-信息源系统.md)（源）的下游。16 定的是四档分诊和简报交互，17 定的是源怎么描述和执行；本文写两件事——简报的采集和判断分成四步，贵的那两步只看少数条目（漏斗）；采集从"生成时跑一趟"变成常驻后台按源轮询，简报从攒下来的条目里取（条目池）。

---

## 为什么

原来的形状是：采集时给每一条都抓正文页、跑 Readability、存最多两万字符，然后把所有条目（每条标题加正文前 1500 字符）拼成一次 AI 调用出简报。订三五个博客时这没问题。

订彭博社、纽约时报这类站点，一天三五百条。抓正文是几百次页面请求（还有付费墙），那一次 AI 调用是二十多万 token。成本和延迟跟订阅量成正比，用户每加一个源都在为不看的东西付钱。

## 四个相位

一次生成按顺序跑四步，`InfoRunPhase` 就是这四个名字。

**发现（discovering）**：每个源一次请求，只吃 feed / 列表页 / API 给的标题、摘要、发布时间。不发任何单篇文章的请求。feed 自带正文的（`fulltext: feed-field`）本来就随列表回来了，留着，不为此多发请求。引擎里是 `collectSource(desc, { discoveryOnly: true })`。

**粗筛（screening）**：AI 只看标题、来源、摘要、发布时间，逐条回答一个问题——为这条抓正文值不值。50 条一批，3 路并发，用便宜的模型（`callModel("chat", ...)`）。不排名、不分档、不写总评、不合并重复报道，那些是 triage 的事。

**取材（fetching）**：只对活下来的条目抓正文，走 `pool.ts` 的并发池和 AbortSignal，沿用现有的 `extract` 和 `textMaxChars`。引擎里是 `fetchBodies(items, descriptors, ...)`。

**分拣（triaging）**：现有的 triage 原样跑，提示词和四档语义没动，只是面前从几百条变成了几十条。

结果是成本和订阅量脱钩：便宜的两步（发现、粗筛）随天量增长，贵的两步（抓正文、triage 的长上下文）只随粗筛留下的条数增长，而那个数有上限。

## 绝对判断，不要相对配额

粗筛是逐条的二元判断。提示词明写没有配额也没有预算：过线的全留，不过线的全丢，一批全留或全丢都可以。不许"每批挑前 N 条"，不许"每个源留几条"，不许因为已经留够了就丢下一条。给 AI 看的那一批是当天的任意切片，不是让它评名次的候选名单。

判不准的时候留。白抓一页很便宜，漏掉唯一重要的那条不便宜。模型漏答某条 id 时，`fillMissingVerdicts` 把它补成留——这条纪律不只写在提示词里，也写死在代码里。

上限（`SCREEN_MAX_KEEP`，现在 120）是成本闸不是配额。粗筛永远不瞄准它。真撞上了才按把握度截断，截掉多少条必须出现在三个地方：日志（`info-screen` 事件的 `cappedOut`）、进度条（`CollectProgress.cappedOut`，简报卡和门厅卡都显示）、简报文件（`briefing.screen.cappedOut`，管家能看见）。静默截断的一天和过严的粗筛在外面看是一回事，所以不许静默。

## 被滤清单两级

- 粗筛丢掉的：只留计数和 id（`briefing.screen`）。管家的提示词只拿到数字，外加一句"这些条目的标题不在你的上下文里，上面那份清单不是当天的全部"。几百个标题塞进上下文会把粗筛省下的钱原样吐回去。
- triage 滤掉的：完整清单不变，标题、来源、类别都在，管家能就某一条翻案。

管家那边（`src/info/companion/chat.ts`）两段分开写，triage 那段的抬头改成"读完正文后滤掉的"，免得它把九条当成一天的全部。

## 断点续跑

`info-run-<日期>.json` 的语义按四相位扩展（`INFO_RUN_VERSION` 升到 2，旧文件读成 null 重跑当天）。中途失败、Stop、被系统杀掉之后，下一次 Generate 不重复付已经付过的钱：

- 已发现的源不重发现（`sources` 里的状态，一个源抓完存一次）。
- 已判过的条目不重判（`verdicts` 按 item id 存，一批落一次）。
- 已抓到的正文不重抓（`material` 存 id，每 10 条落一次盘——checkpoint 是一个自带正文的整文件，一条一写比它保护的抓取还贵）。

Stop 在每个相位都立刻生效：signal 通到每一个 fetch 和每一个 AI 调用，相位边界再查一次。

中途新订阅一个源会让 run 退回发现相位，并清掉 `selection`——迟到的条目要和别人一起过粗筛，上限要按当天整体算。已有的 verdicts 和正文都留着，退回去只花新源那一份钱。

# 条目池

漏斗省的是每条的钱，池子省的是"只在生成那一刻看一眼"丢掉的东西。

## feed 是窗口不是档案

实测：彭博社每个栏目 feed 只有 20 条，覆盖 6 到 22 小时；经济学人一次返回 300 条，覆盖三周；Nature 75 条覆盖一周；Science 新闻 feed 10 条。一天生成一次简报，彭博社那种源当天大半都没看见过，而且没人告诉用户。

没有一个统一的采集节奏同时伺候这两头，所以每个源自己带一个（descriptor 的 `pollMinutes`，见 [17](./17-信息源系统.md)），采集端按它轮询攒进池子（只在那一台上跑，见 [36](./36-采集端与阅读端.md)），简报从池子里取。缺省 120 分钟，钳在 15 分钟到 24 小时之间。写成"2h"这种笔误在 add 时就报错，不静默变成缺省值。

## 池子里两种东西

- 条目（items）：某次轮询拿回来的标题，按第一次见到它的本地日期归档，一天一个文件。重（feed 即全文的源连正文一起给了），留 3 天。
- 标记（marks）：某次 run 对某条已经花过的钱——判过（留/丢）、抓过正文、进过简报。轻，留 30 天。

分开是因为两者过期速度差一个量级。标记必须活得比条目久：经济学人的一条三周后还挂在 feed 里，那时它的标题早被清掉了，没有标记它就会被第二次粗筛、第二次送到用户面前。

## 落盘三个文件

`info-pool-<日期>.json`（一天的条目，轮询新增时重写，过期整个删）、`info-pool-marks.json`（run 的 checkpoint 时写，正常一天两次）、`info-pool-polled.json`（每个源上次轮询的时刻，每轮写）。分三份是因为三部分变化频率不同，合成一个文件的话每次写都要付整份的大小。

池子是省钱不是真相来源：读不出来就当空的，run 退回"池子存在之前"的样子，慢，不是坏。所以有一条硬规矩——某个源在池子里一条都没有时，无论排期怎么说都去轮它。丢一个池子只该花一轮请求，绝不该花掉一份简报。

## 轮询这件事得能在采集端活

阅读端不轮询，见 [36](./36-采集端与阅读端.md)。持有采集权的那台 PC 也会睡眠、也会最小化，不是常驻不间断的。所以定时器只是提示：某个源到没到点，一律从时钟和盘上的 `lastPolled` 现算，不靠定时器本身触发；机器醒来或前台化就补跑欠的那一轮。

一轮里正在生成简报就让路，不在同一批 feed 上叠第二轮请求。轮询和 run 的发现层填的是同一份内存里的池子（`InfoCollector` 持有），run 自己发的请求也照样入池。

开关在设置的 Briefing 组，缺省开。关掉就是"生成时才采集"，简报只看得见那一刻 feed 上挂着的东西。

## 一天从池子里取什么

取：没人判过的（过夜那批，一天一采集时代丢掉的就是它们）、判过留但还没进过简报的（run 中途死掉，或者被当天的 120 条上限截掉的）、以及今天这份简报已经带着的那些——最后一条是"重新生成"合并进当天同一份简报而不是另起一份的原因。

不取：更早的某一天已经了结的。当时发出去了，或者当时判了不值得抓正文，两种都是已有答案的问题。

run 自己重新发现的老条目按同样的规矩丢掉。feed 窗口是天或周宽的，重复发现是常态，不是异常。

## 开 app 就是触发，早上五点也是

没有生成按钮了。打开（以及每次回到前台）做三件判断之一：中途被打断的 run 接着跑完（用户要过，没得到答复，欠他的）；今天既没简报也没 run 就采一份；今天已有简报，或者今天的 run 是被用户 Stop 掉的/失败停在那儿的，就什么都不做——停住的 run 已经花过一次钱，下一次花钱得他自己开口。

自动生成的前提是配了 provider 且至少订了一个源，读不到就不生成。开口的地方是管家（`generate_briefing`），门厅卡上那个按钮改成"Ask the companion"，没简报时的管家提示词知道今天还没有简报、知道失败原因、知道自己不许主动兜售。

只靠开 app 的是被人碰的那台设备。真正采集的那台 PC 常年开着，跨过午夜没有任何触发点，早上起来手机上是空的。所以加第二个触发点：本地时间 05:00，持有采集权的那台把当天的简报刷一遍（`daily.ts`）。

判据不是"到点了"，是"最近过去的那个 05:00 这台还没跑过"——锚点按日期记（05:00 之前算昨天那个），跑过的那个日期落在 `info-daily-round.json`，不同步，也不放进采集端认领文件（那是发给阅读端看的，且换机接管不该继承别人的答案）。机器睡过五点，醒来补跑；醒着一整天只跑一次；时钟跳变和夏令时都只改毫秒数不改日期。定时器只是提示，回到前台再问一次。首次装上（或升级到带这条的版本）只记锚点不跑：那个早上是它知道有这回事之前的事。

走的是 generate（refresh 语义）不是 init：凌晨用户碰过 PC 生成的那份会被合并进来，而不是被 startupAction 的"今天已有简报"挡掉。闸和 init 的 generate 分支一样：provider、至少一个启用的源、本机持有采集权。定时器挂在 pipeline 的装配处，阅读端两个单例都不构造（docs/36），所以它在手机上根本不上；判据不认角色，上了也过不去。撞上正在跑的 run 就让路，且不记日期：一次撞车不该吃掉当天这一轮。
