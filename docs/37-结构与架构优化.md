## 收尾

B 合完之后又做了三件事：给测试装一个 DOM 并补上它查出来的接线洞、一次安全审阅、一次 bundle 探针。

### 测试里的 DOM

`tests/support/dom.ts`：`await useDom()` 装一个 happy-dom 窗口，并把 `@testing-library/react` 一起返回（d6974b3）。

加它的理由：这套组件测试用 `renderToStaticMarkup` 渲染，effect 一次都不跑，于是"接线写在 effect 里"的测试退化成"接线那行源码还在"。三处这样的测试改坏被测代码都不红，见下一节。

注册按文件做，不做全局。`bun test` 全场一个进程，注册过的 window 后面每个文件都看得见，而 `isTauri()`、设置的退出 flush、`debounced-writer`、`external-link`、`overlay.tsx` 全都按有没有 window 分支（坑 120）；`useDom()` 顺手登记把窗口拆掉的 `afterAll`，`tests/dom-harness.test.tsx` 验的就是这条作用域。工具由 `useDom()` 返回而不是调用方自己 import，是因为 react-dom 在模块求值那一刻算死 `canUseDOM`，抢在窗口前面求值就永久失去 `onChange`，而 bun 先求值 node_modules 依赖，调 import 顺序没用（坑 121）。真有人抢先 import 了，`useDom()` 从 `require.cache` 里查得出来并报错。

happy-dom 而不是 jsdom：立起一个窗口 115ms 对 400ms，而且它自带这套注册/注销要用的 global registrator。代价是全场跑过一次真 DOM 多 0.11s，与用它的文件数无关。已有测试没有一个搬上来。

### 那三个接线洞

- `useShellBootstrap` 里删掉 `subscribeStoreErrors(pushToast)`，全场还是绿的——原测试只在源码里找 `onStoreError` 这个词，而写失败从此再也到不了用户面前。订阅收成 `subscribeStoreErrors(pushToast)` 一个出口，测试改成真报一次失败再把 toast 读回来（05b9268），再把 bootstrap 和两个外壳整个挂起来、底下让一个 store 写失败、从屏幕上读那句话（be4cf91）。`tests/support/shell.ts` 关掉 fetch 和失败读的 console，那两条不是被测对象。顺手收掉的另一件事：fulltext 和 figure 两个缓存各自 `console.warn` 一遍再上报，同一次失败出两行，figure 那行还和通道的说法矛盾（7dd5aa5）。
- "两个外壳都把 chat 包在 provider 里"原来只要求开闭标签各自在文件里出现过——把闭标签提到开标签旁边，每个 chat 都在 provider 外面、每张卡片渲染成 null，照样通过。两个外壳改成挂 `CardRegistryProvider`（b9273d8），测试改成在外壳挂屏幕的那个位置渲染一个带卡片的真 chat，卡片必须出来（4ae5d32）。
- 会话搬出 `App.tsx` 时把整个 pass 在挂断那一刻就建好，只推迟 `distillThread`，于是答一半挂断会蒸馏出少一轮的记录——一个发布过的回归，重新引入还是绿的。`deferHangup` 改回原来的分法：线程文件在建 pass 时经回调读，标记和书是挂断那一刻的值（5a57317）。

`tests/platform/sync/pull-wiring.test.ts` 是同一类：路由表的覆盖测试走的是匹配器，`onPulled` 不再调 `dispatchPull`、或者按书的缓存路由不再注册，两端各自拔掉它都还是绿的；现在两端都有值可以拿住（a5161b8）。

### 安全审阅

结论在 `docs/38-安全审阅.md`（分支 `docs/security-review` @ ef6df79，未合）。威胁模型是这个软件真实面对的四种对手：一份恶意 PDF、采集器抓回来的一个恶意网页、同步目录里一份被改过的文件、开发期同一台机器上的另一个页面或进程。

两条要改的都在分支上做完了，一条已合入 `origin/main`，一条没有（在 c2ce8a4 上用 `git merge-base --is-ancestor` 逐个查的）：

- `scripts/sim-bridge.ts` 的 `/__sim/eval` 不认调用方。绑 loopback 挡的是别的机器，挡不住本机浏览器：一个 `enctype="text/plain"` 的表单 POST 不触发预检，任意页面都能把 JavaScript 推进 dev 页面执行，那边能走 http 和 fs 插件拿到书、笔记和 Drive token。改成每次启动新生成的随机 token（`fix/sim-bridge-csrf` 的 542fd34）。复审又查出两个洞：token 原来写在 `node_modules/.sim-bridge/token`，vite 直接把它当文件服务出去；`config()` 钩子返回 `server.fs.deny` 是整份替换而不是追加，把 vite 默认拦的 `.env`、`*.pem` 全放开了（`fix/sim-bridge-followups` 的 59eeb5d、5d27ff6）。三个 commit 都已合入，现象是坑 123（vite 把 `node_modules` 也按 HTTP 发出去）和坑 124（`server.fs.deny` 提供即替换）。
- `saved-articles.json` 在同步范围内，`parseSavedArticles` 把 `html` 原样交给 `dangerouslySetInnerHTML`，一条被改过的记录就是执行。读侧补消毒（`fix/saved-article-sanitize` 的 186a1bc、776fac3）。复审顺着查出原来那个正则消毒器有两个可用绕过——`<tag[^>]*>` 在引号里的第一个 `>` 就把标签算完，删属性时把左右两半拼成一个新属性——改成用 `DOMParser` 解析加白名单，并把"消毒两遍逐字节相同"做成断言（`fix/sanitize-on-a-parser` 的 240c03f、d402518）。这条整条都没合：`fix/saved-article-sanitize` @ 186a1bc 和 `fix/sanitize-on-a-parser` @ 51c684e 都不是 `origin/main` 的祖先。两个现象在分支上写成 `123-a-regex-tag-matcher-ends-the-tag-early` 和 `124-a-sanitizer-that-is-safe-is-not-yet-stable`，而 sim-bridge 那条已经把 123、124 占了，合之前要重编号。

查过没问题的：同步写路径的路径穿越、`retryAfterMs` 的两个分支、`atomic-fs` 的读路径、`settings.ts` 的 `blockWrites` 与串行写链、合并策略的数据丢失面、`raster.ts` 的超时、三个聊天界面里应用自己写的句子进不进下一轮的 assistant 历史。重构没有碰到任何凭据、token 或 Drive OAuth 的代码。

记一笔不立项的两条：`mergeObject`/`writeCollection` 用 `out[key] =` 写回，远端一个 `__proto__` 键会写到这个新对象的原型上（不构成原型污染，后果只是这个键序列化时消失）；设置面板开着时到达的 pull 走 defer，这个窗口里外壳的一次保存会把 pull 前的整份副本写回去（数据丢失，不是安全问题）。

### bundle 探针

两条结论，都不动手：

- 那个共享 chunk 不是重构造成的。两棵树各自跑一次 `vite build`，按 `dist/assets` 里的文件字节数：审计前（2499820）是 `useSyncHealth-DBd6CpEc.js` 1,033.7 kB，`origin/main` @ c2ce8a4 上是 `useShellBootstrap-BojwQf7f.js` 676.8 kB。换名字是 rollup 拿来命名的那个模块换了；变小是 96ff6ce 把文章抽取改成首次用到才加载，`readable-*.js` 356.5 kB 分了出去。同一对构建量出的启动路径（entry + 外壳 chunk + 它们静态 import 到的一切）：桌面 1,924.7 → 1,574.3 kB，手机 1,204.7 → 854.9 kB。
- 直接对 node_modules 写一条 `manualChunks` 会把 `@earendil-works/pi-ai` 的 provider 适配层从懒加载里拽出来，静默失效。真要分包得先绕开它。

## 这一轮的做法教训

一个 worktree 只能有一个写者。并行 agent 共用一个 worktree 会互相盖掉未提交的改动，而且没有任何报错；开工前 `git status --short` 不干净就停。

新加的测试必须靠改坏它保护的那行来验：把断言指着的代码改掉，测试要红，红了再改回来。六轮复核每一轮都查出改不红的测试。

第三种死断言是拿源码字符串当接线测试。`renderToStaticMarkup` 不跑 effect，"这个 hook 订阅了那个通道"就只能退化成 grep 源码，删掉订阅那行照样绿。验 effect 里的接线得真挂起来跑，这是 `tests/support/dom.ts` 的由来，查出来的三个洞见"收尾"。

反复出现的两种死断言。一种是假件同步 resolve，而真实实现是异步的：测试里 `await` 之后状态已经到位，真机上还没到，A2 的推迟回读就是这么漏过去的（ae8056f、49ec00c）。另一种是夹具本身就满足断言，被测行为怎么变都过：B1.5 的卡片注册表测试用静态 import 写，有没有 provider 两种情况都通过，改成从 context 取才真的在测东西（c85be28）。
