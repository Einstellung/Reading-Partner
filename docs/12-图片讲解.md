# 图片讲解：AI 拿着论文的图讲

2026-07-17 拍板。动机：论文的图承载大量信息，AI 讲解时只能引用图注文本，用户得自己翻回去看图。

## 形状

功能分两半，共享同一个 figure 索引：

- 输出侧：AI 回复里写 `[fig:3]`，聊天渲染成内嵌图片卡片（按边界框从渲染页裁剪），点击跳回原页。与 `[p.N]` 引用同一套语法体系。
- 输入侧：`view_figure` 工具，把裁剪图作为图片喂给视觉模型，AI 才能真的回答"图里那个箭头是什么"。备课消化时同样可用。

figure 索引在全文提取时顺带建：pdfjs 枚举每页图片对象取边界框，配对最近的 "Figure N:" 图注，得 `{编号, 页码, 图注, bbox}`，落盘在 fulltext 缓存旁。AI 上下文带图目录（编号+页码+图注，省 token）。

## 已知限制与兜底

- bbox+图注配对是启发式：双栏、多子图（3a/3b）、跨栏图会配错。配不准退化为整页缩略图。
- 扫描版 PDF 整页是一张图，天然整页。
- 图目录进上下文要设上限，超长综述截断到当前章节附近。

## 落地状态

2026-07-17 落地（分支 m9-figures）。图片索引 `src/reading/figures/`：全文提取时顺带跑 `getOperatorList` 枚举图元、CTM 栈算 bbox、正则配最近图注，落盘 `figures-<hash>.json`（独立 version，提取失败退化空索引不影响全文）。输出侧 `[fig:N]` 并入 `[p.N]` 那套 citation，聊天渲染成内嵌卡片（滚动进视口才裁图、按书内存缓存），点击跳页；裁图用已加载的 pdf.js 渲染（不是 EmbedPDF 引擎，见坑 25）。输入侧 `view_figure` 工具把裁剪图作图片喂模型——pi-ai 的 `ToolResultMessage.content` 原生支持 image block，Anthropic 路径确认能上链路，非视觉模型退化成只给图注。图目录进 companion/classroom 系统提示（上限 40，按当前章节就近截断）。备课 digest 提示带上论文图目录（仅提取，不加视觉调用）。

2026-07-18 修（分支 figure-bbox-fix）：矢量图 bbox。原来只从光栅图元算 bbox，论文图多是矢量路径+文字，只有零星光栅碎片，卡片把碎片拉伸成模糊小图。现在 operator 走 `constructPath`（解 flat 参数取点坐标，不信 minMax——它跳过贝塞尔控制点）+ fill/stroke 提交、clip 丢弃，连同光栅图元一起聚成连通区域，配到就近图注后并入落在框内的图注文字。加兜底：bbox 窄于图注宽度或 <15% 页宽就退化成图注锚定区域（图注水平跨度向上到上一段文字，封顶 60% 页高），再不行才整页。卡片渲染改：card tier 固定 2x 页缩放，显示宽 = min(容器, 自然像素/dpr)，小图左对齐按自然尺寸不拉伸。

2026-08-19 修：图注识别和 id 语义。原来的 `/^(?:figure|fig\.?)\s*(\d+[a-z]?)\b/` 不认中文图注，中译本一张图都建不出来；对「Figure 3-1」只捕到 `3`，`assembleIndex` 按 id 去重后每章只活下来第一张。现在图注标签认 `Figure`/`Fig.`/`图`/`图表`/`插图`，编号保留书上印的全部节号（`3.8`、`3-1`、`3-1a`）。图注和正文靠编号后面接什么区分：紧贴着字（`图3.7显示了`）、逗号（`Figure 1-19, this process`）、空格后接小写英文词（`Figure 11 shows`）、空格后接中文谓词（`图 3.23 总结了`）都判正文，标点或别的判图注。残留一类是断行后读起来像图注的句子（`Figure 1-21. This means…`），去重时带 bbox 的真图注赢过它。

id 是书上印的编号原样（去标签、小写）。中英两条图注落在同一个 id，模型写 `[fig:3.8]` 还是 `[fig:3-1]` 都查得到——匹配时把 `.` 和各种破折号折成一种（`figures/lookup.ts`，同时管排序：3.8 在 3.10 前）。跟着改的下游：`[fig:N]` 的引用文法和 href 校验（`prep/anchors.ts`），`view_figure` 写给模型的 id 说明（diagrams 工具已于 2026-08-20 删除，见 docs/40），图目录和索引的排序，`slides/live.ts`、`slides/plan.ts` 的图查找改走 `findFigureById`。`FIGURES_VERSION` 升 4，旧索引全部重建。

拿库里 41 份 fulltext 缓存按行跑（缓存的断行和 `captionLinesFromText` 的基线聚行不完全一样，是个近似）：唯一编号 463 → 696。《从零构建大语言模型》0 → 126，《Hands-On 大语言模型》3 → 82，GPT-3 论文 5 → 25；单编号的论文不变。

## 划线一带的页面图像（视觉窗口）

2026-08-16 拍板。`view_figure` 要 AI 先知道该看哪张图；用户划线提问时想要的是"你自己看这一带"。所以在划线那一轮直接把页面图像送过去：划线页加前后各一页，划线只表示位置，不做 bbox 求交、不做区域标注，模型自己在页面里找相关的部分。

分辨率分档：划线页 1000px 宽（letter 页约 1.7k token），邻页 640px（约 0.7k），一个窗口约 3.1k token。

门控两条，任一命中就送：窗口内有 figure 索引条目；或窗口内某页几乎没有可提取文字（<400 字符）。第二条是扫描件唯一能命中的路径——figure 检测是按图注文本（`Figure N` / `图 N`）锚定的，没有文字层就一个 figure 都建不出来，"扫描版天然整页"那句只对裁剪兜底成立，对门控不成立。

只在当轮送。进历史降级成一行 `[page images of pp.11–13 were attached here]`，贴在那一轮的用户消息后面；每轮上下文里只有一份窗口。这条靠的是"划线线程的页码不动"：本轮的窗口就是历史每一轮的窗口。书级线程（顶栏 AI 按钮）的页码跟着滚动跑，重建不出来，所以不送。

预算上它是一根静默的梯级（`page-window`，按 messages 计价），排在观察快照之后、tool result 打桩之前——图目录还在提示里，`view_figure` 能把图再要回来。每次真送出去在 `events-ai.jsonl` 记一行 `page-window`，带页码区间、命中的是哪条门控、按 (w×h)/750 算的 token 数。

只有真机 + 真 PDF 能验的：`renderPageImage` 在 webview 里的实际输出（旋转页、cropbox 偏移、三页一起渲染的耗时），门控在真实书里的命中率，以及模型看到整页之后答得是不是真的更好。
