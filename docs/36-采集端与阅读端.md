# 采集端与阅读端

> 本文是 [13](./13-账户同步.md)、[17](./17-信息源系统.md)、[22](./22-手机形态.md)、[35](./35-简报漏斗.md) 的下游。多端不是同一个 app 跑在多处：PC 采集，移动端消费。这个分工改了四件已经定过的事：采集的生命周期挂钩、同步范围、`pollMinutes` 的语义、采集编排的归属。

---

## 两个角色

采集端：24 小时开机的桌面机，跑发现、粗筛、取材、分拣四相位，持有条目池，把简报发布出去。

阅读端：iPhone、iPad，读发布出来的简报和正文，播报、聊天、收藏，不向订阅站点发抓取请求。

采集在移动端跑不起来。iOS 上 app 进后台几秒整进程挂起，唯一的后台机制 `BGAppRefreshTask` 单次窗口约 30 秒、频率由系统按使用习惯决定，而用 webview 取一篇彭博正文要 20-28 秒。

角色是每台设备自己的选择，存在不同步的 `device.json`（AppData 下，和 `sync-state.json` 同一类）：`deviceId`（首次启动生成）、`role`、`backgroundCollect`、`fingerDraw`。iOS 和 Android 固定 `reader`，设置里不出现这个选择；桌面平台缺省 `collector`，可以改成 `reader`。

iPad 走桌面外壳（阅读器、PDFium、books 通道都要，docs/22），角色是阅读端。判据是平台加用户声明，不是屏幕尺寸。

没登录同步的单机是采集端，两端分工对它不成立。

"PC" 包括三个桌面平台，webview 取正文只有 Linux 有（`WEBVIEW_FETCH_PLATFORMS`，见"待定"）。阅读端要知道自己这份简报是哪种采集端出的，见状态文件。

只有手机、没有桌面机的用户拿不到简报也加不了源，info 那半在他手上是空的。不为他补移动端采集。

## 采集端得一直在跑

采集现在绑在窗口焦点上：`observeAppLifecycle` 把失焦也算成离开（坑 69），`onBackground` 调 `getInfoCollector().background()` 取消定时器并 abort 在飞的 poll。用户在手机上读、PC 摆在一边，正是不采集的那个状态。

采集端的轮询和每小时心跳改成只在退出时停：`lifecycle.ts` 另出一个只报 `pagehide` 的订阅，`InfoCollector` 的定时器和心跳挂在它上面，最小化和切窗口都照采。`p.flush()` 留在原来的 background 边上，它只写 checkpoint。阅读端的挂法不变。

app 常驻是这条形态的前置条件。托盘（`src-tauri/src/tray.rs`）：图标带菜单，关窗口改成隐藏到托盘，菜单里的 Quit 是唯一的退出路径，托盘状态行和 tooltip 写上次采集的时间（`collectorStatusLine`）。Linux 上托盘图标的鼠标事件不发、tooltip 不支持，所以图标能做的事都同时是菜单项；`libayatana-appindicator3` 是运行期 dlopen 的，编译不需要它，但桌面环境得有 StatusNotifier 宿主（GNOME 要装扩展），没有宿主时图标注册了也画不出来——所以只有托盘建成功了才把关窗口改成隐藏。单实例还没有。

开机自启是设置里一个缺省关的开关（`tauri-plugin-autostart` 2.5.1，Linux 上写 `~/.config/autostart` 的 .desktop）。它是设备级的，不进 `settings.json`：一台机器开机自启不代表另一台也要。存在不同步的 `device.json`（`inSyncRange` 是白名单，它不在上面，有测试盯着），启动时按存的意愿去校正系统那一份。`backgroundCollect` 和 `fingerDraw` 已经搬进来了。

dev 构建里这个开关不出现，启动时的校正一律 `disable()`：登录项记的是 `target/debug` 那个二进制，它的 devUrl 指着 vite dev server（坑 151）。存的意愿不变，装了正式包再生效。

## 采集者唯一

两台桌面机同时采集，钱付两遍，还出两份不同的简报。

每台采集端候选写一份 `info-collector-<deviceId>.json`，单写者，谁都不改别人那份。采集者 = 这些文件里 `claimedAt` 最早且心跳未过期的那一份。纯函数，每台设备各自算，结果一致。`claimedAt` 每次进程启动重置，选出来的是连续在线最久的那台；失权的机器回来排队尾，不夺回。

- 心跳超过 2 小时：判采集端不在线。
- 心跳超过 24 小时：失权，下一台按 `claimedAt` 顺位接管。
- `backgroundCollect` 关掉就退出候选：认领文件写成 `claimedAt: null`，选举当场跳过，下一台立刻接管，不等失权阈值。
- 登录了同步的设备在第一趟 pull 落地之前不认领。启动 30 分钟内一趟都没成功，按单机处理——照常采集、照常写认领文件，同步恢复了再按选举结果决定退不退位。

交接窗口里两台各发布过一份的话，opaque 合并留一份没人读的 `.conflict-*.json`。

状态文件每趟 run 结束写一次，另外每小时心跳一次。字段：`deviceId`、`deviceName`、`platform`、`hasWebviewFetch`、`claimedAt`、`heartbeatAt`、`lastRunAt`、`lastBriefingDate`、`halt`（上次 run 停摆的原因）、`sources`（每源最后一次成功的时刻和错误，就是今天 `info-source-health.json` 的内容）、`sites`（需要登录的站点，和"当前有没有有效会话"这一位）、`lastAskAt`。

`info-source-health.json` 和 `info-site-sessions.json` 本身仍然不同步。状态文件里只放"有没有会话"，不放 cookie。

## 同步范围

docs/13 的"派生缓存不同步"对 info 的日文件仍然成立：`briefing-<date>.json`、`info-items-<date>.json`、`info-articles-<date>.json`、`info-run-<date>.json`、`info-pool-<date>.json`、`info-pool-polled.json`，一个都不进。

进同步范围的是采集端另外发布的两个固定名文件：

- `info-briefing.json`：那份 Briefing 原样复制。45 KB 量级。
- `info-bodies.json`：`{ date, generatedAt, bodies: Record<itemId, { text, html, summaryOnly }> }`，只装当天三档（mustRead / oneLiners / outOfLane）条目的正文。html 里只剥内联 `data:` 图，外链 `<img>` 保留，用的就是收藏那条路的 `stripDataImages`（挪到 `info/extract/sanitize.ts`，两边同一个函数）。

发布点是任何一次 `saveBriefing` 落地之后，`runRun` 和 `retriage` 两条路都算。retriage 重排三档成员，两个文件一起重算。

只挂在落盘那一刻的话，已经存在的简报永远发不出去：升级到带发布功能的版本之前生成的那份，或者发布本身失败的那次，PC 上有简报、手机上空白，界面还不解释。所以采集端拿到采集权的那一刻补发一次（`backfillPublish`）。判据是纯函数 `backfillVerdict`，只看 `generatedAt`：本机最新的那份（不限今天）比发布位上那份新就整对重发，一样且正文配得上就零动作，发布位上那份更新就不动——另一台采集机刚发的，不能被本机的旧简报盖掉。选举那一关由 `live.ts` 把着，落选的机器和阅读端都不走这条路。日文件已经被 prune、正文凑不出配对的（`bodiesIntact`），两个文件都不发：那种情况下补出来的 bodies 每条都是空的，阅读端会把整份简报显示成"这些源只有摘要"。

两个文件都带 `date` 和 `generatedAt`，配对指纹。逐文件独立 reconcile 会让阅读端拿到新简报配旧正文，对不上时按"正文还在路上"显示。

固定名，每次整份替换：远端不按天增长，`SyncBackend` 不加删除能力，docs/13 的"文件级删除不传播"不改。`pruneStaleDailyFiles` 的四个前缀都在同步范围外，判据不改。

体量按 2026-07-23 实测：三档 11 条正文纯文本 96,650 字节，连 `contentHtml` 是 2,927,584，差的那 2.8 MB 几乎全是内联 base64 图（IEEE Spectrum 一条 1,570,403 字符 HTML 对 19,676 字符正文）。剥完 `info-bodies.json` 实测 225,677 字节，加简报 45,501 字节。外链图留下来加多少：2026-08-12 那天 11 条正文 81 个外链 `<img>`、0 个内联图（`img:` 代理上线后不再内联），bodies 从剥光的 226,926 字节变成 272,006，多 45,080。一天两次，阅读端上下行不到 1 MB。蜂窝不做区别对待，不加"仅 Wi-Fi 同步正文"开关——重的两层根本不上云。

`info-pool-marks.json` 也进：它不是派生的，丢了是重复推送（docs/35）。阅读端不采集，不会有第二套 marks；它同步是为了采集权换机或重装之后新采集者知道哪些已经发过。合并要两行：

- `contract.ts` 的 `RECORD_FILES` 加 `"info-pool-marks.json"`。
- `records.ts` 的 `recordShape()` 加 `if (name === "info-pool-marks.json") return { kind: "map", container: "marks", idField: null };`。

记录身份是 item id（`extract/id.ts` 的 `itemId`，`source:key` 的 djb2，纯函数，跨设备一致）。文件里和 `marks` 并列的 `version` 是 wrapper 键，`readCollection` 已经保留它。

`inSyncRange` 的白名单加三条 ROOT_FILES（`info-briefing.json`、`info-bodies.json`、`info-pool-marks.json`）和两条正则（`/^info-collector-.+\.json$/`、`/^info-ask-.+\.json$/`）。本来就在范围里的 `info-sources.json`、`info-feedback.jsonl`、`user-profile.md`、`saved-articles.json`、`threads-*.json` 不动。

data 通道不加每设备策略。`booksPolicy` 那种分叉只有 books 有，两端共用同一个 `inSyncRange`，分层由采集端发布什么决定。

## 阅读端

界面读 `info-briefing.json`。`briefing-<date>.json` 退回成采集端内部的落盘（run 的产物、断点、prune 照旧）。

日期以采集端为准，不做 `parsed.date === todayLocal()` 那道校验，显示文件自带的日期。半夜和跨时区打开看到的是最新那一份，标着它是哪天的，不是空态。简报线程 `threads-info-<date>.json` 的 key 取的就是这个日期，它已经靠 `/^threads-.+\.json$/` 在同步范围里。

文章页四种状态各说各的：

- 三档条目在 `info-bodies.json` 里有正文，`ArticleView` 照常渲染。
- bodies 的指纹和简报对不上：正文还在路上。Keep 和文章级聊天这时不出现。
- 被 triage 滤掉的（那天 93 条）没有正文。Show anyway 保留，点开显示标题、来源、被滤掉的类别，和一个在浏览器里打开。
- 发现层-only 的源本来就没有正文，还是现在那句"这个源只有摘要"。

收藏：Keep 只在有正文的条目上出现，存下来的 `text`/`html` 就是那份正文（不带图，PC 上存同一条带图），`summaryOnly` 取 bodies 里那条的实情，不走 `resolveSummaryOnly` 找不到 item 时的兜底。没有正文的条目不给 Keep，否则空快照会把 PC 上同 id 那条有全文的记录洗掉。

聊天默认锚在简报级。`briefingChatSystemPrompt` 只吃一个 Briefing 对象，加上 `user-profile.md` 和 `info-sources.json`，全在同步范围里——包括被滤清单的标题、来源、类别，所以"这条为什么被滤掉"在简报级答得了。文章级聊天只在三档条目上出现，`articleChatSystemPrompt` 的 text 从 `info-bodies.json` 取。

播报（docs/33）：播放单元是三档的三个有序数组，reason 和 line 在 `info-briefing.json` 里，插问要的正文在 `info-bodies.json` 里。

采集端出了错，据此说话：

- 简报卡显示 `generatedAt`（今天一处都没读）。
- 心跳过期：说采集端上次在线是什么时候，不再说 "Today's is on its way."。几台采集端都不在线时按心跳最新的那份说。
- 上次 run 有 `halt`：把原因说出来。采集端前面没人看屏幕，`startupAction` 停在那儿等的那句话得走到手机上。
- 某个站点会话失效：简报卡上说今天有一批条目只拿到了摘要。简报文件里不加计数字段，这件事只走状态文件。

## 手机上要一份新的

`generate_briefing` 在阅读端不就地跑，转交采集端。full 和 retriage 两档都转交——retriage 要的 `info-items-<date>.json` 是 683 KB 的快照，不在同步范围里。

阅读端写 `info-ask-<deviceId>.json`：`{ deviceId, askedAt, scope, note? }`，单写者，永不合并。采集端注册一条 pull route（`ASK_PULL_ROUTE`）收，另外启动时读一遍——上一次会话已经下载过的 rev 不再触发 pull 事件，只靠事件那条请求会静静过期。收到就拿 `askedAt` 和自己状态文件里的 `lastAskAt` 比：

- `askedAt` 超过 6 小时的不执行。
- 执行过的把 `askedAt` 记进状态文件，不重复执行。
- 两台阅读端各发一条：取 `askedAt` 最新的，scope 取更宽的那档，只跑一趟。

往返最坏十几分钟：上传约 15 秒（`TICK_MS`）+ 采集端下一次 pull 最多 5 分钟（`PULL_INTERVAL_MS`，PC 常开没有前台事件）+ 采集本身几分钟。界面只说"已经转告采集端"加采集端的在线状态，不给倒计时。采集端不在线时请求挂着，6 小时后作废。

聊天里几个卡片动作一并改道：`retry-briefing` 写 ask 文件，画像卡的 `canRetriage` 在阅读端恒 false（它现在按 `getInfoPipeline().snapshot().briefing` 判，点下去就是本地 retriage），add-source 确认卡不出现。

管家的提示词跟着改：`noBriefingChatSystemPrompt` 那句 "Today's briefing is collected automatically when the app opens" 在阅读端是错的，换成采集在另一台设备上、可以替用户转告。

pull 的分发走 `platform/sync/pull-routes.ts` 的路由表。采集端注册 `SOURCES_PULL_ROUTE`（`info-sources.json`）：拉到就调 `getInfoCollector().foreground()`，不等下一次最多 30 分钟的唤醒。阅读端注册 `READER_PULL_ROUTE`（`info-briefing.json`、`info-bodies.json`、`info-collector-*.json`）：重渲染。两个外壳共用同一张表，不再各挂各的监听。

## 加源和站点登录只在采集端

trial 是 add 的闸门，而它要证明的正文能力两端不同：`hasWebviewFetch()` 在阅读端是 false，`trialSource` 调 `collectSource` 时也没传 `fetchViaWebview`，同一个彭博源在手机上 trial 只看得到导语（docs/17 的两组实测数）。

阅读端的管家不注册 `probe_source` / `trial_source` / `add_source`。用户说"我想订 X"——未接线：`info-ask-*.json` 的 `note` 字段目前没有写者（`src/info/briefing/handoff.ts` 的 `AskRecord.note` 注释直说，理由是一次 ask 总要花一趟采集，订阅请求不该白买一趟）。这句话现在靠对话本身同步过去（`threads-info-<date>.json` 在同步范围内），停在用户打字进去的那条线程里，等采集端操作者自己看到。`note` 字段保留形状，留给以后要单独带一句话的请求。`read_page` 保留——那是用户当场贴的链接，不是订阅源的自动抓取。

`SourcesPage` 顶上那个不经过 AI 的粘贴框在阅读端不出现，原位放一行字：加源在 PC 上做。`HomeCard` 在没有源时给的 "Start subscribing" 同样换成一句话，不给按钮。

站点登录本来就只在 Linux 上出现（`InfoHome.tsx` 按 `hasWebviewFetch()` 关掉三个按钮）。阅读端的源列表从"整块消失"改成显示一行状态：这个源的正文需要在 PC 上登录，以及当前登录态，数据从采集端状态文件来。

源的开关和删除在阅读端仍然能做，`info-sources.json` 走 records 合并，采集端下一趟 pull 生效。

## 采集编排的归属

`collector.ts` 保持平台无关：纯逻辑加注入的 deps，编排代码留在自己的领域目录。变的是谁实例化它。

界面不再直接调 `getInfoPipeline()`。抽一个只读接口（`snapshot()` 加 `subscribe()`，形状就是今天的 `InfoSnapshot`），`InfoHome` 和 `InfoCall` 那十几处改成用注入的实例，`live.ts` 按角色给两种实现之一。采集端的实现就是 pipeline：run 进度、halt、error 全从内存来，文件只是发布产物。

阅读端的实现是新模块 `src/info/briefing/reader.ts`：读 `info-briefing.json` 和 `info-bodies.json`，`running` 恒 false，不发请求，不调 AI。`use-info-home.ts` 的 `openArticle` 从 `loadArticle(date, itemId)` 改成读 bodies，`keepArticle` 从 `loadItems(date)` 改成读 bodies 里的 `summaryOnly`。

阅读端两个单例都不构造。`InfoCollector` 不实例化（条目池在阅读端没有意义），`InfoPipeline` 也不构造，`init()` 那条 generate 分支、`observeAppLifecycle` 里的 `foreground()` 和 `p.init()`、构造时那句 `void getInfoCollector().refresh()`、`App.tsx` 和 `PhoneApp.tsx` 的 `refreshInfoCollector()` 一并去掉。回到前台只剩同步引擎跑一趟，加 pull 落地后重渲染。

pipeline 不构造就没人调 `pruneStaleDailyFiles`，跑过老版本的 iPhone、iPad 上会一直留着 `briefing-*.json` 和 `info-articles-*.json`（实测单日 4.4 MB）。阅读端启动直接调 store 那个函数跑一次，另外删掉 `info-pool-<date>.json` 和 `info-pool-polled.json`（它们归 `InfoCollector` 清）。`info-pool-marks.json` 留着，它在同步范围里。

## pollMinutes 改口径

`pollMinutes` 从"后台多久跑一次这个源的发现层"改成"采集端多久轮一次这个源的发现层"。取值规则和消费者都不变，变的是它只在一台设备上被读；阅读端的 `toPoll` 和 `dueSources` 没有调用者。

三处跟着改：`descriptor.ts` 的字段注释、`DESCRIPTOR_GUIDE` 里那句 "how often background collection polls this source"（这段常量同时注入管家提示词和加源 skill）、docs/17 和 docs/35 里对应的两段。

## 每设备的设置

`backgroundCollect` 从 `settings.json` 搬进 `device.json`，语义变成"这台采集端现在采不采"，阅读端不显示它。`fingerDraw` 同样是设备特性（有没有笔），一起搬。docs/13 已经为自动同步开关做过同一件事。

迁移不删旧键：新版本首次启动把 `settings.json` 里这两个值抄进 `device.json` 当初值，之后只读 `device.json`，也不再写那两个键。老版本设备继续读它自己的那份，`settings.json` 的 fields 合并不会来回打架。

`settings.json` 其余字段仍然是账户级。`credentials.json` 不同步这条不变，两端各自登录 AI 账号。落差是阅读端会收到采集端选的 provider id 却没有对应的 key。聊天要用它，所以没有 key 时界面要说"这台设备还没登录 AI"，不能沉默。

花费统计不做：全仓没有任何用量或配额的持久化（`src/budget/` 算的是上下文窗口不是钱），两端各花各的。

## 审核与红线

App Store 5.2.2 管 uses / accesses / monetizes access to / displays 四个动词。

阅读端不对订阅站点发抓取请求。剩下两条出站要点名：`img:` 代理（`image_proxy.rs` 注册在 `#[cfg]` 之外，iOS 上也有）和 `read_page`。前者会被简报的文章页触发：bodies 保留外链 `<img>`，`ArticleView` 把它们指向代理，代理带着文章 URL 当 Referer 去出版方 CDN 取图，`accesses` 这一条命中。两端一致排在它前面——剥掉之后同一篇文章 PC 上有图、手机上没图，在手机上收藏就永远存下一份没图的快照，哪个版本取决于手边是什么设备。真要为上架关掉，改 `buildPublishedBodies` 里那一次调用，剥光而不是只剥 `data:`。后者是用户当场贴的链接。

displays 只剩标题这一层：`BriefingItemMeta` 的 title、url、source、publishedAt 是 denormalized 存在简报文件里的原样字段，`BriefingPage` 的三档和被滤清单渲染的都是它。标题不改写——链接要指得回去。overview / reason / line 是 AI 写的新文本。同步过去的原文只有三档那几条正文。

docs/17 的第二条红线按单设备写的，加一句口径：同一个用户的设备之间传递他用自己账号取到的正文，仍在"自己读"之内。不存凭据、不代抓、不共享账号、不对外分发这四条不变。cookie 不出采集端的 webview jar，`info-site-sessions.json` 不同步。

## 待定

- 上架前要不要把 iOS 端的正文层整个拿掉。拿掉之后 Keep 存不了全文、文章级聊天没有 text、播报的插问只答得了简报级。发布时定。
- 阅读端要不要能看前几天的简报。现在发布的是固定名的最新一份，看不到历史；`briefing-<date>.json` 的历史只在采集端。要做就是另一套按天的发布，连带把远端回收这个问题重新打开。
- 心跳的两个阈值（2 小时判不在线、24 小时判失权）没有实测依据，先按这两个值写，看真实使用再调。
- macOS 和 Windows 的 `webview_fetch` 是 docs/17 M-info-3 的待补项。补上之前，那两个平台当采集端时四家高端源只有发现层。
