# 回合排一条队，一个卡住全部卡住

## 现象

2026-09-29，饭菜页点 Plan this week，回复行一直是 Thinking，没有出现过 "Drafting the week"，也没有报错，点停止没用。设备上没有日志，最终没能确认是下面哪一条，只能从代码推断。

## 机制现状

- 所有 soul 回合（读书对话、简报与饭菜对话、语音通话、课堂、复述、排练、后台 bell）共用一个 harness、一条 lane，严格串行：`src/legion/execute/held.ts` 的 `acquire` 等前一个回合 `release`。没有超时，没有队列长度，界面也不知道自己在排队。
- 回合的唯一保护是停摆计时器（`src/legion/execute/stall.ts`，坑 390）：供应商 90 秒无事件就 `requestAbort`。工具执行期间计时器暂停，且暂停没有上限。
- 回复行的状态只有 thinking / tool / writing 三档（`src/ui/components/chat/phase-line.ts`）。还没收到任何事件、排队中、模型在思考、模型在流式写工具参数，四种情况都显示 Thinking。
- 饭菜的 `propose_meals_plan` 一次调用写满 7 天 × 4 顿；检查不过就要求整周重发，一个回合最多 8 轮（`DEFAULT_MAX_ROUNDS`）。工具行只在参数写完、开始执行时才出现。

## 已打的补丁

分支 `fix/stall-watch-lane-queue`，见坑 490。

- 停摆计时器从第一次发请求才开始计时。之前排队超过 90 秒计时器就触发，此时没有 operation 可掐，计时器结束，之后那条流静默死掉就永远占着 lane。
- `acquire` 接收回合的 abort 信号，排队中停止或离开页面就放弃排队，自己那一格在前一个回合释放时跟着释放。

## 没解决的

- 一个回合可以无限期占着 lane：工具卡住时计时器是暂停的，前面的回合不结束，后面的永远轮不到。需要回合级的总时限，或者让 lane 按对话分开，只在真正共享状态的地方串行。
- 为什么所有对话必须排一条队，理由在 held.ts 里是"一个进程一个 session"，不是业务需要。重做时先回答哪些回合真的不能并行。
- 排队不可见。界面至少要能区分"排在别的回合后面"、"等首包"、"在思考"、"在写工具调用（附工具名）"。pi 流式给了 `toolcall_start`，工具名在参数写完之前就知道。
- 大工具调用加整周重发：一次失败要重写全部参数，慢模型上一轮就是几分钟。可以留下通过检查的那部分，只让模型重写失败的几顿，或者按天分批提交。
- 设备上没有可回读的诊断。回合开始、拿到 lane、首包、每轮结束、结束原因，应该落一条本地日志，用户能导出。这次只能靠读代码猜。
